# Composer foreground-light experiments (issue 663)

These are private renderer diagnostics, not a shipping adapter or a visual-parity claim. Production `src/composer-loader/ComposerLoader.tsx` remains the merged lifecycle implementation. The synthetic APK has no Internet permission and keeps the same locked dependencies and disabled React Compiler as its baseline. iPhone testing is explicitly deferred.

`performance-results.json` records controlled physical Pixel 8a windows and the budget pinned before GPU experiments. Raw frames, CPU samples, memory, read-only thermal status, full viewport screenshots, exact build/lock/source attestations and APKs are retained under `.local/issue-663-material/`. GPU histogram 4950ms is Android's overflow bucket above 25ms, not an observed 4.95-second frame. FrameCompleted latency is reported separately from the display interval. The user’s density420 and font_scale1.15 were preserved.

The initial production SVG baseline misses virtually every deadline. Removing filters isolates the largest CPU cost, but intentionally removes the glow and is not a solution. `react-native-svg` 15.16.0 draws its view into a software Bitmap; its Android Gaussian filter creates RenderScript allocations for each filtered stroke. Moving blur to three foreground-only RN View RenderEffects eliminates that filter cost, but the remaining software rasterization of 42/84 taper strokes still fails the budget. Sharing three animated group offsets and static phased paths reduces native prop updates without solving drawing cost. These unsuccessful experiments are preserved as patches and a text source snapshot, excluded from compilation.

The current `BloomLightProbe.kt` is registered only by the test application's config plugin. A generated clone of the real ComposerLoader changes only its measured light node, retaining its geometry, clock, layout, fade and suspension. It draws the same stroke descriptors and gradient through an accelerated Canvas into three RenderNodes with RenderEffect. A hardware assertion prevents silent software fallback. This is Android API31+ experimentation, with no claim for old Android, legacy RN, iOS, native package integration, or autolinking consumers.

Grouping blur changes the order of alpha compositing at overlapping taper strokes. Pixel comparison must explicitly assess this before any adoption. The probe uses exact .5dp sigma, whereas the rejected RN View filter experiment used .51dp to cross RN's early blur threshold. The existing SVG and fixed-phase captures are the visual reference; equal timestamps alone are not web/native phase equivalence because their rounded-rect path origins differ. Android `PathMeasure.getPosTan(0)` measured the left-bottom arc join for positive radii; the browser geometry gate independently verifies cyclic paths against an authored SVG path.

Its fixed-phase capture restores visible bands but still differs from web in faint tails. It is not selected. The full-resolution/quarter-resolution comparison alone does not prove web fidelity.

Android RenderEffect's JNI converts radius to sigma (`Blur::convertRadiusToSigma`): [AOSP implementation](https://android.googlesource.com/platform/frameworks/base/+/7d59d89f035a/libs/hwui/jni/RenderEffect.cpp). The first grouped quarter probe divided the converted radius, introducing an extra1.5physical-pixel sigma after upscaling. The per-stroke experiment instead divides sigma before conversion; preserve this distinction when comparing its pixels.

## Candidate and capability boundary

After reviewing all six full-size comparisons, the coordinator selected soft sigma0.7 plus bloom intensity0.8 **only as the candidate for motion, budget and lifecycle verification**. The crisp layer,14 authored strokes, path phases, gradient colors and public geometry remain unchanged. The candidate is not a pixel-equivalence claim or permission to ship the private view. The stronger white perimeter of dark native Surface is also present with no loader light and remains a separate material-audit item.

| Environment | Evidence / required behavior before production |
| --- | --- |
| Android16/API36, Pixel8a, RN0.88.1 New Architecture, hardware Canvas | Real compiled private view and fixed-phase captures; grouped predecessor passed repeated budget, calibrated candidate must repeat it and lifecycle. |
| Android API31–35, hardware Canvas | RenderNode/RenderEffect API boundary exists; device performance and fidelity not established by API36 compilation. |
| Android API24–30 | Production must avoid loading/constructing the RenderEffect implementation and retain the existing SVG renderer. Its measured performance degradation is explicit; no uniform-quality claim. |
| Software Canvas / software ancestor layer | Private probe currently asserts hardware acceleration. Production must never keep that assertion: it needs a one-time capability failure path back to SVG, rather than crashing or silently drawing no light. |
| Missing Bloom native binary (Expo Go / consumer not rebuilt) | Detect manager availability before mounting the native light; use current SVG. A JavaScript package update alone cannot install this renderer. |
| RN0.73 minimum peer / legacy architecture | Existing ReactPackage + ViewManager interfaces suggest a route, but the private RN0.88.1 build does not verify old RN or legacy behavior. Compile/runtime verification or a stricter capability guard remains required. |
| iOS | Keep current renderer; physical iPhone verification explicitly deferred by the user. |
| Web | Keep production CSS/SVG path; no native adapter or calibration import. |

Bloom already ships Android autolinking through `android/BloomPackage.kt` and `react-native.config.js`; any eventual integration should extend that owner without a new renderer peer. Package contents, manager discovery, platform guards, release consumer rebuilds and fallback tests must be reviewed before selection becomes a shipping change. The harness's generated clone is diagnostic evidence, not validation of an installed published package.

The selected private candidate passed the repeated physical budget: one/two untapered GPU p95 4/5ms; one tapered6ms; two tapered7/8/7ms across three windows with0/0/0 missed deadlines. All windows recorded thermal status0. `lifecycle-results.json` records actual native pause/resume deltas, identical paused pixels, Screen inactive, background, resize, rapid fade interruption and initial inactive mounts. The fixed Screen test harness needed explicit flexBasis120; its first collapsed-layout failure is retained locally and is not claimed as renderer evidence. The corrected physical run observed zero frames during the initial-inactive10second window. Two approximately12second videos cover full-width forward motion and narrow/radius12/dark reverse motion. Real OS reduced motion was exercised only in the isolated API36.1 AVD, including live change and cold start; its original setting1.0 was restored.

Future probe builds also embed a native source receipt: `prepare.mjs` and the Expo plugin use the same template writer, synchronizing generated Kotlin instead of relying on a manual copy. The template SHA is logged by the actual view and must appear in APK DEX; attestation also checks the generated Kotlin hash. This supplements the existing exact APK/bundle/embedded Bloom source checks and prevents a fresh Metro bundle from hiding stale native probe code. Historical archives without this new receipt retain their original, explicitly narrower attestations.

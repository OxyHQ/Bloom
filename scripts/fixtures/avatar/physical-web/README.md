# Physical web profiling

Use only an authorized, unlocked device and dedicated test Activity/browser. The Java WebView host is in `../native-host`. Connect its own DevTools socket to localhost9340; `AVATAR_WEBVIEW_DEBUG` can select another dedicated endpoint. `AVATAR_TARGET_URL` restricts target selection (default loopback URLs). Scripts disconnect their socket without closing any browser/other tab.

Run `profile-avatar-android-crowd.mjs` from the worktree serving its built `/bloom-character/runtime.mjs`, or supply `AVATAR_FIXTURE_URL` for that server's `native-benchmark.html`. Inputs: `ORIGIN`, `COUNT`, `KIND=blue|authored|catalog`, `SIZE`, `COMPACT=1`, `ID`, `AVATAR_OUTPUT`. Compact layout has4px margin/gap, normal8px. Report actual visible and ready counts: mounting64 is not proof64 are visible. Authored cycles8 presets; catalog cycles4 recipes. Output captures backing size, shaders' renderer stats, RAF intervals, destination copy timestamps, V8 CPU profile, main-thread metrics and a separate unprofiled steady window. Counts are engine submissions/canvas updates, not proof of Android presentation. `KEEP=1` retains the test scene; otherwise it is disposed.

For the real Storybook ManyAvatars DOM, navigate its iframe in the dedicated target first, wait for visible actors, then run `profile-avatar-android-story.mjs`. `STILL_ONLY=1` omits touch scroll and Work tap. Profile and unprofiled samples are separate. Do not change viewport visibility or force hidden actors active to manufacture normal-app counts.

`SETUP_ONLY=1` on the crowd script leaves the ready scene and captures its renderer through Three's existing devtools observation hook. Subsequent `probe-avatar-android-passes.mjs` and `probe-avatar-android-uploads.mjs` temporarily suppress draws/uploads while preserving all other work, and restore methods in finally. They intentionally display invalid/frozen output and are attribution tools ONLY. Deltas include queue/dependency/cache effects and are never accepted performance gains or GPU timings. The fence probe adds flush/fence polling; its latency includes GPU queue/work and main-thread scheduling, not pure GPU execution.

Use fresh pages for every true timing comparison. Never call getImageData/toDataURL on destination canvases before timing: Chromium can migrate Canvas2D to CPU and create artificial copy stalls. Pixel parity belongs on separate pages. Device screenshots and app-filtered Android gfx/atrace diagnostics do not read the destination Canvas2D context. CPU profiles and raw traces may contain local paths/process identifiers; publish only curated summaries, device model/version and test workload metadata.

For Android trace attribution use a short `adb shell atrace -z -b 16384 -t 5 -a so.oxy.bloom.avatarbenchmark gfx view webview` capture, filter spans to the test package, and report wall spans rather than treating nested spans as independent time. Android/WebView/ANGLE backends differ; a standalone Chromium control is a separate host/version comparison, not a universal mobile Chrome certification.

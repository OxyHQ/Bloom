# The native runtime API

Status: agreed, 2026-11-28, by the Android lane (lang-native-android-1, then -2) and the iOS lane
(lang-native-ios-1). [ADR 0003](./adr/0003-native-backends.md) decided that `.bloom` compiles to Kotlin +
Jetpack Compose and to Swift + SwiftUI, with no JavaScript on the device. Both backends read the
same checked program; this document fixes what they emit *against*: the types, the view and
modifier shapes, state and effects, the standard library's native side, the glass and motion
engine, and the island host. A runtime is correct when the conformance suite (below) gives the
same output on both platforms and on the TypeScript backend.

How it changes: a section is agreed when both lanes have signed it off in the PR that edits it.
A change to an agreed section lands in the same PR on both runtimes, or not at all.

## Packages

| | Android | iOS |
|---|---|---|
| Views, modifiers, tokens | `so.oxy.bloom.ui` (Gradle module `bloom-ui`) | Swift package `BloomUI` |
| Standard library | `so.oxy.bloom.std` (`bloom-std`) | `Bloom`, so the emitted `import Bloom` mirrors the source's |
| Theme engine | `so.oxy.bloom.ui` (`BloomTheme.generated.kt`, the engine's port beside it) | `BloomTheme`, Foundation only (its golden tests run on Linux CI); `BloomUI` bridges it to SwiftUI's `Color` and environment |
| Material (glass, motion, haptics) | `so.oxy.bloom.ui.material`, over `so.oxy.bloom.glassmenu` (shared with the React Native package, below) | `BloomUI/Material/`, on SwiftUI (no separate glass engine) |
| Island host | `:bloom-islands`, generated by `bloom build android` (#1074): `BloomIslandView` and `IslandRegistry` in `so.oxy.bloom.islands` | `BloomIsland` |
| Emitted code | `bloom.<app>.<module>` (`bloom.mention.feedisland`), one file per `.bloom` file | module `<Module>`, one file per `.bloom` file |

Emitted code imports only these and the platform. On iOS, Bloom's `Text`, `Image`, `Toggle` and
stacks share SwiftUI's names. Emitted files import `Bloom` and `BloomUI`, plus the SwiftUI
declarations they mean, one by one (`import protocol SwiftUI.View`, `import struct SwiftUI.State`,
…), so an unqualified `Text` is always BloomUI's. One by one, not as `BloomUI` typealiases: in
Swift 6 a public signature may name a type only from a module the file imports, so a typealias of
`SwiftUI.Binding` fails with "SwiftUI was not imported by this file" (`SWIFTUI_IMPORTS` in the
Swift backend).

## Types

| Bloom | Kotlin | Swift |
|---|---|---|
| `Int` | `Long` (64-bit, as the checker pins it); overflow traps through `Math.addExact` and friends (to come in the emitter, which wraps today) | `Int` (traps already) |
| `Double` | `Double` | `Double` |
| `Bool` | `Boolean` | `Bool` |
| `String`, `Character` | `String`; `count`, indices and `characters` by grapheme cluster (`BreakIterator`) | `String`, `Character`, as they are: ADR 0003's grapheme-cluster `count` is Swift's own |
| `[T]` | `List<T>` (read-only; a `var` is replaced, never mutated in place) | `[T]` |
| `[String: V]` | `Map<String, V>` (insertion-ordered `LinkedHashMap`, as JS) | `OrderedDictionary<String, V>` (in `Bloom`): always ordered, since whether order is observed (iteration, `keys`, a later `Codable` encode) is not something an emitter can decide per use |
| `Set<T>` | `Set<T>` (`LinkedHashSet`) | `OrderedSet<T>` (in `Bloom`), always ordered |
| `T?` | `T?` | `T?` |
| `Result<T, E>` | `BloomResult<T, E>` (sealed: `Ok(value)`, `Err(error)`), never Kotlin's `Result` | Bloom's `Result` with `ok`/`err` cases (the rename table, below), not Swift's `success`/`failure` |
| `(A, B)`, `(A, B, C)` | `Pair`, `Triple` (`.0` is `.first`); longer tuples are data classes (to come) | `(A, B)` |
| `Error`, `throws` | `Throwable`; a thrown value that is not an `Error` is wrapped in `BloomError(value)`, and `error.localizedDescription` reads its `message` | `Error`, typed `throws(E)` |
| `struct` | `@Immutable data class` of `val`s; mutation is `copy` | `struct` |
| `class`, `final class` | `class` | as written (`class` or `final class`; Bloom 2.0 writes `final`) |
| `enum` without payloads | `enum class` | `enum` |
| `enum` with payloads | `sealed interface` with `data object` / `data class` cases | `enum` with associated values |
| `protocol P` | `interface P`; `P & Q` is a generic bound `where T : P, T : Q` | `protocol P`; `P & Q` |
| `any P` | `P` | `any P` |
| `func f(of x: T)` | `fun f(of: T)`: the argument label is Kotlin's parameter name. Kotlin does not overload on parameter names, so overloads that differ only in labels (`move(to:)`, `move(by:)`) take the labels into the Kotlin name (`move_to`, `move_by`), chosen at each call from the checker's resolution | `func f(of x: T)` |
| `async` | `suspend` | `async` |
| `actor` | `class` whose public members run on its own `limitedParallelism(1)` dispatcher | `actor` |
| `Binding<T>` | `so.oxy.bloom.std.Binding<T>` (`get`, `set`, `value`) | `Binding<T>` |
| `JSONValue` | `Any?`, as JSON.bloom's `Foreign<"unknown">`: an ordered `LinkedHashMap<String, Any?>`, a `List<Any?>`, `String`, `Double`, `Boolean`, `null`, or `JSONAbsent` | `enum JSONValue`: `absent`, `null`, `bool`, `number`, `string`, `array`, `object` (ordered) |
| `UniqueID` | value class over `String` | `struct UniqueID` over `String` |
| `Duration`, `ContinuousClock`, `Date` | `Duration` and `ContinuousClock` as Time.bloom declares them (compiled through the backend); `Date` the runtime's instant in milliseconds (`Double`) | Swift's own: `Swift.Duration`, `ContinuousClock.Instant`, `Foundation.Date` |
| `static func m`, `static let m` of `T` | a top-level `fun T__m` / `val T__m`, named as the checker lowers it (`T$$m`), so a call site, a derived coder and a witness codec name it one way; no companion objects | `static func`, `static let` |
| a view (`some View`) | `@Composable () -> Unit` | `some View` |

`Codable` is derived at compile time on both, with no reflection. The Kotlin backend emits the
coders the compiler derives in the checked tree (`codable.rs`: `T$$decode`, `T$$encode`,
`T$$self`, the TypeScript backend's own), over JSON.bloom compiled through the backend and a
small ordered JSON parser in the runtime; a wrong value throws Bloom's `DecodingError`, with the
same message as on TypeScript (`Post.id: expected a string, found a number`). Swift uses the
synthesized conformance, with `CodingKeys` when a field is renamed. The JSON text is
byte-identical to the TypeScript backend's for the same value (key order, number formatting,
escapes): a conformance case per type shape.

## Views

- A `struct X: View` is `@Composable fun X(<props>, modifier: Modifier = Modifier)` on Android
  and `struct X: View` on iOS. Props keep Bloom's order and names; `modifier` is last; a trailing
  builder is a trailing `content: @Composable () -> Unit` (Swift: `@ViewBuilder`).
- A BloomUI node keeps its Bloom name and parameter names on both: `VStack(alignment:spacing:)`,
  `Text(_:)`, `Toggle(isOn:label:)`, `VirtualList(_:row:)`. Token parameters take the token type
  (`Space.sm`, `Tone.primary`), never a raw number.
- `VirtualList`'s row closure takes `VirtualListRow<T>` (`item`, `index`) on every backend.
- The node families and their parameters are `spec/language.json`'s `nodes` and `signatures`. A
  generator (`scripts/native/generate-ui-api.ts`, to come) writes the Kotlin and Swift
  signatures from the spec, so neither lane hand-writes a parameter list and a missing node is a
  generator diff, not a runtime surprise. The coverage table it writes is
  `docs/native-ui-coverage.mdx` (to come).

## Modifiers

- A layout or drawing modifier (`padding`, `frame`, `background`, `corner`, `opacity`,
  `aspectRatio`, `border`, `shadow`, `offset`, `scale`) is a `Modifier.bloom<Name>(...)`
  extension on Android and a `.bloom<Name>(...)` view modifier on iOS, with Bloom's parameters.
  On iOS the prefix keeps them out of overload resolution against SwiftUI's own `padding`,
  `frame`, `font` and `opacity`, which costs Swift type-check time in long chains. A node that
  gives a universal modifier its own meaning (`GroupedSection`'s `title`, `Image`'s
  `aspectRatio`) implements `bloom<Name>` itself, under the universal spelling; its method wins by
  type.
- The effect modifiers stay the platform's own where the meaning is identical: SwiftUI's
  `.task`, `.onAppear`, `.onDisappear`, `.onChange`; Compose's effects (State and effects, below).
- A node's own modifiers (`Action.count`, `GroupedSectionItem.description`, `Text.lines`)
  configure its props on every backend. The Kotlin emitter writes them as the node's parameters;
  the Swift emitter as methods on the node type under the spec's names, written before the
  universal ones (`Action(…).padding().count(3)` is `Action(…).count(3).bloomPadding()`). The
  table of each constructor's own modifiers, and of which constructors take children, is
  generated from `spec/language.json` (`generate-swift-tokens.mjs`, into
  `crates/native/src/swift/nodes.generated.rs`), and the Kotlin emitter reads the same table.
- Bloom's chain wraps outward; Compose's runs inward. The Kotlin emitter writes a node's layout
  modifiers in reverse order (`.padding(.horizontal, .lg).padding(.vertical, .sm)` is
  `Modifier.bloomPadding(vertical, sm).bloomPadding(horizontal, lg)`). Swift keeps Bloom's order.
- An inherited modifier (`foreground`, `font`, `disabled`, `tint`, `lineLimit`, `density`,
  `controlSize`) is environment, not layout: a `CompositionLocal` on Android, an
  `EnvironmentValues` key on iOS, set by `Bloom<Name>(value) { content }` and read by the nodes.
- Which modifiers are which comes from the spec: `modifierCategories` in `spec/language.json`,
  generated into the compiler as `MODIFIER_CATEGORIES` (layout, paint, text, environment,
  effect; a modifier in none is its node's own).

## Tokens

The native tokens are generated from `spec/language.json`, which is what a `.bloom` token name
resolves against: the scales (space, corner, sizes), the type ramp, motion and easing, and every
token set as an enum whose raw value is its token. Android: `BloomTheme.generated.kt`
(`scripts/native-theme-kotlin.ts`); iOS: `runtime/ios/Sources/BloomUI/Generated/Tokens.generated.swift`
(`generate-swift-tokens.mjs`). One source for both lanes. Colours are the theme's (next
section), never a token constant. Never edited by hand: the same rule as
every other generated file in Bloom. Pixel parity is measured against today's Bloom on the device, not against the
token file.

## Theme: Bloom's theming carried over unchanged (owner's rule)

Bloom's whole theming system is the native theme, with one source of truth and no hand-copied
colour on either platform: the colour engine (`src/theme/color-engine`, `color-space.ts`,
`build-theme-from-seed.ts`, `build-theme.ts`), colour roles and recipes, presets, accent colours,
label and chart colours, gradients, adaptive colours and prepaint palettes, the ambient accent
(`ambient-store.ts`), dark mode, increased contrast, colour scopes (`src/theme/color-scope`) and
persistence (`persistence.ts`).

### Where each part comes from

| Part | How it reaches Kotlin and Swift |
|---|---|
| Presets (`color-presets.ts`, `preset-vars.ts`, `preset-accent-hues.ts`), their resolved roles light and dark (`token-registry.ts`), label, chart and status colours, gradients, prepaint palettes, `canonical-tokens.ts` | **Generated.** The existing generators (`scripts/generate-design-tokens-json.ts`, `generate-default-token-vars.ts`, and the compiler's `scripts/generate-swift-tokens.mjs`) gain Kotlin and Swift outputs: `BloomThemeTokens.kt` / `BloomThemeTokens.swift`, every preset's resolved palette as constants, by running the TS functions themselves. Nothing is retyped. |
| The colour engine: a theme from a seed (`buildThemeFromSeed`), a scheme variant and contrast level (`dynamic-scheme.ts`, `scheme-variants.ts`, `contrast-curve.ts`), HCT and CAM16, a seed from an image (`seed-from-image.ts`, the Wu quantizer and `score.ts`) | **Ported once per platform**, file for file and function for function, because it runs on the device (the ambient accent, a seed the person picks, an image). Kotlin: `so.oxy.bloom.ui.theme.engine`; Swift: the `BloomTheme` module. |
| Resolution rules (`color-policy.ts`, `adaptive-colors.native.ts`, `press-colors.ts`, `increased-contrast.ts`, `reduced-transparency.ts`) | Ported with the engine; small, and they decide which generated or computed palette a scope draws. |

### Byte-identical, tested against the TS goldens

- The port is correct when it produces the TS goldens byte for byte:
  `src/theme/__tests__/fixtures/color-engine-golden.json` (every seed × variant × scheme) and
  `src/theme/__tests__/__fixtures__/golden-resolved-tokens.json` (every preset, light and dark,
  `generate-theme-golden.ts`). The Kotlin test (JVM, `bloom-ui`'s unit tests) and the Swift test
  read those same files from the repo; there is no native copy of a golden.
- Floating point: the engine's maths runs in IEEE doubles on every platform. Kotlin uses
  `StrictMath` (fdlibm) for `pow`, `cbrt`, `atan2`, `exp`, `log`, so a value that rounds at a hex
  boundary rounds the same as on Hermes and V8. Darwin's libm and glibc both differ from V8 in the
  last ulp for those functions, so the Swift engine vendors the fdlibm functions it calls: Linux
  and Apple give V8's bits. A golden mismatch is a failing test, never a tolerance.
- A golden either lane needs beyond these (ambient, contrast, scopes) is written by a TS script
  into `src/theme/__tests__/fixtures/`, so both lanes read the same file.
- A colour-policy change is rebased the way it is today (`generate-theme-golden.ts`, on
  purpose, never in prebuild), and the native tests follow the new golden with no native edit.

### The API

| | Android | iOS |
|---|---|---|
| The resolved theme | `BloomTheme` (every colour role, label, chart and status colour, the gradients) | `BloomTheme` |
| Providing it | `BloomThemeProvider(preset: AppColorName?, seed: Color?, scheme: ColorScheme.system/light/dark, contrast: Contrast.standard/increased, storage: BloomThemeStorage?) { content }` | the same, as a view |
| Reading it | `BloomTheme.current` (a `CompositionLocal`) | `@Environment(\.bloomTheme)` |
| A colour scope | `ColorScope(preset or seed) { content }`: the subtree's roles from that palette, prepainted from `getPrepaintPalette` so the first frame is right | `ColorScope` |
| The ambient accent | `AmbientTheme` (`state`, `set(accents)`, `clear()`), app-wide snapshot state, the same API and timing as `ambient-store.ts` | `AmbientTheme`, `@Observable` |
| Dark mode and contrast | the system's (`isSystemInDarkTheme`, `Configuration.uiMode`, the high-contrast text setting) unless the provider overrides them | `colorScheme`, `colorSchemeContrast` |
| Persistence | `BloomThemeStorage` over the stdlib `KeyValueStore`, with the same keys and the same JSON (`PersistedThemeState`) as `persistence.ts`, so a theme saved by the React Native app is read by its native islands and by the native app after migration | the same keys and JSON |

A Bloom colour role in `.bloom` code (`.primary`, `.surfaceContainer`, `.primary.opacity(0.1)`)
reads the nearest theme or scope on every backend; the emitter never inlines a colour value.

## State and effects

| Bloom | Compose | SwiftUI |
|---|---|---|
| `@State var x = v` | `var x by rememberSaveable { mutableStateOf(v) }` (`remember` for a non-saveable type) | `@State var x = v` |
| `@State var x = v` in a hook function (2.0) | `var x by remember { mutableStateOf(v) }`, the hook a `@Composable` function | the same as a view's, in a `DynamicProperty` |
| `$x` | `Binding({ x }, { x = it })` | `$x` |
| `@Observable class M` | each stored property a `mutableStateOf` (field-level reads, ADR 0002) | `@Observable` |
| `@Model` (bloom-data) | an `@Observable` record in the store; the store is `so.oxy.bloom.std.data` | the same over `Bloom` |
| `@Environment(\.k)` | `LocalK.current` | `@Environment(\.k)` |
| `.task { }` | `LaunchedEffect(Unit) { }`; cancelled when the view leaves | `.task { }` |
| `.task(id: v) { }` | `LaunchedEffect(v) { }` | `.task(id: v) { }` |
| `.onAppear { }` / `.onDisappear { }` | `DisposableEffect(Unit) { onAppear; onDispose { onDisappear } }` | the same |
| `.onChange(of: v) { old, new in }` | `OnChange(v) { old, new -> }`: runs after the change is applied, before the next frame | `.onChange(of:)` |
| `task { … }` in a handler | `scope.launch { }` on `rememberCoroutineScope()` | `Task { }` |
| `Task.signal` / cancellation | the coroutine's `Job`; `CancellationException` is a cancellation, never an error a `catch` sees | `Task.isCancelled`, `CancellationError` |

Effect timing is the language's (ADR 0003, "Decided with it"): an effect sees the applied state
and runs before the next frame, on all three backends.

## Standard library, native side

The two lanes implement the standard library differently and are held to the same behaviour by
the conformance suite (below):

- **Android compiles `stdlib/Bloom/*.bloom` through the backend** into `so.oxy.bloom.std`
  (`bloom-native --std JSON,Core`, which brings the modules those call: URL and Time). Only the
  `extern` blocks are Kotlin, hand-written under their Bloom names and parameter orders
  (`Externs.kt`, `TimeExterns.kt`), so the emitted code calls them unchanged. JSON, Core, URL and
  Time compile today; Concurrency is next (its `Foreign` handles need typed runtime classes).
  The compiler's own built-in members (spec 12: `slice`, `dropFirst`, `setting`, …) are
  `Builtins.kt`.
- **iOS writes the standard library's public API in Swift**, on Foundation and on Swift's own
  types, because compiling it would shadow or duplicate them (ambiguous lookups, and a Bloom
  `Date` no Apple API takes): `Date` is `Foundation.Date`, `Duration` is `Swift.Duration`,
  `Task` is Swift's, Bloom's `ContinuousClock` value is `ContinuousClock.Instant`, and
  `hasPrefix`, `firstIndex(where:)`, `sorted(by:)` are Swift's members. A rename table covers
  what differs in meaning: Bloom's `AsyncStream` (a broadcast channel) is `BloomAsyncStream`, and
  Bloom's `Result` keeps its `ok`/`err` cases.

| Module | Android (its externs) | iOS (the public API in Swift) | Output identical to |
|---|---|---|---|
| Core (strings, sorting, sets) | Kotlin stdlib, `BreakIterator` for graphemes, ICU `Collator` for `compareStrings` | Foundation | JS on Hermes (`localeCompare`) |
| Concurrency (`sleep`, `spawn`, `awaitAll`, channels, `actorQueue`) | `kotlinx.coroutines` | Swift concurrency | |
| HTTP | OkHttp | `URLSession` | status, headers (lower-cased), body text |
| JSON, `Codable` | JSON.bloom compiled; a small ordered parser and writer (`parseJSON`, `stringifyJSON`) | `JSONSerialization` with order kept | `JSON.stringify` |
| Data (`@Model`, sources, actions, realtime) | bloom-data's model over SQLite (`bloom-lang-native-7-sqlite`'s module) | the same schema over SQLite | |
| Storage (`KeyValueStore`, `SecureStore`, `FileStore`) | `BloomStorage`'s Kotlin, called directly (no TurboModule) | Keychain, `UserDefaults`, files | |
| Time (`formatDate`, `formatRelative`, ISO) | Time.bloom compiled; `android.icu.text` (DateFormat skeletons, RelativeDateTimeFormatter), which is what Hermes' `Intl` uses on Android | Foundation's ICU formatters | `Intl.DateTimeFormat`, `Intl.RelativeTimeFormat` |
| Math (`formatNumber`, `formatCompact`) | `android.icu.text.NumberFormat`, `CompactDecimalFormat` | `NumberFormatter`, `.formatted(.number.notation(.compactName))` | `Intl.NumberFormat` |
| Localization | the package's catalogs compiled to resources | the same catalogs | |
| Navigation | the runtime's typed stack over `Routable`, deep links from `Package.bloom` | `NavigationStack(path:)` | the route paths |
| Image | Coil 3 or the prototype's pipeline (decided by M1's measurement) | Nuke or a `URLSession` cache | |
| Video | Media3 (phase F's `BloomVideo` players, reused) | `AVPlayer` | |
| URL, Regex, Logger | URL.bloom compiled over `java.net.URI` (WHATWG's normalisation: lower-cased host, `/` for an empty http path, a default port dropped); `java.util.regex` with JS-flag translation; `Log` | Foundation, `NSRegularExpression`, `os.Logger` | JS `URL`, `RegExp` |

Formatting is the hard part of "identical": ICU versions differ between Android releases, iOS
and Node. The conformance suite pins a set of `(locale, value, options)` cases with Node's
output as the expected text; a platform whose ICU disagrees gets a documented override, never a
silent difference.

## Material: one base for glass and motion (owner's rule)

Every glass and motion effect must feel at least as good as today (the glass material, blur and
backdrop; the stretch and elastic press and drag; the menu's open and close motion; haptics;
overscroll stretch), and it is built **once**: a single material primitive that every component
draws through. A glass button and the bottom bar are the same material. No component implements
its own blur, tint, rim, shadow, press, stretch or haptic.

### The primitive

The language already has it: `.glass(_:)` with `GlassMaterial` (`regular`, `clear`) and its
methods (`.tint(role, opacity)`, `.dimmed()`, `.interactive()`), `glassID` / `glassUnion` /
`glassTransition`, and `Surface`. The native runtimes implement that surface once, as one type
and one modifier:

| | Android | iOS |
|---|---|---|
| The value | `BloomMaterial` (sealed): `Glass(kind: GlassMaterial, tint: ColorRole?, opacity: GlassOpacity?, interactive: Boolean, dimmed: Boolean)`, `GlassProminent(tone)` (regular glass tinted with the tone's `toneRole`), `Solid(fill: ColorRole)`, `Flat` | `enum BloomMaterial` with the same cases |
| On any node | `Modifier.bloomMaterial(material, shape)` | `.bloomMaterial(_:in:)` |
| A container | `BloomSurface(material, shape, content)` (Bloom's `Surface`) | `BloomSurface` |
| Grouping and morphs | `BloomGlassGroup { }` with `Modifier.bloomGlassID(id, ns)` / `bloomGlassUnion(id, ns)` | `GlassEffectContainer` with `glassEffectID` / `glassEffectUnion` |
| Press response | `Modifier.bloomPress(material, onPress)`: the material's scale, stretch and haptic | `.bloomPress(_:action:)` |

A Bloom component takes a `material:` and passes it to this primitive; that is all it does about
its look. The components that draw through it, on both platforms: `Button` (every
`buttonMaterial`), the header's glass buttons (`src/page-header`), `BottomBar` (`src/bottom-bar`),
`Fab` (`src/fab`), `TabBar` (`src/tab-bar`), `Menu` and its trigger, `Sheet`, `Popover`, `Toast`,
and `Surface` itself.

### Its tokens

`MaterialTokens` (generated, like every token file, never hand-edited) holds, per material and
scheme:

- **tint:** the untinted fill (`glass.<kind>.fill`), the default tint opacity
  (`glass.<kind>.tintOpacity`), and `toneRole` for a tinted control;
- **blur:** at rest (`glass.<kind>.lensBlur`), grown into a menu panel (`lensMenuBlur`), and
  iOS's `iosStyle` / `iosFallback`; Android's values are the lens engine's radius in dp, already
  set on the Pixel 8a (`src/floating/lens/lens-frost.ts`, `LENS_FROST`);
- **border and highlight:** the sheen and the rim optics (`src/surface/optics.ts`,
  `SURFACE_LOOKS`: saturate, slope, offset, the rim's angle-by-depth gains and glow), light and
  dark;
- **shadow:** Surface's elevation for a floating material;
- **press and stretch:** `motion.press` (100 ms, `inOutQuad`), `pressScale` / `pressFade`, and
  the elastic stretch and drag (the engine's `motion/GlassJelly.kt`, `GlassSpring.kt`,
  `GlassMorphTuning.kt`), so a button and the FAB stretch the same way;
- **menu motion:** open and close (`motion.present` 220 ms, `motion.dismiss` 150 ms, the morph
  out of the trigger in `GlassMorphFrame.kt`);
- **haptics:** which feedback plays at press, at a menu's open, at a scrub step and at a
  selection (`overlay/GlassFeedback.kt`'s constants; `UIImpactFeedbackGenerator` /
  `UISelectionFeedbackGenerator` styles on iOS).

The sources are `spec/language.json` (`glass`, `motion`, `toneRole`), `src/design-tokens/`, and
the TS side, which already centralises the material (`src/surface`, `src/platform-surface`,
`src/floating/lens`). The generator reads them, so the TypeScript, Kotlin and Swift materials
cannot drift; the spec's tests already hold `lensBlur` equal to `LENS_FROST`.

### The rules it carries from today's TS

- A lens is never drawn inside a lens: inside a material container, a control's glass is the
  container's surface (`useControlMaterial`, `useInLensBase`).
- A region publishes its controls' material: a floating header, a toolbar or a bar makes its
  controls glass without each one saying so (`LensMaterialProvider`), and a floating control is
  Bloom's one floating size, 44 (`FLOATING_CONTROL_SIZE`).
- In a separate window (a sheet, a dialog) there is nothing behind to refract: the material keeps
  the shared paint, never an empty dark lens (`useLensAvailable`).
- A material in a scrolling list is the shared paint, not a live lens: each live lens has a cost
  and the window-drawn lens does not follow the overscroll stretch (`Surface`'s `material` doc).

### Android: once, on the bloom-lens engine

- **Reuse, do not rewrite.** `packages/bloom-lens/android/src/main/java/so/oxy/bloom/glassmenu/`
  (chrome, overlay, motion, render, backdrop, field; about 7,300 lines) is plain Android Views and
  RenderEffect shaders. Three files touch React Native: `com.facebook.react.R` ids in
  `motion/GlassGroup.kt` and `chrome/SurfaceNodesHost.kt`, and `ReactFontManager` in
  `content/GlassMenuContent.kt`. The engine moves into an RN-free Gradle module (its own id
  resources, a font provider interface) that the React Native package and the Compose runtime
  both depend on, so one engine serves both. That edit is in `bloom-lens`, agreed with its owners
  first.
- `bloomMaterial` and `BloomSurface` are the only Compose code that touches the engine: the lens
  surfaces through `AndroidView` (`GlassChromeView`, `SurfaceNodesView`), groups through
  `GlassGroup`, menus through `GlassMenuOverlay` / `GlassMenuSession` with the same `records/`
  the TurboModule builds today, haptics through `GlassFeedback`.
- **A gate keeps it single:** a check in the runtime's build fails when a file outside
  `so.oxy.bloom.ui.material` uses `RenderEffect`, `BlurMaskFilter`, `Modifier.blur`, a press
  `graphicsLayer` scale or `performHapticFeedback`.
- **Overscroll:** every Bloom scroll container uses Compose's overscroll stretch (Android 12+),
  matched to today's `EdgeEffect` stretch; window-drawn lenses stay out of scroll views, as above.

### iOS

The same `BloomMaterial`, `.bloomMaterial(_:in:)`, `BloomSurface`, groups and
`.bloomPress(_:action:)`, on SwiftUI, in `BloomUI/Material/`:

- **iOS 26+:** `glassEffect(Glass.regular|.clear .tint(role at opacity) .interactive(), in: shape)`;
  groups are `GlassEffectContainer` with `glassEffectID` / `glassEffectUnion`, and morphs are the
  system's.
- **iOS 17 to 25:** the spec's `iosFallback` (`systemThinMaterial` / `systemUltraThinMaterial`),
  then the tint at 0.72 (0.8 for a control fill), then Bloom's rim and sheen.
- **Accessibility is Bloom's rule, not the system's:** with reduce transparency or increased
  contrast the material paints `.solid` with the composited fill and the 3:1 hairline, on both
  platforms. The material's scheme is Bloom's theme (`.environment(\.colorScheme, theme.scheme)`),
  never the window's.
- **Press:** glass materials take the system's interactive glass (the platform's press, bounce and
  stretch on iOS); solid and flat ones take Bloom's press (scale 0.98, `motion.press` 100 ms
  `inOutQuad`). Haptics go through `.sensoryFeedback` with today's intent table: `tap` a light
  impact, `confirm` a medium one, `selection` and `toggle` selection feedback, success, warning and
  error notifications; buttons and the FAB fire none, as today.
- **The gate, on iOS too:** a check fails when a BloomUI file outside `Material/` uses
  `glassEffect`, a `Material` background, `UIVisualEffectView`, `.blur`, `sensoryFeedback` or
  `UI*FeedbackGenerator`, or a press `scaleEffect`.
- **What the system does not give, and the plan for each:**
  - the frost radius, rim and glow optics on glass: the system's on iOS 26 (the platform's
    glass); the tokens apply on the fallback;
  - the lens jelly (swell, lean, tanh stretch): the system's interactive glass;
  - the scrubbable tab capsule (1:1 highlight, a haptic per boundary, `minimizeProgress` /
    `hideProgress`): Bloom's own tab bar over the material with a `DragGesture`, not `TabView`'s,
    which is used only where the app takes the system bar;
  - the header's flat smoothstep scrim and `titleReveal`: Bloom's own overlay on the system
    toolbar;
  - menus: the system `Menu` / `contextMenu`; custom rows (swatches, sub-flyouts) are a Bloom
    popover on the material;
  - sheets: the system `.sheet` with detents; Bloom's detached sheet (16 gaps, radius 24) and its
    dismiss physics are a custom presentation on the material;
  - the progressive blur band: stacked masked materials.
- **To settle first:** `docs/surface-material-study.mdx` still says "No Liquid Glass.
  expo-glass-effect stays out of Bloom", and today's iOS kit draws buttons, the FAB and header
  controls as opaque tinted pills with only floating surfaces blurred. The owner's direction
  (the system's Liquid Glass) changes how iOS controls look: that study is updated with the iOS
  lane's first material PR, and the side-by-side recordings on the Mac show the result is at
  least as good.

## Islands (migration)

A natively compiled `.bloom` screen runs inside today's React Native app as one native view.

- **Marking.** `.module("FeedIsland", native: .island)` in `Package.bloom`. The island is the view
  named after its module (`FeedIsland`): its `Codable` props are its data, and each event prop
  (`(T) -> Void`) an intent. State lives native.
- **The host side.** The stdlib's `Island(name, props:, onEvent:)` (`stdlib/Bloom/Island.bloom`)
  over `extern native "BloomIsland"`: the component `BloomIsland` with `island: String`, `props:
  String` (the props as one JSON object) and `onIslandEvent: { name, payload }` (the event prop's
  name, the value's JSON). JSON text crosses for the first islands; a typed Fabric event per
  island can come later, if a measurement asks for it.
- **Android:** the backend writes `@Composable fun <Module>__island(props: String, emit: (String,
  String) -> Unit)` beside the view: each prop decoded by its type's derived decoder, remembered
  by its own JSON value (a props change re-decodes only what changed), each event prop calling
  `emit`. `bloom build android` (#1074) generates `:bloom-islands`: the islands' Kotlin and the
  runtime (`bloom-native emit --module <islands> --std JSON,Core --runtime`), `IslandRegistry`
  (`Map<String, @Composable (String, (String, String) -> Unit) -> Unit>`), and `BloomIslandView`,
  an `AbstractComposeView` whose `island` and `props` are snapshot state (content set once, a
  props change recomposes and keeps the island's state), with the direct event `topIslandEvent`
  → `onIslandEvent`. **iOS:** a Fabric component hosting a `UIHostingController`, with the same
  props and event.
- **What crosses.** Data in, intents out: the island never calls TypeScript. The feed island
  takes post slices and paging cursors and emits `like`, `repost`, `open(post)`, `loadMore`,
  `menu(post)`; the React Native side keeps the network and the stores until they are Bloom.

## Conformance

One suite, `packages/bloom-language-compiler/conformance/`: each case is a `.bloom` program and
its expected output (printed lines, JSON text, formatted strings). It runs on the TypeScript
backend (Node), on Kotlin (JVM unit tests, plus a device lane through hangar) and on Swift (the
Mac lane; the Foundation parts also on Linux, `swift test` against Node's expected output). Golden emit tests per construct live with each backend; the conformance suite is what
proves the three mean the same.

## Decided in review

1. Swift imports: scoped, one SwiftUI declaration at a time (Packages).
2. `Map` and `Set` on Swift: always ordered (Types).
3. Each modifier's category: in the spec, `modifierCategories` (Modifiers).
4. The island's encoding: JSON text for the first islands (Islands).
5. `BloomMaterial`'s cases beyond the spec's (`GlassProminent`, `Solid`, `Flat`): runtime
   shorthands for `buttonMaterial` and `sheetMaterial`, until the spec owners decide otherwise.

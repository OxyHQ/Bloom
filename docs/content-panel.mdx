# ContentPanel

The column a screen's content lives in. It caps the reading width and, above a
breakpoint, decides whether that column reads as a framed surface or as the
page itself.

```tsx
import { ContentPanel } from '@oxy.so/bloom/content-panel';

<ContentPanel framed framedFrom={640}>
  <SettingsScreen />
</ContentPanel>
```

## The panel's edge

```tsx
<ContentPanel framed chrome="elevated" />   {/* default: hairline + panel shadow */}
<ContentPanel framed chrome="border" />     {/* hairline only */}
<ContentPanel framed chrome="none" />       {/* flat rounded surface */}
<ContentPanel framed shadow="0 8px 24px rgba(0,0,0,.12)" />  {/* your own lift */}
```

A framed panel wears the same edge the [`Sidebar`](/docs/bloom/main/sidebar)
does — a hairline **and** the floating-panel shadow, from one recipe in
`styles/panel-chrome.ts` (`resolvePanelChrome`, `PANEL_SHADOW`) so the two
surfaces cannot drift apart. The border alone read as a box drawn on the page;
the shadow is what makes it a panel lifted off it.

- On **web** the shadow rides the same sticky overlay as the hairline, so the
  lift and the edge always describe the same rectangle, and it paints outward
  into the gutter the page background shows.
- On **native** the surface carries both.
- `chrome` is ignored while the panel is full-bleed (below `framedFrom`, or
  `framed={false}`) — there is no edge to draw.

## Which prop decides what

| prop               | decides                                                  |
| ------------------ | --------------------------------------------------------- |
| `framed`           | whether the panel draws a surface at all                   |
| `framedFrom`       | the breakpoint it starts framing at — `500` `640` `768` `1024` |
| `showStickyFrame`  | whether the frame persists behind sticky content           |
| `surfaceStyle` / `surfaceClassName` | the surface itself                        |
| `contentStyle` / `contentClassName` | the column inside it                      |
| `maskColor`        | the colour the gutter mask fades to                        |
| `overlaySizing`     | (web) how the mask/border overlays size themselves — see below |

## `overlaySizing`: the panel's own box, or a constant frame

The web overlays (the border frame and the gutter bleed-mask) default to
**`overlaySizing="panel"`**: sized to the panel's own real box through CSS Grid
layer-stacking. The edge behaves like any other border — it scrolls with the
content, you see the two side edges while reading and the rounded corners at the
ends of the page.

`overlaySizing="viewport"` is the other mode: the overlays are `100dvh` and
`position: sticky`-pinned, so a rounded top and bottom edge follow the viewport
down the page. It was the default until it was measured against a long feed: the
frame holds still while the content moves inside it and it jumps 8px on the
first scroll, which reads as the panel breathing. It remains for a consumer that
wants that constant frame — and it is also the mode `overlayTopOffset` exists
for.

Panel mode is additionally the right answer whenever the consumer's OWN shell
bounds the panel (a fixed app shell with internal scroll containers): a
viewport-sized overlay there paints over anything placed outside the panel, such
as a header above it.

```tsx
<View style={{ flex: 1 }}>
  <ExternalHeader />
  <ContentPanel framed overlaySizing="panel">
    <SettingsScreen />
  </ContentPanel>
</View>
```

## `framedFrom` is why the branch is not in your screen

A phone wants a plain column: a frame a few pixels from the screen edge reads
as a rendering bug, not as a card. A desktop wants the framed surface. Handling
that in the screen means every screen re-derives the same breakpoint, and they
drift.

## Panels are siblings, never nested

`ContentPanel` **throws** if you nest one inside another. That is deliberate: a
panel in a panel would frame inside a frame and inset the reading column twice,
which looks merely "a bit padded" and would survive review indefinitely. A loud
failure in development is the cheaper outcome.

Two columns side by side are two panels as **siblings**:

```tsx
<View style={{ flexDirection: 'row', gap: 16 }}>
  <View style={{ flex: 2 }}><ContentPanel framed>…</ContentPanel></View>
  <View style={{ flex: 1 }}><ContentPanel framed>…</ContentPanel></View>
</View>
```

A screen picks one panel per column; the sections inside it are plain views.

## Do not put a Card immediately inside a framed panel

They are both surfaces. A card filling a framed panel is two borders with a few
pixels between them. Use the panel's frame, and reach for
[`Card`](/docs/bloom/main/card) for things *within* the column that are
genuinely separate objects.

# ContentPanel

The column a screen's content lives in. It caps the reading width and, above a
breakpoint, decides whether that column reads as a framed surface or as the
page itself.

```tsx
import { ContentPanel } from '@oxy.so/bloom/content-panel';

<ContentPanel framed framedFrom={640}>
  <SettingsScreen />
</ContentPanel>
```

## The panel's edge

```tsx
<ContentPanel framed chrome="elevated" />   {/* default: hairline + panel shadow */}
<ContentPanel framed chrome="border" />     {/* hairline only */}
<ContentPanel framed chrome="none" />       {/* flat rounded surface */}
<ContentPanel framed shadow="0 8px 24px rgba(0,0,0,.12)" />  {/* your own lift */}
```

A framed panel wears the same edge the [`Sidebar`](/docs/bloom/main/sidebar)
does — a hairline **and** the floating-panel shadow, from one recipe in
`styles/panel-chrome.ts` (`resolvePanelChrome`, `PANEL_SHADOW`) so the two
surfaces cannot drift apart. The border alone read as a box drawn on the page;
the shadow is what makes it a panel lifted off it.

- On **web** the shadow rides the same sticky overlay as the hairline, so the
  lift and the edge always describe the same rectangle, and it paints outward
  into the gutter the page background shows.
- On **native** the surface carries both.
- `chrome` is ignored while the panel is full-bleed (below `framedFrom`, or
  `framed={false}`) — there is no edge to draw.

## Which prop decides what

| prop               | decides                                                  |
| ------------------ | --------------------------------------------------------- |
| `framed`           | whether the panel draws a surface at all                   |
| `framedFrom`       | the breakpoint it starts framing at — `500` `640` `768` `1024` |
| `showStickyFrame`  | whether the frame persists behind sticky content           |
| `surfaceStyle` / `surfaceClassName` | the surface itself                        |
| `surfaceColor`     | what the panel tells its content it is painted in — only when `surfaceClassName`/`surfaceStyle` repainted it |
| `contentStyle` / `contentClassName` | the column inside it                      |
| `maskColor`        | the colour the gutter mask fades to                        |
| `overlaySizing`     | (web) how the mask/border overlays size themselves — see below |

## `overlaySizing`: viewport chrome vs. a bounded shell

The web overlays default to `overlaySizing="viewport"`: sized to `100dvh` and
`position: sticky`-pinned, so they read as a constant frame around the visible
slice of a panel whose own DOM height can exceed one screen — the right choice
in a document that actually scrolls (a feed page that grows with content).

A consumer whose OWN shell already bounds the panel's height — a fixed app
shell with its own internal scroll containers, no document scroll — doesn't
have that problem, and viewport-sizing there is actively wrong: the overlay
still reads `100dvh` regardless of how much of the viewport is actually the
panel's, so anything placed OUTSIDE the panel (a header above it, say) gets
painted over. `overlaySizing="panel"` fixes that: the overlays size to the
panel's own real box via CSS Grid layer-stacking instead of viewport math, so
they never extend past whatever height the panel actually has.

```tsx
<View style={{ flex: 1 }}>
  <ExternalHeader />
  <ContentPanel framed overlaySizing="panel">
    <SettingsScreen />
  </ContentPanel>
</View>
```

## `framedFrom` is why the branch is not in your screen

A phone wants a plain column: a frame a few pixels from the screen edge reads
as a rendering bug, not as a card. A desktop wants the framed surface. Handling
that in the screen means every screen re-derives the same breakpoint, and they
drift.

## Panels are siblings, never nested

`ContentPanel` **throws** if you nest one inside another. That is deliberate: a
panel in a panel would frame inside a frame and inset the reading column twice,
which looks merely "a bit padded" and would survive review indefinitely. A loud
failure in development is the cheaper outcome.

Two columns side by side are two panels as **siblings**:

```tsx
<View style={{ flexDirection: 'row', gap: 16 }}>
  <View style={{ flex: 2 }}><ContentPanel framed>…</ContentPanel></View>
  <View style={{ flex: 1 }}><ContentPanel framed>…</ContentPanel></View>
</View>
```

A screen picks one panel per column; the sections inside it are plain views.

## The panel says what colour it is, so chrome does not have to guess

A panel is the surface a screen sits on, which makes it the thing in-panel
chrome keeps asking about: a sticky header that has to be **opaque** over the
scrolling column, a tab rail, a search field's backing, a reply bar pinned to
the bottom. Each one only ever wanted "be the colour of the surface I am on",
and the only way to say that used to be to repeat the panel's own `bg-card` at
the call site — which turns one decision about the panel's surface into a sweep
through every screen the next time it changes. Mention carries ~65 of those.

So the panel publishes it. Anything inside reads it:

```tsx
import { useSurfaceFill } from '@oxy.so/bloom/styles';

function StickyReplyBar() {
  const surface = useSurfaceFill();          // the panel's fill — `colors.card`
  return <View style={{ backgroundColor: surface }}>…</View>;
}
```

`useSurfaceFill()` is the cross-platform answer and the one to reach for.
[`styles`](/docs/bloom/main/styles#surface-levels) has the rest of the model:
the rung the panel publishes with it (`1`), the derived hairline and text rungs,
and `--bloom-surface`, the web variable the panel writes on the element it
paints so a stylesheet can follow the surface too.

Two things are worth knowing here:

- **It is the panel's REAL fill, not a rung.** `theme.colors.card` is not rung 1
  in dark mode — the rung is a computed step off the page — and chrome that took
  the rung would sit a visible shade off the column it is supposed to vanish
  into. The panel publishes the fact.
- **Repainting the surface makes the panel stop claiming to know.**
  `surfaceClassName` is a utility Bloom cannot resolve to a colour, and a
  `surfaceStyle` with a `backgroundColor` is the same repaint by the other door
  — the colour is legible there, but which of the two actually paints differs by
  platform, so the panel refuses to guess. Either way it falls back to publishing
  the rung alone rather than a confident wrong answer. `surfaceColor` is how that
  caller gets the exact answer back:

```tsx
<ContentPanel surfaceClassName="bg-background" surfaceColor={colors.background} />
```

`surfaceColor` changes nothing about how the panel looks — the class still
paints it. It only decides what the panel tells its content.

## Do not put a Card immediately inside a framed panel

They are both surfaces. A card filling a framed panel is two borders with a few
pixels between them. Use the panel's frame, and reach for
[`Card`](/docs/bloom/main/card) for things *within* the column that are
genuinely separate objects.

# Typography

Bloom's text primitives. Every one is a flat component, and every one accepts `className` so a NativeWind consumer can override it — except `Blockquote`, for the reason below.

```tsx
import { H1, Lead, Muted, P, Small, Text } from '@oxy.so/bloom/typography';
```

Or as a namespace, which costs no tree-shaking because the family ships as its own subpath:

```tsx
import * as Typography from '@oxy.so/bloom/typography';
```

## Base

`Text` is the base: theme-aware colour, Bloom's sans family, 13px. `Span` is the same component under the name you reach for inline.

`H1` through `H6` are headings, and on web they carry `role="heading"` with the matching `aria-level` — which is what makes a screen reader's heading navigation work.

`P` is body copy at 16px over a 28px line, with a leading margin (`mt-3`, 24px from the `sm` breakpoint up) and `role="paragraph"` on web.

## The heading ramp

react-native-reusables' own numbers, resolved from its `text-4xl font-extrabold tracking-tight` and the three `font-semibold` levels under it. `tracking-tight` is −0.025em, so the letter-spacing is computed against each level's own size. `H5`/`H6` have no upstream counterpart and continue the ramp.

| | size / line | weight | also |
| --- | --- | --- | --- |
| `H1` | 36 / 40 | 800 | centred, like shadcn's `h1` |
| `H2` | 30 / 36 | 600 | a 1px rule underneath, 8px clear of the text |
| `H3` | 24 / 32 | 600 | |
| `H4` | 20 / 28 | 600 | |
| `H5` | 18 / 28 | 600 | |
| `H6` | 16 / 24 | 600 | |

The FAMILY is not upstream's. shadcn sets everything in one sans face; a Bloom heading is set in the display family, which is the same layer as the colour roles and is Bloom's own.

A caller's `className` replaces the size, weight and tracking (react-native-css merges utilities into `style` first, so an inline default repeating those keys would silently beat `text-2xl`). Only the family survives it.

## Prose variants

Ported from react-native-reusables, which spells them as a `variant` prop on one `Text`. Bloom keeps them flat, because `H1`–`H6` already are and a second way to ask for a heading is an ambiguity, not a feature.

```tsx
<H2>Device sessions</H2>
<Lead>Every device you sign in from gets its own session.</Lead>
<P>A session is minted per origin and refreshed in the background.</P>
<Blockquote>A session you cannot end from elsewhere is a key you cannot take back.</Blockquote>
<Large>Ending a session</Large>
<Small>Last active 4 minutes ago</Small>
<Muted>Sessions older than 90 days end on their own.</Muted>
```

| Component | What it is |
| --- | --- |
| `Lead` | An intro paragraph. Larger than body, in the secondary colour. |
| `Large` | Emphasised body text — a section's opening line. |
| `Small` | A dense label, set on its own baseline with no extra leading. |
| `Muted` | De-emphasised supporting text. |
| `Blockquote` | A quotation, with the rule down its left edge. |

react-native-reusables' `code` variant is deliberately absent: Bloom's [`code`](/docs/bloom/main/design-tokens) family already owns monospace text, and a second spelling of one thing is what this library removes rather than adds.

## `Blockquote` takes no `className`

The one exception, and it is a platform limit rather than a preference. React Native draws no border on a text node — Android renders a `TextView`, iOS an attributed string, and neither paints a left rule — so the rule has to be a `View` wrapping a `Text`.

That splits the component in two: the node the parent lays out is the `View`, while the utilities anybody would write (`text-lg`, `text-primary`) belong on the `Text` inside it. A `className` would land on one of them and silently do nothing for the other, which is exactly the failure Bloom's className rules exist to prevent. So it is not offered:

```tsx
<Blockquote style={{ borderLeftWidth: 4 }} textStyle={{ fontStyle: 'normal' }}>
  Styled container and text, separately.
</Blockquote>
```

A caller who wants utility classes composes a `View` and a `Text` directly.

## `className` and inline defaults

Every other variant drops a default only for the keys the `className` claims (a custom class it cannot read, such as `chip-label`, is assumed to claim all of them): `text-<size>` (and `text-[14px]`) claims size and line height, `text-<colour>` claims colour, `leading-*` line height and `font-<weight>` weight. react-native-css merges utilities into `style` first, so an inline default repeating a claimed key would win the merge and silently break the caller's `text-lg` or `text-primary`; every other default still applies, so `<Muted className="mt-2">` keeps its secondary colour (dropping all defaults left it unset, and invisible in dark mode). `fontFamily` is the exception and stays inline either way.

Because the family is inline, a family utility cannot beat it, so `Text` reads the ones it can answer from `className` itself: `font-display` (or a size from `text-3xl` up) sets BlomusModernus, and `font-mono` sets JetBrains Mono, at any breakpoint or state prefix (`md:font-mono`). An explicit `font-mono` wins over a family implied by size or variant: `text-4xl font-mono` is mono. Bloom defines no serif family (`fonts/tokens.ts` has `sans`, `display` and `mono`), so `font-serif` has no counterpart.

Layout classes on web need the consumer's Tailwind pipeline to be scanning Bloom's `lib/`. Colours work regardless, because Bloom applies those inline — which is what makes a missing pipeline look like a layout bug rather than a missing stylesheet.

## What a `Text` costs

A feed row draws dozens of texts, so `Text` is kept cheap. Without a `className` there is nothing for react-native-css to resolve, and `Text` renders React Native's text node directly: on native one component, no hook slot, and two context reads (the theme and the typography scope). The display face's Bold cut is chosen from the same style it would be under the interop. Only a `Text` with a `className` mounts the interop host that resolves the utilities. `useThemePaint` reads the prepaint context on the web alone (`theme/prepaint/use-paint-colors.native.ts`). `src/typography/__tests__/text-host-cost.test.tsx` pins these numbers.

## Desktop text styles

On a desktop platform (`useDesktopPlatform()`) Bloom's ramp is drawn in the
desktop text styles (`DESKTOP_TEXT_STYLES`, `DESKTOP_TYPE_SCALE`): one style per
role, each with its size, line height and weight, and tracking by size
(`DESKTOP_TRACKING`: +0.12 at 10, 0 at 12, −0.08 at 13, −0.43 at 17, back to
positive from 24).

| Role | Size/line | Weight | Bloom steps drawn in it |
|---|---|---|---|
| `large-title` | 26/32 | regular | — |
| `title-1` | 22/26 | regular | `title-1-*` |
| `title-2` | 17/22 | regular | `title-2-*` |
| `title-3` | 15/20 | regular | `title-3-*`, `headline-*` |
| `headline` | 13/16 | bold | an alert's title |
| `body` | 13/16 | regular | `body-*`, an unsized `Text` |
| `callout` | 12/15 | regular | `body-2-*` |
| `subheadline` | 11/14 | regular | `caption-1-*`, a menu's group label |
| `footnote`, `caption-1`, `caption-2` | 10/13 | regular, regular, medium | `caption-2-*` |

A step keeps its own weight (`body-semibold` is the body role, semibold). The
hero steps (`large-title`, `display-*`) keep their size and their display face;
`title-*` and headings are set in the sans on a desktop. `TypographyScope
scale="desktop"` asks for these styles off a desktop platform and
`scale="default"` keeps Bloom's ramp on one; `useDesktopTypography()` reads the
answer.

## Bloom control size is a separate scope

Semantic text variants, headings, prose helpers and `Blockquote` keep their
typographic recipes under `BloomScope`; a compact control scope does not shrink
the text a person is reading. `TypographyScope scale="desktop"` selects the
desktop text ramp independently of control size. Native-renderer and DOM web
tests compare the exported typography parts under default, `xs`, `lg` and
nested control scopes.

## Local system-font scope

`<TypographyScope mode="system">` changes the font family of Bloom text and composed controls in its subtree to the platform system font. Semantic variants retain their size, weight and spacing. It applies to headings, body text, buttons and segmented controls without changing global fonts. `mode="default"` explicitly returns to Bloom families; omitted mode inherits the enclosing scope. The provider is stable across mode changes, preserving mounted controls and media.

## Titles and subtitles

Bloom uses BlomusModernus for semantic titles and subtitles: H1–H6, `large-title-*`, `display-*`, `title-1-*`, `title-2-*` and `title-3-*`. `Title` and `Subtitle` also select this family when their chosen size is a smaller headline/body variant. `Text` marked as an accessible heading follows the same rule. Plain headline/body/caption variants and control labels remain sans; a small button label does not become a display title merely because it uses `headline-medium`.

Use `Title`/`Subtitle` for a screen's heading pair and ordinary `Text` for description, price and terms. Dialog headers, page headers and subscription hero headings share this policy.

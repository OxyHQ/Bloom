# Portal

`Portal` renders its children at an outlet instead of where they were written.
It is what lets a menu escape a parent's `overflow: hidden`, a clipping
scroll view, or a stacking context that would otherwise trap it.

```tsx
import { Portal } from '@oxy.so/bloom/portal';

<View style={{ overflow: 'hidden' }}>
  <Trigger />
  {open ? (
    <Portal>
      <OverlayRoot>
        <Panel />
      </OverlayRoot>
    </Portal>
  ) : null}
</View>
```

## Content keeps the context of where `<Portal>` is written

On web this is `createPortal`'s own behaviour. On native it is a bridge
(`src/portal/context-bridge.tsx`), because React Native has no portal into a
view: `ReactFabric.createPortal` commits with `completeRoot(containerTag, …)`,
which replaces a whole ROOT's children. Bloom's native portal is therefore a
context + outlet — and the content renders under the outlet, so until 15.50
every provider between the outlet and the `<Portal>` was lost. Bloom bridged
its theme and nothing else: Allo's Settings → Account crashed on Android with
`AlloSettingsProvider is missing` while the same tree worked on web.

Now the `<Portal>` reads its own fiber, collects every context provider above it
(nearest first), subscribes to each, and the outlet renders the content inside
the same providers with the same values — react-query, i18n, navigation, the
app's own contexts. A new value re-registers the content in a layout effect, so
it lands in the same frame as the tree around the `<Portal>`.

Deliberately NOT bridged — the content sees the OUTLET's value, as before:

| Context | Why |
| --- | --- |
| React Native's `TextAncestorContext`, `ScrollView.Context`, `VirtualizedList`'s context | They say where a node is in the host tree; bridged, a list in a portal written inside a list registers as that list's nested child. |
| safe-area insets and frame | The outlet covers the root window; the window's insets describe the surface. |
| the portal group's own contexts | The outlet's element changes on every append; a portal subscribed to it re-appends forever. |
| `blur/blur-target.tsx`'s window contexts | A portal written inside a `<Modal>`'s `BlurWindow` renders in the ROOT window: bridged, its backdrop would blur its own ancestor (SIGSEGV). |

A module declares its own as `excludeFromPortalBridge(createContext(…))`
(exported from `@oxy.so/bloom/portal`; it marks the context object and returns
it) — for host-position contexts only, never for data.
`OverlayRoot` separately resets screen, scroll, edge and surface-level contexts
for every surface, on both platforms. Gate: `PortalContextBridge.test.tsx`.

## `PortalProvider` and `PortalOutlet` are NATIVE-ONLY

On web the fork portals directly to `document.body`, so both are explicit no-op
exports there. You still render them — the API is the same on both platforms —
they simply do nothing in a browser.

This matters because "this app doesn't mount a Portal Outlet" is **never** a
valid reason to fork a web-facing component. That reasoning once produced a
742-line fork that diverged for two months and shipped strictly worse than the
thing it replaced.

## Where the outlet goes

Near the app root, after the content it must paint over. Mounting it too early
puts every portaled surface behind the app; mounting two duplicates every
surface.

Outlets deliberately stay **out** of `BloomProvider`: their tree position is an
app decision, and a second mount is silent — you get two of everything, which
reads as a render loop rather than as a duplicated outlet.

## Wrap the app content in `OverlayInertBoundary`

A modal surface must keep a screen reader inside it. The outlet renders every
surface as the app content's **sibling**, so the surface can only mark itself
modal; it cannot hide the content. iOS honours that (`accessibilityViewIsModal`
hides siblings). Android does not: TalkBack only skips a subtree whose own root
says `importantForAccessibility="no-hide-descendants"`, and that root is the
app's. With the settings modal open, TalkBack walked straight into the Home feed
behind it (OxyHQ/Mention#1126).

Wrap everything that is **not** the outlet:

```tsx
import { OverlayInertBoundary, PortalOutlet, PortalProvider } from '@oxy.so/bloom/portal';

<PortalProvider>
  <OverlayInertBoundary>
    <AppContent />
  </OverlayInertBoundary>
  <PortalOutlet />
</PortalProvider>
```

While any `OverlayRoot modal` is mounted the boundary hides what it wraps:
`importantForAccessibility="no-hide-descendants"` on Android,
`accessibilityElementsHidden` on iOS, `inert` + `aria-hidden` on web (removing
the page from the tab order too — web dialogs set no focus trap of their own).
Non-modal overlays — menus, popovers, tooltips, toasts — never trigger it.

- **Never wrap the outlet.** The surfaces would hide themselves.
- **Layout is unchanged.** On web the boundary is `display: contents` (no box;
  document scroll is untouched). On native it is a `flex: 1` view that is never
  collapsed; pass `style` if its parent is not a column the content fills.
- Surfaces outside the boundary (a media-flight layer beside the outlet) stay
  reachable — put only the app's own screens inside it.
- `useModalOverlayActive()` reads the same state for app code that needs it.

## Portal is not enough on its own

A portaled surface still needs:

- an [`OverlayRoot`](/docs/bloom/main/overlay) for its stack position and its
  interactive root — the web portal root is `pointer-events: none` and that
  **inherits**, so a surface without one is entirely click-through;
- a `Backdrop` if it should dismiss on an outside press.

## Several portals coexist

Each portal is tracked by its own id, so opening a second does not replace the
first, and unmounting one removes only that one. Order at the outlet follows
mount order (an update keeps a portal's place) — which is also why the overlay stack, not the outlet, decides what
paints on top.

# SettingsModal

An 871×614 panel with a 274px navigation rail on the left and a titled, scrolling page on the right, using the shared floating `PageHeader` for its title, back and close controls, plus the row chrome and the four pages it ships (General, Profile, Tools, Storage). Everything the demo hardcodes — rail groups, plan, servers, files — comes in as props.

```tsx
import { useDialogControl } from '@oxy.so/bloom/dialog';
import {
  SettingsModal,
  SettingsProfilePage,
  SettingsTextField,
} from '@oxy.so/bloom/settings-modal';
import { RiSchoolLine, RiSettings6Line, RiBankCardLine } from '@oxy.so/bloom/icons';

const control = useDialogControl();

<Button onPress={() => control.open()}>Settings</Button>
<SettingsModal
  control={control}
  groups={[
    {
      label: 'Settings',
      items: [
        { key: 'general', label: 'General', icon: RiSettings6Line, page: 'general' },
        { key: 'profile', label: 'Profile', icon: RiSchoolLine, page: 'profile' },
        { key: 'billing', label: 'Billing', icon: RiBankCardLine, onPress: openBillingPortal },
      ],
    },
  ]}
  pages={{
    general: { title: 'General', content: <GeneralSettings /> },
    profile: {
      title: 'Profile',
      content: (
        <SettingsProfilePage
          sections={[
            {
              key: 'identity',
              rows: [
                {
                  key: 'first',
                  label: 'First name',
                  control: <SettingsTextField label="First name" value={user.first} onCommit={saveFirst} />,
                },
              ],
            },
          ]}
        />
      ),
    },
  }}
/>
```

## Driving it

Drive it like `Dialog`: **`control` from `useDialogControl()`** is the preferred path (`control.open()` / `control.close()`), and `open` + `onClose` is the controlled alternative (in controlled mode `onClose` is a close *request* — backdrop, close button, Escape, Android back — and you flip `open`). On compact screens, `initialView="page"` opens the selected page directly (useful for deep links); the default `"navigation"` opens the section list. Back returns to the list in either case. The choice resets on each open and leaves desktop navigation unchanged. The page shown on every open is `defaultPage` (or the first rail row with a `page`); `page` + `onPageChange` control it.

Rail rows with a `page` navigate; rows without one call their `onPress` (or are static). The Storage page sets `compactTitle` — its page already reserves headroom for the upload badge, so the content's gap below the shared header drops from 12 to 6.

## Responsive layout

The modal's base size is a fixed 871×614 panel. Bloom adapts it to the window width (`useSettingsLayout()` exposes the current one to pages):

| Layout | Window | What changes |
|---|---|---|
| `regular` | ≥ 900px | The base panel: 274px rail, 32px insets, radius 24. |
| `medium` | 640–899px | Same panel inside a 16px gutter; rail 220px, insets 24px. |
| `compact` | < 640px | Full screen (no radius or gutter, content inside the safe area). Two levels: the section list with chevrons, then the page pushed over it with the shared `PageHeader` back island. Android's back button returns to the list before it closes. The panel rises 16px instead of scaling from .85. |

In `compact`, `SettingsRow` lets its control wrap under the label when both do not fit (a switch stays beside it, a `SettingsValueField` drops below and fills the row), and the Storage table keeps the file name and actions while the date and size columns drop and its toolbar wraps. `labels.back` names the back button (default `Back`). Every default string — the modal's `labels`, the Storage and Tools pages' copy, the plan chip — is localised via `BloomProvider locale`, and `SettingsDateField` formats its date in that locale.

## Shared header

Every layout uses `PageHeader` as the opaque `bar` presentation (the floating islands and gradient scrim let scrolling content ghost through), painted in the modal's published surface fill with its hairline once scrolled. A `ButtonGroupItem` supplies the close action; compact pages use its native back action to return to sections. The modal owns safe-area padding once, so the header uses `safeArea={false}`. Each page uses `Screen scroll="auto" documentScroll={false}` with an isolated navigation scope, a `PageHeader` in its header slot and `ScreenScrollView` for its body. The viewport fills the entire panel and Bloom's shared scrollbar observes that owner. Screen reserves header clearance once and the header reads this viewport's offset to update its material; neither follows the document underneath. Compact section navigation uses the same Screen composition. Changing pages resets the page viewport. Only the page body owns content padding. See [Compose application layouts](/docs/bloom/main/compose-layouts) for the shared contract.

Pages with `fullBleed: true` own their scrolling and insets. A `content` render callback receives `{ onBack, backLabel, onClose, closeLabel }` and owns its header too: `onBack` returns to sections on compact screens and is absent beside the desktop rail. Render that action in the page’s existing header to avoid a second title. A full-bleed page with static React content keeps the compact shell’s back header. The default page layout continues to use its shared `PageHeader`.

## Why it is not a `Dialog`

This shell differs from `Dialog`'s centered card in every load-bearing way: black 70% backdrop with no blur, 24px radius on `background/full`, a fixed 871×614 size, a fade + scale-from-0.85 + 4px blur on `cubic-bezier(0.32, 0.72, 0, 1)`, and a **Saved toast that straddles the panel's bottom edge** — outside the panel's clip, which `Dialog`'s card owns. So the shell is built from the same authorities `Dialog` uses — `Portal`, `OverlayRoot` (the one stacking rank) and `Backdrop` (the pointer-events contract) — and accepts `Dialog`'s `control`.

Menus, selects, tooltips and the date popover opened inside a page stack above it through the overlay stack. **Escape closes the innermost surface first:** shared `ModalKeyboard` checks overlay and floating-surface ownership before claiming the key. Its capture/deferred handling also hears Escape from React Native Web text fields. Focus moves into the panel on open, Tab remains inside, and closing restores the opener.

## The saved toast

`useSettingsSavedToast()` returns the enclosing modal's trigger (a no-op outside one). `SettingsTextField` and `SettingsDateField` call it when a changed value commits (`showSavedToast={false}` opts out); a custom control calls it itself. It rises 12px in, holds 2s and drifts 10px up as it fades.

## Rows

| Export | Geometry |
| --- | --- |
| `SettingsCard` | background/secondary, radius 16, **pl 12** |
| `SettingsRow` | min-height 52, py 10 pr 10, gap 16, 1px separator under every row **except the last** |
| `SettingsSection` | label body-2-medium (inset 12, or 8 on Tools), optional description and trailing action, 8 above the card |
| `SettingsSectionLabel` | body-2-medium text/secondary |
| `SettingsValueField` | 32×202, radius 10, background/tertiary |
| `SettingsTextField` | small `TextField`, 202 wide, commits on submit/blur only when changed |
| `SettingsDateField` | 32×202 bordered trigger (pill) opening `Calendar` in a `Popover` |

**The hairline stops 12px short of the card's left edge** because the padding lives on the card, not the row — rows must be direct children of `SettingsCard` (fragments are flattened). "Last" is derived from the card's children, since React Native has no `:last-child`.

## Entries

Metro does not tree-shake barrel exports, and a web bundler splitting lazy
chunks hoists any module two lazy chunks share into the common chunk that loads
at first paint. So importing one name from `@oxy.so/bloom/settings-modal` links
everything that barrel reaches. Import from the narrowest entry that has what
you draw:

| Entry | Exports | Does not link |
| --- | --- | --- |
| `@oxy.so/bloom/settings-modal` | everything on this page | — |
| `@oxy.so/bloom/settings-modal/modal` | `SettingsModal`, `SettingsCard`, `SettingsRow`, `SettingsSection`, `SettingsSectionLabel`, `SettingsValueField`, `useSettingsSavedToast` and the modal/nav/page/row prop types | the General/Profile/Tools/Storage pages, `SettingsPlanCard`/`SettingsPlanArt`, the text/date fields — and through them `Select`, `FileUpload`, `Pagination`, `DropdownMenu`, `Checkbox`, `Chip`, `Tooltip`, `EmptyState`, `TextField`, `Popover` and the calendar |
| `@oxy.so/bloom/settings-modal/fields` | `SettingsTextField`, `SettingsDateField` and their prop types | the modal and every page |
| `@oxy.so/bloom/settings-modal/rows` | `SettingsCard`, `SettingsRow`, `SettingsSection`, `SettingsSectionLabel`, `SettingsValueField` and their prop types | the modal, every page and the fields |

Every entry hands out the same components (identical references) as the full one,
so mixing entries in one app is safe.

An app whose pages are its own rows of switches and values — the usual case —
draws the modal from `modal`, adding `fields` only if it uses the committing
fields:

```tsx
import {
  SettingsCard,
  SettingsModal,
  SettingsRow,
  SettingsSection,
} from '@oxy.so/bloom/settings-modal/modal';
import { SettingsTextField } from '@oxy.so/bloom/settings-modal/fields';
```

Measured in GoWay's web export (Bloom 6.2.1, before `modal` existed): its
lazily loaded settings modal, drawn from the full entry, reached `Select` through
the Storage page it never rendered. Another lazy chunk also uses `Select`, so the
bundler moved it into the first-paint common chunk: +4.7 KB gzip on every page
load.

A preference card on a screen or in a sheet, outside the dialog, imports `rows`:

```tsx
import { SettingsCard, SettingsRow } from '@oxy.so/bloom/settings-modal/rows';
```

Gate: `lean-entries.test.ts` walks each entry's static import graph, with
`.native` and `.web` forks resolved as each platform's bundler does, and fails if
`modal` or `fields` reaches a page or a page-only family; a control asserts the
full entry does reach them.

## Pages

- **`SettingsGeneralPage`** — `plan` (`SettingsPlanCard`) then `sections`. The plan card's artwork is `SettingsPlanArt`: on web, a WebGL "burning flag" shader over `artworkSource` (or Bloom's generated accent/success/warning discs), eased toward the pointer; native, reduced motion and a failed WebGL context get the static discs. A radial fade melts it into the card.
- **`SettingsProfilePage`** — cards of rows.
- **`SettingsToolsPage`** — scope pills (sliding thumb), the authentication switch, the scope's servers (`SettingsServerList`), Team servers (empty state when none) and plugin servers. Server tiles take a theme `tone`; the "…" menu's actions and callbacks are props.
- **`SettingsStoragePage`** — Bloom's `FileUpload` dropzone (`upload` props; `upload={false}` for a read-only store) over the file table: type/order selects, search, sortable columns, row selection, delete (rows collapse out before `onDeleteFile`), the "⋮" menu and pagination. Files that appear in `files` grow in from under the header.

## Colours

All surfaces come from the theme ramps (`button/shared`): background/secondary is neutral-100 (dark 900), secondary/hover neutral-200 (800), tertiary neutral-200 (800), separators neutral-200 (800), background/full the card (dark neutral-925). The status dot and error text use `colors.error` through the danger table — not `negative`, whose dark value is M3's pale on-container pink and never reaches a saturated red.

## Known gaps

- Bespoke file-type illustrations aren't included; the default is the Remix document / spreadsheet / video glyph. Pass `renderFileIcon` for artwork.
- The Storage search uses `TextField`'s own tertiary fill — `TextField` owns its shell paint.
- The panel's 4px blur during open/close is web-only; native fades and scales.

### Preventing unfinished work from being discarded

`onBeforeLeave(reason)` synchronously returns `false` to keep the current content mounted, with no exit animation. Reasons are `close` (close action, backdrop, Escape, Android back from navigation, or `control.close()`), `navigation` (compact back to sections, including Android back), and `page` (selecting a different page). It runs once per intention with the latest callback; selecting the same page does not invoke it. An imperative close callback runs only if the close was accepted.

Use the imperative control for guarded flows. External changes to controlled `open` or `page`, and parent unmounts, remain the caller's authority and are not vetoed. Preserve the application's router leave guard as well when navigation can unmount the modal. The guard should read the application's completion state; the modal never stores recovery phrases or other sensitive content.

The modal uses the shared Surface gradient and rim over its existing full backing. It publishes that backing to nested controls through the surface context and web CSS variable; the navigation rail publishes its own secondary backing. Neither replaces the modal’s layout, scrolling or overlay behavior.

A `SettingsPageSection` can provide `emptyState: EmptyStateProps`. General and Profile
pages render that EmptyState inside the section card only when `rows` is empty,
retaining the section heading, description and action. The compact variant is the
default; the section can override it and supply its own illustration and actions.

# BloomProvider

Mount one `BloomProvider` above every render branch, including loading UI. It
composes theme, image resolution, haptics and scroll storage without importing a
router. It is exported from both `@oxy.so/bloom` and `@oxy.so/bloom/provider`.
Without `scrollAdapter`, automatic route restoration is inactive.

```tsx
import { BloomProvider } from '@oxy.so/bloom/provider';
import { expoRouterScrollAdapter } from '@oxy.so/bloom/scroll/expo-router';

<BloomProvider scrollAdapter={expoRouterScrollAdapter}>
  <App />
</BloomProvider>
```

Pass `locale` to set the language every Bloom component below speaks — dates,
month names and Bloom's own strings (Cancel, Apply, …). Unset, components follow
the runtime's locale; a component's own `locale` prop still wins. See
[Locale](/docs/locale).

```tsx
<BloomProvider scrollAdapter={expoRouterScrollAdapter} locale={i18n.language}>
  <App />
</BloomProvider>
```

Server-rendered apps can opt into compositor CSS in the initial HTML with
`ssrStyles="inline"` when their Content Security Policy permits inline styles,
or `ssrStyles={{ nonce: requestNonce }}` when the stylesheet nonce is authorized.
Pass the same policy and nonce during hydration. Without this option, Bloom emits
no inline server stylesheet and retains its readable compact server fallback.
The client always adopts the current sheet before removing the server element,
so later descriptor changes cannot compete with stale server rules. This option
covers AppShell and embedded AppShellPanels; it does not replace the host's
React Native Web CSS extraction or authorize its separate inline style attributes.
A nonce on the stylesheet alone does not authorize those attributes under CSP.

```tsx
<BloomProvider ssrStyles="inline">
  <AppShell panelLayout={workspace} />
</BloomProvider>
```

For a themed first paint, share one `BloomThemeBootstrapConfig` between
`BloomThemeHead` in the document head and `BloomProvider prepaintTheme`. The head
publishes light and dark palettes from Bloom's color engine, with a CSS system
preference fallback. Its small synchronous script reads `modeStorageKey` before
body content paints. That key holds a plain `light`, `dark`, `system` or
`adaptive` string; it is not Bloom's JSON persistence format. The app's existing
controlled `mode` must restore the same preference. No account data enters the
document bootstrap.

```tsx
import { BloomThemeHead, type BloomThemeBootstrapConfig } from '@oxy.so/bloom/theme';

const themeBoot: BloomThemeBootstrapConfig = {
  defaultMode: 'system',
  modeStorageKey: 'app_theme_preference',
};

// In the document <head>, before body content:
<BloomThemeHead config={themeBoot} nonce={requestNonce} />

// In the app, using its current persisted preference:
<BloomProvider mode={themePreference} prepaintTheme={themeBoot} ssrStyles="inline">
  <App />
</BloomProvider>
```

For a saved named color preset, add `persistKey: 'app.bloom.theme'` to that
same configuration and pass `storage={webLocalStorage}` to the provider on web
(an AsyncStorage-compatible adapter on native). The provider derives its key
from the shared configuration. This uses Bloom's existing JSON persistence;
`modeStorageKey`, when present and valid, still takes priority in the document,
so retain the matching controlled mode above. No separate preset cache or
app-specific bootstrap script is needed. Use `awaitHydration={false}` when
public app chrome must remain mounted while an asynchronous adapter resolves.

Preset prepaint emits the registered palette variants on the server, sharing
aliases only when their complete color vectors agree. Material recipes retain
the document preset independently of a forced local color or mode, so nested
surfaces compose against their actual parent. Hydration adopts each server
sheet verbatim before replacing it with the live palette; the browser does not
calculate every registered preset. Dynamic owned sheets are released normally.
Measure the exported HTML size and first paint when opting into this broader
palette coverage. A first visit without a saved preference necessarily uses
the configured default until the app supplies the account color.

Use both `prepaintTheme` and `ssrStyles` for shared component first paint: the head supplies semantic tokens, while `ssrStyles` authorizes the instance-specific surface and chrome recipes. Omitting the latter does not provide complete SSR paint.

The host must authorize both head resources through its CSP: pass an authorized
nonce, or hash the exact `css` and `script` returned by `getThemeBootstrap(config)`.
Static hosts can collect these hashes from their final export. A stylesheet
nonce does not authorize a script, and Bloom does not loosen the host policy.
With scripts disabled or storage unavailable, the configured default and OS
preference remain usable.

The provider first hydrates the same raw semantic palette as the server. It
leaves the head's chosen paint intact until the client preference is available,
then publishes the real palette. This prevents React from leaving mismatched
server inline colors unchanged. Semantic color math still receives RGB values;
opted-in web paint reads CSS variables. Use `useThemePaint()` for semantic colors assigned to final styles; keep `useTheme()` for numeric color calculations and behavior. Shared surfaces resolve both complete material recipes through the same color engine, then emit ordinary mode-selected CSS declarations before their content. Local forced color scopes retain their chosen mode, including when portaled. Native and providers without this option
retain their existing behavior. Keep bootstrap defaults consistent with the
root provider; later account color changes remain runtime updates.

Verify actual painted panel pixels from the first frame through hydration for
stored dark on a light OS, forced light on a dark OS, and system mode. Checking
only the root `dark` class or body background misses a light sidebar or list
whose server inline color survived hydration. Also assert node identity and
capture hydration errors; a correct final palette alone does not prove a
continuous transition.

Keep the adapter reference stable. Vite and other router integrations supply their
own `ScrollRouterAdapter`; Expo consumers now pass the adapter explicitly instead
of receiving an implicit router dependency.

`BloomProvider` also mounts `AgentAvatarProvider`: no UI, nothing fetched until a bot's character is
drawn, so `Avatar account={bot}` works anywhere below it. `characterRuntimeUrl` replaces the
hosted runtime for an app that self-hosts it; `storage` (the theme's adapter) persists drawn
stills. See [Avatar](/docs/avatar).

Visual hosts (`ToastOutlet`, `SurfaceHost`, portal/dialog outlets) stay outside the
provider: their position determines stacking, and mounting duplicate outlets draws
duplicate surfaces. `Screen` scopes coordinated geometry and motion locally.

The original depth hazards remain: `useScrollRestoration()` throws outside its
provider, and legacy `useMinimizeState()` creates a private fallback without its
provider. Mounting providers beneath a sibling scroll region recreates those
failures. New screen chrome uses the local `Screen` shared values, rather than
sharing one global motion state across retained routes. `useTheme()` also throws
outside its provider, including an early-return splash branch on cold start.

`PortalProvider`/`PortalOutlet` are native infrastructure; the web portal uses its
own DOM implementation. Choose outlet placement deliberately and mount each once.

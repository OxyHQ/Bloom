# Swipe Row

`SwipeRow` is the drag behind a row. It is the library's ONE implementation of
that gesture: `chat-list` and `mail-list` both compose it, and a third family
that wants actions behind a row composes it too rather than writing a fourth
pan handler.

```tsx
import { SwipeRow, useSwipeAvailable } from '@oxy.so/bloom';

<SwipeRow
  actions={{
    left: [{ key: 'archive', label: 'Archive', icon: RiArchiveLine, tone: 'accent' }],
    right: [
      { key: 'snooze', label: 'Snooze', icon: RiTimeLine },
      { key: 'delete', label: 'Delete', icon: RiDeleteBinLine, tone: 'negative' },
    ],
  }}
  onAction={(key) => run(key)}
>
  <MyRow />
</SwipeRow>;
```

## The sides name the EDGE, not the finger

`left` is uncovered by dragging RIGHT, because the pane is anchored to the left
edge and grows from it. `right` is uncovered by dragging left. Every mail and
messaging convention is written that way round, and naming the panes after the
direction of travel instead would make `left` the one on the right.

## The geometry, and why each number is where it is

| | |
| --- | --- |
| pane width | 76 per action (`actionWidth`) |
| commits at | 40% of the pane's full width |
| tap slop | 10 |
| snap | 160ms, dropped under reduced motion |
| activation | 12 horizontal; FAILS past 12 vertical |

The row travels with the finger, clamped to the pane's full width, and snaps to
whichever end is nearer once the commit fraction is crossed — so a half-hearted
drag never leaves a row stuck ajar. Under the tap slop the whole thing is a tap
and the row springs straight back.

Activation decides which drags become a SWIPE: the pan claims the touch only
past 12px of HORIZONTAL travel and fails outright past 12px of vertical, so a
vertical drag that wanders sideways never opens a pane.

## Touch-action: what actually keeps the list scrollable on web

Activation is not what lets a touch browser scroll the list. On web,
react-native-gesture-handler writes an inline `touch-action` on the detector's
view, and its default is `none` — "never pan from this element". Rows tile the
whole list, so with that default the list could be swiped but not scrolled by
touch at all, wherever the finger landed. `failOffsetY` cannot help: it is a
JavaScript decision, and the browser decided whether it may scroll before any
JavaScript ran. A `touch-pan-y` class on the row cannot help either, because
the inline style wins.

So the detector passes `touchAction="pan-y"`:

- **Vertical** panning is the browser's. When it starts scrolling it cancels
  the pointer, and the pan with it, so a scroll never leaves a row half-open.
- **Horizontal** movement is not something the browser may take, so its
  pointer moves keep reaching the pan, which activates past 12px as above.

The rule for every gesture in the library, not just this one: a detector that
sits inside something that scrolls vertically and only wants HORIZONTAL travel
passes `touchAction="pan-y"`; `none` is only for elements that are not scroll
content (an overlay, a fixed bar) or whose gesture genuinely needs both axes (a
2-D drag, a pinch). Native ignores the prop. Each detector's decision, with its
reason, is pinned by `gesture-detector-touch-action-census.test.ts`, and
`scripts/verify-swipe-row.mjs` reads the computed `touch-action` off the row
and scrolls the list with a real touch gesture that starts on a row.

The panes are laid UNDER the row and grow with it. The row is what moves; the
action underneath is revealed, not pushed in from outside. Each button keeps its
full width the whole time and is CLIPPED by the growing pane, so the label never
squashes as the row travels.

## Colour

Pass nothing and the panes come from the theme: `negative` and `accent` are the
SOLID pairs a filled button uses, `neutral` is the subtle default pair — the one
fill that reads as a surface behind the row rather than as a second control.
Nothing is derived, appended or eyeballed.

A family that already resolved its own palette passes `paint` instead, so its
panes match the rest of its rows exactly. That is what `chat-list` does.

## Who gets the gesture

### Elastic action capsules

`actionPresentation="bubbles"` replaces the touching rectangular panes with
separate rounded capsules. Their widths follow the revealed space, compressing
together as the row closes and settling with a spring. Reduced motion removes
the spring. The existing `panes` presentation remains the default.

An optional `fullSwipeAction={{ right: 'archive' }}` chooses an action **by key**
for a complete swipe on that side. Only the bubbles presentation uses it. The
chosen capsule expands while its neighbours shrink; the action runs on release,
after the completion animation. Moving back before release cancels that intent.
There is no built-in undo state. Without an explicit key the gesture only reveals
buttons, and a missing key or a row too narrow for the extra travel also falls
back to reveal-only.

Full swipe requires the greater of 72% of the measured row width or the resting
action width plus 48px. This keeps revealing two actions distinct from executing
one. Cancelling a gesture or unmounting during completion does not execute it.
The same menu/keyboard alternative remains required.

The Unified Lists Storybook demo opts into this presentation for review.
`CHROME_PATH=<chrome> node scripts/verify-swipe-bubbles.mjs` checks actual capsule
growth, compression, reversal, release-only action dispatch and prevention of
an accidental row click in the browser. Explicit Reanimated mapper dependencies
must include the shared travel and row-width values on web: depending only on a
helper callback leaves the capsules frozen even while the row itself moves.

```tsx
<SwipeRow
  actionPresentation="bubbles"
  actionWidth={56}
  fullSwipeAction={{ right: 'archive' }}
  actions={{ right: [
    { key: 'pin', label: 'Pin', icon: RiPushpinLine },
    { key: 'archive', label: 'Archive', icon: RiArchiveLine, tone: 'accent' },
  ] }}
  onAction={runAction}
>
  <MyRow />
</SwipeRow>
```

## Pointer availability

`useSwipeAvailable()` — every touch pointer, on any platform:

```tsx
const swipe = useSwipeAvailable();
return swipe ? <SwipeRow …>{row}</SwipeRow> : row;
```

It is the POINTER, not the platform. A web build runs on a phone as readily as
on a desktop, so the question `(pointer: coarse)` answers is the right one, and
it is a hook rather than a constant because the answer changes without a reload
— a tablet with a keyboard folio attached and detached is the same document.
Where there is no `matchMedia` at all (SSR, a test renderer, an old browser) it
answers no, and the calling family's pointer affordance is what shows.

## A SWIPE IS NOT REACHABLE BY KEYBOARD OR BY A SCREEN READER

This is the part that is easy to ship without. A drag has no tab stop, no role
and no announced name; a reader who cannot perform the gesture cannot archive
the message, and nothing on the screen says an action exists.

`SwipeRow` does the one thing it can do from inside: while a pane is CLOSED it
is hidden from assistive technology entirely (`aria-hidden` plus
`importantForAccessibility`), rather than leaving 0-wide invisible buttons in
the tab order for the focus ring to disappear into. Opening a pane reveals it.

**The second path is the caller's, and it is not optional.** The two families
here answer it like this:

- **A pointer** gets the actions as real buttons: `chat-list`'s hover rail and
  `mail-list`'s `actions` rail. Both appear on `:focus-within` as well as on
  hover, so they are in the tab order and a keyboard reaches them.
- **A touch reader** gets `accessibilityActions` on the row itself — the rotor
  path, which is the platform's own answer to "this control has actions I cannot
  gesture for". `MailRow` passes every rail and pane action through it, once per
  key. `chat-list` does NOT, today: on native its swipe actions are reachable by
  the gesture alone, which is a gap recorded rather than a decision.

Do not invent a third affordance for this. A row that already has a menu should
put the same actions in it.

## What it does not do

- **It does not decide WHETHER to swipe.** The caller asks
  `useSwipeAvailable()` (or is told by a prop) and renders the row bare
  otherwise — which is what keeps a mouse from getting a gesture it cannot
  discover.
- **It paints exactly one colour.** Its children are the row, whole; it adds
  the panes, the clip, the transform — and an opaque `background` under the
  travelling layer, because the panes are BEHIND the row and a transparent row
  lets the delete pane read through its own subject line. It defaults to the
  ambient surface (`useSurfaceFill()`), so a row inside a panel or card is that
  panel's colour without being told. Defaulting to the page colour made every
  chat row on a phone's `card` panel look selected.
- **It does not size the row.** Pass `height` for a fixed row and the container
  takes it exactly; omit it and the panes stretch to whatever the child turns
  out to be, which is what a row with a MINIMUM height needs.
- **It does not open programmatically.** There is no `open` prop: an app that
  opens a row nobody touched has drawn a menu, and a menu is a different
  component.


Horizontal `ScrollArea` descendants reserve their gestures through the shared scroll owner. Their native gesture blocks the enclosing row pan, including drags at the rail's edges. On touch web, the scroller path permits browser scrolling while the surrounding row content keeps vertical browser panning and horizontal row actions. Removing the scroller restores the default row touch policy. Applications do not need event propagation handlers or gesture offsets.

### Native gesture and animation regressions

Android testing of the published 22.0.1 package found that attachment buttons
inside ListItem did not fire, while the same Button in a standalone ChipRow did.
`Gesture.Native().shouldActivateOnStart(true)` claimed the touch on DOWN and
cancelled the child Pressable. The scroll gate now lets the native ScrollView
intercept actual travel, retaining `blocksExternalGesture` and
`disallowInterruption`. Do not restore forced activation to reserve the rail.
The SwipeRow test pins this configuration; the browser gate exercises real
attachment taps, scrolling and outward drags at both rail edges.

The same Android run exposed invisible swipe bubbles: the row moved, but bubble
width remained zero. Native mapper subscriptions do not traverse a captured
function's closure. Calling a geometry worklet that privately reads shared
values therefore missed drag updates, despite working on web with an explicit
dependency array. Geometry is a derived shared value read directly by both
animated styles. `SwipeRowBubbleNativeMapper.test.ts` runs the actual Reanimated
mapper registry with Babel-generated native closures, checks drag and layout
updates without a React render, and reproduces the old failure as a negative
control. This proves subscriptions, not native drawing.

For a native release check, install the exact published package in the Android
consumer: tap an attachment and check its callback runs once without opening
the row; drag the rail in both directions and outward at both edges without
opening row actions; scroll the page vertically; partially swipe the row body,
check the bubble is visible and accessible, tap it, then verify full-swipe
dispatch separately. Record package integrity and callback counts. Local
candidate packages must use a distinct prerelease version and do not replace
the final published-package check.

# PageFooter

Page-local actions float over a bounded scroller, above the app's bottom
navigation. The background uses the same surface color and gradient as
`PageHeader`, mirrored upward. Content continues behind the footer; the measured
clearance lets the last item scroll fully above its controls.

```tsx
import { AppShell } from '@oxy.so/bloom/app-shell';
import { Button } from '@oxy.so/bloom/button';
import { PageHeader } from '@oxy.so/bloom/page-header';
import { PageFooter } from '@oxy.so/bloom/page-footer';
import { Screen, ScreenScrollView } from '@oxy.so/bloom/screen';

function MessageScreen() {
  return (
    <Screen
      header={<PageHeader title="Message" />}
      bottomBarPlacement="overlay"
      bottomBar={<PageFooter actions={<Button onPress={reply}>Reply</Button>} />}
    >
      <ScreenScrollView><MessageBody /></ScreenScrollView>
    </Screen>
  );
}

export function MailApp() {
  return (
    <AppShell
      header={null}
      scroll="fixed"
      contentMaxWidth="none"
      panelLayout={{
        flow: 'bounded',
        panels: [{ id: 'message', span: 1, content: <MessageScreen /> }],
      }}
    />
  );
}
```

### Screen footer slot

Compose page controls in `Screen.bottomBar`. The application frame spans its
host; `span: 1` lets the primary panel fill the available track. Screen owns
placement and measures the footer's actual footprint, including safe-area
padding. Its scroll owner clears the content once. Do not add a fixed-height
preview box, manual bottom padding or a second `PageFooterProvider` around this
composition. App-wide navigation belongs in `AppShell.bottomBar`.

`contentContainerStyle` styles the controls row. Override padding with the
matching longhands (`paddingTop`, `paddingBottom`, `paddingLeft`, `paddingRight`);
`style` addresses the outer host. Shared controls inherit normal Bloom sizing.

The ordinary Page Footer stories use this full application composition. The
standalone document-anchor and custom input-geometry regression fixture lives
under **Labs / Layout / Page Footer Contracts**; it intentionally exercises the
lower-level API below, outside Screen's placement contract.

### Persistent panel footer

Use descriptor `bottomBar` for panel-wide content such as a sign-in prompt that
persists across routes. The first route Screen stacks it below its own bottomBar,
measures both and keeps them inside that panel’s width and framed bottom inset.
This works with document and bounded hosts. Do not add an outer Screen just to
hold this footer: nested Screens intentionally establish separate scroll owners.
AppShell’s application navigation bottomBar remains a separate occupied edge.

### Position outside Screen

For an existing host that cannot use Screen, `PageFooterProvider` adds no layout
and scopes `usePageFooterInset()` to one pane. The hook returns the measured row
height, safe-area padding and bottom offset. Use it instead of adding the
navigation inset again; when the footer is removed, use `useBottomEdgeInset()`
as the fallback if navigation still overlaps the content. The gradient tail does
not reserve layout. Independent panes need independent providers.

`bottomInset` defaults to Bloom's occupied bottom edge. Pass zero only when the
containing frame already ends above navigation; `safeArea={false}` applies when
that host already handles safe area. The Screen slot handles these contracts.


The default `position="absolute"` anchors this page chrome inside a bounded parent.
Place it beside the scroller, never inside its scrolling content.

For web pages that scroll the document, use `position="document"`. Bloom pins
its controls to the viewport bottom while an invisible, zero-height anchor
tracks the actual content column. Sidebar widths, responsive layout and RTL
remain owned by the page layout; consumers need no fixed styles or measured
coordinates. Mount it in the column, outside transformed/animated containers
(which establish a different fixed-position containing block). Resize observers
follow its ancestor frames, and horizontal scrolling updates the viewport
coordinate without rendering again for unchanged bounds. Native keeps the
existing absolute positioning within its bounded screen.

`position="inline"` keeps the footer in normal flow. `position="sticky"` also reserves its natural height, while pinning to the scroll container's bottom on web above the occupied bottom edge. Native sticky falls back to inline. Render these footers after the scroller; their in-flow footprint needs no extra scroll padding and publishes no `usePageFooterInset()` claim. Native safe-area defaults still apply. `WizardFooter` uses these positions while retaining its workflow controls.

Absolute and document positions publish the same measured `usePageFooterInset()` clearance.
Wrap the page and footer in `PageFooterProvider` and use that value as bottom
padding, instead of a guessed spacer. A purchase
summary with price and booking controls belongs to `ActionBar`, which has a
different opaque, in-flow layout contract.

### Follow the bottom edge of the content

Set `scrim="auto"` inside `ScrollMetricsProvider`, with a sibling `ScrollArea`
(or a list bound with `useScrollMetricsBinding`). The gradient is absent at the
bottom, for non-scrollable content, and before measurements arrive. It fades
in over `scrollThreshold` (default 20px) of remaining content. The actions stay
visible and their measured clearance does not change. Without a metrics owner,
`auto` remains hidden; the existing default `always` is unchanged.

Use `PageHeader scrim="auto"` in the same provider for matching behavior at the
top. Both keep their existing `scrimColor` override independently of scroll
visibility; neither paints a backing behind the gradient.

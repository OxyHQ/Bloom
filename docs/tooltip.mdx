# Tooltip

A short hint attached to a control.

```tsx
import { Tooltip, TooltipTrigger, TooltipTextBubble } from '@oxyhq/bloom/tooltip';

const [visible, setVisible] = useState(false);

<Tooltip visible={visible} onVisibleChange={setVisible} position="top">
  <TooltipTrigger>
    <Pressable
      onHoverIn={() => setVisible(true)}
      onHoverOut={() => setVisible(false)}
      onPress={copy}
      accessibilityLabel="Copy link"
    >
      <LinkIcon />
    </Pressable>
  </TooltipTrigger>
  <TooltipTextBubble>Copies the link to your clipboard</TooltipTextBubble>
</Tooltip>
```

## Look

The light-surface tooltip (`components/base/tooltip`), coloured from the theme (`floating/menu-palette.ts`):

| | `sm` (default) | `md` |
| --- | --- | --- |
| padding | 10 / 6 | 12 / 8 |
| corner | 8px | 10px |
| text | 12/16 medium, +0.15px | 14/20 medium |

A card-coloured bubble with the `neutral-200` hairline and `shadow-dropdown`, `text-primary`, hugging its text up to 240px, 10px from the trigger with a 12×7 caret pointing at it (filled with the surface, stroked with the hairline, joined to the bubble's border). On web it enters and leaves on a 200ms `ease-out` fade + `scale-90` + 4px blur and ignores the pointer. Dark mode takes `neutral-800` and `neutral-700`.

```tsx
<TooltipTextBubble size="md">Copies the link to your clipboard</TooltipTextBubble>
```

`size` is on `TooltipTextBubble` and `TooltipContent`; a `TooltipContent` with your own children sizes the surface only, so style your text to match.

The web bubble is portaled (`OverlayRoot`) and `position: fixed` against the TRIGGER's measured box, centred on it and nudged inside an 8px viewport gutter (the caret keeps pointing at the trigger). It follows the trigger every frame while mounted, because a web font swapping in reflows the page without any scroll or resize — measured once, bubbles drifted 2–15px off their triggers after Inter loaded. It used to be `position: absolute` in the tree, which on react-native-web (every `View` is `position: relative`) anchored it to whatever box contained the `Tooltip`. The bubble centres on `TooltipTrigger`'s box, so in a stretching column wrap the trigger in a box that hugs it.

**No dismiss layer on web.** An outside press closes the tooltip through a capture-phase document `pointerdown` listener (presses on the trigger are left to the trigger). It used to be a full-screen pressable over the page — which covered the trigger itself, so a hover-opened tooltip got an immediate hover-out and closed within a frame, and the next click landed on the layer instead of the control.

Text uses the type ramp: `TYPE_SCALE['caption-1-medium']` (`sm`) and `['body-medium']` (`md`), in Inter.

## Why it is controlled

What should open a tooltip differs by platform and by trigger — hover for a
desktop pointer, long-press on touch, focus for a keyboard — and the right
answer depends on what the trigger already does with a press. `Tooltip` takes
`visible` and leaves that decision at the call site rather than guessing.

`TooltipTextBubble` renders its own content surface, so it is a **sibling** of
the trigger inside `Tooltip`, not something you wrap in a `TooltipContent`.

## A tooltip is never the only place the information appears

It cannot be reached by touch without an interaction that also does something
else, and it dismisses on the next tap. So:

- The control still needs its own `accessibilityLabel`. A tooltip is a hint
  about a labelled control, not a substitute for the label.
- Nothing required to complete a task goes in one. If the user must know it,
  put it on the page.

## `position` is a preference

A bubble near a screen edge is nudged back into view, so `position="top"` on an
element at the top of the viewport still renders somewhere readable rather than
off screen.

## Two platform notes

The **web** tooltip is not portaled and takes no rank in the overlay stack; the
**native** one is portaled and does. So on native it participates in overlay
ordering and on web it does not — check for a `Portal` before reasoning about
what paints above what.

**Known gap on native:** `TooltipTrigger` measures in page coordinates while
the content renders into the root portal group, so a tooltip inside a
`BottomSheet` portals *outside* that window and lands in the wrong place.
Fixing it needs a real device — jest cannot see a native window boundary.

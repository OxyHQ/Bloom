# UserHoverCard

The card that appears when you hover a name or an avatar: photo, display name,
handle, bio, a couple of stats, one action — and a `footer` slot for whatever
your app knows about a person that Bloom does not.

```tsx
import { UserHoverCard } from '@oxy.so/bloom/user-hover-card';
import { FollowButton } from '@oxy.so/services';

<UserHoverCard
  avatar={user.avatar}
  displayName={user.name.displayName ?? user.username}
  username={user.username}
  bio={user.bio}
  stats={[
    { label: 'Following', value: formatCount(user.following) },
    { label: 'Followers', value: formatCount(user.followers) },
  ]}
  verified={user.verified}
  action={<FollowButton userId={user.id} />}
  onPressProfile={() => router.push(`/@${user.username}`)}
/>
```

## Showing it

`UserHoverCard` draws the person and nothing else — it does not decide **when**
or **where** it appears. That is [`HoverCard`](/docs/bloom/main/hover-card)'s
job: hover or keyboard focus on web, long press on native, anchored to the
trigger and kept open while the pointer travels onto it.

```tsx
import { HoverCard, HoverCardContent, HoverCardTrigger } from '@oxy.so/bloom/hover-card';

<HoverCard>
  <HoverCardTrigger asChild>
    <Link href={`/@${user.username}`}>@{user.username}</Link>
  </HoverCardTrigger>
  <HoverCardContent label={user.name.displayName}>
    <UserHoverCard displayName={user.name.displayName} username={user.username} />
  </HoverCardContent>
</HoverCard>
```

Inside `HoverCardContent` the card draws no surface of its own — the panel's
border, background, shadow and inset are the card's, and the entrance plays
once. Rendered anywhere else it wears the same surface itself.

## `footer` is where your own content goes

The card renders what every Oxy app agrees a person is — photo, name, handle,
bio, a couple of counts — and nothing else. Anything past that is yours:

```tsx
<UserHoverCard
  displayName={user.name.displayName ?? user.username}
  username={user.username}
  bio={user.bio}
  stats={stats}
  action={<FollowButton userId={user.id} />}
  footer={
    <View style={{ gap: 4 }}>
      <Text>Activity</Text>
      <ActivityHeatmap data={activity} endDate={today} numDays={119} cellSize={11} gap={3} />
    </View>
  }
/>
```

It renders **after** the stats, spanning the full inner width, with the same
vertical rhythm the bio and stats use. Bloom adds no label, no divider and no
clip — the block is yours to shape.

It is a **sibling** of the identity area, never a child, and that is the part
worth knowing. Nested, every press on your content would also fire
`onPressProfile`, and on web the block would sit inside a real `<button>`, where
interactive content is invalid HTML.

## `badge` sits beside the handle

The second slot, for the quiet marker that says what KIND of account this is —
a channel, an account on another server:

```tsx
<UserHoverCard
  displayName={user.name.displayName ?? user.username}
  username={user.username}
  badge={<AccountBadge kind={user.kind} isFederated={user.isFederated} />}
/>
```

It renders after `@handle` in the same row, and it renders even when there is no
`username`, because it describes the account rather than the handle. A long
handle truncates to make room; the marker never shrinks.

Unlike `footer`, this slot is **inside** the identity area — that is where it has
to be to sit beside the handle. Two things follow, both measured rather than
assumed:

- **Your marker's press stays yours.** react-native-web implements React
  Native's responder system, so a pressable badge fires its own handler and not
  `onPressProfile`, on both platforms. No `stopPropagation` is needed. (If you
  have seen that call in an app's own hover card, it is guarding a different
  ancestor — a raw `onPointerUp` on a plain `View`, which does receive the
  bubbled event.)
- **Prefer an inert marker anyway.** With `onPressProfile` set the identity area
  is a real `<button>`, so a pressable badge nests a button inside a button:
  invalid HTML, which Chrome tolerates and other user agents need not. A marker
  is usually a statement, not a control.

The card's accessible name is unaffected either way. The identity area carries
an explicit label, and an explicit label wins over contents in the ARIA name
computation — checked against Chrome's accessibility tree with a badge nested
inside the button, whose name came back as exactly its label.

## How wide your content can be

```tsx
import { USER_HOVER_CARD_CONTENT_WIDTH } from '@oxy.so/bloom/user-hover-card';
```

**256px**, and it is exported so you can size against it rather than discover it.
The card is `USER_HOVER_CARD_WIDTH` (286) with `USER_HOVER_CARD_INSET` (15) on
each side; the content width is the decided number and the card's width is
derived from it. The card does **not** clip, so anything wider paints outside the
border rather than being cut off — louder than a silent truncation, still wrong.

That inversion is recent, and the reason is worth stating: the width was an
unexplained `280` from the day the family shipped, and the 248px that fell out of
it missed the first real slot content by **one pixel**. A contribution graph of
119 days is eighteen columns once the leading partial week is counted, which at
`cellSize={11} gap={3}` is 249px. 256 clears it with room and sits on the 8px grid
the spacing scale follows.

There are two named slots, not three. The positions a third consumer might want —
above the bio, beside the action — are still free to be added as their own named
slots; a `children` prop would have claimed the generic name for one arbitrary
position.

### Inside a hover card, everything you put here stays pressable

`HoverCard` (and `AvatarGroup`'s `hoverCard`) keep the card open with a pointer
bridge that is deliberately not a `Pressable`, so the cursor can reach a button
in `action` or `footer` without the card closing. Why, measured:
[HoverCard](/docs/bloom/main/hover-card).

## Bloom holds no follow state

`action` is a slot, and that is the whole design. Following is session-aware,
optimistic, and shared across every Oxy app — it belongs to `@oxy.so/services`,
which owns the mutation and the cache. A follow button living in Bloom would
either duplicate that or force Bloom to depend on the SDK.

The same reasoning applies to `onPressProfile`: Bloom does not know your router.

## `avatar` goes to `source`, and this fails silently

Internally the value is handed to `Avatar`'s **`source`** prop, so a bare Oxy
file id resolves through the app's `ImageResolver`. If you build a card by hand
somewhere and pass a file id as `uri` instead, the image 404s and you get a
placeholder letter with no error anywhere. That is the single most common way
avatars break across the ecosystem.

## Display name fallback

`displayName` is optional upstream. Fall back to the normalized handle —
`displayName?.trim() || handle` — and never recompose a name from
`name.first` / `name.last`. A wrong display name is fixed in the serializer or
the SDK type, not in a frontend helper.

## Stats are strings

`value` is a string, not a number: formatting a count (`4.8K`, `1,204`) is
locale- and product-specific, and a component that formatted it for you would be
wrong in one app or the other.

## Chrome

This card is built from the vocabulary of Bloom's existing components, and
sits beside them as one family:

| Part | Recipe |
| --- | --- |
| Panel | The floating menu surface from `floating/menu-palette.ts` (the same one `DropdownMenu`, `Select` and the `Sidebar` account menu wear): radius 16, 1px `border/button/default` (neutral-200 / neutral-700), `background/primary` (card / neutral-800), `shadow-dropdown`. 286 wide (`USER_HOVER_CARD_WIDTH`), p15 — 256 of inner width. |
| Cover | Optional `cover`: full-bleed, 88 tall, clipped to the inner radius (15), `background/tertiary` under the image (neutral-200 / neutral-700). |
| Avatar | Bloom's ported `Avatar` at 48 (initials disc when there is no photo). Over a cover it wears a 3px ring of the panel colour and overlaps the cover's edge by half. |
| Action | Pinned top-right and centred on the avatar's visible band. Pass Bloom's `Button` (`size="small"`, `primary` to follow, `secondary` once following) or the SDK's FollowButton. |
| Name | `headline-medium`, `text-primary`, one line, + 16px `RiVerifiedBadgeFill` in accent-500. |
| Handle | `body-regular`, `text-secondary` (neutral-500), 2px under the name. |
| Bio | `body-regular`, `text-primary`, three lines. |
| Stats | Profile-card stat tiles: flex-1, radius 10, p10, `background/secondary` (neutral-100 / neutral-900), value `body-medium` over label `body-2-medium` `text-secondary`, 8 apart. |
| Rhythm | 12 between blocks. |

Colours come from the theme through `resolveButtonRamps(theme)`, in light and dark.

### `loading`

`loading` draws the skeleton in the same geometry — avatar disc, name and handle
bars, two bio lines, two stat tiles (and the cover band, if `cover` is set) — so
the card does not jump when the profile lands. The card reports itself busy
(`aria-busy` on web, `accessibilityState.busy` on native). `action` and `footer`
are not rendered while loading.

### `cover` resolves like `avatar`

A non-URL `cover` goes through the app's `ImageResolver` with `coverVariant`, the
same rule the avatar hazard above describes. `null`/`''` draws no cover band at
all, so an absent image never leaves an empty grey strip.

### Motion

On mount the card runs the floating-menu entrance — opacity 0 → 1, scale 0.95 →
1, and on web `blur(2px)` → none, 150ms Tailwind `ease-out`, growing from the top
edge — the constants `FloatingPanel`'s `menu` surface uses. There is no press
scale. Reduced motion skips it; `animateIn={false}` turns it off.

### Why the border is 1px, not the 0.5px hairline

The card used to compose `Card` with `BORDER_WIDTH.hairline` (0.5px). It now
draws a 1px `border`, the width every neighbouring panel uses. The
measured facts behind that choice still hold: in Chrome a 0.5px border is snapped
UP to one device pixel, so at `devicePixelRatio` 1 it paints 1px and is
indistinguishable from `thin`, while at `devicePixelRatio` 2 it paints 0.5px and
is visibly finer. `StyleSheet.hairlineWidth` is hardcoded to **1** on web, and on
native is 0.5 at @2x and ~0.333 at @3x. A hairline card beside 1px menus would
therefore match them on a 1× monitor and look lighter than them on every HiDPI
screen — the mismatch this card now avoids.

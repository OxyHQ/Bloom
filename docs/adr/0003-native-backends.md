# ADR 0003: Native backends for `.bloom`

- **Status:** draft (2026-11-28). A measured prototype for the owner's decision; nothing here is
  adopted. Spanish summary: [0003-resumen-es.md](0003-resumen-es.md).
- **Builds on:** [ADR 0001](0001-bloom-own-language.md) (the language) and
  [ADR 0002](0002-swift-grade-language-and-toolchain.md) (the 2.0 surface, the toolchain, phase F).
- **Question:** should `bloomc` compile `.bloom` straight to native code (SwiftUI on iOS, Kotlin +
  Jetpack Compose on Android), with no JavaScript in between, so Bloom is as fast as Swift or Rust?

## Context

Today `bloomc` emits TypeScript. Hermes runs it and React Native draws Bloom's views (Fabric).
ADR 0002 already measured the JavaScript side's ceiling:

- Static Hermes compiled the Notifications screen's own code no faster: under 10% of a tap is
  the module's code; the rest is React and the bridge to native views.
- `bloom build android` without Expo is at parity with the Expo path, and its cold start and
  storage are faster. It is still React Native: 17–18 MB of JavaScript bundle, Hermes, Fabric.

What remains on the table is the owner's option 3: the same checked program, emitted for the
platforms' own UI toolkits. The 2.0 surface is SwiftUI's (`struct X: View`, `@State`,
`VStack(spacing:)`, modifiers, `switch`, `async`), so the mapping is direct on iOS and close on
Android. This ADR measures it before anyone commits to it.

## The prototype

- **A backend, outside the main stack.** `crates/native` (`bloom_native`, binary
  `bloom-native`) depends on `bloom_lang` and on nothing of `bloomc`'s:
  - `bloom-native emit --target kotlin-compose <package> --android-project <dir>`;
  - it reads `Package.bloom` and `Sources/<Module>/*.bloom`;
  - it checks every file with `bloom_lang::check` (a file the main checker rejects is not
    emitted), and emits from the parsed 2.0 tree, before the TypeScript lowerings. Bloom's
    surface is SwiftUI's, so `Toggle`, `List`, `VStack(spacing:)` map to the platforms' views more
    directly than the language nodes they lower to for React Native;
  - the checker's types, by span, qualify what the tree leaves implicit (`.ready` is
    `LoadState.ready`, a `switch` subject's enum, `.count` on a list or a string);
  - anything outside the covered subset is a diagnostic naming the construct, so coverage is
    countable;
  - it writes the Gradle project: an app module, the emitted sources, the runtime, R8 on,
    `profileinstaller`, signed with the debug key.
- **The mapping** (`crates/native/src/kotlin.rs`):

  | Bloom | Kotlin + Compose |
  |---|---|
  | `struct Post: Identifiable, Equatable { let id: String; var likes: Int = 0 }` | `@Immutable data class Post(override val id: String, val likes: Int = 0) : Identifiable` |
  | `enum PrefKey { case likes … }` | `enum class PrefKey { likes, … }` |
  | `enum PostKind { case text; case image(url: String, aspect: Double) }` | `sealed interface PostKind { data object Text; data class Image(val url: String, val aspect: Double) }` |
  | `extension Prefs { func isOn(_ key: PrefKey) -> Bool; var age: String { … } }` | `fun Prefs.isOn(key: PrefKey): Boolean`, `val Post.age: String get() = …` |
  | `func handle(of name: String) async -> String` | `suspend fun handle(of: String): String` (labels are Kotlin's parameter names) |
  | `struct PostRow: View { let post: Post; var body … }` | `@Composable fun PostRow(post: Post, modifier: Modifier = Modifier)` |
  | `@State private var prefs = Prefs()` | `var prefs by remember { mutableStateOf(Prefs()) }` |
  | a view's `func save() async`, `func row() -> some View` | a local `suspend fun`, a local `@Composable fun` |
  | `.task { }`, `.onAppear { }`, `.onChange(of: v) { old, new in }` | `LaunchedEffect(Unit) { }`, `OnChange(v) { old, new -> }` |
  | `task { await save(k, on) }` | `scope.launch { save(k, on) }` over `rememberCoroutineScope()` |
  | `switch x { case .image(let url, _): … }` | `when (val s = x) { is PostKind.Image -> { val url = s.url; … } }` |
  | `try? await sleep(for: .milliseconds(300))` | `runCatching { sleep(Duration.milliseconds(300.0)) }.getOrNull()` |
  | `.padding(.horizontal, .lg).padding(.vertical, .sm)` | `Modifier.bloomPadding(Edge.vertical, Space.sm).bloomPadding(Edge.horizontal, Space.lg)`: Bloom wraps outward, Compose's chain runs inward, so the order is reversed |
  | `VirtualList(posts, { row in PostRow(post: row.item) })` | `VirtualList(posts) { row -> PostRow(row.item) }` over `LazyColumn` keyed by `id` |

- **A runtime, Compose Foundation only** (`crates/native/runtime/android/`, about 830 lines of Kotlin):
  BloomUI's tokens (space, corner, the type ramp, colour roles), stacks, `Text`, `Icon` (Bloom's
  own glyph paths, generated by `scripts/icons.py`), `Avatar`, `Image`, `Toggle`, `Button`,
  `GroupedSection`/`GroupedSectionItem`, `ActionBar`/`Action`, `VirtualList`, `ScrollView`, a tab
  `NavigationStack`, `OnChange`; and the standard library the screens call (`range`,
  `updating(where:)`, `Duration`, `ContinuousClock`, `sleep(for:)`, `print`, `Binding`). No
  Material, no image library: the image pipeline is ~120 lines (disk and memory caches, decoded
  at the drawn size, four decode threads).
- **The screens** (`examples/NativeBench`), one source for both builds:
  - **Settings → Notifications**, Mention's phase-0 screen (#2046) in 2.0 form: three grouped
    sections, seven toggles with descriptions, a button row, a simulated 300 ms save with a
    progress indicator.
  - **A feed of PostItem rows** (#2049) for text and image posts: avatar, name, verified badge,
    handle and age, text, a 4:3 picture, and the action bar (reply, repost, like, share, counts).
    500 rows of fixture data in a virtualized list, with an optimistic like.
- **iOS.** Not built. The Mac is not in hangar yet and there is no Swift toolchain on this
  machine; SwiftUI does not exist on Linux, so `swiftc -typecheck` would need a stub SwiftUI and
  would prove little. `--target swiftui` reports itself unbuilt. The mapping is the closest of
  the three: the surface is SwiftUI's (see "What the language needs").

### What it took

- **The emitter is small.** About 1,400 lines of Rust (`kotlin.rs`) cover the two screens: no change to the
  parser or checker, which already give a typed tree. The first Compose build compiled after
  four emitter fixes (argument labels for `_` parameters, a payload enum's bare case, the
  manifest comment, `compileSdk`).
- **The runtime is the work.** Most of the time went into the runtime's views and the image
  pipeline, not the emitter: each Bloom node is a component to write twice more (Compose,
  SwiftUI) with pixel parity against Bloom's React Native one.
- **Found on the way, in today's path:**
  - `VirtualList(posts, { post in … })` type-checks, but the TypeScript runtime hands the row
    FlashList's `{ item, index }`, so the row crashes on first draw (`post.author` of
    `undefined`). The checker should type the parameter as `VirtualListRow<T>`. The bench writes
    `{ row in PostRow(post: row.item) }`, which both backends read.
  - `Image(url).aspectRatio(r)` in a `.leading`-aligned `VStack` draws nothing on React Native:
    the stack's `alignItems: flex-start` leaves the image zero wide, so the aspect ratio gives
    zero height. `.frame(width: .full)` fixes it. Compose fills the width. This is likely the
    "blank images" seen with `BloomImageView` in the hybrid Mention build (lang-native-8's
    handoff): with the frame, `BloomImageView` draws in a Bloom build.
  - Mention's `.bloom` corpus is migration-mode: PostItem imports about 90 TypeScript modules
    (stores, hooks, i18n, routes). None of it can reach a native backend until those modules are
    Bloom.

## Method

- **Device:** Pixel 8a (Android 16, 1080×2400, 120 Hz; the device's own font scale and dark
  mode), through hangar (`hangar lock`/`hangar adb`). USB powered.
- **Builds:** both release, R8 on.
  - **React Native + Hermes:** `bloom build android --release` of `examples/NativeBench`, arm64,
    this branch's compiler and language, the Bloom pack with `BloomImageView` (#1027, #1034,
    #1036 and #1029). That is today's path: `.bloom` → TypeScript → Hermes bytecode → Fabric.
  - **Kotlin + Compose:** `bloom-native emit --target kotlin-compose` then Gradle; Compose 1.12.1,
    Kotlin 2.2.10, AGP 9.2.1.
- **The same bytes on both sides.** The feed's 28 pictures (picsum.photos, Unsplash licence) are
  inlined as `data:` URLs (`scripts/fixture_images.py --inline`), so no network is in the
  measurement; React Native decodes them with Fresco (through `BloomImageView`), Compose with the
  runtime's pipeline. Both decode at the drawn size.
- **Per run** (`packages/bloom-language-compiler/bench/native/`: `rn-build.sh`, `compose-build.sh`,
  `bench.sh`, `toggle.sh`, `sum.py`): after install, one warm-up launch,
  then `cmd package compile -m speed-profile -f` (what background dexopt does after install; it
  applies Compose's baseline profiles and React Native's observed profile alike). Then 5 runs:
  - **cold start:** `am force-stop`, then `am start -W`'s `TotalTime` (the first frame the
    window draws) and, from logcat, launch → `BENCH feed-shown` (the feed's `.onAppear`, after
    its first rows are committed);
  - **idle PSS** after launch;
  - **fast scroll:** `gfxinfo reset`, then 30 flings (`input swipe` 1,400 px in 60 ms, 250 ms
    apart) down the 500 rows (session 1: they reach row ~450; session 2: 40 flings, the end); `dumpsys gfxinfo` frames, janky % (frames that missed their
    deadline at 120 Hz) and frame-time percentiles;
  - **PSS after the 500 rows;**
  - **toggle latency:** the Settings tab, then 20 taps on the "Likes" switch, 1.2 s apart. The
    app logs, from the same `.onChange(of: prefs)` in the `.bloom` source, the time from the
    switch's handler to the committed update (React: the passive effect after the commit;
    Compose: the `SideEffect` after the composition is applied). gfxinfo over the taps.
- **Medians and p95** over the 5 runs (toggle: over the 100 taps).

SESSION2

Reading the numbers:

- **Startup.** Both draw their first frame at ~135 ms, but React Native's is the splash
  (`LaunchTheme`); the feed follows 180 ms later, after Hermes loads the 19 MB bundle and React
  commits. Compose's first frame *is* the feed.
- **Scrolling.** Both are smooth on a Pixel 8a, React Native included (FlashList, Fabric). Compose
  has a third of the frame time at p90 and a tenth of the missed deadlines. gfxinfo does not see
  React Native's blank cells during a fling (rows rendered late on the JS thread), so it favours
  React Native here.
- **Memory** is the largest gap: Hermes, the bundle, React's trees and Fabric's shadow tree cost
  ~200 MB before the first row, and the rows themselves cost ~2.5× more.
- **Interaction.** A toggle costs one frame on Compose (the update applies in the next frame);
  on React Native it crosses to the JS thread, renders, commits, and crosses back: ~5 frames.
  The measured span starts at the JS handler, so React Native's input-to-JS hop is not even in it.
- **Size.** React Native's floor is ~40 MB per ABI (React Native, Hermes, Reanimated, the
  bundle). Compose Foundation and the app are ~1 MB after R8.


## What the language needs for a native backend

The prototype emitted the subset two screens need. A complete backend needs these decisions,
most of which ADR 0002's surface already made the right way:

- **Memory model.** Bloom's `struct`s are values and its `class`es references (ADR 0002 §5).
  - Kotlin: a `data class` of `val`s is a value with structural `==` and `copy`; `var p = post;
    p.likes += 1` is `p = p.copy(likes = p.likes + 1)` (the prototype does the one-level case).
    The JVM's GC replaces Hermes's.
  - Swift: `struct` and `class` are Bloom's own semantics, copy-on-write collections included.
  - Today's JavaScript emit already treats structs as immutable objects, so no `.bloom` code
    relies on JS reference identity of a struct. That is what makes the native mapping sound.
- **Numbers and strings.** `Int` is a 53-bit-safe integer on Hermes and 32/64-bit on the
  platforms. The checker should pin `Int` to 64 bits (Kotlin `Long`, Swift `Int`), with
  overflow trapping, before any backend ships. Integer division already truncates (spec 4.3).
  `String` is UTF-16 on Hermes and the JVM and grapheme-based in Swift; `Character` and
  `count` must mean grapheme clusters everywhere (the standard library already defines them so).
- **Closures.** Kotlin lambdas and Swift closures map one to one. Compose's strong skipping
  memoises a lambda by what it captures, which replaces the TypeScript emitter's memo cache; a
  view's `static func ==` maps to Swift's `Equatable` view and, on Compose, to a stable wrapper
  (not built: strong skipping compared the prototype's rows correctly without it).
- **Async and actors.** `async`/`await` → Kotlin `suspend` and structured concurrency
  (`rememberCoroutineScope`, `LaunchedEffect`) → Swift's `async`/`Task`/`.task`. `actor` maps to
  Swift's `actor` and to a Kotlin class confined to a single-thread dispatcher (a `Mutex`
  where it must be reentrant). Cancellation is native on both; the prototype's image pipeline
  had to own its work so a cancelled row did not cancel a shared decode.
- **Errors.** `throws`/`try`/`do`-`catch` → Swift's own; Kotlin exceptions with a sealed
  `BloomError`. Typed throws (`throws(APIError)`) map to Swift 6's typed throws and, on Kotlin,
  to a checked wrapper the emitter enforces (Kotlin has no checked exceptions).
- **The standard library per platform.** Each `public` API of `stdlib/Bloom/*.bloom` needs a
  Kotlin and a Swift implementation (Foundation covers most of Swift's). The written-in-Bloom
  parts compile through the backend itself; only `extern` bindings need hand-written Kotlin and
  Swift. Today those bindings are TypeScript (`runtime.ts`, `router.ts`, `models.ts`).
- **Codable and HTTP.** `Codable` is derived at compile time (no reflection), so the backend
  emits the encoder and decoder directly: Kotlin over `org.json`/a streaming reader, Swift over
  `Codable` itself. `HTTPClient` → OkHttp (already in every React Native APK) or
  `HttpURLConnection`, and `URLSession`.
- **Stores.** `KeyValueStore`, `SecureStore` and `FileStore` are already Kotlin
  (`BloomStorage`, phase F); a native backend calls them directly, without the TurboModule
  bridge. `@Observable` models map to Compose snapshot state (`mutableStateOf` per field, which
  gives the field-level subscriptions ADR 0002 promises for free) and to Swift's `@Observable`.
- **Navigation.** The typed `Routable` enum maps to Navigation Compose's typed routes (or the
  runtime's own stack, as in the prototype) and to `NavigationStack(path:)`. Deep links come
  from `Package.bloom`, as today.
- **Images and video.** Coil 3 (Compose) or the platform's own pipeline (`AsyncImage` is not
  enough on iOS; Nuke or a small URLSession cache), and Media3 / AVPlayer, which phase F's
  `BloomVideo` already wraps on Android.
- **BloomUI itself.** Every Bloom node and modifier needs a Compose and a SwiftUI
  implementation with the design's pixel parity: about 90 node families and 200 modifiers in
  the spec. This is the largest item by far.

## Interop during a migration

- **A Compose island in React Native.** A Fabric native component that hosts a `ComposeView`
  is the same mechanism as `BloomImageView` (`extern native` views, phase F step 3): a `.bloom`
  screen compiled natively is one native view inside the React Native app. Props cross once;
  state lives in Compose. This is how a hot screen (the feed, a chat) could go native first.
- **React Native in a native app.** The reverse: a Compose/SwiftUI app hosting a
  `ReactRootView`/`RCTRootView` for the screens not yet ported. Mention's 157 route files would
  need the router to span both.
- **npm and TypeScript.** A native backend cannot call TypeScript. Every TS import of a `.bloom`
  file (90 in PostItem) must become Bloom, or an `extern native` binding with Kotlin and Swift
  sides. ADR 0002 §4's `extern module "npm-package"` bindings have no native meaning. In
  practice a module compiles natively only once its whole dependency closure is Bloom.
- **Over-the-air updates** (Oxy Updates, ADR 0002 §7) ship JavaScript. Natively compiled screens
  update only through the stores. That is a product decision as much as a technical one.

## The web

The web stays on the TypeScript backend: the same `.bloom` → TypeScript → React DOM path
as today. Wasm is not a UI target: React Native Web and the DOM are already native to the
browser, and ADR 0002 measured that a wasm decoder still pays for building JS objects. So a
native-backend Bloom is three backends (TypeScript for the web, Kotlin, Swift) behind one
checker, with the TypeScript one also kept for React Native during the migration.

| Phase | Scope | Estimate |
|---|---|---|
| N0 | This prototype: the Kotlin emitter for two screens, the runtime they need, the measurements | done (1 agent-day) |
| N1 | The Kotlin backend over the whole checked language: generics, protocols as interfaces, classes and `@Observable`, `Codable`, typed throws, `Int` as 64-bit; emit from a typed IR rather than spans | 6–8 |
| N2 | The Kotlin standard library (every `stdlib/Bloom` module) and `bloom build android --native` (Package.bloom → Gradle, signing, resources, icons, deep links) | 6–8 |
| N3 | BloomUI for Compose: every node family and modifier, pixel parity against the React Native Bloom, the parity harness on device | 12–16 |
| N4 | Interop: the Compose island as an `extern native` view, React Native hosted in a native app, the router across both | 4–6 |
| N5 | The SwiftUI backend, the Swift standard library and BloomUI for SwiftUI (N1–N3 again, smaller for the mapping, the same size for the views); needs the Mac lane | 16–24 |
| N6 | Mention module by module: each screen's TypeScript dependencies ported to Bloom first | open-ended; months |

Roughly 50–70 agent-weeks before an app could ship natively on both platforms, most of it
BloomUI twice. Android alone (N1–N4) is 28–38.

## Risks

- **Three UI implementations.** BloomUI exists once today (React Native, plus the web through
  RNW). A native backend means a Compose and a SwiftUI BloomUI kept in pixel parity with it and
  with each other: every component change lands three times.
- **The corpus is not native-ready.** The `.bloom` that Mention has is mostly migration-mode
  (TypeScript imports, bindings). The speed only arrives for code whose whole closure is Bloom.
- **No over-the-air updates** for native screens.
- **Semantic drift** between backends (number width, string indices, async ordering, effects'
  timing: React's effects run after the commit, Compose's after apply). One spec and one
  conformance suite run on all three backends are required.
- **Build times.** A Gradle release build of the bench is 40–55 s against Metro's seconds;
  iteration needs Compose's hot reload or Live Edit, which `bloom run` would have to drive.
- **iOS is unmeasured.** SwiftUI's `List` performance and memory with 500 rich rows, and
  SwiftUI's own quirks, are known risks the Mac lane must measure before N5.
- **Fairness of this bench.** The Compose runtime is a prototype (no Material, a minimal image
  pipeline), while the React Native side carries all of Bloom; a complete BloomUI for Compose
  will be larger and somewhat slower than the prototype's. The scroll numbers measure the UI
  thread and RenderThread, not React Native's blank cells during a fast fling, which gfxinfo
  does not see.

## Recommendation

**Hybrid, going native in two steps, Android first.** The measurements answer the speed question
clearly: on the same `.bloom` source, Kotlin + Compose reaches the screen 2.7× sooner, uses a
quarter of the memory, answers a toggle 6× sooner, scrolls with a third of the frame time at
p90, and ships in 1/33 of the APK. Nothing in the JavaScript path (Static Hermes, ADR 0002) comes
close, because the cost is React Native itself, not the module's code. So option 3 is worth
building. But its cost is mostly not the compiler: it is a second (and with iOS, a third)
BloomUI and standard library, and a corpus that is not yet pure Bloom. So:

1. **Go on the backend, as a target, not a rewrite.** Build N1–N3 for Android behind
   `bloom build android --native`, for modules whose dependency closure is pure Bloom. Keep the
   TypeScript backend as the default and for the web; the checker stays one.
2. **First ship native islands inside the React Native app** (N4): a natively compiled `.bloom`
   screen hosted as a Fabric view (the `BloomImageView` mechanism). Islands get the scroll and
   interaction gains for the hottest screens (the feed, Notifications) without leaving React
   Native. They do not get the startup, memory and size gains: those need step 3.
3. **Whole-app native when an app's module graph is pure Bloom.** That is where the 2.7×
   startup, ÷4 memory and ÷33 APK come from. Mention gets there only as phase D ports its
   TypeScript dependencies (stores, hooks, i18n, routes) to Bloom, which phase D wants anyway.
4. **iOS: measure before committing.** The Mac lane builds the same bench with SwiftUI (the
   mapping is the most direct) before N5 starts; on a go there, the iOS work mirrors N1–N3.
5. **Decide the language questions now**, since every backend depends on them: `Int` is 64-bit
   with trapping overflow, one conformance suite runs on every backend, effects' timing is
   specified (after the update is applied, before the next frame), and the checker types
   `VirtualList`'s row as `VirtualListRow<T>` (the crash above).
6. **Go/no-go checkpoint:** the Mention feed as a Compose island, at pixel parity with today's
   rows, measured on the Pixel 8a. If its scroll and interaction gains hold with a complete
   BloomUI (not this prototype's minimal one), continue to whole-app native; if they do not,
   stop at islands and keep React Native as Bloom's platform.

Not recommended: a big-bang native rewrite of Mention (no OTA, the corpus is not ready, three
BloomUIs at once), or dropping the TypeScript backend (the web needs it).

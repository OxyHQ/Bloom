# Platform surfaces

A native menu is a bottom sheet in an RN `Modal`: the right presentation on a
phone. A platform with its own popup surfaces can do better: an OxyOS
compositor popup is anchored to the trigger and may extend beyond the
application window, over other applications. Bloom does not learn any
platform's protocol. The app registers an **adapter** that reports what the
platform can do and supplies the component that does it.

```tsx
import type { PlatformSurfaceAdapter } from '@oxy.so/bloom/platform-surface';

const oxyos: PlatformSurfaceAdapter = {
  platform: 'oxyos',
  capabilities: new Set(['popup-surface']),
  PopupSurface, // the platform's host component, below
};

<BloomProvider platform={oxyos}>
  <App />
</BloomProvider>
```

Without an adapter, or with one that does not report `popup-surface`, every
family keeps its default presentation. Existing Android, iOS and web apps are
unchanged.

## `popup-surface`

`PopupSurface` receives `PopupSurfaceProps`:
- `anchorRef`: the trigger's view. It may change while the popup is open, and the
  panel's size with it: the platform places the same popup again against the new
  view, at the new size, never closing it for another (a menu bar's one popup
  changing from one menu into the next, below);
- `point` (optional): a point in the anchor, in layout pixels from its top-left
  corner, to place the popup against instead of the anchor's frame (a context
  menu opens where the pointer pressed); placement applies to it as to a frame
  of no size;
- `trackingRef` (optional): a view outside the popup that keeps taking the
  pointer's movement while the popup is open: a menu bar, whose titles open
  their menus in turn as the pointer crosses them, as a Mac's bar tracks the
  pointer with a menu open. The platform delivers the movement over that view,
  and over nothing else outside the popup, while the popup holds its input grab.
  A press there still closes the popup, as any press outside it does. A platform
  that cannot do this ignores it, and the bar then switches menus by press only;
- Bloom's placement (`side`, `align`, `sideOffset`, `alignOffset`, the same
  `FloatingPositionProps` the web panel takes);
- the content's `role` and accessible `label`, which the popup carries (the panel inside it
  is not labelled again, so the menu's name is announced once). A `tooltip` (the native
  `Tooltip`'s bubble) is a hint, not a control: the platform shows it while it is mounted
  without taking the pointer or the keyboard (no grab; presses pass through it) and closes it
  itself only with its parent;
- `onDismiss`;
- `onKey` (optional to call): the keys pressed while the popup has keyboard
  focus, as W3C `KeyboardEvent.key` names.

It renders its `children` in a popup of the platform, **in the same React
tree**, the way RN's `Modal` renders into another window. Providers, theme,
locale and state reach the panel as they reach any child; a React portal alone
could not cross the window's clipping.

- The panel sizes itself; the platform places it and keeps it on screen. It
  flips on the side axis and slides on the other.
- The platform closes the popup itself on an outside press, a refused grab, or
  its parent going away. `onDismiss(reason)` then closes the menu (`reason` is
  `'outside-press'`, `'denied'` or `'closed'`).
- A native popup has no focusable rows, so the panel keeps an **active row**
  (`floating/popup-navigation`), painted like hover: <kbd>↓</kbd>/<kbd>↑</kbd>
  move it (the first press lands on the first or last row), <kbd>Home</kbd>/
  <kbd>End</kbd> and <kbd>PageUp</kbd>/<kbd>PageDown</kbd> jump,
  <kbd>Enter</kbd>/<kbd>Space</kbd> activate it, <kbd>Esc</kbd>/<kbd>Tab</kbd>
  close the menu, and typed characters find the next row whose label starts
  with them (typeahead, 500 ms). The pointer and the keyboard share the
  highlight: hovering a row makes it active. A platform without a keyboard
  never calls `onKey`, and nothing changes.
- `usePopupSurface()` returns the component only when the capability is
  reported. An adapter that reports it without the component throws instead of
  silently falling back.

Today native `DropdownMenu`, `ContextMenu` and `Menubar` use it: their content
becomes `floating/PopupPanel` in the popup (the web menu panel's chrome: the
menu surface painted as Bloom's material, its 1px edge under it,
`shadow-dropdown`, the 16px corner, the 266px floor), with the same rows.
`ContextMenu`'s secondary button (or a long press) opens its panel at the
press, the trigger the anchor and the press its `point`; a `Menubar`'s menus are
ONE popup, hanging under the open menu's trigger with the web's menubar offsets:
moving to another menu while one is open changes that popup into the next menu
([Menubar](/docs/bloom/main/menubar)), Bloom moving its anchor (a box in the bar,
from title to title) and its size frame by frame, the platform placing the same
popup again each time with its grab and the bar's `trackingRef` kept. Where a pointer drives
the platform (`window` or `pointer`), a submenu flies out beside its row in a
popup of its own, anchored to the row: its `PopupSurface` is rendered inside
the menu's, so the platform knows it as the menu's child (OxyOS opens it on top
of the menu's grab), and its `onKey` is the menu's own. The rest of the native
overlay families still present through `dialog/SheetShell`.

## `pointer`

A pointer (a mouse, a touchpad) drives the platform, though Bloom is not in a
window of its own there: a desktop's shell, its top bar and dock. Controls take
a desktop's compact geometry (`useTouchInput()` is false: menu rows at their
desktop height, no 44pt floor) and menus a desktop's presentation (submenus
beside their rows), as `window` gives an application. An OxyOS adapter reports
it everywhere.

## `window`

The application runs in a desktop window with controls in its top leading
corner. The adapter supplies the window (`window: PlatformWindow`):

```ts
interface PlatformWindow {
  readonly controls: 'bloom' | 'platform';   // who draws them
  readonly metrics: {
    controls: { start: number; top: number; width: number; height: number }; // leading-relative
    room: { top: number; leading: number };
    radius: number;
  };
  getState(): { active: boolean; maximized: boolean; fullscreen: boolean };
  subscribe(listener: () => void): () => void;
  close(): void;      // the application's close request
  minimize(): void;
  zoom(): void;       // maximize or restore
  startMove(): void;  // from the press being handled
  setSizeLimits?(limits: { minWidth: number; minHeight: number; maxWidth: number; maxHeight: number }): void; // 0 = no bound
}
```

`getState()` and `subscribe()` are an external store, read with
`useSyncExternalStore`; a fresh but equal state object is not a change. Bloom
reads it through `@oxy.so/bloom/window` ([Window](/docs/window)): `AppShell`
and `SettingsLayout` keep the controls' room and draw them where `controls` is
`bloom`. `usePlatformWindow()` returns the window only when the capability is
reported, and an adapter that reports it without a window throws.
`setSizeLimits` is optional: a platform whose windows take any size leaves it
out, and `useWindowSizeLimits` then asks nothing.

## `menu-bar`

The platform shows the active window's menus in a bar of its own: OxyOS's
top bar, a Mac's `NSMenu`. The adapter supplies it (`menuBar:
PlatformMenuBar`), and a `Menubar` then draws nothing in the window: it
describes its menus and runs the item the person chooses there
([Menubar](/docs/menubar)).

```ts
interface PlatformMenuBar {
  setMenus(menus: readonly PlatformMenu[]): void;   // the window's menus now; [] for none
  onActivate(listener: (id: string) => void): () => void;
}
interface PlatformMenu { id: string; label: string; items: readonly PlatformMenuItem[] }
type PlatformMenuItem =
  | { kind: 'item'; id: string; label: string; enabled: boolean; shortcut?: string; checked?: boolean }
  | { kind: 'submenu'; id: string; label: string; enabled: boolean; items: readonly PlatformMenuItem[] }
  | { kind: 'separator' };
```

- Ids are Bloom's, stable while the entry is mounted and unique in the window.
- `checked` is present on check items and on each item of a radio group.
- `enabled` is false under a disabled menu or submenu too.
- A group's label is an item that is never enabled.
- `shortcut` is the chord in one canonical spelling: `Mod+Ctrl+Alt+Shift+Meta+<Key>`, the modifiers it has in that order, a letter in upper case, `Space` and `Plus` for those two, and otherwise a W3C `KeyboardEvent.key` name (`Enter`, `ArrowUp`, `F5`). `Mod` is ⌘ on Apple platforms and Ctrl elsewhere.

The platform only shows a shortcut. Bloom matches the window's keys and runs
the item itself, on every platform, so the platform must never run an item
for a key of its own.

`usePlatformMenuBar()` returns the bar only when the capability is reported;
an adapter that reports it without `menuBar` throws.

## `appearance`

The platform has an appearance for every application beyond light or dark, as
OxyOS's Settings does (OxyOS ADR 0019, decision 4) and a Mac's accent colour and
Reduce transparency do. The adapter supplies it (`appearance:
PlatformAppearance`):

```ts
interface PlatformAppearance {
  getState(): {
    accent: string | null;
    reduceTransparency: boolean;
    increaseContrast?: boolean;
  };
  subscribe(listener: () => void): () => void;
}
```

- **Light or dark is not part of it.** React Native's `Appearance` and
  `useColorScheme` carry that, and `mode="system"` already follows them.
- **An external store**, as the window's state is: a fresh but equal state is
  not a change. `BloomThemeProvider` reads it once for the whole app
  (`usePlatformAppearanceState()`), so a change applies at once, with no restart.
- **`accent`** is the name of one of Bloom's colour presets (`APP_COLOR_PRESETS`:
  `oxy`, `blue`, `purple`, `pink`, `red`, `orange`, `yellow`, `green`, `gray`,
  …). It is the palette's preset, under the rule below. A name Bloom does not
  know is no accent: the app keeps its own colour, never an error.
- **`reduceTransparency`** draws every blurred material opaque, as
  `BloomProvider reduceTransparency` does ([Surface](/docs/surface), *Reduced
  transparency*).
- **`increaseContrast`** (optional) reduces transparency and edges every surface
  with a hairline, as `BloomProvider increaseContrast` does
  ([Surface](/docs/surface), *Increased contrast*).

`usePlatformAppearance()` returns the appearance only when the capability is
reported; an adapter that reports it without `appearance` throws.

### Whose colour: the app's or the system's

As on a Mac, an app follows the system's accent unless it has a colour of its
own (its tint):

| The app | Its palette |
| --- | --- |
| sets no preset (no `colorPreset`, `defaultColorPreset`, `prepaintTheme.defaultColorPreset`, nothing chosen or persisted) | the platform's accent; `oxy` without one |
| has its own colour: `colorPreset`, `defaultColorPreset`, or a preset the person chose with `setColorPreset` (persisted or not) | its own; the platform's accent never replaces a brand |
| has its own and passes `followSystemAccent` | the platform's accent, its own wherever there is none (or an unknown one) |

A dynamic `seed` (or `useAmbientTheme`) still themes the whole app from that
colour. `useBloomTheme().colorPreset` is the preset drawn, the accent included.
The accent is never persisted as the app's choice, and `resetTheme()` returns an
app with no default to following it.

## `keyboard`

Not a capability (it changes no presentation): the window's key presses, for
a platform whose keys do not reach Bloom through a DOM `document`.

```ts
interface PlatformKeyboard {
  subscribe(listener: (event: PlatformKeyEvent) => boolean): () => void;
}
interface PlatformKeyEvent {   // W3C KeyboardEvent's fields, as React Native's key events carry them
  key: string; code?: string;
  altKey: boolean; ctrlKey: boolean; metaKey: boolean; shiftKey: boolean;
  repeat?: boolean; isComposing?: boolean;
}
```

The platform calls the listener with each key press in the window **before**
the focused view receives it, as a Mac's menu bar sees key equivalents first.
It returns true when Bloom took the key (a menu's shortcut ran), and the
platform then does not deliver it to the view. Bloom asks React Native which
view has focus (`TextInput.State`) to leave a text field its editing keys.

Without it Bloom listens on the `document` where there is one (the web). React
Native has no window-wide key event (`onKeyDown` reaches only the focused view
and its ancestors), so a native runtime that supplies no `keyboard` has no
menu shortcuts. `usePlatformKeyboard()` returns it, or null.

Both menus' shortcuts and an application's own keys (`useWindowKeys`,
[`Kbd`](/docs/bloom/main/kbd)) come from this one source per window
(`kbd/window-keys`), menus first.

## `editing`

Not a capability (it changes no presentation): the window's first responder for the standard editing actions, the focused text field, for a platform that knows which it is and what it can do.

```ts
type PlatformEditAction =
  'undo' | 'redo' | 'cut' | 'copy' | 'paste' | 'pasteAndMatchStyle' | 'delete' | 'selectAll';
interface PlatformEditing {
  getState(): Readonly<Record<PlatformEditAction, boolean>> | null; // null: no text field has focus
  subscribe(listener: () => void): () => void;
  perform(action: PlatformEditAction): boolean;
}
```

`getState` is an external store's (`useSyncExternalStore`): what the focused field can do now, one flag per action, as `NSTextView`'s `validateMenuItem:` answers, or null while no text field has focus. `subscribe` hears every change of it (focus, the field's text, selection and history, the clipboard). `perform` does the action on the focused field as its own key or context menu row would, citing the person's latest input for the clipboard. A `MenubarItem` with an `action` ([Menubar](/docs/bloom/main/menubar)) uses it: while a field has focus the item is the field's, enabled by its state and performed there; otherwise the application's own item. `usePlatformEditing()` returns it, or null.

## `files`

Not a capability either: the person's files beyond what `expo-file-system`
reaches, for a platform that has them. A file manager needs three things that
API does not have (the person's places, the Trash and their tags on their
files), and a desktop has them; a desktop that backs them up gives their
backups too:

```ts
interface PlatformFiles {
  places(): Promise<readonly PlatformPlace[]>;       // the home, its standard folders, the volumes
  watchPlaces(listener: () => void): () => void;     // a volume mounted or gone
  trash(uris: readonly string[]): Promise<readonly PlatformFileOutcome[]>;
  trashed(): Promise<readonly PlatformTrashedItem[]>;
  watchTrash(listener: () => void): () => void;
  restore(uris: readonly string[]): Promise<readonly PlatformFileOutcome[]>;
  erase(uris: readonly string[]): Promise<readonly PlatformFileOutcome[]>;
  emptyTrash(): Promise<void>;
  readonly chooser?: PlatformFileChooser;            // only in the person's file chooser
  readonly tags?: PlatformFileTags;                  // the person's tags on their files
  readonly backups?: PlatformFileBackups;            // their backups: versions, a folder as it was
}
```

- **Places:** the person's home (`kind: 'home'`), the standard folders in it
  that exist (`desktop`, `documents`, `downloads`, `pictures`, `music`,
  `videos`) and the volumes mounted for them (`volume`, by their label).
- **The Trash** is the platform's, the one every file manager on it shares (on
  OxyOS the freedesktop.org Trash): `trash` puts items in it, `trashed` lists
  what it holds with where each was and when, `restore` puts items back where
  they were (never over an item there now), `erase` deletes them for good and
  `emptyTrash` deletes everything. A request about several items answers each
  (`PlatformFileOutcome`), so one that fails never hides what came of the rest.

Every URI is `file://`: what a place holds is read, changed and watched through
`expo-file-system` (`Directory.list`, `File.move`, `Directory.watch`), the same
API on every platform. `usePlatformFiles()` returns the adapter's `files`, or
null: then an application has the folders `expo-file-system` gives it
(`Paths.document`) and deletes as that API does, for good, saying so.

### Tags: `tags`

A desktop keeps the person's tags on their files, as a Mac's Finder does, so
every file manager on it shows the same ones, a file keeps them when it is
copied, moved or put in the Trash, and one index answers "everything tagged
Red" without a crawl per question. `files.tags` is present on a platform that
keeps them, and absent elsewhere: an application then keeps its own, or shows
none.

```ts
type PlatformTagColor = 'red' | 'orange' | 'yellow' | 'green' | 'blue' | 'purple' | 'grey';

interface PlatformFileTag { name: string; color: PlatformTagColor | null }
interface PlatformTagChange { add?: readonly PlatformFileTag[]; remove?: readonly string[] }
interface PlatformTagName { name: string; count: number }
interface PlatformTaggedItem {
  uri: string; name: string; isDirectory: boolean;
  size: number | null;                // bytes; null for a folder
  lastModified: number | null;        // ms since the epoch
  tags: readonly PlatformFileTag[];
}

interface PlatformFileTags {
  inFolder(folderUri: string): Promise<Readonly<Record<string, readonly PlatformFileTag[]>>>;
  ofItems(uris: readonly string[]): Promise<readonly (readonly PlatformFileTag[] | null)[]>;
  change(uris: readonly string[], change: PlatformTagChange): Promise<readonly PlatformFileOutcome[]>;
  tagged(name: string): Promise<readonly PlatformTaggedItem[]>;
  names(): Promise<readonly PlatformTagName[]>;
  watch(listener: () => void): () => void;
}
```

- **What an item carries:** `inFolder` gives the tags of everything a folder
  holds, keyed by each item's URI exactly as `Directory.list()` writes it, and
  leaves out items with none (one call for a folder's view); `ofItems` gives
  each item's tags in the order asked, null for an item that is not there.
- **A tag's colour** is the item's own only where the item says one (a file
  tagged on a Mac does); otherwise `null`, and the application colours the tag
  from the person's own tag definitions, which are its to keep.
- **Changing them:** `change` applies the same change to each item on its own:
  each tag of `add` is appended once (names compare without regard to case, the
  first spelling kept) and each name of `remove` goes. Each item gets its
  outcome (`PlatformFileOutcome`, `result` its URI), so one that fails never
  hides what came of the rest.
- **Across the person's places:** `tagged(name)` lists every item in the
  person's places (never the Trash) carrying a tag, and `names()` every tag
  found with how many items carry it, both from the platform's index; `watch`
  hears every change to it (an item's tags, a tagged item moved, gone or come),
  for a view of a tag to stay current.
- **In the Trash:** each `PlatformTrashedItem` says its `tags` as it sits
  there, as Finder's Trash shows them (empty when it has none, and on a
  platform that keeps no tags).

On OxyOS the tags are the files' own extended attributes, written as the
freedesktop.org `user.xdg.tags` and read from a Mac's own attribute when a file
came from one, so they travel with the files.

### Backups: `backups`

A desktop backs the person's files up (a Mac's Time Machine), and a file
manager is where they get them back: an item's past versions (*Browse
Versions…*), a folder as it was at a backup (*Browse Backups*, Time Machine's
*Enter Time Machine*), and *Restore*. `files.backups` is present on a platform
that makes backups, and absent elsewhere (the web, a phone). Present, it may
still keep none (nobody set a backup disk up): an application shows its backup
commands only while `state()` names a destination, and follows `watch` for one
being added or taken away.

```ts
interface PlatformBackup { destination: string; id: string; time: number }   // ms since the epoch
interface PlatformBackupDestination {
  id: string; name: string; kind: 'disk' | 'share';
  available: boolean;                 // connected or reachable: browsable now
  lastBackup: number | null; oldestBackup: number | null;
}
interface PlatformBackupsState {
  destinations: readonly PlatformBackupDestination[];
  lastBackup: number | null; backingUp: boolean;
}
interface PlatformFileVersion {
  backup: PlatformBackup; isDirectory: boolean;
  size: number | null; lastModified: number | null;
}
interface PlatformBackupItem {
  uri: string; name: string; isDirectory: boolean;
  size: number | null; lastModified: number | null;
}
interface PlatformRestoreOptions {
  to?: string;                        // Restore to…: a folder's file:// URI
  replace?: boolean;                  // Replace, or (default) Keep Both
  onProgress?: (progress: { bytesWritten: number; totalBytes: number | null }) => void;
  signal?: AbortSignal;
}

interface PlatformFileBackups {
  state(): Promise<PlatformBackupsState>;
  watch(listener: () => void): () => void;
  versions(uri: string): Promise<readonly PlatformFileVersion[]>;
  contents(backup: PlatformBackup, folderUri: string): Promise<readonly PlatformBackupItem[]>;
  restore(backup: PlatformBackup, uri: string, options?: PlatformRestoreOptions):
    Promise<{ uri: string; skipped: number }>;
}
```

- **Versions:** `versions(uri)` lists what the backups held of an item, newest
  first: a file once for each backup it changed in, a folder in every backup
  (what it holds may have changed though the folder did not), which is the
  timeline *Browse Backups* shows beside it. An item no backup holds has none.
- **A folder as it was:** `contents(backup, folderUri)` lists what the folder
  held in that backup, each item's `uri` where it was (and may still be),
  under the folder's URI as asked: an item deleted since is there to restore.
- **Restoring** writes the item as the person, where it is or was, or into
  the folder `to` names. Where an item of the same name is there, the platform
  keeps both unless `replace` is asked: the restored item goes beside it, named
  as a Mac's Time Machine names it, `notes (original).txt`, then
  `notes (original 2).txt`. `replace` exchanges it with the one there in one
  step; the person's home's standard folders are never replaced. An
  application asks the person first, as a Mac does (*Keep Both*, *Replace*).
  Nothing half written is ever left: a restore that fails, or whose `signal`
  is aborted, leaves no trace. `onProgress` says the bytes written (`totalBytes`
  is null for a folder). A folder's links that lead out of it, and its devices,
  are not restored (`skipped` counts them).
- **Errors:** a promise rejects with an `Error` whose `code` is a file error
  (`not-found`, `exists`, `refused`, `denied`, `io`) or `unavailable` (the
  backup's disk is not connected, the backups are not running),
  `not-permitted` (the application may not reach the person's backups) or
  `cancelled`.

On OxyOS the backups are the system's backup service's (restic, OxyOS ADR
0059), asked from the application's own process as the person: only what was
in their own home, and only for an application granted `files`.

### The file chooser: `chooser`

A desktop shows its open and save panels as a system service, never as the
asking application's code: the platform starts the person's file manager to
show the panel as a sheet of the asker's window, and passes the answer back
to the asker alone. That file manager learns it is the chooser only here:
`files.chooser` is present in an application the platform started for a
request, and absent everywhere else.

```ts
interface PlatformFileChooserRequest {
  mode: 'open' | 'save';
  multiple: boolean;                  // several items may be chosen (open)
  directory: boolean;                 // folders are chosen, not files (open)
  types: readonly string[];           // media types (image/png, image/*) and .ext; empty: any
  title: string | null;
  suggestedName: string | null;       // save
  folder: string | null;              // file:// where to start, if the asker said
  application: { id: string; name: string } | null; // who asks
}

interface PlatformFileChooser {
  request: PlatformFileChooserRequest;
  choose(uris: readonly string[]): void; // file:// URIs; save: the one file to write
  cancel(): void;
}
```

The application shows its panel for `request` and answers once: `choose` with
the `file://` URIs the person chose (for `save`, the one file to write, after
the panel asked before replacing an existing one), or `cancel`. The platform
cites the latest press the application received for a choice, then closes the
panel. Where the panel starts, and what it remembers between requests (the
folder last used for each asking application), are the application's own.

## `search`

Not a capability either: the platform's search across the person's files,
applications, Settings and applications' own items, for a platform that keeps
an index (a desktop's Spotlight; OxyOS's, ADR 0051 there). A Mac's
`NSMetadataQuery` (asking) and Core Spotlight (donating) are the models:

```ts
type PlatformSearchCategory =
  | 'application' | 'settings' | 'folder' | 'document' | 'pdf' | 'text' | 'source'
  | 'presentation' | 'spreadsheet' | 'image' | 'movie' | 'music' | 'archive'
  | 'contact' | 'event' | 'mail' | 'message' | 'other';

type PlatformSearchToken =                       // a search field's token (Finder's "Kind: PDF")
  | { kind: 'category'; value: PlatformSearchCategory }
  | { kind: 'tag'; value: string }
  | { kind: 'date'; value: 'today' | 'yesterday' | 'week' | 'month' | 'year' }
  | { kind: 'name'; value: string };

type PlatformSearchQuery = {
  text: string;                                  // words, "phrases", kind:pdf tag:Work date:today name:report
  tokens?: readonly PlatformSearchToken[];
  within?: readonly string[];                    // file:// folders, recursively
  categories?: readonly PlatformSearchCategory[];
  limit?: number;                                // default 60, at most 200
  language?: string;                             // BCP 47; the platform's own when absent
};

type PlatformSearchItem = {
  id: string;                                    // file URI, application:<id>, settings:<page>, <app id>:<its id>
  category: PlatformSearchCategory;
  title: string;
  uri?: string;                                  // a file's or folder's
  url?: string;                                  // what opens anything else
  application?: string; icon?: string; contentType?: string; size?: number;
  modified?: number; created?: number; lastUsed?: number;   // ms since the epoch
  tags?: readonly string[]; snippet?: string; location?: string;  // `Documents › Work`
};

type PlatformSearchResults = { items: readonly PlatformSearchItem[]; topHit: string | null; indexing: boolean };

type PlatformSearchableItem = {                  // Core Spotlight's CSSearchableItem
  id: string; title: string;
  category: 'contact' | 'event' | 'mail' | 'message' | 'other';
  text?: string; keywords?: readonly string[];
  url: string;                                   // what opens it
  modified?: number;
};

interface PlatformSearch {
  query(query: PlatformSearchQuery): Promise<PlatformSearchResults>;
  watch(listener: () => void): () => void;
  used(id: string): void;
  readonly index: {
    donate(items: readonly PlatformSearchableItem[]): Promise<void>;
    remove(ids: readonly string[]): Promise<void>;
    removeAll(): Promise<void>;
  };
}
```

- **Asking:** `query` answers from the index, best first, with the id of the
  item it judged best (`topHit`, shown first) and whether it is still indexing
  (`indexing`: the results may be incomplete). `text` is what the person typed:
  words matched as prefixes of words in names and contents, "quoted phrases",
  and typed filters (`kind:pdf`, `tag:Work`, `date:today`, `name:report`);
  `tokens` are the filters the person chose as a search field's tokens
  ([Search](/docs/bloom/main/search) draws them); `within`, `categories` and
  `limit` bound it; titles come in `language`.
- **Staying current:** `watch` hears every change to the index, to query again.
- **Ranking:** `used(id)` says the person opened a result, and the platform
  ranks it higher.
- **What opens:** a file or folder by its `uri` (`file://`), anything else by
  its `url` (an application's, or Settings' page).
- **An application's own items:** `index.donate` adds or replaces items by id,
  `index.remove` removes some and `index.removeAll` all of this application's.
  Each is found by its title, `text` and `keywords`, and opened by its `url`.
  Results give its id as `<application id>:<its id>`.

`usePlatformSearch()` returns the adapter's `search`, or null: then an
application searches only what it holds itself.

## `sounds`

Not a capability either: the platform's own sounds, for a platform that has
them. An application asks for a sound by what the person did, never by a file,
and ships no copy of it: every application sounds the same, as a Mac's Finder
and Dock sound alike when items go to the Trash.

```ts
type PlatformSystemSound = 'move-to-trash' | 'empty-trash';
interface PlatformSounds {
  play(sound: PlatformSystemSound): void;
}
```

`play` plays the sound for what the person just did (`move-to-trash` once items
are in the Trash, `empty-trash` once it is emptied), without waiting for it. The
platform decides whether it is heard: never when the person turned interface
sound effects off, nor while the sound output is muted, and only after the
person's own input (it cites the latest the application received).
`usePlatformSounds()` returns the adapter's `sounds`, or null: then the
application plays nothing.

```tsx
const sounds = usePlatformSounds();
const outcomes = await files.trash(uris);
if (outcomes.some((outcome) => outcome.ok)) sounds?.play('move-to-trash');
```

## `drag-and-drop`

Dragging between applications, on a platform that moves content between them
(OxyOS's, ADR 0035 there). The adapter supplies two parts, both required with
the capability (`usePlatformDropTarget()` and `usePlatformDrag()` throw if one
is missing, as the other hooks do):

- **`DropTarget`**, a host component taking `PlatformDropTargetProps`: what it
  accepts (`files`, `text`, `url`, `html` or media types), the media types of
  files it takes (`acceptFileTypes`), its actions (its preferred one first),
  the `folder` files dropped on it go into (a `file://` URI), `disabled`, and
  `onDragEnter`, `onDragOver`,
  `onDragLeave` and `onDrop`. It renders its children. The platform answers the
  drag itself from those props, so a drag never waits on JavaScript; the
  callbacks follow it, and `onDrop` receives the content (`DropData`: files as
  `file://` URIs, URLs, text, HTML, other named types). Each drag event says
  the media type of each file dragged (`fileTypes`), as the source declares
  them, before the drop; with `acceptFileTypes` a drag of files is taken only
  when every file is of a type named there. With a `folder`, where the
  platform knows the volume each dragged file is on, it answers a drag of
  files with a move when every one is on the folder's volume and a copy when
  any is not, as Finder does, if the target's actions allow both (Option and
  Command still force theirs); a drag that says no volumes keeps the preferred
  action. Applications use it through `DropZone` (`docs/drop-zone.mdx`),
  never directly.
- **`drag`** (`PlatformDrag`): `start({ data, actions, previewRef, count, vanish, onCancel })`
  begins a drag from the press the application is handling, with what it drags
  (`files` as `file://` URIs, `text`, `url`, `html`, and `other` media types by
  name, each with its content as text) and the actions it allows. The platform
  declares the type of each file dragged to the targets it passes over.
  It resolves with the action the drop took, or null when it was cancelled or
  refused. An application that runs its own pointer gestures (a file manager's
  items) calls it once its own drag begins (the pointer moved past its slop
  while pressed), as macOS's `beginDraggingSession` is called from
  `mouseDragged`.

  The drag's image is the dragged view itself, as a Mac's is: `previewRef` is
  the view pressed, where it is on screen (an item's icon and name, a card),
  never a view drawn for the purpose, and a view of its own (one that draws
  nothing itself takes `collapsable={false}`, as a view snapshot needs). The
  platform draws its rendered subtree as it looks (React Native's view
  snapshot, `captureRef`), translucent, its
  transparent margins left out, with the point pressed in it kept under the
  pointer. `count` is how many items go: above one the image is stacked, with
  the count on a red badge at its top right. The platform's pointer shows the
  action (a copy's plus, a link's arrow), and a drag that drops nothing slides
  its image back to the view, unless it was started with `vanish`: then a drop
  on nothing that takes it makes the image vanish in a puff of smoke where it
  is, as an icon dragged off a Mac's Dock does (Escape still puts it back). The
  promise resolves null either way. `onCancel(reason)` is called once, before
  it resolves, when the drag ended without a drop: `escape`, `not-accepted`
  (released over nothing that takes it), `refused` (at its start) or
  `cancelled` (the source cancelled it, its window went, the session locked);
  where Escape cannot be told from a release over nothing (HTML5's `dragend`),
  the platform says `not-accepted`. The application removes the item for a
  release off its list, not for Escape:

```tsx
const drag = usePlatformDrag();
// In the application's own gesture, once the pressed pointer moved 4 px:
if (drag) {
  const action = await drag.start({
    data: { files: selected.map((item) => item.uri) },
    actions: ['copy', 'move', 'link'],
    // The row pressed, as it is drawn; the others selected go with it.
    previewRef: rowRef,
    count: selected.length,
  });
} else {
  // No platform drag (the web, a phone): the application's drag stays inside it.
}
```

An application dragged out of a launcher or a dock, removed when dropped on
nothing:

```tsx
const action = await drag.start({
  data: { other: { 'application/x-oxyos-application': app.id } },
  actions: ['move'],
  previewRef: iconRef,
  vanish: !running,
  onCancel: (reason) => {
    if (reason === 'not-accepted' && left) removeFromDock(app.id);
  },
});
```

With `move` of data the application deletes its original once the promise
resolves; files are moved by the target, as Finder and every Linux file
manager do, and the source deletes nothing.

`drag.watchWindow(listener)`, optional, follows drags over the application's
window from any application, for `useWindowDrag` (`docs/drop-zone.mdx`): the
listener is told `{ type: 'enter' }` when a drag first comes over any of the
window's surfaces and `{ type: 'exit', dropped }` when it has left all of them
or ended, `dropped` true when it was dropped on one of them, told once that
drop was delivered (after the target's `onDrop`). It returns the function that
stops following. Without it, `useWindowDrag` tells nothing.

## Who registers the adapter

The runtime that runs the application: the web build's, a native runtime's,
the OxyOS Bloom host's, never the application. It wraps the application in
`PlatformSurfaceProvider` (or a `BloomProvider platform={…}`), and the
application's own `BloomProvider`, with no `platform` of its own, keeps that
adapter for everything below it. A `platform` given to an inner provider
replaces the outer one for its subtree.

The OxyOS adapter, and the host component behind it, live with the OxyOS
runtime (OxyHQ/OxyOS, `tools/rn-host-spike`): Bloom stays free of OxyOS,
protocol and SDK imports.

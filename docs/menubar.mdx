# Menubar

A desktop-style menu bar: a row of triggers, each opening a menu, with at most one open at a time.

New to Bloom in this release. Its parts are shadcn's, and its rows are the same rows `DropdownMenu` and `ContextMenu` publish.

## Basic

```tsx
import {
  Menubar,
  MenubarContent,
  MenubarItem,
  MenubarMenu,
  MenubarSeparator,
  MenubarTrigger,
} from '@oxy.so/bloom/menubar';

<Menubar>
  <MenubarMenu value="file">
    <MenubarTrigger>File</MenubarTrigger>
    <MenubarContent>
      <MenubarItem shortcut="Mod+T" onPress={newTab}>
        New tab
      </MenubarItem>
      <MenubarItem onPress={open}>Open…</MenubarItem>
      <MenubarSeparator />
      <MenubarItem tone="danger" onPress={closeWindow}>
        Close window
      </MenubarItem>
    </MenubarContent>
  </MenubarMenu>

  <MenubarMenu value="edit">
    <MenubarTrigger>Edit</MenubarTrigger>
    <MenubarContent>
      <MenubarItem onPress={undo}>Undo</MenubarItem>
      <MenubarItem onPress={redo}>Redo</MenubarItem>
    </MenubarContent>
  </MenubarMenu>
</Menubar>
```

Each `MenubarMenu` needs a `value`. That value IS the open state.

## One open menu, one state

`Menubar` owns which menu is open, and each `MenubarMenu` derives its own boolean from it:

```tsx
const [open, setOpen] = useState<string | undefined>(undefined);

<Menubar value={open} onValueChange={setOpen}>
```

Uncontrolled by default (`defaultValue` sets the initially-open menu; omit it for none). Switching menus is a single state write, so there is never a frame with both open or neither.

## Presentation

`MenubarTrigger` draws its own chrome — `rounded-md px-2 py-1.5` with a `text-body-medium` label (`TYPE_SCALE` + Inter, `text-primary`), washed with the menu row highlight (`neutral-100`, dark `neutral-700` @60%) while its menu is open. The bar uses the menu recipe's field: the select trigger's white surface, `border-button-default` hairline and `shadow-xs`, `rounded-2lg`. Pass a string and it is set for you; pass nodes and they go inside that button; pass `asChild` and your own element replaces the whole thing.

On web each menu is an anchored panel under its own trigger, aligned to the trigger's left edge. On a phone each is the bottom sheet the other menu families use — a phone has no room for a hanging panel, and every Bloom overlay resolving to the same sheet is what makes the native surfaces feel like one system.

On a native desktop — an adapter reporting [`popup-surface`](/docs/bloom/main/platform-surface) (an OxyOS window, or its shell) — each menu is the web's desktop menu instead: the same panel in the platform's popup, hanging under its trigger with the web's `sideOffset={8} alignOffset={-4}` and 266px floor, its chrome the web panel's (the menu surface as Bloom's material, its 1px edge under it, `shadow-dropdown`, the 16px corner, the separators ending at the rows' edges as the web's scroller clips them), its submenus flying out beside their rows when a pointer drives the platform (`window` or `pointer`), and its rows driven by the platform's keys. Never a bottom sheet there.

Pressing an open menu's trigger closes it.

## Rows

`MenubarItem`, `MenubarCheckboxItem`, `MenubarRadioGroup` / `MenubarRadioItem`, `MenubarLabel`, `MenubarSeparator`, `MenubarShortcut`, `MenubarGroup`, and `MenubarSub` / `MenubarSubTrigger` / `MenubarSubContent`.

Sub-menus fly out beside their trigger row on web and on a native desktop, and render as an inline disclosure in a phone's sheet — see [DropdownMenu](/docs/bloom/main/dropdown-menu).

## Shortcuts

`MenubarItem`, `MenubarCheckboxItem` and `MenubarRadioItem` take a `shortcut`: a key chord, `+`-separated modifiers and then one key.

```tsx
<MenubarItem shortcut="Mod+N" onPress={newDocument}>New</MenubarItem>
<MenubarItem shortcut="Mod+Shift+Z" onPress={redo}>Redo</MenubarItem>
<MenubarCheckboxItem shortcut="Mod+Shift+D" checked={dense} onCheckedChange={setDense}>
  Dense rows
</MenubarCheckboxItem>
```

- **The modifiers**, in any case and any order: `Mod`, the platform's command modifier (⌘ on Apple platforms, Ctrl elsewhere, OxyOS included), `Ctrl`, `Alt`, `Shift` and `Meta` (⌘ on a Mac, the Windows or Super key elsewhere). The key is one character, or a key name (`Enter`, `Escape`, `Tab`, `Backspace`, `Delete`, `Home`, `End`, `PageUp`, `PageDown`, the arrows as `ArrowUp`…, `F1`–`F24`), with `Space` and `Plus` for those two. A chord that is none of these warns in development and gives the item no shortcut.
- **The row draws it** for the platform as its trailing hint: `⌘N` and `⇧⌘Z` on a Mac (⌃⌥⇧⌘, then the key), `Ctrl+N` and `Ctrl+Shift+Z` elsewhere. A row's own `trailing` wins. `MenubarShortcut` is still the drawn-only hint (`trailing={<MenubarShortcut>⌘N</MenubarShortcut>}`): its text is not a chord and runs nothing.
- **Pressing it runs the item** exactly as pressing its row does (a check item toggles, a radio item selects, an open menu closes unless the item `keepOpen`), on every platform, whether its menu is open or closed and whether or not any bar shows it. A held chord runs it once. A disabled item's chord (or one in a disabled menu or submenu) runs nothing and is left to the page.
- **Who takes a key.** A menu's chord comes before the focused control, as a Mac's key equivalents do, except:
  - a focused text field keeps what it edits with: every key without Ctrl, Alt or Meta; moving and deleting (the arrows, Home, End, Page Up and Down, Backspace, Delete) with any modifiers; `Mod+C`, `Mod+X`, `Mod+V`, `Mod+A`, `Mod+Z` and `Mod+Shift+Z`; and on Apple platforms Option alone, which types characters. An Edit menu's Copy item acts through the field (the application's own `onPress`);
  - while a menu or a list is open, a key without Ctrl, Alt or Meta is that menu's (its arrows, its typeahead);
  - a key something before it took (`defaultPrevented`), and an input method's composition.

  A chord that ran an item is consumed, so the browser's own `Ctrl+N` or `Ctrl+S` does not also happen.
- **Where the keys come from.** On the web, the page's `keydown` in the capture phase (a bubble listener never hears a key typed in a text field: react-native-web's `TextInput` stops them). On native, the platform adapter's `keyboard` ([Platform surfaces](/docs/bloom/main/platform-surface)): React Native has no window-wide key event, so a native app whose runtime supplies no key source has no shortcuts; its menus still work by pressing.
- Several bars in one window share the keys: the first mounted bar with the chord runs it, once.

Matching reads the character typed (`event.key`), and the physical key (`code`) where that character is not the key's name: under Alt (a Mac's Option+N types `˜`), Shift with a digit, and a non-Latin layout. A symbol that needs Shift to be typed (`Mod+?`) matches without `Shift` in the chord; a letter, digit or named key wants exactly the modifiers declared.

## A platform's menu bar (`menu-bar`)

Where the platform shows the active window's menus in a bar of its own (OxyOS's top bar, a Mac's), its adapter reports `menu-bar` ([Platform surfaces](/docs/bloom/main/platform-surface), OxyOS ADR 0021). The application's declaration does not change.

- **`Menubar` draws nothing in the window.** It gives the platform a description of its menus (`PlatformMenuBar.setMenus`): each menu's label, and its items, check items (`checked`), radio items (each `checked` or not), separators and submenus, with each item's label (its text), `enabled` and its chord (`Mod+Shift+Z`, the one canonical spelling). A group's `MenubarLabel` is an item that is never enabled. `MenubarGroup` and `MenubarRadioGroup` are their items.
- **It describes again whenever the description changes**, once for the commit that changed it however many items changed, never per item and not when it came out the same. Unmounted, it gives the platform `[]`.
- **An item chosen in the platform's bar** (`onActivate(id)`) runs exactly as a press on its row would, once. A disabled item, an id it no longer has and a menu's own id run nothing.
- **Ids** are Bloom's (`bloom-menu-…`), stable while the item is mounted, unique in the window.
- **One bar per window.** The platform shows one set of menus, so the first `Menubar` mounted publishes; another mounted while it is publishes nothing, runs no shortcut and warns in development, and takes over (publishing its own menus) when the first unmounts. Declare the window's menus in one `Menubar`.

### How the bar knows its declaration

Each part registers itself with its bar while it is mounted: a trigger its menu (its label, `disabled`), an item its kind, label, state, chord and a `run` that calls the part's own current handler, so `onPress`, `onCheckedChange` and `onValueChange` stay the application's closures. With the capability the whole declaration is mounted **headless**: the parts register and render nothing. Without it, a closed menu's (or submenu's) content is mounted headless beside its panel, so its shortcuts work while it is closed; open, the rows draw exactly as before and register too.

The description keeps the declared order: each container (the bar, a menu's content, a group, a submenu's content) records its children's positions, arrays and fragments flattened into them, so an item that mounts later between two others is described between them. Items rendered by one custom component share its position and keep the order they mounted in.

A menu's content is its rows. Something else placed in one (a bare `View` or `Text`) is mounted with the declaration, so it would draw where the declaration is mounted headless, and it is not part of the description.

The labels are the text under each part (strings and numbers, through element children, without a `MenubarShortcut` hint), else its `accessibilityLabel` (an item) or `label` (a trigger). Text a custom component renders is not seen; give such a row an `accessibilityLabel`.

## The bar from the keyboard (`focusValue`)

A desktop's bar is driven from the keyboard once the keyboard is put on it — a Mac's <kbd>Control</kbd>-<kbd>F2</kbd>, OxyOS's <kbd>Super</kbd>-<kbd>F2</kbd>. `Menubar`'s `focusValue` is the `value` of the menu whose title has the keyboard (`undefined`: the keyboard is elsewhere), controlled with `onFocusValueChange`. The owner puts the keyboard on the bar by setting it, to the first menu's value as a Mac does:

```tsx
const [open, setOpen] = useState<string | undefined>();
const [focus, setFocus] = useState<string | undefined>();
// The system's shortcut for the bar:
onBarShortcut(() => setFocus('app'));

<Menubar value={open} onValueChange={setOpen} focusValue={focus} onFocusValueChange={setFocus}>
  …
</Menubar>
```

While it is set:

- <kbd>←</kbd> · <kbd>→</kbd> move across the titles, round the ends, skipping a disabled menu; with a menu open the next one opens in its place, on its first row. An open menu keeps the arrow it acts on: <kbd>→</kbd> on a row that opens a submenu, <kbd>←</kbd> inside a submenu.
- With none open, <kbd>↓</kbd> · <kbd>Enter</kbd> · <kbd>Space</kbd> open the focused menu on its first enabled row, <kbd>↑</kbd> on its last; a letter moves to the next title that starts with it (letters typed within 500ms build one query); <kbd>Esc</kbd> leaves the bar.
- With one open, every other key is the menu's own: its rows, typeahead, and <kbd>Esc</kbd>, which closes it back to its title.
- A row chosen closes the menu and leaves the bar (`onFocusValueChange(undefined)`), so the owner can give the keyboard back to where it was.
- A key with <kbd>Ctrl</kbd>, <kbd>Alt</kbd> or <kbd>Meta</kbd> is never the bar's.

The keys come from the platform adapter's `keyboard` before anything else sees them (a native host), or from the document in the capture phase (the web); a key the bar takes goes no further. The focused title is lit as an open one is, and the screen reader's focus (the web's DOM focus) follows it while no menu is open.

`MenubarMenu` also takes `openFocus` (`'first'` | `'last'`), as `DropdownMenu` does: an open the owner makes from its own keys starts with that row active.

Both `value` and `focusValue` are controlled whenever the prop is passed, `undefined` included: `undefined` is "no menu open" and "the keyboard elsewhere", never a hand-back to the bar's own state.

Pinned by `MenubarDesktop.test.tsx`; the desktop reference is the `Desktop menus` story.

## Keyboard (web)

Each menu takes the keys `DropdownMenu` documents: <kbd>Enter</kbd> · <kbd>Space</kbd> · <kbd>↓</kbd> on a trigger open its menu onto the first row (<kbd>↑</kbd> onto the last), the arrows move between rows and wrap, <kbd>Home</kbd> · <kbd>End</kbd> jump, <kbd>Enter</kbd> · <kbd>Space</kbd> activate, and <kbd>Esc</kbd> · <kbd>Tab</kbd> close the menu with focus back on its trigger. See [DropdownMenu → Keyboard](/docs/bloom/main/dropdown-menu).

## What is not here yet

One thing a desktop menu bar has that this one does not, deliberate rather than forgotten:

- **Hover to switch.** On a real desktop bar, once one menu is open, moving the pointer across a sibling trigger switches to it without a click. That needs hover intent, which is the same machinery a sub-menu flyout needs.
A press opens, a press closes, and every menu is reachable by <kbd>Tab</kbd> and operable from the keyboard once open. Nothing is half-wired.

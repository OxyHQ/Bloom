# DropdownMenu

The menu that drops from a button. A bottom sheet on native, an anchored panel on web, one API on both.

On a native platform with its own popups (an adapter reporting `popup-surface`, registered with `BloomProvider platform={…}`; see [Platform surfaces](./platform-surface)), the content is instead an anchored panel in the platform's popup, placed by `side` / `align` / `sideOffset` / `alignOffset` and free to extend beyond the window. An OxyOS compositor popup is one. The rows are the same.

The parts are shadcn's, so a `@shadcn/ui` or `react-native-reusables` call site ports across unchanged: `DropdownMenu` owns the open state, `DropdownMenuTrigger` opens it, `DropdownMenuContent` is the surface, and the rows are `DropdownMenuItem`, `DropdownMenuCheckboxItem`, `DropdownMenuRadioGroup` / `DropdownMenuRadioItem`, `DropdownMenuLabel`, `DropdownMenuSeparator`, `DropdownMenuShortcut`, `DropdownMenuGroup` and the `DropdownMenuSub` trio.

`ContextMenu` and `Menubar` publish the same row vocabulary under their own prefixes. They are one implementation, so a row behaves identically in all three.

## Basic

```tsx
import {
  DropdownMenu,
  DropdownMenuContent,
  DropdownMenuItem,
  DropdownMenuLabel,
  DropdownMenuSeparator,
  DropdownMenuShortcut,
  DropdownMenuTrigger,
} from '@oxy.so/bloom/dropdown-menu';
import { Button } from '@oxy.so/bloom/button';

<DropdownMenu>
  <DropdownMenuTrigger asChild label="Open menu">
    <Button appearance="outline" tone="neutral">Open menu</Button>
  </DropdownMenuTrigger>

  <DropdownMenuContent>
    <DropdownMenuLabel>My account</DropdownMenuLabel>
    <DropdownMenuSeparator />
    <DropdownMenuItem onPress={openProfile}>Profile</DropdownMenuItem>
    <DropdownMenuItem trailing={<DropdownMenuShortcut>⌘,</DropdownMenuShortcut>}>
      Settings
    </DropdownMenuItem>
    <DropdownMenuItem disabled>Billing</DropdownMenuItem>
    <DropdownMenuSeparator />
    <DropdownMenuItem tone="danger" onPress={signOut}>
      Sign out
    </DropdownMenuItem>
  </DropdownMenuContent>
</DropdownMenu>
```

A row dismisses the menu after it fires. Pass `keepOpen` to a row that should not — a checkbox row you expect the user to toggle twice, say.

## `asChild`

`asChild` is Radix's composition escape hatch and it works the same way here: the trigger's single element child *becomes* the trigger and receives the open handler plus the accessibility props. Without it, the children render inside Bloom's own pressable.

```tsx
<DropdownMenuTrigger asChild label="Actions">
  <Button onPress={track} appearance="outline" tone="neutral">…</Button>
</DropdownMenuTrigger>
```

Handlers the child already carries are composed, not replaced — `track()` runs first, then the menu opens.

`disabled` on the trigger is guarded the same way, at the composition layer rather than on the child alone — pass `disabled` to `DropdownMenuTrigger`, not to your own child element, or the open handler still fires.

`className` and `style` land on the trigger's anchor wrapper, the node the parent lays out and the web surface measures. With `asChild`, keep the button's visual chrome on the child and use the trigger props for anchor geometry. If the child is positioned out of flow instead (`position: absolute` on the button), the wrapper is left an empty 0×0 box: the surface then anchors to the child and development builds warn once, naming the fix — move the position and size onto the trigger.

## Controlled

```tsx
const [open, setOpen] = useState(false);

<DropdownMenu open={open} onOpenChange={setOpen}>
  …
</DropdownMenu>
```

Uncontrolled by default; pass `open` to take over. `onOpenChange` fires either way. There is no imperative control to reach for and no `close()` to call: the menu's state is one boolean, and a row closes it by returning.

## Checkbox and radio rows

```tsx
import { RiCheckLine as CheckIcon } from '@oxy.so/bloom/icons';

<DropdownMenuCheckboxItem checked={dense} onCheckedChange={setDense} keepOpen>
  Dense rows
</DropdownMenuCheckboxItem>

<DropdownMenuRadioGroup value={sort} onValueChange={setSort}>
  <DropdownMenuRadioItem
    value="newest"
    indicator={<CheckIcon size="sm" />}
    indicatorPosition="trailing">
    Newest
  </DropdownMenuRadioItem>
  <DropdownMenuRadioItem
    value="oldest"
    indicator={<CheckIcon size="sm" />}
    indicatorPosition="trailing">
    Oldest
  </DropdownMenuRadioItem>
</DropdownMenuRadioGroup>
```

Both announce their state as `aria-checked`, which is the spelling react-native-web reads and React Native folds back into `accessibilityState` — so it reaches assistive tech on both platforms.

The established defaults stay unchanged: checkbox rows use a check and radio rows use a dot, both in the leading gutter. `indicator` replaces that selected mark, `indicatorPosition="trailing"` moves its reserved gutter to the opposite edge, and `indicator={null}` suppresses the visual mark without removing `aria-checked`. These props are implemented once by the shared row factory, so `ContextMenu` and `Menubar` receive the identical contract.

## Lining rows up: `alignRows`

A check or radio row draws its indicator in a leading gutter, and a row with a `leading` icon starts its label after the icon. By default each row keeps its own layout and `inset` lines a plain row up with indicator rows by hand. `alignRows` on the content does it for the whole panel, like a desktop menu:

```tsx
<DropdownMenuContent alignRows>
  <DropdownMenuCheckboxItem checked={tabsInSidebar} onCheckedChange={setTabsInSidebar}
    trailing={<DropdownMenuShortcut>Ctrl+Shift+S</DropdownMenuShortcut>}>
    Show Tabs in Sidebar
  </DropdownMenuCheckboxItem>
  <DropdownMenuItem leading={<RiShareLine size="sm" />}>Share link</DropdownMenuItem>
  <DropdownMenuItem>Rename</DropdownMenuItem>
</DropdownMenuContent>
```

When any row has a leading indicator, every row (and `DropdownMenuLabel`) takes the gutter; when any row has a `leading` icon, rows without one keep an empty icon-wide slot. Rows add and remove themselves as they mount, so a menu built at run time aligns without the caller computing `inset` or passing blank spacers. A web flyout aligns its own rows and inherits the parent's `alignRows` (`DropdownMenuSubContent alignRows={false}` opts out); on native the inline sub-menu sits in, and aligns with, the parent's column. Same prop on `ContextMenuContent` and `MenubarContent`.

## Keyboard (web)

The web menu follows the ARIA menu-button pattern, and the same keys reach `ContextMenu` and `Menubar` — all three render one row set (`floating/menu-keyboard.ts`):

| where | key | does |
| --- | --- | --- |
| trigger | <kbd>Enter</kbd> · <kbd>Space</kbd> · <kbd>↓</kbd> | opens the menu with focus on the first enabled row |
| trigger | <kbd>↑</kbd> | opens the menu with focus on the last enabled row |
| trigger, menu already open (pointer) | <kbd>↓</kbd> · <kbd>↑</kbd> | moves focus into the menu (first / last row) |
| menu | <kbd>↓</kbd> · <kbd>↑</kbd> | next / previous enabled row, wrapping at the ends |
| menu | <kbd>Home</kbd> · <kbd>End</kbd> | first / last enabled row |
| menu | <kbd>Enter</kbd> · <kbd>Space</kbd> | activates the row: a checkbox row toggles, a radio row selects, and `keepOpen` still decides whether the menu closes |
| menu | <kbd>Esc</kbd> · <kbd>Tab</kbd> | closes the menu; a menu is not part of the page's tab order |
| sub trigger | <kbd>→</kbd> · <kbd>Enter</kbd> · <kbd>Space</kbd> | opens the flyout on its first row (below) |
| flyout | <kbd>←</kbd> · <kbd>Esc</kbd> | closes the flyout onto its trigger row, leaving the menu open |
| flyout | <kbd>Tab</kbd> | closes the whole menu |

Whenever the menu closes with focus inside it — a row activated, <kbd>Esc</kbd>, <kbd>Tab</kbd> — focus returns to the trigger. A pointer open leaves focus where the pointer put it; a right-click opens a `ContextMenu` onto its first row (no ring is painted — rows highlight on `:focus-visible`), since the menu's keys need focus inside it.

Before this the trigger opened the menu and focus stayed on it: the rows are portaled to the end of `<body>`, so the arrows had nothing to move, <kbd>Tab</kbd> walked on through the page behind the open menu, and <kbd>Space</kbd> pressed nothing (react-native-web presses a `menuitem`, `checkbox` or `radio` on <kbd>Enter</kbd> only). Verified in jest (`MenuKeyboard.web.test.tsx`) and in a real browser (`scripts/verify-web-keyboard.mjs`). Native is unchanged — the menu is a bottom sheet there — except in a platform popup, whose keys arrive through the adapter (`platform-surface.mdx`).

## Sub-menus: a flyout on web, an inline disclosure on native

The API is one thing on both platforms — a shadcn call site ports across unchanged — and the presentation is the platform's own, matching what each platform's upstream does.

```tsx
<DropdownMenuSub>
  <DropdownMenuSubTrigger>Send to…</DropdownMenuSubTrigger>
  <DropdownMenuSubContent
    side="right"
    align="start"
    sideOffset={2}
    className="w-[150px]"
    testID="effort-menu">
    <DropdownMenuItem>Email</DropdownMenuItem>
    <DropdownMenuItem>Messages</DropdownMenuItem>
  </DropdownMenuSubContent>
</DropdownMenuSub>
```

**On web** the sub-panel flies out beside its trigger row, the way shadcn's does, and its chevron points right:

- Real mouse or pen movement over the row opens it; a reflow or transition that moves the row under a parked pointer does not count as hover intent. Leaving either surface schedules a close 300 ms later, and real pointer movement over either one cancels that — which keeps it open while the pointer travels diagonally across the gap between them.
- Moving to a SIBLING sub-trigger does not close one panel while another opens: the new panel takes over where the old one is seen, then travels to the new row and resizes to the new submenu while its rows fade in (~200ms), so one panel moves instead of two overlapping. The LIVE panel travels (transform, width and height through the Web Animations API), never a view-transition snapshot: a snapshot is painted without the page behind it, so the material's blur dropped out for ~400ms on every move (measured from Windows' composited frames). Without `Element.animate`, or with reduced motion, the swap is instant.
- Pressing the row toggles it, so a click and a touch-web tap both work.
- <kbd>→</kbd> opens it and moves focus onto its first row; <kbd>←</kbd> closes it and returns focus to the trigger.
- <kbd>Esc</kbd> closes the **innermost** surface first: one press shuts the sub-panel and leaves the menu open, a second shuts the menu.
- It takes its own rank from `overlay/stack.ts` on mount, like every other surface, so it paints above the menu it opened from and carries no `zIndex` of its own.
- It positions itself through the same `overlay/dropdown-placement` every other anchored surface uses, with `side="right"`. With no room to the right it flips to the left of the row on its own — there is no second positioner.

**On native** it is an inline disclosure: the trigger expands its content in place, under the row, and the chevron swaps between down and up. react-native-reusables renders it the same way there, and a menu on native is a bottom sheet — there is nowhere for a flyout to fly to.

In a platform popup (OxyOS) the keys reach the same disclosure through the adapter (`floating/popup-navigation.tsx`), as the web flyout's do: <kbd>→</kbd> on the sub trigger opens it and makes its first enabled row active (on one already open, moves into it); <kbd>←</kbd> inside it, or <kbd>Esc</kbd>, closes it and makes the trigger active again; <kbd>Esc</kbd> outside a submenu closes the menu. Pinned by `PlatformSurfacePopup.test.tsx`.

`DropdownMenuSubContent` accepts `side="left" | "right"`, `align`, `sideOffset`, `alignOffset`, `minWidth`, `maxWidth`, `className`, `style`, `label` and `testID`. Web applies the geometry to the flyout and still fit-flip-clamps it; native keeps the same API, forwards identity and styling to the inline disclosure, and ignores flyout-only placement.

The split is a build-time one, not a `Platform.OS` branch: `floating/menu-sub-flyout.tsx` and `floating/menu-sub-inline.tsx` are passed to `createMenuRows` by each family's own platform fork, so the web-only `FloatingPanel` never reaches a native bundle.

Verified in a real browser by `scripts/verify-submenu-flyout.mjs` — jest can see none of it.

## Placement (web)

`DropdownMenuContent` takes `side` (`'top' | 'bottom'`, default `'bottom'`), `align` (`'start' | 'center' | 'end'`, default `'start'`), `sideOffset` and `alignOffset` — the same four Radix takes. They are preferences: the surface flips to the other side when the named one does not fit and clamps into the viewport when neither does. Opened from inside an `AppShell` panel, it collides with that panel while it fits there (see [Popover › Inside a panel](./popover.mdx)).

`side` also accepts `'left'` and `'right'`, which make the horizontal axis the one that fits, flips and clamps, and `align` the vertical one. That is how the sub-panel positions itself; a root dropdown has no use for it.

On native these are ignored. The menu is a bottom sheet, which is anchored to the screen rather than to the trigger.

An open menu follows its trigger as the page scrolls, at one measurement per animation frame and no re-render when nothing moved — the same panel behaviour every anchored surface gets, described under [Popover → Following the anchor](/docs/bloom/main/popover).

## Naming a row that is not a plain string

A row whose child is a string names itself. A row composed of elements does not:

```tsx
<DropdownMenuItem accessibilityLabel="Profile">
  <UserIcon />
  <Text>Profile</Text>
</DropdownMenuItem>
```

Without it a screen reader announces the row as nothing. This is where the upstream primitive's `textValue` lands — spelled `accessibilityLabel` because in Bloom that is all it does.

## Screen-reader focus

On NATIVE, opening a menu moves the VoiceOver/TalkBack cursor into the sheet, and closing it returns the cursor to the trigger. Both are automatic for every Bloom surface that presents through a sheet — menus, context menus, the menubar, popovers and select — and neither needs any wiring at the call site.

They are a pair on purpose. Moving the cursor in without giving it back strands it on the root view after the surface unmounts, which is worse than never moving it.

The platform's own dismiss gesture works too: a two-finger Z scrub under VoiceOver, a back gesture under TalkBack. Android's hardware back already closed these, since every Bloom sheet is an RN `<Modal>`.

On WEB none of this applies — the browser owns focus and the hooks return early rather than calling an API that is a no-op there.

## Rows are className-first

Every row is one pressable node built from Bloom's `styled()` primitives, shared by all three menu families through `floating/shared.tsx` — so the disabled treatment, the destructive colour, the pointer highlight and the ARIA state stay in one place and a fix lands in every menu at once.

`appearance/control-geometry.ts` owns the size recipes; `floating/constants.ts` owns shared chrome. Rows resolve their size through BloomScope, including across portals. Normal md uses 28px rows and 14/20 regular labels; section labels use 12/16 medium and shortcuts use the caption ramp. Native and coarse-pointer web keep at least 44px targets; a desktop window on native (a platform reporting the `window` capability, an OxyOS window) is pointer-driven and takes the compact rows, as fine-pointer web does (`styles/pointer.ts` `useTouchInput`). Typography is applied as TYPE_SCALE + Inter by `floating/menu-type.ts`; caller text classes retain precedence.

Every part takes a `className` and APPENDS it to its own, so a layout class cannot strip the chrome. Two utilities for one property are then resolved by Tailwind's own emission order, exactly as in any shadcn consumer; `style` remains the unambiguous override.

**A web consumer must have the Tailwind/NativeWind pipeline wired and `@source`-scanning `@oxy.so/bloom/lib`.** That was always required; without it the rows keep their colours (inline, below) but lose every piece of geometry.

## Look

The panel and rows share one menu recipe, used by `DropdownMenu`, `ContextMenu`, `Menubar` and the select list:

- **Panel** (web) — 266px minimum width, sized to its rows above it (a sub-panel too; `minWidth` / `maxWidth` set the range), 6px inset (8px touch), 16px corner, 1px `neutral-200` hairline, card surface, `shadow-dropdown`, a 2px inter-row gap at md. It opens and closes on a 150ms `ease-out` fade + `scale-95` + 2px blur, with no slide. A popover keeps its own panel and motion (`FloatingPanel`'s `surface` prop).
- **Row** — 28px at normal md (8px horizontal/4px vertical inset, 8px gap, 10px corner), 14/20 regular `text-primary`. Hover, keyboard focus (`:focus-visible` only — a mouse press does not leave a row painted) and a CHECKED checkbox or radio row share the `neutral-100` wash, on a 150ms colour transition (web). Destructive rows are `red-500` (`red-400` dark); disabled rows are `text-disabled` with a not-allowed cursor.
- **Label** — 8px horizontal inset, 12/16 medium in `text-secondary`, 4px above and below.
- **Separator** — a full-bleed 1px `neutral-200` rule with 4px total vertical separation per side (margin plus row gap).
- **Check, shortcut, sub chevron** — `text-secondary`, Remix glyphs at 16px: `RiCheckLine`, `RiArrowRightSLine` (web flyout), `RiArrowDownSLine` / `RiArrowUpSLine` (native disclosure).
- **Material and themes** — shared Surface paint uses the menu fill composited against the actual parent, including its sheen, rim and backdrop treatment. Semantic foreground, disabled, border and highlight colours follow the active theme; density does not replace the material.

These colours come from the theme through `button/shared.ts`'s ramps (`floating/menu-palette.ts`) and are applied INLINE, since the ramp stops exist as no CSS variable. A caller's `style` still overrides them; a `className` on a label or shortcut drops the inline colour so a `text-*` utility applies. The leading slot no longer dims its icon — pass the glyph in `text-secondary`.

## Size and viewport ownership

Action rows inherit the app's `BloomScope size` through portals and submenus;
`DropdownMenuContent size` optionally overrides the local subtree. Normal `md`
rows are 28px on desktop; xs/sm/lg are 24/26/32px. Native and coarse-pointer rows
keep a 44px minimum target. Context menus and menubars use the same recipe.

The floating base owns scrolling and the Bloom scrollbar, including flyouts.
An optional `maxHeight` on Content lowers its viewport ceiling; every panel is
bounded by the window. Do not add a consumer scroll container around menu rows.
Surface paint and panel/row radii are unchanged.

### Navigation rows

`DropdownMenuItem`, `ContextMenuItem` and `MenubarItem` share `href?: string`.
Web rows render a real anchor with menu-item semantics. With `onPress`, only an
ordinary unmodified activation is intercepted for a router; modified clicks keep
the browser's new-tab/window behavior and leave the menu open. Disabled rows have
no destination. Enter follows the anchor's native activation; Space uses the shared
menu keyboard engine. Native rows open `href` through `Linking` when no callback is
supplied. Use the row directly, rather than nesting a link inside another action.


## Hover navigation with a primary action

Set `activation="hover"` for a pointer/focus preview using the same menu engine,
Surface, scrolling, roving keys and dismissal. Defaults are 400ms open intent and
150ms close intent (`openDelay`/`closeDelay`). Moving into the panel or focusing a
row keeps it open. Touch hover is ignored; long press opens the same menu on touch web or its usual
sheet on native. With no primary action, ordinary press also opens the menu.

A trigger child with `href` or `onPress` retains that primary action; ArrowDown
and ArrowUp enter navigation. `pressTrigger={<PopoverTrigger asChild />}` composes
an independent primary popup around the same Button after menu handlers, without
nesting interactive controls. Primary activation cancels pending/open hover and
its open popup suppresses further hover. Escape returns focus without restarting
the dismissed preview. Default click activation is unchanged.

Keyboard opening retains its requested first/last row while lazy content loads;
arrival of an enabled row completes focus, and dismissal cancels the wait. Entering
with arrows also cancels a pending pointer-leave close.

All shared menu items accept `current` for a current navigation destination. It
uses existing selected-row paint and sets `aria-current="page"` on the real host;
combine it with `href` for native and web navigation.

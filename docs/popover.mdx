# Popover

A small surface of arbitrary content, anchored to what opened it. An anchored panel on web, a bottom sheet on native.

Three structural parts, shadcn's own — `Popover`, `PopoverTrigger`, `PopoverContent` — plus the panel parts every floating surface repeats: `PopoverHeader`, `PopoverTitle`, `PopoverDescription`, `PopoverFooter` and `PopoverSeparator`.

Reach for it when the content is not a list of actions. When it IS a list of actions, reach for [DropdownMenu](/docs/bloom/main/dropdown-menu) — it gives you the rows, the keyboard state and the ARIA roles for free.

## Basic

```tsx
import {
  Popover,
  PopoverContent,
  PopoverDescription,
  PopoverHeader,
  PopoverTitle,
  PopoverTrigger,
} from '@oxy.so/bloom/popover';
import { Button } from '@oxy.so/bloom/button';

<Popover>
  <PopoverTrigger asChild label="What is this?">
    <Button  tone="neutral" appearance="outline">What is this?</Button>
  </PopoverTrigger>

  <PopoverContent label="Two-factor authentication" align="start">
    <PopoverHeader>
      <PopoverTitle>Two-factor authentication</PopoverTitle>
      <PopoverDescription numberOfLines={0}>
        A second step when you sign in, so a leaked password is not enough on its own.
      </PopoverDescription>
    </PopoverHeader>
  </PopoverContent>
</Popover>
```

## The panel

`PopoverContent` is Bloom's floating surface — the one every menu, picker and account panel shares:

| | |
| --- | --- |
| width | `266` (`w-[266px]`), capped at the viewport minus 32 |
| height | At most the viewport minus 16, optionally reduced by `maxHeight`; placement keeps 8px from viewport edges |
| corner | `16` (`rounded-2xl`) |
| border | 1px semantic menu border plus the shared Surface rim |
| surface | Shared Surface material over the resolved menu fill and actual parent backing; light/dark colours follow the theme |
| inset | `6` on desktop; `8` on native or coarse-pointer web |
| elevation | `shadow-dropdown` |
| motion | 150ms `ease-out`: fade + `scale-95` + 2px blur, in and out, from the corner nearest the trigger |
| offset | `8` from the trigger |

The colours come from the same theme ramps as `Button` and the menus (`floating/menu-palette.ts`), in light and dark. Popovers have no close button or arrow.

## Panel parts

| Part | Classes | Use |
| --- | --- | --- |
| `PopoverHeader` | `flex items-center gap-2 px-2 pt-1` | A heading row; `leading` takes an avatar or icon beside the text column |
| `PopoverTitle` | `text-body-medium text-text-primary` | `tone="secondary"` is the group-label colour ("Users with access") |
| `PopoverDescription` | `text-body-regular text-text-secondary` | One line by default; `numberOfLines={0}` for prose |
| `PopoverFooter` | `flex items-center gap-3 px-2 pb-2` | Actions with their own 8px inset inside the surface |
| `PopoverSeparator` | negative surface inset, 4px vertical margin, 1px rule | Full-bleed rule between sections |

Header and footer inset their content by 8px inside the surface. Separators use the same surface inset and 4px total vertical separation per side (margin plus row gap).

## The inset: row lists and prose share it

Put `PopoverItem` directly in a mixed action/form panel. Its inherited menu recipe supplies row spacing, typography and the 10px corner. Prose uses the header/description parts. `FloatingPanel` supplies the single bounded ScrollArea; consumers do not add a wrapper to create popup scrolling.

## Overriding the panel

Every default is resolved INLINE, before the caller's `style`, so `style` overrides any of it:

```tsx
<PopoverContent label="Event details" side="right" style={{ width: 302, borderRadius: 20 }}>
```

`className` works too, and this is the part worth knowing. On web an inline style outranks every class, so an inline default would silently beat a caller's `w-[200px]`. `PopoverContent` reads which chrome properties the caller's utilities name — width (`w-*`, `size-*`), `max-w-*`, padding (`p-*`, `px-*`, …), `rounded-*`, border width (`border`, `border-0`, `border-x-2`), border colour (`border-red-500`), `bg-*`, `shadow-*`, `overflow-*`, through `md:`/`dark:` variants and `!` — and leaves THAT default out, so the class is the only rule for it.

Padding and margin are read PER SIDE, because the utilities are: `px-4` claims the left and right and says nothing about the top, so a `pt-*` default stays. The **panel parts** (`PopoverHeader`, `PopoverTitle`, `PopoverDescription`, `PopoverFooter`, `PopoverSeparator`) use the same scan, so `<PopoverSeparator className="bg-red-500" />` paints red and `<PopoverTitle className="mt-1">` keeps its colour.

```tsx
<PopoverContent label="More actions" className="w-[200px] p-2">
```

Panel classes still apply to the outer surface. The shared ScrollArea owns child flow and the inherited row gap; use an explicit `style={{ gap: ... }}` only when mixed content genuinely needs a different rhythm. That gap is forwarded to the scroll content. A gap utility on the outer surface does not space its grandchildren.

A padding override from `style` may use the shorthand (`padding: 0`) — the defaults are longhands, and an inline shorthand still replaces them.

## Controlled

```tsx
const [open, setOpen] = useState(false);

<Popover open={open} onOpenChange={setOpen}>
```

Uncontrolled by default. `onOpenChange` fires either way. Closing it from inside its own content is a `setOpen(false)`.

## Placement (web)

`PopoverContent` takes `side` (`'top' | 'bottom' | 'left' | 'right'`, default `'bottom'`), `align` (`'start' | 'center' | 'end'`, default `'center'`), `sideOffset` (default `8`, the panel's own `offset={8}`), `alignOffset`, `minWidth` and `maxWidth`. The surface flips to the other side when the named one does not fit and clamps into the viewport when neither does.

A popover centres on its trigger by default, where a menu starts at its left edge — that is the one placement default the two families disagree on, and it matches shadcn.

A numeric `maxWidth` prop replaces the viewport cap.

## Following the anchor (web)

## Inside a panel

A surface opened from a trigger that lives in an `AppShell` panel is fitted, flipped and clamped against **that panel** while it fits there, so a menu opened at a panel's edge no longer hangs over the neighbouring panel. When it does not fit — the panel is narrower or shorter than the surface plus its 8px gutters — it falls back to the viewport rather than being squeezed. A panel that runs past the screen, or is scrolled partly off it, counts only for the part the reader can see. The surface is still portaled to the document, so a panel's `overflow` cannot clip it; only the box it collides with changes. Nothing is passed per call: `DropdownMenu`, `ContextMenu`, `Menubar`, `Select`, `Popover` and submenus all inherit it, and outside a panel (or inside a `Dialog`) the viewport is used exactly as before.

An open panel tracks its trigger. Bloom listens for `scroll` in the CAPTURE phase, which is the only listener that hears a scroll inside an ancestor — a panel opened from a row of a scrolling list stays on its row — plus `resize`, because the viewport is what the surface flips and clamps against.

What it does NOT do is work per event. A scroll gesture dispatches a stream of events and nested scrollers dispatch one each, while the browser paints once; so the measurement is coalesced to at most one pass per animation frame, and the frame boundary is the last moment before the paint, which makes it the most recent position the panel can be given. A pass that resolves to the box the surface already holds is dropped rather than stored: the anchor and the placement keep their identity, nothing re-renders, and the listeners — registered once when the panel opens — are not detached and re-attached. Opening still measures synchronously in a layout effect, so the first painted frame is already in the right place.

This is `FloatingPanel`'s behaviour, so it is every menu, popover and select's; `Tooltip` follows its trigger every frame instead, for the reason its own page gives. The cost model is pinned by `src/__tests__/floating-anchor-cost.test.tsx`, which counts measurements, commits and listener registrations in a real DOM.

## Native

The popover is a bottom sheet on native: a phone has no room to float a panel beside a control, and every Bloom overlay resolving to the same sheet is what makes the native surfaces feel like one system. The sheet is the chrome (its surface, corner and drag handle), so the placement props are ignored and only the body takes the panel geometry — an 8px inset on the sides and bottom, below the handle's clearance — so the panel parts line up exactly as they do on web. `className`, `style` and `testID` land on that body.

## `asChild` and `disabled`

`disabled` on an `asChild` trigger keeps the panel closed whatever element the caller passed. The guard lives in `floating/TriggerSlot`'s `cloneTrigger`, not in the child: a child that forwards `onPress` but has no notion of `disabled` would otherwise still open the panel. The browser is the weaker instrument here — a real `Pressable` child swallows its own press and hides a missing guard — which is why the `Base/Popover` `AsChildDisabled` story carries a forwarding control, gated by `scripts/verify-trigger-disabled.mjs` and `src/__tests__/PopoverTriggerDisabled.test.tsx`.

## Dismissal

Press outside or hit Escape. `dismissible={false}` turns both off, for a popover the user has to answer.

Escape stops at the innermost open surface, so a popover opened from inside a dialog closes the popover and leaves the dialog up.

By default the outside press is caught by a transparent backdrop (it closes the popover and goes no further), so a popover opened inside a dialog cannot dismiss the dialog with the same click.

`<Popover modal={false}>` lays down no backdrop: the outside press still closes the popover, and it also reaches whatever is under it. Use it for a panel that sits beside a control the user keeps working in — an @-mention picker under a text field, where a backdrop made the first click in the field only close the picker. It is the same option `Menubar` and `HoverCard` use. Web only: the native popover is a bottom sheet, which is always modal.

## The panel publishes its surface

`FloatingPanel` — the surface behind every menu, popover, select and tooltip —
wraps its children in `SurfaceLevelProvider level={1}`
([Styles → Ambient level](/docs/bloom/main/styles)). A `TextField` inside used to
step off the PAGE and land on exactly the panel's own fill (1.000:1, no shell).

## Flat content surface

`PopoverContent material="flat"` omits the floating panel's optical tint, sheen,
rim and refraction. Its authored `style.backgroundColor` paints directly and is
published as the descendant surface backing. On native the owning bottom sheet
uses the same flat fill. Padding, radius, shadow and keyboard/placement behavior
are unchanged; the default `material="surface"` preserves the standard treatment.

On web, closing with Escape or an action inside the panel returns focus to its trigger without scrolling. Focus deliberately moved to another control is preserved. This also applies when the caller conditionally unmounts `PopoverContent` on close; the native sheet retains its existing focus lifecycle.

## Mixed action and form panels

`PopoverItem` composes an action row from the same recipe as menu rows, with a
button role appropriate inside a dialog. It takes `title`, `leading`, `trailing`,
`disabled`, `destructive` and `onPress`; it inherits `BloomScope` and never closes
the panel automatically. This supports an anchored panel that switches between
actions, a rename field and settings without custom row geometry.

`PopoverContent` inherits the application size (normally `md`); `size` is an
optional local override. Its shared floating base owns the scroll viewport and
Bloom scrollbar, caps the panel to the window and accepts an optional numeric
`maxHeight`. Consumers render their content directly and must not add a nested
ScrollView just to bound the popup. Native content retains the sheet's scroll
owner. The panel keeps Surface material and its existing rounded shape.

# Bloom data

`packages/bloom-data` (`@oxy.so/bloom-data`, public, released like the other
packages here when its version changes on `main`) is the data and state layer of the [Bloom language](./bloom-language.mdx).
It replaces an app's separate caches (a SQLite table, query pages and snapshot
maps) with one model, the way SwiftUI pairs `@Observable` with SwiftData. It
adds no dependency: React is its only peer, and the SQLite copy uses the
`expo-sqlite` database the app passes in.

## The parts

| Part | SwiftUI and SwiftData | What it is |
|---|---|---|
| `entity` | `@Model` | Records of one type, by id, in memory. |
| `list` | a sorted `@Query` result | Ordered ids into an entity, per key, plus what the source keeps beside them. |
| `source` | the fetching half of `@Query` | Fills a list (paged) or a record from the server. |
| `action` | a mutation | An optimistic change, the server call, then settle or roll back. |
| `realtime` | | Writes a socket's events into the same records. |
| `useEntity`, `useList`, `useRecord`, `useListState` | `@Observable` reads | Read them, re-rendering only for what changed. |

```ts
import { action, entity, list, realtime, source } from '@oxy.so/bloom-data';

export const User = entity<PostUser>('user', { id: (u) => u.id, persist: true });

export const Post: Entity<HydratedPost> = entity<HydratedPost>('post', {
  id: (p) => p.id,
  refs: { user: User, quotedPost: () => Post, 'boost.originalPost': () => Post },
  viewerFields: ['viewerState'],
  persist: { version: 17 },
});

export const Feed = list('feed', { of: Post, persist: true });

export const feed = source(Feed, {
  key: (type: FeedType) => type,
  load: ({ cursor, signal }, type) => api.get(`/feeds/${type}`, { params: { cursor }, signal }),
});

export const like = action({
  key: (id: string) => `like:${id}`,
  optimistic: (id) =>
    Post.patch(id, (p) => ({
      viewerState: { isLiked: true },
      engagement: { likes: p.engagement.likes + 1 },
    })),
  run: (id) => api.post(`/posts/${id}/like`),
  settle: (result, id) => Post.merge(id, result.post),
});

realtime(socket, {
  'post:engagement': (e) => Post.merge(e.postId, { engagement: e.counts }),
});
```

```tsx
function Home() {
  const view = useList(feed, 'for_you'); // ids, state, more(), refresh()
  return <List data={view.ids} renderItem={({ item }) => <PostRow id={item} />} />;
}

function PostActions({ id }: { id: string }) {
  const post = useEntity(Post, id); // re-renders when engagement.likes or viewerState.isLiked changes
  return <LikeButton count={post?.engagement.likes} active={post?.viewerState.isLiked} />;
}
```

Differences from the design proposal, each with its reason:

- A ref to the entity being defined is a function (`() => Post`), and that
  entity needs its type written out. JavaScript cannot read `Post` inside its
  own initializer.
- `load` receives `{ cursor, signal, current }` first and the arguments after
  it. Cancellation needs the signal, and the arguments are variadic, so
  nothing could follow them.
- A list is stored as one row of ordered ids, not one row per position. A page
  append then rewrites one row.
- `model()` (one record for app and UI state) is not built yet. It is
  `entity` with a single id, and nothing has needed it so far.
- Reads at boot have one synchronous form (`list.loadNow`), for the first
  frame of a cold start; see [The boot read](#the-boot-read).

## Entities

Records are plain JSON-shaped data and are never mutated. A write builds a new
value and shares every unchanged part with the old one (structural sharing), so
an equal answer from the server changes nothing and wakes nobody.

- `put(records, { anonymous })` stores records as the server sent them.
  `anonymous` marks a payload hydrated for no viewer (a broadcast); the
  entity's `viewerFields` are then kept from the copy already held.
- `merge(id, partial)` merges plain objects key by key. `patch(id, fn)` merges
  a partial computed from the current record. `update(id, fn)` replaces it
  (`null` removes it).
- `remove(id)` removes the record from memory, disk and every list of its
  entity. A list's `dropFromExtra` removes it from what the list keeps beside
  its ids.
- `refs` normalise embedded records. On write, the embedded record goes to its
  own entity and the field keeps its id. On read, it resolves again. One copy
  serves every record that embeds it, and `referencing(target, id)` finds the
  records that embed one.
- `combine(incoming, held)` decides how an incoming record joins the one held
  (the server's copy, never an optimistic layer). Returning `held` refuses a
  payload that is worse than what is held, such as one that lost an embedded
  record; returning a merge keeps what a sparse payload does not carry.
- `onStore(records)` is told about every record a write stored, whichever path
  wrote it.
- A page can carry `related` records: stored, not listed (slice posts, say).
- `get(id)` returns a plain object with its refs resolved, cached until a
  dependency changes. Use it outside render. Use the hooks in render.

## Field-level subscriptions

This is the one clever piece, and it follows one rule: record what a reader
reads, two levels deep, and wake the reader when one of those paths changes.

`useEntity(Post, id)` returns a read-only proxy. Each property read is
recorded: `engagement.likes` for a nested field, `title` for a top-level one.
A ref resolves to a proxy over the referenced record, recorded under that
record. A top-level plain object comes back as a proxy of its own, so reading
`post.engagement` alone records only whether it is there.

A proxy's identity follows what was read through it: it is replaced exactly
when a path read through it changed. `memo`, `useMemo` and the React Compiler
therefore see a new value precisely when what they used changed. A child
handed `post.engagement` keeps the same object until a field it read changes.
Reads always see the current record, so the first read of a field returns its
current value. Values below the second level are returned as stored.

`useEntity(Post, id, select, isEqual)` is the selector form. It returns
`select(record)` and re-renders when that result changes.

Proxies support spread, `Object.keys` and `JSON.stringify`, and they refuse
writes. Do not pass one to `structuredClone`; use `Post.get(id)` there.

## Sources

A source has one state per store and key: `status`, `fetchStatus`
(`fetching` or `paused`), `error`, `failureCount`, `updatedAt` and `origin`
(`network` or `disk`). React Query's edge cases are carried over on purpose,
and each has a test in `src/__tests__/source.test.tsx`:

- One request per key at a time. A second caller joins the one in flight.
- `refresh` supersedes what is in flight, and the late answer of a superseded
  read is dropped. `more` joins a first page in flight and never appends to a
  list refreshed since it started. A repeated cursor ends paging.
- A failure retries with exponential backoff (1s, 2s, 4s, up to 30s; `retry`
  and `retryDelay` change it). The rows on screen stay through retries and
  errors.
- Offline, a read waits (`paused`) and resumes on reconnect. A retry also
  waits while the app is in the background.
- `stale` is an age in milliseconds (default 0) or a rule. Fresh data is not
  read again when a screen mounts; stale data is shown and then read again. A
  disk copy is always stale.
- Coming to the front and reconnecting read the stale keys that are on screen
  (`refetchOnFocus`, `refetchOnReconnect`).
- A key nobody observes leaves memory after `gcTime` (default 5 minutes). Its
  disk copy stays.

`useListState(list, key)` reads a held list without reading it from the
server. `useList(source, skip)` observes nothing until its arguments are known (the
signed-in account, say). A list source's `fold(current, extra, mode)` folds each page's `extra` into the
list's (`first` replaces it, `next` appends). A record source's `load` returns
the record, or `null` when the server says it is gone, which removes it.

Native apps report the device: `environment.setOnline(netInfo.isConnected !==
false)` and `environment.setFocused(appState === 'active')`. Web reads the
browser's events.

## Actions

`optimistic` runs first, and every entity write it makes becomes the call's
layer: concrete values held over the server's copy, not written into it.

- While the layer stands, server writes to the same fields (a feed refresh, a
  realtime echo) update the copy beneath it without moving what the reader
  sees. This replaces a hand-written echo guard for the call's duration.
- When `run` resolves, the layer is written into the server's copy (the server
  accepted it) and `settle` writes the server's own answer over it, in one
  notification.
- When `run` rejects, the layer goes. That is the rollback: the copy beneath
  is current, including anything realtime brought in the meantime.

A `key` makes the action exclusive: a second call with the same key, while the
first is in flight, resolves to `undefined` at once. Keys are shared by every
action, so a like and its undo can use one key.

## Realtime

`realtime(socket, handlers)` queues events as they arrive and applies them
after the next frame, in arrival order, with one notification. Each event goes
to the store that was in scope when it arrived. An event that arrived for an
account that has since been left is dropped.

## Persistence

`sqlitePersister(open)` from `@oxy.so/bloom-data/sqlite` keeps a durable copy
in one SQLite file. `open` returns expo-sqlite's database:
`SQLite.openDatabaseSync(name)` to allow the boot read below, or
`SQLite.openDatabaseAsync(name)` for the asynchronous API alone.

- Writes go out after the frame, in one transaction, from a queue of changed
  records and lists. Only the server's copy is written, never a layer still in
  flight. Upserts and deletes are multi-row statements.
- Reads happen when a screen opens (`useList` and `useRecord` read the disk
  copy while the network read runs, and concurrent reads of one list share
  one read) or at boot, never during render. Memory always wins over disk.
- A changed entity `persist.version` drops that type's rows when the file
  opens. Rows not written for 7 days are dropped with the first write.
- `createAccounts({ persister: (account) => ... })` opens one store, and one
  file, per account. `open(account)` closes the previous store at once: its
  queued writes still reach its own file, and anything that lands for it later
  is dropped.

### The boot read

`list.loadNow(key)` is the one synchronous read. It runs at boot, for the
screen the app opens on, before that screen's tree mounts. It opens the file,
reads the list with its records in one query, then the records those name (a
quoted or boosted post), and puts them in memory, so the first frame shows the
last session. It never runs during render. On a Pixel 8a it takes 6 to 9 ms for
a 20-post feed. Everything after it is asynchronous, on the same connection.

Why one synchronous read: each expo-sqlite asynchronous call is three or four
JS-to-native hops (prepare, execute, read, finalize), and each hop's promise
waits for a free turn of the JS thread. During startup that thread stalls for
200 to 650 ms at a time (measured with an event-loop lag sampler in a release
build). A cold start reading the home feed asynchronously therefore got its
first post from the network, about 5 s later than a synchronous read.
Cutting the statements per call (open is one script and one read, a list comes
back with its records in one query) took the queries themselves to 5 to
240 ms. But opening the file asynchronously still took 1.4 s, inside those
stalls. The sync read avoids every hop for the one read that decides the first
frame.

On the web, `indexedDbPersister(name)` from `@oxy.so/bloom-data/indexeddb`
keeps the copy in IndexedDB, one database per account (expo-sqlite on web
needs `SharedArrayBuffer`, and so COOP and COEP headers, which break popup
sign-in). IndexedDB has no synchronous API, so `list.loadNow` finds nothing
there; `hasIndexedDb()` says whether the runtime has it.

`createAccounts().forget(account)` closes an account's store and deletes its
copy (`Persister.destroy`): sign-out leaves nothing of the account behind.
`sqlitePersister(open, remove)` deletes the file with `remove`
(`() => SQLite.deleteDatabaseAsync(name)`); without it, it empties it.

## Stores, accounts and the server

A `Store` holds one account's data, or one server request's.
`<DataProvider store>` gives it to the hooks below. Code outside React (an
action, a handler, a source) acts on the store in scope: the one it captured
when it started, otherwise the active store. A store makes no timer, listener or
disk access until it is used, and the hooks pass React a server snapshot, so a
server render reads a request's own store and nothing else
(`src/__tests__/server.test.tsx`).

## Plan: the Oxy SDK on the same model

Mention's posts and feeds are on this store
(Mention `feat/bloom-data-posts`). Users, sessions and every SDK-owned list are
not yet. They live in `@oxy.so/services`, which peers on `@tanstack/react-query`,
both React Query persisters, `zustand` and AsyncStorage, so every app keeps
those in its tree whatever it does itself. The move is its own step:

1. **Publish `@oxy.so/bloom-data`**, or re-export it from
   `@oxy.so/bloom-language`, so the SDK can depend on it. Until then Mention pins
   a local pack.
2. **A `User` entity in the SDK.** `@oxy.so/services` exports
   `User = entity<User>('user', …)` and writes every user it fetches into it.
   Apps declare `refs: { user: User }` on their own entities, so one copy of
   each person serves every post, notification and profile. That retires
   Mention's `lib/actorCache.ts` and `stores/identityUpdates.ts`.
   - One guard comes first. A degraded user (the "unresolved author" placeholder
     an Oxy outage returns) must not replace a resolved one, and a sparse
     author must not strip the counts and relationship a profile read stored.
     That is the entity's `combine` rule.
3. **Sessions open stores.** The SDK's session epoch drives
   `createAccounts().open(account)`, in place of each app's account-switch
   boundary. A store per account replaces the SDK's own cache wipes.
4. **The SDK's queries and mutations move.** About 66 files in
   `packages/services/src` use React Query or zustand:
   - user and profile reads become record sources;
   - lists (followers, sessions, devices) become list sources;
   - writes become actions;
   - the zustand stores (follow state, assets, theme) become entities or
     `model()`, which is built then.
5. **Transport stays the SDK's.** Sources load through
   `oxyServices.createLinkedClient()`, and sockets authenticate per handshake
   with `getAccessToken()`, as today.
6. **Peers drop.** `@tanstack/react-query`, both persisters, `zustand` and
   AsyncStorage leave `@oxy.so/services`' peers when the last caller moves, then
   each app's manifest.

Each step ships on its own, with the SDK's gates and a consumer check in an
app. During each one, the old and new paths coexist only for the flows being
moved.

Where it stands: steps 2, 3 (Services writes every person it reads into
`User`) and 6 (the session opens the stores, `OxyProvider`'s `dataPersister`)
are on oxy `feat/services-bloom-data`, and Mention runs on the session's store
(Mention `feat/sdk-bloom-data`). Mention's identity overlay
(`stores/identityUpdates.ts`) stays: a feed answer hydrated before a profile
edit carries the old picture as a real value, and nothing in a post's author
says which copy is newer, so `combine` cannot refuse it. Retiring the overlay
needs a freshness mark on every embedded user (its `updatedAt`).

What step 4 needs here first, each found moving Services' reads:

- `useRecord(source, skip)`, as `useList` has: most SDK reads wait for the
  signed-in account (`enabled`).
- A record read by another key than its id (a profile by username), without a
  one-item list.
- `model()`: settings, plans, security activity and the like are one value per
  account, not records by id.
- An action's pending state for a screen (`isPending`, `error`) and for the
  "Syncing" indicator (`useMutationStatus` counts mutations in flight).
- A durable copy on web (today the SDK's caches live in `localStorage`), and a
  way to delete an account's file at sign-out (the SDK deletes the signed-out
  account's cache today).

Step 5 also removes `OxyProvider`'s `queryClient` and `accountQueries`: Alia,
Homiio, Inbox, Gemies, Atlas, Syra, Clarity and Nilo persist their own React
Query data through them, so each moves its data first or mounts its own
client.

## Gates

`bun run build`, `bun run typescript` and `bun run test` in
`packages/bloom-data`. CI runs them in the workspace package loop. The tests use
Node's built-in SQLite behind the same async interface.

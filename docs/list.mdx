# VirtualList

Bloom's list. On web it windows against the scroller of the Screen in front;
on native it is FlashList when the app installs it, `FlatList` otherwise. Same
props either way.

```tsx
import { VirtualList } from '@oxy.so/bloom/list';

<VirtualList
  data={posts}
  keyExtractor={(post) => post.id}
  estimatedItemSize={96}
  renderItem={({ item }) => <PostRow post={item} />}
  ListEmptyComponent={<Empty query={query} />}
  onEndReached={loadMore}
  onEndReachedThreshold={0.5}
/>
```

## Which prop decides what

| prop                    | decides                                              |
| ----------------------- | ----------------------------------------------------- |
| `data` / `renderItem`   | what is drawn                                         |
| `keyExtractor`          | identity across updates                               |
| `estimatedItemSize`     | how the scrollbar behaves before rows are measured    |
| `ListHeaderComponent` / `ListFooterComponent` / `ListEmptyComponent` | the slots |
| `ListHeaderComponentStyle` | the view around the header                         |
| `numColumns` / `overrideItemLayout` | a grid, and which items span it            |
| `stickyHeaderIndices`   | rows that stay pinned once scrolled past              |
| `onEndReached` / `onEndReachedThreshold` | pagination                           |
| `refreshing` / `onRefresh` | pull to refresh (native)                           |

## `estimatedItemSize` is why scrolling feels right or wrong

It is a hint, but a badly wrong one makes the scrollbar jump as real heights
replace the estimate. Estimate the **common** row, not the average of a bimodal
set: for a list that is mostly one-line rows with occasional images, the
one-line height is the better answer even though it is nowhere near the mean.

## `ListEmptyComponent` is the one to wire first

An unstyled empty list is indistinguishable from a list that failed to load.
The empty state should say which — "No results for *bloom*" is a different
message from "Couldn't load your feed".

## `onEndReached` can fire while a page is in flight

It fires once per approach to the end, not once per scroll event — but a second
approach can happen before the first request resolves. Guard on your own
loading flag; the list does not know what your fetch is doing.

Both platforms honour it with the same semantics. `onEndReachedThreshold` is in
viewports and defaults to 2, as `FlatList`. The end includes `ListFooterComponent`.
It re-arms when the user scrolls back out of range or the row count changes, so
a page that still leaves the end in range asks again. It never fires while `data`
is empty. On web an end marker after the footer is observed against the list's
scroller (below), so no footer sentinel of your own is needed.

```tsx
onEndReached={() => { if (!isFetching && hasMore) fetchNext(); }}
```

## Grids: `numColumns` and `overrideItemLayout`

`numColumns` lays the items out in that many equal columns, on every platform.
`overrideItemLayout` sets `layout.span`, how many columns an item takes, so a
full-width row (a header, an empty state) can sit inside the grid. An item that
does not fit the rest of its row starts the next one, as FlashList packs them.

```tsx
<VirtualList
  data={rows}
  numColumns={3}
  overrideItemLayout={(layout, row) => {
    if (row.kind !== 'cell') layout.span = 3;
  }}
  renderItem={renderRow}
/>
```

Native FlashList and web honour the span; the `FlatList` fallback gives every
item one column. On web the virtualizer windows whole rows, so
`estimatedItemSize` estimates a row. `FlatList` cannot change `numColumns` in place, so a new count
remounts it.

## Sticky rows: `stickyHeaderIndices`

The indices are into `data`; `ListHeaderComponent` is not counted. A sticky
row scrolls with the list until it reaches the top, then stays pinned until the
next sticky row takes its place. It pins **below** the header that overlaps the
list (`useHeaderDockInset()`), not underneath it, so no offset is passed.

| engine | how |
| ------ | --- |
| FlashList | its own sticky headers, with `stickyHeaderConfig.offset` set to the header inset |
| web | the last sticky row at or above the viewport stays mounted (TanStack's sticky pattern) and is laid out in flow at its own offset with `position: sticky`, so the browser pins it at the header inset; in a grid the row holding the item is pinned |
| `FlatList` | the indices are mapped onto its cells (the header, then grid rows); it pins at its own top edge, with no header clearance |

## Pull to refresh

`refreshing` and `onRefresh` are native. The list draws its own
`RefreshControl`: the spinner takes the theme's primary colour (`tintColor` on
iOS, `colors` on Android) and, under a Screen, rests below the header rather
than behind it. There is no `refreshControl` prop; a spinner that does not
follow the theme was the reason to pass one.

## `keyExtractor` is not optional in practice

Without stable keys, rows recycle onto the wrong data: a list that reorders
shows the previous row's content for a frame, and inputs inside rows keep the
wrong value. Use the entity's id, never the index.

## Web: the Screen in front decides the scroller

The list creates no scroll container. It reads the nearest `Screen`'s viewport:

| Screen                                         | the list scrolls             |
| ---------------------------------------------- | ---------------------------- |
| document flow (`documentScroll`, a document panel), or no Screen | the window |
| an element-kind panel's `Screen scroll="auto"` | that panel's own element     |

Rows, `scrollMargin`, `onEndReached` and the `ref` handle all follow that
scroller, so the same call site works in a full-page route and in a side panel,
and keeps working when a panel changes flow. There is no prop for it.

A screen that is not in front (`Screen active={false}`, a hidden panel) leaves
its list idle: its scroll owner and row observations detach while measured heights
stay in the layout model. Disabling the virtualizer would erase offscreen heights
and shift the reading position on return. Rows measured at `display: none` would move a scroller the reader
is still using elsewhere. The list's origin is re-read whenever its box could
have moved — shown again, or content above it grew — never from a box-less
wrapper. Returning to retained content or resizing the viewport preserves measured
row heights; it must not reset unchanged rows to `estimatedItemSize`. Row resize
observations update actual content changes. When a retained list changes between
document and panel scrolling, its measurement refs attach to the new virtualizer.
The adapter resolves the Screen scroll ref after commit, so a parent element that
attaches after child layout effects is still observed without an unrelated render.

`screen={{ active, restoration }}` binds the window to the Screen's chrome only
when no Screen viewport already does; a Screen that owns its viewport drives
the header and bar from it.

## Native: FlashList when installed

`@shopify/flash-list` (v2) is an optional peer. Install it and every native
`VirtualList` recycles its rows through FlashList; leave it out and the same
call sites render through `FlatList`. The props, the Screen binding (header and
bar insets, chrome motion, restoration) and the `ref` handle are identical, so
switching is an install, not a migration.

```sh
npx expo install @shopify/flash-list
```

## Scroller and tuning props

Each is honoured by the engine that understands it and accepted-but-ignored
elsewhere, so one call site type-checks on every platform:

| prop | honoured by |
| ---- | ----------- |
| `scrollbar` | native, as `ScrollArea`: `never` hides the system indicator, `always` keeps it on Android, iOS's indicator follows the theme. Web: the list scrolls its Screen's scroller, which owns the bar. There is no `showsVerticalScrollIndicator` |
| `keyboardShouldPersistTaps`, `keyboardDismissMode` | native (both engines); web has no list scroller to configure |
| `drawDistance`, `maxItemsInRecyclePool` | FlashList |
| `getItemType` | FlashList: rows of one type recycle into each other, so give each row shape its own |
| `maintainVisibleContentPosition` | FlashList (on by default; `false` turns it off) |
| `removeClippedSubviews`, `maxToRenderPerBatch`, `windowSize`, `initialNumToRender` | `FlatList` |
| `estimatedItemSize`, `overscan` | web |
| `recycleItems` | nothing; kept for `@legendapp/list` call sites |

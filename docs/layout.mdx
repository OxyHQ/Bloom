# Layout

The questions every floating surface and every piece of scroll-linked chrome has
to answer, answered once for all of them.

```tsx
import {
  EDGE_GAP,
  windowEdgeGap,
  useBottomEdgeInset,
  useClaimBottomEdge,
  useTopEdgeInset,
  useClaimTopEdge,
  ScrollOffsetProvider,
  useScrollOffset,
  ScreenScope,
} from '@oxy.so/bloom/layout';
```

## `windowEdgeGap` — how far from the edge

```tsx
const insets = useSafeAreaInsets();

windowEdgeGap(insets.bottom);      // 34pt iOS · 24dp Android · 16 web
windowEdgeGap(insets.bottom, 16);  // 50pt iOS · 40dp Android · 16 web
```

The safe-area inset is the band the platform has **reserved for its own
affordance** — the iOS home indicator, the Android gesture handle. A floating
surface clears it in full. `gap` is that surface's breathing room *on top of*
the band, never an allowance to spend inside it: a bigger `gap` floats the
surface further from the affordance, never closer.

`EDGE_GAP` (16) is the floor for every caller, so a device reporting a 4dp inset
never ends up tighter than a browser reporting none.

<Admonition kind="warning">
Anything laying out **around** a floating surface wants its total footprint, and
must get it from the surface — never by adding `insets.bottom` to a hardcoded
height. The inset is already folded into the gap, so adding it again
double-counts the home indicator and strands a band of dead space.
</Admonition>

## `useBottomEdgeInset` / `useClaimBottomEdge` — what is already there

Knowing where the edge is does not tell a FAB that a tab bar is already parked
on it. A surface that parks there **claims** its footprint; a surface that wants
to avoid it **reads** the total.

```tsx
// The surface that parks there — a floating tab bar.
useClaimBottomEdge(gap + barHeight);

// The surface that avoids it — Bloom's Fab does this for you.
const occupied = useBottomEdgeInset();
<View style={{ position: 'absolute', bottom: windowEdgeGap(insets.bottom) + occupied }} />
```

Neither imports the other, so any combination composes: a tab bar with no FAB, a
FAB with no tab bar, both, or a surface written later.

`BloomProvider` mounts the registry. Outside one, `useBottomEdgeInset()` returns
`0` and `useClaimBottomEdge` is a no-op, so a surface stays usable standalone.

## `useTopEdgeInset` / `useClaimTopEdge` — the same thing, one edge up

A header that participates in layout answers this by existing: the content
starts where the header ends, because they are siblings in a column. A header
that **overlays** content — [`PageHeader`](/docs/page-header)'s
`placement="overlay"`, where the page scrolls under translucent islands —
occupies no layout space at all, and the first item of the content lands
underneath it.

```tsx
// The chrome that parks there — PageHeader does this for you.
useClaimTopEdge(measuredHeight);

// The content that has to clear it.
<ScrollView contentContainerStyle={{ paddingTop: useTopEdgeInset() }}>
```

Same registry object as the bottom edge, so everything below about `max`,
about a nested provider and about the one-frame settle applies unchanged.

**The height is measured, not computed.** A subtitle, an enlarged font and a
notch all move it, and a constant plus the insets fails silently — the content
starts a few points under the islands and looks like a design decision.

**Apply the safe area once.** The header pads itself by `insets.top`, and the
claim already includes that padding. Adding `insets.top` again in the scroll
container double-counts the notch.

## `ScrollOffsetProvider` / `useScrollOffset` — which scroller

A screen has exactly one scroll owner, and the owner publishes its offset. Chrome
reads it. Neither imports the other, so two panels side by side — each with its
own header and its own scroller — resolve correctly, because the provider's
position in the tree is what pairs them.

```tsx
const scrollY = useSharedValue(0);
const onScroll = useAnimatedScrollHandler(
  { onScroll: (e) => { scrollY.value = e.contentOffset.y; } },
  [scrollY],
);

<ScrollOffsetProvider value={scrollY}>
  <PageHeader title="Inbox" />
  <Animated.ScrollView onScroll={onScroll} scrollEventThrottle={16}>…</Animated.ScrollView>
</ScrollOffsetProvider>
```

The context carries the **`SharedValue`**, not a number: it crosses once, at
mount, and every subsequent frame reaches the chrome on the UI thread through
`useAnimatedStyle`, with no React render. A context whose value changed per frame
would re-render every consumer per frame, which is precisely the cost this
avoids — the same reasoning as the section below.

Without it, chrome falls back to `window.scrollY` on web and to nothing on
native. That default is right for exactly one layout — a web page whose document
*is* the scroller — and silently wrong for a desktop panel and for every native
screen, with no error: the header simply never reacts.

## `ScreenScope` — a surface that is its own screen

The top edge and the scroll offset are per-SCREEN, and a modal, a sheet or a
detail panel is a second screen drawn over the first. Without a boundary both
contracts cross it, and neither failure has an error in it:

- A header inside a full-screen dialog claims the top edge of the page
  UNDERNEATH it. Claims combine with `max`, so the page behind is padded for
  chrome it does not have — and the padding appears and disappears with the
  modal, because the claim unregisters on unmount.
- Chrome inside the sheet reads the page's scroll offset and follows a scroller
  the user is not touching.

```tsx
<ScreenScope>
  <PageHeader title="Edit listing" onBack={close} />
  <ScrollView contentContainerStyle={{ paddingTop: useTopEdgeInset() }}>…</ScrollView>
</ScreenScope>
```

A fresh top-edge registry, a fresh bottom-edge registry and a `null` scroll
offset — the honest value, because nothing inside has said which scroller it owns
yet. A scroll owner INSIDE publishes in the ordinary way and wins, being nearer.

The bottom edge is scoped for the mirror reason, and it is the same point the
"modal surface should not read the registry" note below makes: a sheet is drawn
OVER the tab bar and the FAB, so a form inside it that cleared the tab bar would
end in a band of empty space.

**`DialogBody` and `BottomSheetBase` mount it**, so every Bloom dialog placement
and every bottom sheet is already a scope. Mount it yourself only around a
surface Bloom does not own.

## The collapse is not here, on purpose

The tab bar minimizes 58 → 44 on scroll. This registry twice tried to publish
that so a FAB could react — as a live pixel height, then as a boolean. Both felt
wrong on a device, for a structural reason rather than a tunable one:

> The bar animates on the **UI thread**. Anything reading it from this registry
> arrives via `runOnJS` plus two React render passes.

The reaction therefore *starts* one to three frames late, and the delay is
variable — worst exactly while scrolling, because that is when the JS thread is
busiest. Fading rather than moving does not hide it: the eye still sees two
pieces of chrome change at different moments.

A collapse is **motion**, and motion that must stay locked to a reanimated
animation has to travel as a shared value on the UI thread. React state is the
wrong transport for it at any width, so it is not offered here.

The **app** owns that signal. Mention drives its header, its tab bar and its FAB
from one `SharedValue` through `useAnimatedStyle`, and everything moves together
because nothing crosses a thread. This registry stays what it is good at:
**geometry** — where things are, not when they move.

## Things that are easy to get wrong

**Claims combine with `max`, not `sum`.** Every claim is measured from the same
window edge, so two surfaces there overlap rather than stack. Summing would
strand a reader at twice the height, floating mid-screen.

**A z-index cannot substitute for the offset.** A tab bar host is typically the
last sibling of the app shell, so it paints over every descendant no matter what
they claim. The FAB has to be somewhere *else*, not merely on top.

**A modal surface should not read the registry.** A detached `BottomSheet`
renders above the tab bar and covers it; offsetting it by a bar it is already
hiding would float it off the bottom of the screen for nothing.

**The registry settles one frame after mount.** A claim registers in an effect,
so a reader mounted in the same commit as its claimant reads `0` on the first
commit. These are layout offsets rather than measurements, so nothing here waits
on a real layout pass.

# Tab pager

Every place an app's navigation leads, declared once. From that one list Bloom
draws the pager (Home, Videos, Notifications, a profile side by side, swiped
between on native), the bottom bar with its highlight following the finger, and
— under an `AppShell` — the sidebar's rows, their selection, badges and the
compose action, at whichever width puts navigation where. The app writes no
bar, no sidebar items and no navigation handlers.

```tsx
// app/(app)/_layout.tsx — the provider sits above the AppShell, because the
// bar renders over pushed routes too
import { TabPagerProvider } from '@oxy.so/bloom/tab-pager/expo-router';
import type { AppDestination } from '@oxy.so/bloom/tab-pager';

const destinations: AppDestination[] = [
  { name: 'camera', href: '/camera', page: true }, // swiped to; no item anywhere
  { name: 'index', href: '/', bar: true, preload: true, label: 'Home', icon: RiHome5Line, activeIcon: RiHome5Fill },
  { name: 'explore', href: '/explore', label: 'Explore', icon: RiSearchLine }, // a sidebar row
  { name: 'notifications', href: '/notifications', bar: true, preload: true, label: 'Notifications', icon: RiNotification3Line, badge: unread },
  { name: 'you', href: '/you', bar: true, preload: true, label: 'Profile', icon: ProfileAvatar, onLongPress: openAccounts },
  { name: 'settings', href: '/settings', label: 'Settings', icon: RiSettings3Line, onPress: openSettings },
  { name: 'write', href: '/write', page: true },
];

<TabPagerProvider destinations={destinations}>
  <AppShell
    sidebar={{ logo, footer }} // the chrome around the rows, not the rows
    primaryAction={{ icon: RiQuillPenLine, label: 'Compose', onPress: () => selectTab('write') }}
    …
  />
</TabPagerProvider>
```

```tsx
// app/(app)/(tabs)/_layout.tsx — one route file per page name in this group
export { TabPagerLayout as default } from '@oxy.so/bloom/tab-pager/expo-router';
```

## Destinations

`AppDestination` is one place, in pager order for the pages and sidebar order
for the rows:

- **`name`** identifies it — for a page, the route's name in the tabs group —
  and **`href`** is its exact path, which is how a pathname is recognised as it.
- **`label`**, **`icon`** (a component, `RiHome5Line`, drawn at the bar's and the
  sidebar's own size and tint), **`activeIcon`** (the filled shape while
  selected) and **`badge`** (a count) are what the bar item and the sidebar row
  show.
- **`bar`** draws a bottom-bar item, and makes the destination a page.
  **`page`** makes it a page without one: reached by swiping or `selectTab`,
  the bar fading and sliding away while it is in front, its highlight parked
  on the nearest item.
- **`preload`** mounts a page ahead of a visit — as a neighbour of the page in
  front, and kept laid out while the bar can reach it — so neither a swipe nor a
  tap lands on a blank screen. Leave it off for a heavy page (a composer) or one
  that holds hardware (a camera): those mount when the reader lands on them.
- **`sidebar`** draws a sidebar row; it defaults to whether there is a label and
  an icon.
- **`onPress`** makes it an action rather than a place (Settings opening a
  dialog); **`onLongPress`** adds a second one (the account switcher on Profile).

Pressing a destination does the same thing wherever it is drawn: its `onPress`
if it is an action; a reselect if it is already in front — the screen in front
back to its top, and a reload once it is there (see [Screen](/docs/bloom/main/screen),
"Reselect"; the provider's `onReselect` replaces it); a page through the pager,
dismissing anything pushed over it; anything else by navigating to its `href`.
The drawer closes itself once a choice is made in it.

Labels, icons and badges may change as often as a count does: only the bar and
the sidebar re-render for them.

## The shell

Under a `TabPagerProvider`, `AppShell` composes its navigation from the
destinations:

- **Sidebar** (desktop, tablet, the drawer): `sidebar.items`, `selected` (the
  destination in front) and `onNavigate`; `primaryAction` becomes the compose
  row. `sidebar` carries only the chrome around them — logo, footer, modes.
- **Bottom bar** (where navigation is a drawer): the bar items, with
  `primaryAction` as its FAB.

What the app passes itself still wins — `sidebar.items`, or a `bottomBar`
(`null` for none on a route, such as over the keyboard or a full-screen
composer). `TabPagerBottomBar` is the same bar for an app that replaces the
shell's.

## `useTabPager()`

From `@oxy.so/bloom/tab-pager`, under a `TabPagerProvider`:

| Field | |
| --- | --- |
| `pages` | The destinations that are pages, in pager order. |
| `activePage` | The page in front, or `null` on a route pushed over the pages. |
| `selectTab(name)` | Bring a page to the front. A route pushed over the pages is dismissed first. |
| `leaveTab(from, to)` | Bring `to` to the front and forget `from`: neither Back nor the pager returns to it (a published composer). On web the browser entry is replaced. |
| `selectDestination(name)` | Press a destination, exactly as its bar item or sidebar row would. |
| `progress` | The highlight's position in bar-item units, on the UI thread. |
| `chromeProgress` | The bar's absence, 0 to 1, on the UI thread. |

`pages` on the provider (`TabPage`, with `bar: { label, icon }` elements) still
works and is deprecated: it declares pages only, so the sidebar draws nothing
from it.

## Native

`TabPagerLayout` is an expo-router tabs navigator (`useTabsWithTriggers`,
`backBehavior: 'history'`) whose pages render inside `react-native-pager-view` —
ViewPager2 on Android, `UIPageViewController` on iOS, the platform components
that arbitrate a drag between the pager and a child that also scrolls.

- **The finger drives the bar on the UI thread.** `onPageScroll` writes
  `progress` and `chromeProgress` from a worklet, interpolated between the two
  pages under the finger. Nothing else writes `progress` while the pager is
  mounted.
- **A tap transitions without travelling.** To the page next door it slides,
  exactly as a swipe would (that neighbour is laid out, and the finger's
  `onPageScroll` path drives the highlight). Further away it fades through,
  Material's bottom-navigation transition: the page in front fades out in 90ms,
  the pager cuts, and the destination fades in from 96% scale in 210ms, instead
  of an animated scroll through every page in between (unmounted and blank,
  ~680ms a tap on a Pixel 10 Pro). Reduced motion cuts.
- **Pages are admitted lazily.** The focused page renders first; preloading
  neighbours of the page the pager has come to rest on mount on the next frame,
  or at once when a drag starts.
- **Off-screen pages are cheap.** Each page is a `react-native-screens`
  `Screen`: the page in front is active, preloading bar pages and the resting
  page's neighbours stay laid out, and the rest are parked.
- **Expo routes are preloaded**, so every page has its route before its first
  visit.
- **Navigating does not re-render the tabs layout.** Its navigator hook
  (`useTabsWithTriggers`) is not memoized upstream (~36ms a render on a Pixel
  10 Pro), so the layout reads only what changes with the pages' structure; the
  page in front lives in a context of its own that only the bar and
  `useTabPager()` read.

`react-native-pager-view` is an **optional peer**. Without it the same pages
switch by tap only, and a dev warning names the package.

## Web

`TabPagerLayout` renders the route in place (`<Slot/>`): the web shell scrolls
the document, which side-by-side viewport-height pages cannot coexist with. The
provider still moves the highlight the moment the reader presses, navigates by
`href`, and prefetches every page's route chunk up front. The pager package
never enters a web bundle.

## The bar's presence

`chromeProgress` settles on the route in front whenever a route lands, whoever
moved it there: a route pushed over a page without a bar item (a post opened
from the camera) is not that page, and keeps the bar. `TabPagerBottomBar`
passes it to `BottomBar`'s `hideProgress`, which fades and slides the bar off
its edge and, past halfway, removes it from hit testing and the accessibility
tree.

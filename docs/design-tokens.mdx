# Design Tokens

`@oxy.so/bloom/design-tokens` ships the **Oxy Unified Design Language**: the
spacing, radius, border, type and shadow scales, the colour roles, and the
resolved token values behind them. Bloom has no Tailwind preset or theme
stylesheet ([Bloom without NativeWind](./no-nativewind.mdx)): a component reads
the scales from `@oxy.so/bloom/styles` and its colours with `useColorTokens()` /
`createTokenStyles()` from `@oxy.so/bloom/theme`, and the Bloom language names
every token as a modifier.

Color roles are aliases onto Bloom's resolved theme tokens (`--background`,
`--surface`, `--primary`, …), so they follow the active light/dark mode and
color preset automatically.

## Preset recipes and runtime colour

Bloom ships **65 named recipes**, authored once in the type-checked
`COLOR_PRESET_REGISTRY`. A recipe is not a frozen light/dark token table: it is
an identity seed, a scheme variant and optionally explicit secondary/tertiary
seeds. `BloomThemeProvider`, `getResolvedTokens()` and `BloomColorScope` run
those seeds through the same colour policy for the active mode and scope.
Arbitrary consumer seeds remain supported through `buildThemeFromSeed()` and
`BloomSeedScope`; the named catalog is a set of useful starting points, not the
limit of the dynamic engine.

An arbitrary seed costs once per process. `buildThemeFromSeed()` and
`buildSeedScopeVars()` keep what they solved (bounded, 128 entries each), so a
second `BloomColorScope` with the same seed, or one re-rendering under a new
parent theme, reads the same frozen theme; a scope's `tokens` count by value, so
an inline `tokens={{ … }}` does not resolve the scope again on every render. The
first solve is the accent search (`deriveAccentHues`: the most vivid tone of ~50
hues, 63 gamut solves each); a named preset reads its accent hues from a
generated table instead. On Hermes a cold seed took 43 ms before the solver kept
each luminance's cut of the RGB cube and stopped building CAM16 colours nobody
read, 26 ms after (one seed, dark, best of six on the same machine); the OxyOS
shell's first full render, which mounts such a scope, went from 117 to 89 ms of
JavaScript.

```ts
import {
  COLOR_PRESET_REGISTRY,
  COLOR_PRESET_FAMILY_REGISTRY,
  COLOR_PRESET_GROUPS,
} from '@oxy.so/bloom';

const cobalt = COLOR_PRESET_REGISTRY.find((recipe) => recipe.name === 'cobalt');
cobalt?.displayName;   // 'Cobalt + Signal Yellow'
cobalt?.family;        // 'ocean'
cobalt?.tertiaryHex;   // '#ffd000'

COLOR_PRESET_FAMILY_REGISTRY[0].displayName; // stable family copy and order
COLOR_PRESET_GROUPS.ocean.presets;            // ordered recipes for a picker
```

The 47 `pairing: 'curated'` recipes pin an intentional action seed. The first 16
pin `tertiaryHex`; 30 more are complete three-seed combinations and pin
both `secondaryHex` support and `tertiaryHex` action. Identity remains
`--primary`, support resolves through `--secondary`, and the standout action is
`--tertiary`, which is the role used by FABs and compose actions. The other 17
recipes derive both accent families dynamically.

The `oxy` brand recipe goes one step further: it carries a
hand-authored `tokens` scheme per mode (`#rrggbb` keyed by canonical token)
taken from the brand's own drawn palette. Those values win over the engine for
the tokens they name — the accent fills and their labels verbatim, and the
surface ladder (page, surface, popover, muted, card) in the scheme's own hue and
chroma but on Bloom's four-tone ramp. Everything they leave out stays derived on
purpose: text roles, borders, subtle tints, status fills and charts are what the
policy holds at AA on that ladder, and a scheme drawn for shallower surfaces
does not. An app-wide `secondaryColor`/`tertiaryColor` override still replaces
the authored accent it pins. Every recipe exposes
`displayName`, `description`, `family`, `pairing` and `featured` metadata, so
consumer pickers do not need a second name/category map. Historical
`APP_COLOR_PRESETS`, name arrays, hex lookup and access-gate arrays are derived
from this registry and retain their existing public shapes.

For visual review, run Storybook and open **Theme / Color System Playground**
(`src/theme/ColorSystemLab.stories.tsx`). It keeps signed-in and public Mention
views, renders both modes from `getResolvedTokens()`, and filters the complete
registry by family or curated/derived pairing.

## Apps still using `className`

For apps still using `className` (removed once the fleet has migrated), Bloom
keeps two generated token outputs: `@oxy.so/bloom/design-tokens/theme.css`, the
Tailwind v4 `@theme` block (`--color-<role>: var(--canonical)`, spacing, radius,
type and shadow), and `@oxy.so/bloom/tailwind-preset`, the same vocabulary as a
JS preset. Import the CSS after Tailwind; never paste the tokens into the app:

```css
@import "@oxy.so/bloom/design-tokens/theme.css";
```

They come from the same scales and roles as Bloom's own styles. Bloom itself
styles without them.

## Outside a component

### The pre-JS palette (prerendered apps)

`BloomThemeProvider` writes the theme's tokens (`--background`, …) at startup.
Between first paint and hydration a prerendered page shows whatever palette its
own stylesheet declares, and a hand-written one is a second source of truth that
drifts from the preset it claims to mirror. Generate it instead, at build time:

```ts
import { getPresetVars, buildSeedScopeVars } from '@oxy.so/bloom/design-tokens';

// Document root.
getPresetVars('oxy', 'dark'); // { '--background': 'rgb(16 13 16)', … }

// A scoped block — a brand section, a forced-dark region — from one seed.
buildSeedScopeVars({ seed: '#7c5aed', mode: 'dark' });
```

When only the page colour is needed — a boot splash painted before the theme
resolves, often in the mode the device is NOT in — use `getPresetBackground`.
It returns exactly `getPresetVars(name, mode)['--background']` for one tone
solve, where the full set costs ~50 ms on a 4x-throttled mobile profile:

```ts
import { getPresetBackground } from '@oxy.so/bloom/preset-vars';

getPresetBackground('blue', 'dark'); // the same string getPresetVars('blue', 'dark') carries
```

A preset's own `hex` + `variant` reproduces `getPresetVars` token-for-token, so
the document root and a brand scope go through the same code path. Both
functions are pure — no react, no react-native — so a plain node/bun script can
import them.

### Consumers that are not browsers

A consumer that cannot run a stylesheet — native UI code, a design tool, a
codegen step — reads the resolved tokens as data instead. Bloom ships them in
W3C Design Tokens (DTCG) format, generated from the same colour engine, so the
JSON and the CSS cannot disagree:

```ts
import tokens from '@oxy.so/bloom/design-tokens/tokens.json';

tokens.color.oxy.dark.card.$value;    // '#3b323c' — the value of --card
tokens.color.teal.light.primary.$value; // '#1d6a75'
tokens.spacing['space-8'].$value;     // '8px'
tokens.typography.body.fontWeight.$value; // 400
```

The JSON is an interoperability artifact generated by `generate:tokens-json`,
not an editable source. Each preset group also carries a `so.oxy.bloom`
extension with its seed recipe and picker metadata (family, description,
pairing, featured and optional secondary/tertiary seeds). Keeping the authored
registry in TypeScript gives duplicate/shape checks and inferred identifier
types; generating JSON from it gives non-TypeScript tools the same data without
introducing a second catalog.

`color.<preset>.<scheme>.<token>` covers every preset Bloom ships and both
schemes. Token names are the CSS custom properties with the leading `--`
removed, so the mapping to `getPresetVars` output is mechanical. Values are
sRGB hex — `#rrggbb`, or `#rrggbbaa` for the translucent `-subtle` family.
Font families and shadows are deliberately absent: families resolve to
`var(--bloom-font-*)`, which is meaningless off the web, and shadows ship as a
platform-forked style object (`bloomShadowStyle`). If you need the same data in
memory rather than from the file, `bloomDesignTokens()` from
`@oxy.so/bloom/design-tokens` returns it.

### One quiet-text role, one colour

`text-text-tertiary` and `theme.colors.textTertiary` are the **same colour**:
`--muted-foreground`'s, the theme's one quiet-text colour. `textTertiary` has a
token of its own, `--faint-foreground` (`faintForeground` from
`useColorTokens()`), which every preset holds at that colour, so a component
can paint the tertiary text from the tokens. It differs only in
`mode="adaptive"` on Android and iOS, where the platform answers it with its
own tertiary label (Material You `outline`, iOS `tertiaryLabel`), as it answers
`textTertiary`.

They were not. The utility has always aliased `--muted-foreground` (8.42:1 light
/ 11.33:1 dark) while `theme.colors.textTertiary` read the engine's `outline`
(4.04:1 / 6.12:1) — one named role, two colours, and the JS one was **below AA
for body text in light**. The tie is broken toward the token, because a fixed
third grey cannot be a third rung: it is measured against one surface and used on
all of them. `neutral-400` is the same mistake one ramp over — it clears AA on
the page and measures 2.42:1 on a chart card.

**A genuinely quieter rung is asked for against the fill it lands on**, with
`surfaceTextOn(theme, fill).textTertiary` — see
[Styles](/docs/bloom/main/styles). That is what `chart-cards`,
`property-insights`, `media-header` and `text-field` now do.

Gates: `surface-levels.test.ts` (both spellings agree, and clear AA, over all 64
presets x 2 modes) and `surface-level-adoption.test.ts` (the families).

## Neutral surfaces and the label levels

`BloomThemeProvider surfaces` decides how the surfaces take the preset's colour
(`SurfaceTint`). `tinted` carries its hue through the page, the surface rungs,
the text and the boundaries. `neutral` draws them in greys of no hue at the
same tones, and drops an authored surface ladder (the Oxy preset's pink page
and aubergine dark), so the hue is left to the accent alone: selection, the
default button, the focus ring, a switch that is on. The default is `neutral`
on a desktop platform (`useDesktopPlatform()`), whose windows stay neutral
whatever the accent, and `tinted` elsewhere. It travels with the pinned accents
(`ExplicitAccents.surfaces`), so the scope vars, the JS theme and the cache all
key on it.

`resolveLabelColors(theme)` / `useLabelColors()` give the four levels of label
ink a desktop's chrome is drawn in: the theme's `text` at alpha 1, 0.65, 0.42
and 0.18 (`LABEL_ALPHA`). Composited over whatever they land on, each level
reads the same on every surface. `secondary` holds 4.5:1 against the page and
every surface rung in both modes; `tertiary` is a placeholder's and a disabled
row's; `quaternary` is never text (a separator, a quiet fill).
`colors.textTertiary` keeps its meaning (the one AA-legible quiet text colour,
equal to `textSecondary`); `tertiary` is the level below it.

## Surfaces above the page

The ramp below answers where the PAGE's own rungs sit. It does not answer "the
surface one level above the current one", which is what a card, a popover tile
or a field inside either of them needs — and thirty families each answered that
by hand, leaving four different dark card fills in one tree.

That question belongs to `styles/surface-levels.ts`
([Styles](/docs/bloom/main/styles)): `resolveSurfaceLevel`, `surfaceFillOn`,
`hairlineOn`, `surfaceTextOn` and the `SurfaceLevelProvider` that lets a
container publish the rung its children sit on. It is built BESIDE the policy,
reading `theme.colors`, and changes no preset and no token.

## The tonal surface ramp

The shell carries its seed hue throughout the surface, text and border families,
using HCT chroma 28 where the gamut permits it. Monochrome seeds retain grayscale
and their original tones. Labels and boundaries read canonical token pairs, so
JavaScript and CSS consumers share the same palette.

| Mode | Card | Page | Surface/sidebar | Popover | Muted/accent |
| --- | --- | --- | --- | --- | --- |
| Chromatic light | 98 | 94 | 90 | 86 | 82 |
| Monochrome light | 100 | 96 | 92 | 88 | 84 |
| Dark | 22 | 4 | 10 | 14 | 18 |

These are authored HCT tones. The light card stops short of white to preserve
its hue; the rest of the chromatic light ladder shifts with it. Content-area
keeps an intermediate tone: 96 in chromatic light, 98 in monochrome light and
6 in dark. It is not another four-tone ladder rung.

The original low-chroma investigation found M3's two-tone container steps
around 1.2 ΔE00, below the intended distinction between large flat surfaces;
four-tone steps measured about 2.4 ΔE00. Those historical measurements are not
claimed for the new chromatic palette. The current 64-preset × two-mode matrix
measures every declared ladder neighbour in quantized HCT tone: the smallest
actual gap is 3.68. Both foreground roles clear AA on all six surfaces, with a
minimum measured ratio of 5.75. `tonal-surfaces.test.ts` guards these contracts.

Never move just one surface without measuring its neighbours: a tone that
separates one pair can land directly on another. The intentional sidebar/surface
and muted/accent aliases do not represent separate elevations.

## Scales

- **Spacing** (px, `SPACING`): `space-2/4/8/12/16/20/24/32` + `screen-margin` (20).
- **Radius** (px, `RADIUS`): `radius-8/12/20/28/max`.
- **Hairline border** (`BORDER_WIDTH`): 0.5px, paired with the image border role.
- **Typography** (`TYPOGRAPHY`): size, line height, family and weight for
  `caption, bodySmall, bodyTitleSmall, body, subtitle, sectionTitle,
  headerBold, buttonLarge`.
- **Shadow**: `bloomShadowStyle('s' | 'm')` (web box-shadow, native
  elevation/shadow props).

### Chart series

`--chart-1` through `--chart-9` and their `--chart-N-active` partners are
the canonical categorical palette. `useTheme().chartColors` exposes these
same nine `{ color, activeColor }` pairs to JavaScript. The original five
series retain their colors; four interleaved hues extend the palette.
Monochrome presets use nine separate grayscale steps in both modes.

Chart cards read these pairs by default. Explicit series `color` and
`activeColor` overrides still take precedence. Hand-authored themes may omit
`chartColors`; charts then derive the same policy from the theme's primary
color and mode. For a deliberate custom categorical palette, provide all
nine pairs on `Theme.chartColors`.

### Media and creator surfaces

Media, library, queue, creator and property-insight palettes resolve structural
fills and quiet labels from the tonal surface helpers. Artwork bands preserve
caller-supplied hues, darkened only when their paired labels require it; their
black/white image ink is intentional. Energy bands remain categorical data
colors with measured black/white foregrounds. They are not shell backgrounds.
`media-semantic-palette.test.ts` checks those pairs across all presets and modes.


## Exact local color scopes

`BloomColorScope` accepts an optional `mode` (`light` or `dark`) and `tokens`,
a partial map keyed by `CanonicalToken` without the `--` prefix. These values
are exact React Native color strings, not seeds: Bloom does not derive or adjust
them. Supply readable foreground/fill pairs; unspecified tokens inherit the
selected `colorPreset`, or the parent scope when no preset is supplied.

```tsx
import { BloomColorScope, type BloomColorScopeTokens } from '@oxy.so/bloom/theme';

const colors = {
  background: '#5433eb',
  foreground: '#ffffff',
  card: 'rgba(255, 255, 255, 0.12)',
  'card-foreground': '#ffffff',
} satisfies BloomColorScopeTokens;

<BloomColorScope mode="dark" tokens={colors}>
  <Content />
</BloomColorScope>
```

The scope publishes the same values to canonical CSS variables (web), the
scope context `useColorTokens()` reads (native) and `useTheme()`.
Bloom portals carry this scope to their destination, so a dialog or menu
opened inside it keeps the same colors. Siblings and the app's stored theme,
document classes and native global color scheme stay unchanged. The setters returned by `useBloomTheme()` still control the app provider;
change local props to update the scope. Local mode
selects the token palette and JS theme; it does not redefine a consumer's CSS
`dark:` selector or change the device color scheme.

Nested mode overrides resolve the parent's original preset or seed at the new
mode and retain explicit ancestor token overrides. A new `colorPreset` starts
a fresh palette. Updating or clearing scope props preserves mounted children
and their state. `asChild` retains its existing single-child style contract.
An omitted token inherits; an empty color, unknown token, CSS variable reference
or color that React Native cannot parse is rejected. One token follows another:
an exact `muted-foreground` also sets `faint-foreground` unless the scope names
it too, because every preset holds the two at one colour and a scope that
redraws its quiet text for its own fill wants its tertiary text legible there,
not the preset's grey. Resolve app-specific colors
before passing them; do not restate Bloom's standard palette.

### Persisted profile colours

Account services persist a named preset or an RGB hex value. Resolve those values
with the React-free `@oxy.so/bloom/color-presets` entry point, and pass the result
to the shared scope:

```tsx
import { resolveProfileColor } from '@oxy.so/bloom/color-presets';
import { BloomColorScope } from '@oxy.so/bloom/theme';

<BloomColorScope {...resolveProfileColor(account.color)}>
  <Profile />
</BloomColorScope>
```

Names retain their full preset recipe, including curated secondary and tertiary
colours. Historical `amber` resolves to `yellow`. Three- or six-digit hex values
retain their exact RGB seed; they are never rounded to a preset or randomly
reassigned. Missing or unknown values inherit the surrounding theme.

`BloomColorScope.seed` takes precedence over `colorPreset`. Both its JS theme and
CSS/native variables derive from Bloom's existing seed engine; nested mode and
exact-token scopes retain that seed. An asynchronously arriving colour does not
replace the scope's element tree. `Screen` does not accept seed values; scope the
screen with `BloomColorScope` when rendering an account identity.

The resolver displays existing identities, including reserved or premium presets.
Permission to choose one is separate: account services must use Bloom's gate
catalogue (`FREE_COLOR_NAMES`, `HANDLE_COLOR_NAMES`, `PREMIUM_COLOR_NAMES`) when
assigning or validating selections.

# Material composition

Surface has one shared material: a frosted body (72% of an opaque fill over a blurred backdrop) with shallow satin relief and an edge of light along its top and bottom. There is no material selector. A component keeps its layout, interaction and accessibility semantics; only its paint is shared. Semantic actions keep their fill and foreground pairs with the same subtle transparency. BottomBar's optional blur band remains independent.

## Choose the existing base

| Need | Base | Current consumers |
| --- | --- | --- |
| Filled action | Button | ButtonGroup items, SocialButton, FrostedIconButton, gallery controls, chat jump controls, composer actions, attachment actions, reactions and emoji actions |
| Quiet icon action with ref/hover contracts | GlyphButton | PlayerIconButton, QueueIconButton and other existing glyph adapters |
| Card content | Card | LinkPreviewCard and existing card-shaped families; the Social template now uses LinkPreviewCard directly |
| Passive container | Surface | Standalone content with caller-owned spacing |
| Existing universal interactive/layout host | SurfacePaint | Button native, Card, Sidebar, Dialog/BottomSheet, QueuePanel, standalone UserHoverCard, native Tooltip, ComposerPanel/Pill, Toast, docked MailCompose native ContentPanel and SettingsModal; the field family (TextField, Search, PhoneInput, Textarea, InputGroup, TagField, InputOtp cells) and SelectTrigger; Chip, Badge pills, UnreadBadge counts; SegmentedControl track and thumb; the tab and bottom bar highlight; Notification, Announcement, Admonition and CloseButton; the Menubar bar, the current Pagination cell, the FileUpload frame, ShareTargetButton discs and the PlayButton disc; the Switch track, the Slider thumb, an empty Checkbox box and the RadioIndicator surface |
| Existing web host with its own fill/classes | useSurfaceMaterial | FloatingPanel, Tooltip and ContentPanel; inherits the host's actual radius without measurement |
| Anchored overlay behavior | FloatingPanel | Web Popover, DropdownMenu, ContextMenu, Menubar, Select and HoverCard |
| Modal/sheet behavior | Dialog / BottomSheet / SheetShell | AlertDialog, Command and existing native overlay adapters |

`SurfacePaint` can own a supplied fill, or omit `fill` to decorate a host-owned background with the shared light and relief. Hosts that hand their fill to the material stay transparent so they do not hide the backdrop. Explicit alpha is preserved; default fills keep 72% opacity on web. Native uses one View with tint, satin relief and inset box-shadow rim/glow; in-flow surfaces have no blur, while floating iOS surfaces may use the system material. The web host hook adds shared pseudo-elements, without a wrapper or a per-frame JavaScript loop. Backdrop filtering still incurs compositor cost per painted surface.

Surface and painted Card resolve depth from the actual parent and publish the fill composited against that backing through both React context and the web CSS variable. Plain transparent containers inherit; a plain explicit background publishes that backing without increasing the level. Material does not own padding, dimensions, geometry, elevation or state. Foreground/fill pairs stay with the semantic palette. A surface-level context must continue to describe the fill its descendants actually sit on. Never replace the parent's layout node just to paint material.

The shared optics add bounded inset light and shade inside the existing paint
layer. They do not replace semantic button fills or foregrounds, change depth,
or add a painted wrapper to the compositor. Large panels retain a quiet centre.
The web baked path keeps the same relief; no extra backdrop pass is added.
`sheen={false}` and reduced transparency suppress the body relief, and increased
contrast retains its existing opaque body and hairline. Responsive ContentPanel
framing gates the relief with the rim. Native device appearance and performance
still require device verification; paint-structure tests do not establish it.

## Intentional exceptions

- `appearance="plain"`, unstyled Toast and a caller-owned custom background do not silently acquire a surface. Trending demonstrated this: painting a plain square Card added a bright rectangle around a flush widget.
- A UserHoverCard inside HoverCard uses the existing floating pane. A QueuePanel in sheet mode and a MailCompose inside a sheet do not paint a second panel.
- ContentPanel's unframed/mobile state, optional-provider path and custom paint contract remain intact. Web framing follows the existing CSS breakpoints.
- ComposerIconButton now composes Button and forwards its recording press-in/press-out, long-press and anchor ref contracts. Composer actions use Button; radio rows, tabs and overlay dismissal planes retain their own semantics.
- MapSearchArea's auto-update control remains a named checkbox with checked state. Its role cannot be replaced by an ordinary action button.
- Fields, selection controls, meters, charts, rows and decorative status tabs keep their dedicated behavior and visual encodings. Reusing Surface does not mean wrapping every primitive in another panel.
- Too small or too thin for the edge light, so flat: status and presence dots, the radio dot, the Switch thumb (its height also animates), the Slider rail and range (at 4-8px the edge lines cover the whole rail), a marked Checkbox box and the selected RadioIndicator (their accent gradient and inset highlight are their own paint). A disabled Checkbox box or RadioIndicator is flat too: the rows and cards around them dim with `opacity`. A tab glyph's count badge is `material="flat"`: the glyph layers crossfade with `opacity`.

## Hosts, fills and states

A painted host keeps its background transparent and renders `SurfacePaint` as its first child. A host whose border is a state ring (transparent at rest) passes the border width as `outset`, so the paint covers the border box; a host with a visible border paints inside it, at the inner radius. A translucent theme tint (an error or accent wash) passes `composite`, so on the web the material shows the colour the token reads as over its surface (`backing` names that surface when it is not the one in context); native keeps the tint as is. `transition` carries a host's fill transition onto the material. Content without its own position (a raw SVG glyph) sits in a view, or it paints beneath the positioned material.

Never give a material's host or any ancestor `opacity < 1` or a `filter` (even `blur(0px)`): on the web it becomes the backdrop root and the blur vanishes, then pops back. Disabled controls dim their content, strokes and the material's own presence (`SurfacePaint presence`, `--bloom-surface-presence`); hosts that appear and leave move with `transform` and fade the material through `--bloom-surface-presence` and their content in wrappers of its own (Notification, Announcement). Native keeps dimming the host: it has no backdrop filter.

## Android decorative paint caching

On Android, `SurfacePaint` requests a hardware texture for its childless rim/sheen
layer. Scrolling can reuse that rasterized decoration instead of redrawing inset
shadows on every frame. Content, layout, hit targets and accessibility remain on
the normal host; plain fills without optical decoration do not request a texture.
Changes to fill, geometry and optical props invalidate the paint layer. This
trades some graphics memory for less RenderThread work, so device comparisons
must include memory, rapid scrolling and theme/pressed-state changes. Web and iOS
keep their existing rendering paths.

## Verification

Check both modes, nested overlays, custom styles and responsive framing in Storybook. Test opening and dismissal with real pointer/keyboard events: paint-only tests cannot see covered targets. `surface-composition.test.ts` pins the migrated composition paths; existing interaction and layout suites remain authoritative. Native paint structure is tested separately; browser checks do not establish device coverage.

The hierarchy audit also covers the actual fills published by floating panels, Tooltip, QueuePanel, UserHoverCard, ComposerPanel/Pill/Popover, Sidebar, Toast and SettingsModal. Plain/bare paths inherit instead of claiming a new pane. SettingsListGroup already derives its nested fill from the parent and now benefits from Card publishing it. Action colors and selection states remain semantic palettes; a Button is not automatically another container level. Custom CSS-only backgrounds require an explicit resolved fill when descendants need to compute from them; ContentPanel already exposes `surfaceColor` for this purpose.


## Shared shells and docked chrome

ChartCardSurface, ActionCardShell and HousingCard compose Card, as do dashboard, authentication, creator, booking and saved-search cards. Nested palettes read the actual card backing; data colours and status pairs remain semantic. Card forwards its host reference and layout callback so responsive consumers keep their existing measurements.

Composer pickers, recording panels, search panels and floating media controls use Surface. Hosts with their own size animation or keyboard handling keep that host and use SurfacePaint with matching fill context. Docked screen chrome publishes its actual backing without adding a raised frame. Sheet contents inherit their sheet instead of painting a second panel; illustrations, media, chart marks, selection controls and scrims retain their own rendering.

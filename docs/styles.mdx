# Styles

`@oxy.so/bloom/styles` holds the style primitives Bloom itself uses.

```tsx
import {
  atoms as a,
  tokens,
  BREAKPOINTS,
  web,
  native,
  select,
  resolveSurfaceLevel,
  useSurfaceLevel,
  useSurfaceFill,
  SurfaceLevelProvider,
  surfaceFillVars,
  surfaceFillOn,
  hairlineOn,
  surfaceTextOn,
  quietText,
  contrastRatio,
} from '@oxy.so/bloom/styles';
```

## `atoms`

Utility style objects — `a.flex_1`, `a.flex_row`, `a.align_center`, `a.px_sm`.
They are the inline equivalent of the Tailwind utilities, and they exist
because **a className is inert on web without the consumer's Tailwind
pipeline**. Anything Bloom must draw correctly with or without that pipeline
uses atoms; layout that only apps compose can use classes.

## `tokens`

The t-shirt view of the scales — `tokens.space.lg`, `tokens.borderRadius.xl`.

The numbers themselves live in `design-tokens/scales.ts` and are read from
there by reference, so a rung cannot exist in one spelling and not the other.
They did once diverge: `borderRadius.full` was 999 against `radius-max` 9999,
and each file's comments claimed to match the other.

Prefer the numeric names (`radius-20`) when you are naming a rung in an API —
[`Card`](/docs/bloom/main/card)'s `radius` prop takes those — and the t-shirt
names in ad-hoc inline style.

## `BREAKPOINTS`

The shared widths, so a component and the screen around it agree about when the
layout changes.

## `web` / `native` / `ios` / `android` / `platform` / `select`

Platform-conditional style helpers. Use them for a genuine platform difference
— a shadow, a font smoothing, a scrollbar — and not to work around something
that should be the same on both.

## `webDataSet`

The web-only `dataSet` hook an adopted sheet's selectors hang off, as spread
props. On web react-native-web turns it into a `data-*` attribute; on native it
spreads nothing.

```tsx
<Pressable {...webDataSet({ bloomTrackRow: 'true' })} />
// web:    <div data-bloom-track-row="true">
// native: nothing
```

This is how a component reaches a CSS rule it cannot express inline — a hover
state, a focus ring, a transition. A class never reaches the DOM here, so a
`data-*` attribute is the only hook an
[adopted sheet](/docs/bloom/main/styles) can select on.

## `clamp` / `clamp01`

```ts
clamp(value, min, max)   // held inside [min, max]
clamp01(value)           // held inside [0, 1]; undefined / NaN / ±Infinity → 0
```

Two edges worth knowing, because the copies these replaced disagreed about
them:

- `clamp` resolves an INVERTED range (`min > max`) to `min`. That is what pins
  a dropdown taller than the viewport to the top gutter, so its first rows stay
  reachable instead of its start going off-screen.
- `clamp01` answers `0` for a non-finite value, including `Infinity`, where
  `clamp(v, 0, 1)` would answer `1`. A non-finite share means "not measured
  yet", and a full bar is the wrong thing to draw for that.

## `contrastRatio` / `relativeLuminance` / `readableOn` / `darken` / `darkenUntilContrast`

WCAG maths and the two decisions every surface painted from a computed colour
has to make. `AA_TEXT_CONTRAST` (4.5), `AA_LARGE_TEXT_CONTRAST` (3) and
`AAA_TEXT_CONTRAST` (7) are the bars, named once.

```ts
readableOn(background, ['#ffffff', '#141414'])       // which ink reads on it
darkenUntilContrast(artworkColor, '#ffffff', 7)      // { color, amount } | null
```

`readableOn` takes one surface or several, and picks the candidate whose WORST
contrast across them is highest — text over a gradient has to read at both ends.

`darkenUntilContrast` returns the LIGHTEST shade of a colour on which every
given foreground clears the ratio: the colour itself when it already does, else
pulled toward black in 5% steps. `null` for a colour that does not parse, so a
caller falls back to its own neutral rather than being handed one it did not ask
for.

**Darken the colour; never walk its ramp.** A generated ramp re-derives every
stop's lightness and chroma from the hue, so a near-black input comes back ten
times lighter than it went in and a vivid one has a channel zeroed. Scaling
every channel by the same factor keeps their ratio, which is why a darkened teal
is still teal. Four music surfaces — the lyrics pane, the immersive player, a
generated cover and a browse tile — had five implementations of this between
them, under four names for 4.5.

## `Z_INDEX`

**Within-context values only.** Which overlay paints on top is decided by the
overlay stack, not by a constant: `overlay/stack.ts` ranks surfaces by when
they OPENED, and a per-component z-index answers that question by what a
surface *is*, which leaves some pairings permanently inverted.

Never give an overlay surface a `zIndex` of its own.

## Surface levels

**The answer to "what colour is the thing I am sitting on, and what do I put on
top of it".** Before this existed every family resolved it alone, and the tree
carried four different dark "card on a page" fills and two light ones. Two of
those collisions were not drift: a dark `TextField` painted `neutral-800` inside
a menu painted `neutral-800` measured **1.000:1**, and a tab rail painted
`neutral-800` inside a queue panel measured **ΔE 0**. Both controls simply were
not there.

A control cannot know its parent, so the answer is relative. Three primitives,
all pure, all taking the fill they land on:

| | what it answers |
| --- | --- |
| `surfaceFillOn(theme, parent)` | the next surface up — a field, a track, a tile, a hovered row |
| `hairlineOn(theme, parent)` | the line that separates them — a divider, a card edge, a tab rail |
| `surfaceTextOn(theme, parent)` | `text` / `textSecondary` / `textTertiary` / `textGraphical`, each floored on that fill |

A step moves the parent toward `theme.colors.text` by a fixed alpha, so nothing
new enters the palette. Light and dark are ONE rule: moving toward the text
colour darkens a light surface and lightens a dark one.

### The named rungs

`resolveSurfaceLevel(theme, level)` names the four a screen stacks, and levels 0
and 1 land on what Bloom already painted, so adopting the API is not a repaint.

| level | light | dark |
| --- | --- | --- |
| 0 page | `theme.colors.background` | `theme.colors.background` |
| 1 card on page | `theme.colors.card` (white) | a step off the page — within 1.03:1 of the menu surface |
| 2 card on card | a step off level 1 — a popover's inner tile, a field | ditto |
| 3 deep | a step off level 2 | ditto |

The ladder is **not monotonic in lightness**: in light the first step goes up to
white and every step after goes down. What is monotonic is the SEPARATION —
measured on `blue`, 1.11 / 1.15 / 1.15 in light and 1.23 / 1.30 / 1.30 in dark.
1.11 is thin, which is why every rung also carries the `border` that separates it
from its parent (1.21 / 1.53 / 1.50 in light). `surface-levels.test.ts` pins both
mechanisms over all 64 presets, so losing either goes red.

### Ambient level

A container that PAINTS a surface publishes it, and everything inside steps off
the right parent without being told:

```tsx
<SurfaceLevelProvider level={1} fill={colors.card}>{children}</SurfaceLevelProvider>
```

`ContentPanel`, `FloatingPanel` (so every menu, popover, select and tooltip),
`QueuePanel`, and every sheet and dialog surface do this. `useSurfaceLevel()`
reads the current rung's paint, `useSurfaceLevel(1)` the one above it,
`useSurfaceFill()` just the fill. Nothing published means level 0 — the page —
which is what every unwrapped consumer already assumed.

An overlay that paints the page colour publishes `level={0}`, which RESETS the
ambient surface rather than inheriting it. That matters because a portal keeps
React context from where it was rendered: without the reset, a dialog opened
from inside a `ContentPanel` would tell its own content it is sitting on the
panel's card.

### `fill` — the rung is a derivation, the fill is a fact

A rung answers from the page down, which is all a control needs to find a
legible step off its parent. It is not enough for the other question a surface
gets asked — **"paint yourself the same colour as me"** — because a container
may paint something the ladder would not have chosen. `ContentPanel` is exactly
that: it paints `bg-card`, and in dark mode `theme.colors.card` is not rung 1
(the rung is a computed step off the page, pinned within 1.03:1 of the menu
surface). Chrome that took the rung would sit a visible shade off the column it
is supposed to disappear into.

So a container that knows what it painted says so, and `useSurfaceFill()`
returns that colour verbatim. Everything derived from it — the hairline, the
raised fill, the text rungs, `useSurfaceLevel(1)` — is then computed off the
REAL parent, which is what the relative primitives always wanted and could not
have while the parent was inferred. A provider with no `fill` behaves exactly as
it did.

### `useSurfaceFill()` or `colors.card`?

**`colors.card` is a palette token: the colour a CARD paints.** It is the right
answer when you are drawing a card — an object that is genuinely separate from
what is behind it.

**`useSurfaceFill()` is a question about position: the colour of the surface
underneath you.** It is the right answer for chrome that has to be OPAQUE in its
container's own colour and otherwise not be seen — a sticky header over a
scrolling feed, a tab bar, a search field's backing, a reply bar pinned to the
bottom of a column. Those are the ones that were written as `bg-card` at every
call site, and they were only ever right for as long as the container's surface
stayed `card`; the hook is right afterwards too, and it is right inside a sheet,
a menu or a scoped subtree where `card` never was.

### `--bloom-surface` (web), for CSS that cannot call a hook

The same containers write the published fill onto the element they paint:

```tsx
<View style={[surfaceFillVars(colors.card), …]}>   {/* no-op on native */}
```

so web CSS below it can follow the surface:

```css
background-color: var(--bloom-surface, var(--background));
```

```tsx
className="bg-[var(--bloom-surface,var(--background))]"   /* web only */
```

`SURFACE_FILL_VAR` and `SURFACE_FILL_CSS` are the exported spellings. Three
things about it are deliberate:

- **The fallback is part of the reference.** The variable exists only where a
  container published one, so outside every surface it resolves to the page.
- **It is never declared at `:root`.** A custom property whose value is a
  `var()` substitutes where it is DECLARED, so a root-level
  `--bloom-surface: var(--background)` would answer for the whole document and
  a `BloomColorScope` subtree — which paints its own `--background` — would keep
  reading the app-wide one. Both halves of the reference above substitute at the
  USING element, so a scope gets its own.
- **It is web-only, and the hook is not.** Propagating a custom property to a
  native subtree means react-native-css's `VariableContextProvider`, i.e. the
  `nativewind` OPTIONAL peer, and a panel's surface must not depend on whether a
  consumer installed it. Cross-platform code reads `useSurfaceFill()`; a
  `.web.tsx` fork or a consumer stylesheet may read the variable. A
  `var(--bloom-surface)` class in shared code would be right on web and
  quietly wrong on native.

It is the opposite number of `--bloom-ring-offset` below: a CONTAINER publishes
this one, a CONTROL consumes that one, and they are the same colour.

### Quiet text is not a ramp stop

`quietText(surface, text, minRatio)` returns the QUIETEST blend of the theme's
text over the theme's surface that still clears `minRatio` **as rendered** (the
8-bit colour is re-checked, because a nominal 4.50 quantizes to 4.49).
`quietTextOver([surfaces], text, min)` does it for a label that lands on more
than one fill.

This is the only way to build a caption grey in Bloom. A ramp stop cannot do the
job: `neutral-400` clears AA on the page and measured **2.42:1** on a chart card,
because the card is not the page. The floors are `AA_TEXT` (4.5, body text),
`AA_TEXT_STRONG` (7, the secondary rung) and `AA_GRAPHICAL` (3, gridlines, rules
and disabled glyphs).

## Interactive web CSS — the one recipe

`interactiveWebCss()` builds the stylesheet for a raw-DOM fork or a
`dataSet`-hooked react-native-web control. **It is THE way to write one.** It
existed before and nobody called it — thirty-odd families used only the
`useInteractiveWebCss()` adopter and hand-wrote the sheet, which is exactly why
rings, hovers and disabled states drifted apart.

```tsx
const CSS = interactiveWebCss({
  selector: '[data-bloom-filter-chip]',
  varPrefix: 'bloom-filter-chip',
  reset: 'none',            // react-native-web: no <button> reset, no press scale
  transition: 'background-color 120ms ease, border-color 120ms ease',
  focus: { mode: 'ring' },  // gap colour from the surface
  disabled: { opacity: null }, // this family fades in its inline style, for native parity
});
useInteractiveWebCss(STYLE_ID, CSS);
```

- **`reset`** — `button` (default) emits the `<button>` reset. A react-native-web
  caller passes `none`: RNW lays a `View` out with `display: flex`, so
  `inline-flex` from a stylesheet silently changes how the control participates
  in its parent's layout.
- **`focus`** — `outline` (default) is the canonical 2px outline at
  `outline-offset`. `ring` is the `box-shadow` form, for a control whose ring
  must sit on a CHILD element (a slider thumb, a checkbox glyph).
- **`hover`** is optional. An RNW control gets `onHoverIn` in JS and paints hover
  through its inline style; a CSS rule would be a second source of truth.
- **`disabled`** defaults to `cursor: default` plus `DISABLED_OPACITY`.

### The focus ring gap

**One mechanism.** The gap is `var(--bloom-ring-offset)`, set inline from the
surface behind the control with `useRingOffsetStyle()`. It used to be the literal
`#FFFFFF` — Tailwind's `ring-offset-color` default, never overridden — so in DARK
mode a focused filter chip, filter text button, stepper value, slider thumb,
checkbox, radio, radio card, property tile, energy-rating pill and sortable photo
tile each drew a 2px white halo against a near-black page. A gap is a hole in the
ring, and a hole is the colour of what is behind it.

Three families (`sidebar`, `select`, `settings-modal`) name their own offset
variable. Each is already surface-derived and each knows its surface exactly, so
they stay — as a written list in `interactive-recipe.test.ts`, not as a
threshold.

## Disabled

**Recolour if you can; fade only if you cannot.**

A control with a token pair to swap to swaps to it and keeps opacity 1 — that is
what `Button` does. A fade multiplies against whatever is behind the control, so
over a coloured card a 0.5 label goes muddy rather than quiet, and fades stack
when a disabled control sits inside a disabled group.

Opacity is the fallback, for a control with no pair to swap to: an icon drawn in
`currentColor`, a `Pressable` that paints nothing of its own, a row of mixed
children. When it is used it is `tokens.DISABLED_OPACITY` (**0.5**) — one value,
because three were in the tree (0.5 in twenty-five places, 0.4 in six, 0.6 in
one) and nothing distinguished them. A disabled control is exempt from the WCAG
contrast floors, which is what makes one blanket value defensible at all; it is
not licence to pick a new one per family. Gate:
`interactive-recipe.test.ts`.

## `flatten`

`StyleSheet.flatten` re-exported for code that already depends on the RN
runtime. A raw-DOM web fork should use `flattenWebStyle()` instead — jest's RN
mock stubs `StyleSheet.flatten` as identity, so the array form would survive
and crash the DOM with `Failed to set an indexed property [0]`.

# ConnectionStatusToasts

Mount it once and the app announces losing and regaining its connection.

```tsx
import { ConnectionStatusToasts } from '@oxy.so/bloom/connection-status';

<ConnectionStatusToasts />
```

`ConnectionStatusToasts` renders no interface. It reports through Bloom's
shared `Toast` engine, which owns the visible notification and its sizing; a
`BloomScope` around this reporter does not set the toast's control size.

## Which prop decides what

| prop                   | decides                                              |
| ---------------------- | ----------------------------------------------------- |
| `offlineMessage`       | shown while there is no connection                    |
| `reconnectingMessage`  | shown after `reconnectingDelayMs` offline             |
| `restoredMessage`      | shown when the connection comes back                  |
| `locale`               | the language of the three default messages            |
| `reconnectingDelayMs`  | how long to wait before escalating                    |
| `restoredDurationMs`   | how long the restored toast stays                     |

The three messages default to Bloom's own strings in the app's language
("No internet connection", "Reconnecting…", "Back online" in English; see
[Locale](/docs/locale)); a message prop replaces its string.

## "Back online" is only shown to someone who saw the outage

The restored toast is suppressed unless an outage toast was actually up. A
"Back online" that appears on its own is confusing — the user never knew
anything was wrong, and the message implies they missed something.

## The delay is the point

Connectivity flaps. Announcing every dropped packet produces a toast that
appears and disappears while the user is reading, which is worse than silence.
The offline toast is shown immediately because the user is about to hit a
failure; the *reconnecting* escalation waits, so a two-second blip never
escalates at all.

## `useNetworkStatus`

The reading the toasts are built on, for an app's own decisions: whether the
device is online, and whether its connection is metered.

```tsx
import { useNetworkStatus } from '@oxy.so/bloom/connection-status';

const { online, metered } = useNetworkStatus();
```

On native, `online` is netinfo's link being up with the internet not known to
be unreachable, and `metered` is a cellular connection or one netinfo marks
`isConnectionExpensive`. On the web, `online` is `navigator.onLine` (the link,
not reachability) and `metered` is a cellular connection or the viewer's
Save-Data, where the browser exposes the Network Information API. Until the
platform answers, and without netinfo installed, it reads
`{ online: true, metered: false }`: nothing is held back and no outage is
announced on a guess. Every caller shares one subscription. Media autoplay's
"Wi-Fi only" preference reads `metered` from it.

## Optional peer

Connectivity on native comes from `@react-native-community/netinfo`, loaded
through Bloom's optional-require boundary. Without the package installed the
component mounts and does nothing (and says why once, in development) rather
than failing the build.

That is why the require is written the way it is — a literal specifier, as a
direct statement of a `try` block. Metro's optionality walk returns at the
first enclosing block, so one `if` of nesting inside the `try` would lose
optionality and turn a missing optional peer into a build failure.

## Mount it once

It presents through the shared [toast](/docs/bloom/main/toast) engine with a
fixed id, so a second mount does not duplicate the toast — but it does double
the listeners and the timers. One per app.

`useNetworkStatus({ enabled: false })` starts no subscription and reads the unknown status (online, unmetered) — for a caller that only sometimes needs the answer, as media autoplay outside "Wi-Fi only".

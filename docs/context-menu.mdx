# ContextMenu

The secondary menu for an object on screen. Right-click on web, long press on native.

Its parts are shadcn's, and its rows are the SAME rows `DropdownMenu` and `Menubar` publish — one implementation under three prefixes, so a row behaves identically wherever it is.

## Basic

```tsx
import {
  ContextMenu,
  ContextMenuContent,
  ContextMenuItem,
  ContextMenuSeparator,
  ContextMenuShortcut,
  ContextMenuTrigger,
} from '@oxy.so/bloom/context-menu';

<ContextMenu>
  <ContextMenuTrigger label="Photo actions">
    <Image source={photo.source} style={styles.thumb} />
  </ContextMenuTrigger>

  <ContextMenuContent>
    <ContextMenuItem
      onPress={() => share(photo)}
      trailing={<ContextMenuShortcut>⌘S</ContextMenuShortcut>}>
      Share
    </ContextMenuItem>
    <ContextMenuItem onPress={() => save(photo)}>Save to library</ContextMenuItem>
    <ContextMenuSeparator />
    <ContextMenuItem tone="danger" onPress={() => remove(photo)}>
      Delete
    </ContextMenuItem>
  </ContextMenuContent>
</ContextMenu>
```

`asChild` composes the trigger onto your own element instead of wrapping it, exactly as it does on `DropdownMenu`.

## It opens where the pointer is

On web the menu anchors to the CLICK POINT, not to the trigger's box: right-clicking the bottom-right corner of a large card opens the menu there, not under the card's top-left. A click point is a zero-area anchor, which the same fit / flip / clamp arithmetic every other Bloom surface uses already handles.

On native there is no cursor to anchor to, so a long press presents the same bottom sheet `DropdownMenu` uses. A native platform with popups (an adapter reporting [`popup-surface`](/docs/bloom/main/platform-surface), a desktop) has one: there the secondary button (a W3C `pointerdown` with `button` 2) opens the menu where it pressed, in the platform's popup, as does a long press. The innermost trigger takes the press, so an item's menu opens rather than its list's. An `asChild` child that states its own role (a list item, a list) keeps it, without a menu button's `aria-haspopup` and `aria-expanded`: a region that opens a context menu is not a button.

The native trigger (without `asChild`) times the hold off raw touch events and never takes the touch responder. On Android the responder's view intercepts every later move of its touch, so a `Pressable` trigger kept a horizontal `ScrollView` inside it — a code block in a chat turn — from scrolling. Taps still reach whatever the content makes pressable; a drag past 10dp, an early lift or a scroller taking the touch cancels the hold, and assistive tech opens the menu through the `longpress` accessibility action. With `asChild` your own element takes the long press, responder and all.

## Opening it from code: `anchor`

A context menu has ONE fact — where it is anchored — so there is still no `open` prop that could disagree with it. To open one from code (a toolbar button's handler, a right-click forwarded from outside the page, a keyboard shortcut), pass that fact instead:

```tsx
import { ContextMenu, ContextMenuContent, ContextMenuItem, type ContextMenuAnchor } from '@oxy.so/bloom/context-menu';

const [anchor, setAnchor] = useState<ContextMenuAnchor | null>(null);

<Button onPress={() => setAnchor({ x: lastPointer.x, y: lastPointer.y })}>More</Button>

<ContextMenu anchor={anchor} onAnchorChange={setAnchor}>
  <ContextMenuContent>
    <ContextMenuItem onPress={rename}>Rename</ContextMenuItem>
    <ContextMenuItem onPress={remove}>Delete</ContextMenuItem>
  </ContextMenuContent>
</ContextMenu>
```

| Prop | Type | |
| --- | --- | --- |
| `anchor` | `ContextMenuAnchor \| null` | Controlled. Open exactly while non-null; omit it (`undefined`) for the right-click menu. |
| `onAnchorChange` | `(anchor: ContextMenuAnchor \| null) => void` | The anchor the menu asks for: a trigger's point when one opens it, `null` on every dismissal. |
| `onOpenChange` | `(open: boolean) => void` | Fires in both forms, from any cause. |

`ContextMenuAnchor` is a viewport point `{ x, y }` (CSS client coordinates — `event.clientX/clientY`) or a rect `{ top, right, bottom, left }` to open beside a box. Either goes through the same fit / flip / clamp a right-click does, so a point at the bottom-right corner opens the menu up and to the left, on screen.

- **Dismissal asks; the caller decides.** An outside press, <kbd>Esc</kbd>, <kbd>Tab</kbd>, a row that closes the menu and (native) a sheet swipe all call `onOpenChange(false)` and `onAnchorChange(null)`. The menu stays open until you clear `anchor`.
- **Focus lands on the panel, not a row**, as a desktop menu opened from code does: nothing is highlighted, <kbd>↓</kbd> moves to the first row and <kbd>↑</kbd> to the last, and every other menu key works at once. A new `anchor` while open is a new open (moved, focus re-taken).
- **No trigger needed.** Without a `ContextMenuTrigger`, focus returns on close to the element that held it before the open (if it is still in the document). With one, it returns to the trigger, and the trigger's right-click no longer opens the menu by itself — it calls `onAnchorChange({ x, y })` with the click point for you to store.
- **Sub-menus and keys are unchanged**: flyouts, → / ←, the escape order and row activation are the right-click menu's.
- **Native** presents the same bottom sheet a long press does while `anchor` is non-null; the position is ignored. A trigger's long press reports the press point.

Without `anchor` the menu is the uncontrolled right-click menu, exactly as before. `onOpenChange` still reports it:

```tsx
<ContextMenu onOpenChange={(open) => setDimmed(open)}>
```

## Rows

Everything `DropdownMenu` documents applies, under the `ContextMenu` prefix: `ContextMenuItem`, `ContextMenuCheckboxItem`, `ContextMenuRadioGroup` / `ContextMenuRadioItem`, `ContextMenuLabel`, `ContextMenuSeparator`, `ContextMenuShortcut`, `ContextMenuGroup`, and `ContextMenuSub` / `ContextMenuSubTrigger` / `ContextMenuSubContent`.

Sub-menus fly out beside their trigger row on web and render as an inline disclosure on native — see [DropdownMenu](/docs/bloom/main/dropdown-menu) for the hover, keyboard and placement behaviour, which is shared.

On web a right-click opens the menu with focus on its first row, so the menu's keys work at once: the arrows move and wrap, <kbd>Home</kbd> · <kbd>End</kbd> jump, <kbd>Enter</kbd> · <kbd>Space</kbd> activate, and <kbd>Esc</kbd> · <kbd>Tab</kbd> close it, returning focus to the trigger. No ring is painted for a pointer open — rows highlight on `:focus-visible` only.

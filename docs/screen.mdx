# Screen

Retained inactive screens suspend scroll observers and pagination. Their viewport
handles ignore imperative scrolling while inactive, including calls held by a
background chat as new messages arrive. `ScreenScrollView.onLayout` on web reports
the enclosing Screen's viewport, rather than the growing transcript wrapper.

## Declarative screens in any host

A route declares its own chrome once. The shell supplies the surface and available
region; the same screen can render as a document page or inside a Deck column.

```tsx
<Screen scroll="auto"
  header={<PageHeader title="Conversation" />}
  bottomBar={<PageFooter><ReplyComposer /></PageFooter>}
>
  <ScreenScrollView><Messages /></ScreenScrollView>
</Screen>
```

On web, `scroll="auto"` uses the document in a document-flow host and one local
viewport in a bounded host. `ScreenScrollView` reuses that owner; it never adds
another scroller. Changing host flow preserves the screen's content tree.
`headerPlacement="overlay"` lets a profile hero or media page extend under its
header. Insets otherwise reserve the measured header/footer once.

On native, auto reserves chrome space but the screen's list or `ScreenScrollView`
continues owning scrolling. `scroll="content"` (the compatibility default) keeps
existing explicit list/inset bindings. `documentScroll` remains an explicit override.

`useScreenViewport()` exposes the existing owner (`kind`, `scrollRef`, `metrics`,
`active`, `scrollTo`). Virtualizers bind to that ref rather than assuming a window.
The host publishes the same stable ref above the Screen for route-level hooks;
the Screen fulfills it without a portal or a global registry. Scroll restoration
uses the enclosing adapter when available, scoped to a panel's own history.
`--bloom-screen-viewport-height` and `--bloom-screen-viewport-top` describe the
usable web content region for shared CSS components such as a pager.

A `PageFooter` in `bottomBar` draws only its content and scrim. Screen owns its
position and clearance; it does not create a second sticky footer or register
another inset. Host controls that persist across routes use the panel's `headerActions`.
The Screen's PageHeader composes them with its existing actions in one header.

## Explicit content-owned scrolling

`Screen` owns a continuous page canvas. It paints the containing surface fill,
so a Screen inside an AppShell panel matches that panel in light and dark mode.
Standalone Screens use the page fill. `header` and `bottomBar` overlay the content;
`ScreenScrollView` reserves their measured footprints, adding its own content padding.
Safe-area padding belongs to the chrome, so it is included exactly once in those measurements.

Under an `AppShell` with a bottom bar, the app's navigation already owns the bottom
edge. A route's own `bottomBar` (a listing's `BookingBar`, a wizard's footer) stacks
on top of that navigation, never under it, and the content clears both. Off a phone
layout the shell publishes no bottom edge and the bar sits at the bottom.

```tsx
import { Screen, ScreenScrollView } from '@oxy.so/bloom/screen';

<Screen header={<PageHeader title="Inbox" />} bottomBar={<Navigation />}>
  <ScreenScrollView><Messages /></ScreenScrollView>
</Screen>
```

`PageHeader` automatically reads its enclosing screen's offset. `useScreen()` exposes
`scrollY` and `collapseProgress` to coordinated chrome. Pass `collapseProgress` as
`BottomBar`'s `minimizeProgress`; navigation and the lateral action then move together.

For a virtualized list, call `useScreenScroll({ active, handler })`, bind `onScroll`,
and apply `contentInsets.top`/`bottom` to its content container. `handler` accepts a
processed Reanimated handler, preserving drag and momentum subscriptions. Only the
active binding drives chrome. Set `active={false}` on retained background lists.
Nested `Screen`s keep scroll offsets local. Under AppShell they inherit navigation motion and bottom clearance; `navigationScope="isolated"` creates an independent modal scope. Do not place several active scrollers
in one screen; designate the primary list explicitly.

`ScreenScrollView` forwards its ref. Scroll restoration remains the independent
`useScrollRestoration` binding: pass it as `restoration={binding}` and pass the same ref. Pending restored content
stays laid out with opacity zero; native offset recording is forwarded automatically. Web restoration observes the actual DOM scroller itself.

The shell does not choose a router or create overlay outlets. Measurements settle
on layout; content footprint stays expanded while visual chrome contracts, avoiding
scroll-range changes during animation.

For a standalone action, `primaryAction={<Fab ... />}` anchors a static action
inside the screen. With navigation, pass the action to `BottomBar.action` instead.
`headerHeight` and `bottomBarHeight` declare initial footprints for custom chrome;
defaults match Bloom's 56-point header and 58-point bottom bar plus safe area.
Measured heights replace those estimates. Custom chrome should declare its height
to prevent the first layout changing the content's padding.

On web, `documentScroll` makes the document the scroller: Screen grows with its
children and automatically observes `window.scrollY`. Do not wrap ordinary
content in a ScrollView or constrain Screen to a fixed-height flex slot.

```tsx
<Screen documentScroll header={<PageHeader title="Home" />} bottomBar={<Navigation />}>
  <LongContent />
</Screen>
```

Header and bottom chrome stay sticky within the Screen column's width. The
header slot owns positioning, including a framed panel's inset; a PageHeader
placed there does not add another sticky container. PageHeaders outside the slot
retain their own positioning. Screen
reserves their measured footprints in document flow, including bottom clearance;
content can scroll fully above the bottom bar. The initial declared heights still
apply before measurement. Without chrome slots Screen adds no content padding,
so a composed shell can own those slots and their spacing itself.

### One page for both platforms

`ScreenScrollView` reads the mode from its Screen, so one page implementation
serves web and native with no `.web.tsx` fork. Under an `AppShell`, use
`scroll="page"` — the recommended mode for apps whose routes are Screen pages:
the window scrolls on web, and on native the shell is one screen whose routes'
`ScreenScrollView`s scroll, never nested in a shell `ScrollView`, with the
bottom bar's clearance reaching them (`docs/app-shell.mdx`, Screen pages). It
replaces `scroll={Platform.OS === 'web' ? 'document' : 'fixed'}`.


```tsx
const ref = useRef<ScrollView>(null);
const restoration = useScrollRestoration(ref);

<Screen documentScroll header={<PageHeader title="Notes" safeArea={false} />}>
  <ScreenScrollView
    ref={ref}
    restoration={restoration}
    contentContainerClassName="gap-4 p-4"
    onEndReached={() => { if (hasNextPage && !isFetchingNextPage) fetchNextPage(); }}
  >
    {notes.map((note) => <NoteCard key={note.id} note={note} />)}
  </ScreenScrollView>
</Screen>
```

Inside a web `documentScroll` Screen it creates no scroll container: its content
renders in document flow with `contentContainerStyle`/`contentContainerClassName`
on the content View and `style` on an outer View that grows to fill the page.
It binds the window for the screen (as Screen's own listener would), so chrome
follows `window.scrollY`. A nested scroller would hold the document at one
viewport and clip everything below it. Its ref answers `scrollTo`/`scrollToEnd`
with the window, and `getScrollableNode()` returns the document's scroller,
which `useScrollRestoration` treats as `'window'` — so the native call site above
restores the window too. ScrollView-only props (`refreshControl`,
`keyboardShouldPersistTaps`, a Reanimated `handler`) have nothing to act on there.
Everywhere else — native, and web without `documentScroll` — it is the animated
`ScrollView` it always was.

`onEndReached` pages either way, with `FlatList`'s semantics and default
(`onEndReachedThreshold` is in viewports, default 2): it fires once each time
the end of the content comes within the threshold, re-arms when the user scrolls
back out of range, and fires again while still in range only after the content
changes length — so a first page too short to scroll still asks for the next.
Native reads its own scroll, layout and content size; document flow observes an
end marker against the viewport. It can fire while a page is in flight, so guard
on your own loading flag. Use `VirtualList` (same two props) for long or
uniform rows; `ScreenScrollView` is for grids and composed pages.

With `contentContainerClassName` on native, the chrome footprint pads the scroll
content and the class lays out a container inside it, since an inline padding
would override the class's.

`VirtualList screen={{ active, restoration }}` connects both platforms without a
surrounding ScrollView. Use `useScreenWindowScroll` for another window virtualizer;
its explicit writer takes priority over Screen's automatic listener. During a
pending restoration it updates the offset without collapsing navigation. When
that binding unmounts, automatic window tracking resumes. Returned `contentInsets`
are zero in document mode because Screen already reserves the spacing; applying
them does not add a second footprint. `useScreenScroll` remains the animated
native/container binding. Only one explicit scroller should be active per scope.

When navigation retains whole screens, set `Screen active={focused}` (or
`AppShell active={focused}`). That boundary disables every descendant scroll
writer; an explicitly isolated modal keeps its own navigation scope. During restoration,
offsets update the header but do not trigger a new collapse. On native, showing
the keyboard hides bottom chrome and releases its reserved content footprint;
hiding it restores the previous footprint.

AppShell establishes `navigationScope="shared"`. Route Screens use the default
`inherit`: their local header offset is independent, while the focused list owns
the shared navigation progress. Set every retained route's `active` explicitly;
use `navigationScope="isolated"` for modal screens that cover the shell navigation.


### Storybook document hosts

Full-screen stories that demonstrate document scrolling declare
`parameters: { layout: 'fullscreen', bloomScroll: 'document' }`. The preview then
uses a minimum viewport height, allowing the document to grow. Contained demos
keep a bounded height. This is a preview host choice, not an application prop;
consumer roots must likewise allow the document to grow.

Native keyboard visibility is read on mount, so a screen opened while the
keyboard is already visible does not briefly reserve bottom navigation. While
visible, both owned and inherited bottom chrome leave only content clearance.
`ScreenScope` also isolates navigation progress and scroll ownership; overlays
mount this shared boundary automatically while retaining theme, locale and
`BloomScope` appearance.

### Shared scroll indicators

Web `Screen` viewports, `ScreenScrollView`, AppShell document scrolling, and
Deck's document horizontal axis use Bloom's existing `ScrollBar`. It observes
and controls the actual scroll owner; it does not add a scroll container.
`ScrollArea` and sidebar scrolling use the same indicator. Native keeps its
platform scroll indicator. A custom external scroll implementation can attach
`ScrollBar` to its ref, or use `target="document"` for a standalone document owner.

Panel history supplies the existing PageHeader Back slot. It is absent
at the initial entry; forward navigation remains available through the history
controller without adding another header button. Host `headerActions` remain
separate from the screen's own action groups.

### Screen color recipe

`<Screen colorPreset="teal">` applies the existing Bloom recipe to its content,
header, footer and enclosing panel surface. The declaration belongs to that
panel host: sibling columns and the application theme do not change. Leaving
the screen restores the prior host recipe. Retained route wrappers should omit
`colorPreset` when their own screen is not active. The scope keeps its subtree
mounted while the recipe changes.

In a bounded web panel the Screen viewport fills the entire panel. Header and
footer are overlay siblings; their insets pad the scrollable content, so content
passes beneath the chrome while scrolling, exactly as in document flow.

A modular shell in document flow restores the shared document once, using the
outer route adapter. Its Screen instances read that owner without competing
restoration writes. Bounded Deck columns restore their own element and history;
a standalone document Screen remains its own restoration owner.

A composer passed through `bottomBar` sets
`bottomBarKeyboardBehavior="visible"`, so typing keeps the composer and its
measured clearance present. The default `hide` retains navigation's keyboard
behavior. `ScreenScrollView onScroll` observes the existing viewport on web and
native; it never creates another scrolling container.

The bounded viewport contains overscroll and draws its single overlay scrollbar
at the viewport edge. Header/footer clearance pads the content; it does not
shorten or inset the scrollbar track. Keep reading-column width and content
padding inside `ScreenScrollView.contentContainerStyle`, so they do not move
the viewport, header or scrollbar inward.

### Nested activity and viewport constraints

A nested Screen inherits the inactivity of its ancestor. `navigationScope="isolated"`
separates navigation progress; it does not reactivate hidden content. The first
Screen consumes its panel host. Nested Screens own their metrics and chrome,
without claiming the outer host's color recipe or actions. Dialog's ScreenScope
provides a fresh boundary for modal content.

`ScreenScrollView scrollEnabled={false}` constrains user scrolling on the actual
web viewport, including document mode and scrollbar dragging. Multiple constraints
share a reference-counted lock, so one unmount does not unlock another owner.
Programmatic scrolling and restoration remain available.

Bounded web viewports use CSS size containment. Give their host a usable width
and height; a parent that depends only on contained content for its intrinsic
dimensions can collapse. Put max-width on the reading content, not that viewport.

Screen's browser entry explicitly binds the browser ScrollBar, color scope and
restoration hook. Shared factories receive these bindings instead of relying on
a bundler to resolve bare relative imports to `.web` files.

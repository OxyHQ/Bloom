# Icons

Bloom draws [Remix Icon](https://remixicon.com) (Remix Icon 4.9.1, **Remix Icon
License 1.0** — the full text ships at `src/icons/remix/LICENSE.txt`). Every
glyph is its own module under `src/icons/remix/`, named exactly as Remix's
React package names it, and re-exported flat from `@oxy.so/bloom/icons`.

```tsx
import { RiNotification3Line as BellIcon } from '@oxy.so/bloom/icons';

<BellIcon size="lg" fill={colors.text} />
```

## The naming is `Ri<Subject><Line|Fill>`

The name on remixicon.com is the import: `arrow-right-s-line` is
`RiArrowRightSLine`. The suffix is not decoration — it is *which drawing you
get*. `Line` and `Fill` are separate exports rather than a prop on one
component, because they are different artwork: `Fill` reads as "on"/selected,
`Line` as the resting state. A tab bar uses both for the same subject. A handful
of Remix glyphs have no variant and no suffix (`RiHashtag`, `RiLinkM`,
`RiDoubleQuotesL`).

Import the exact identifier and alias it locally, as above.

## `fill` and `size`, not inheritance

Colour travels on `fill` and size on `size` (the `xs`…`xl` rung, or `width` /
`height`). Neither is inherited from a surrounding `Text`, so an icon beside a
label has to be told both — an icon that "looks black in dark mode" is almost
always one that was never given a `fill`.

## `BloomIconComponent` — the type of an icon you hand to a component

Most Bloom components that take an icon take the COMPONENT, not an element, so
they can size and colour it themselves.

```tsx
import type { BloomIconComponent } from '@oxy.so/bloom/icons';
import { RiHotelBedLine } from '@oxy.so/bloom/icons';

interface FactProps {
  icon: BloomIconComponent;
  label: string;
}

<ListingFact icon={RiHotelBedLine} label="2 beds" />   // ✅ the component
<ListingFact icon={<RiHotelBedLine />} label="2 beds" />  // ✗ an element
```

```ts
type BloomIconComponent = ComponentType<{
  width?: number; height?: number; fill?: string;
}>;
```

All three props are optional, which makes this the WIDEST icon a component can
be handed: a component whose props are stricter is not assignable, on purpose.
It is also the LEAST a part may ask for, so it is the right type wherever a part
only sets width, height and fill — which is nearly everywhere.

### What this type is NOT for

A part that hands its icon more than those three props takes `Props` from
`@oxy.so/bloom/icons` instead — the full Bloom icon surface, with `style`,
the `size` rung, `gradient` and everything `react-native-svg` accepts.
`IconCircle` is the clear case: it sets `size` and a `color` style, so only a
real `Ri*` icon will do and `ComponentType<Props>` says so. `ChatIconComponent`
(`chat-indicators`) is narrower for its own reason — it adds `testID`, because
the chat parts label their glyphs for tests.

Those are deliberate and stay. Reaching for `Props` when you only set
width/height/fill is not: it refuses a caller's own glyph for no benefit.

### The per-family names still work

Twenty-five families had declared this same type under their own name
(`SidebarIcon`, `TrackIconComponent`, `ListingFactIcon`, `PlayerGlyph`,
`BadgeIcon`, `CallGlyph`, …). Those names still work — they are `@deprecated`
aliases of this one — so nothing needs changing; new code should reach for
`BloomIconComponent`.

That sentence is checked rather than promised. Writing the shape out again is
never a compile error (the literal IS the type), so a family can quietly mint a
twenty-sixth spelling and nothing goes red — which is exactly what happened to
`PlayerGlyph`, `BadgeIcon` and `CallGlyph`: named in this page as converted
while their own files still declared the literal.
`src/__tests__/icon-component-type.test.ts` now parses `src/` and holds four
properties: the shape is declared exactly once, that one declaration is
`icons/icon-component.ts`, the alias list is an EQUALITY (dropping one breaks a
consumer; adding one is a new name for a type that has one), and every alias
carries `@deprecated`.

## Migrating from the retired Bloom icon set

The old `<Subject>_<Stroke2|Filled>_Corner0_Rounded` exports (and the unsuffixed
`VerifiedCheck`, `AppleLogo`, `Bookmark`, …) are replaced by Remix. Every old
name has a reviewed Remix equivalent in **`src/icons/remix-mapping.json`**
(`{ "Check_Stroke2_Corner0_Rounded": "RiCheckLine", … }`); the
`Foundations/Icons → Migration` story renders each mapping so a decision can be
checked against its drawing.

The codemod applies it to an app:

```bash
node <bloom>/scripts/migrate-icons-to-remix.mjs <app-root> --dry-run --diff   # review
node <bloom>/scripts/migrate-icons-to-remix.mjs <app-root>                    # write
```

It rewrites named imports from `@oxy.so/bloom/icons` (and the legacy
`@oxyhq/bloom/icons`), `Icons.<Name>` namespace members, bare in-file usages of
an unaliased import, relative imports inside Bloom (`../icons/Check` →
`../icons/remix/RiCheckLine`), and old names in Markdown prose. Props need no
change — Remix components take the same `size` / `fill` / `style`. Anything it
cannot rewrite safely is **reported, not guessed**: an old name left in a string
or a shape it does not parse, and the logo wordmark `Full`, whose `markFill` /
`textFill` props have no Remix equivalent.

Two visual differences worth checking after migrating:

- **The two-tone badges are one colour now.** `VerifiedCheck` / `VerifierCheck`
  painted a white check over the badge; `RiVerifiedBadgeFill` cuts the check out,
  so it shows whatever is *behind* the icon.
- **Some subjects have no Remix drawing** and map to the nearest concept (a
  bell-with-plus becomes `RiNotificationBadgeLine`, a shaka `RiHandHeartLine`, a
  pizza slice `RiRestaurantLine`). The mapping file is the list.

## A wrong name is invisible to `tsc`

A name that does not exist — a shortened one, or a retired Bloom name in a doc
that was never migrated — is not a compile error anywhere such a reference
usually appears: in a **doc comment** or an `.mdx` example, TypeScript never
sees it. A reader copies it, gets `undefined`, and React reports "Element type is
invalid … but got: undefined" against *their* file — which is how a phantom
release blocker once got filed against the tab bar.

`src/__tests__/icon-references.test.ts` scans `src/`, `docs/`, `README.md` and
`AGENTS.md` for references that do not resolve against the real export union.
It is the only gate on this class of bug, and it deliberately does **not** strip
comments, because the comments are the surface under test.

## Two import shapes are correct, one is not

```tsx
import * as Icons from '@oxy.so/bloom/icons';   // ✅ the subpath, as a namespace
import { Icons } from '@oxy.so/bloom';          // ✅ the root barrel's namespace
```

The third shape — importing `Icons` as a *named* export from the **subpath** —
is `undefined` at runtime. The subpath exports the components flat; the `Icons`
name is assembled by the root barrel (`export * as Icons from './icons'`), so
there is no such named export to destructure.

The gate below flags that shape too, which is why this page describes it rather
than showing it: a counter-example spelled as a literal is indistinguishable
from the mistake it warns about, and the scan is right to flag both.

## Adding an icon

Generate it from the Remix SVG rather than hand-copying a path: one
`src/icons/remix/<RiName>.tsx` per glyph (a `createSinglePathSVG` call on the
24×24 viewBox), and `src/icons/remix/index.ts` regenerated from the directory
listing — never hand-edited. Use the exact Remix name, so a glyph found on
remixicon.com is findable here by the same string.

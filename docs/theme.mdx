# Theme

Mount `BloomProvider` once above the app's loading, auth and content branches.
It owns theme state together with Bloom's other app-wide contexts. See
[Provider](./provider.mdx) for the complete root and outlet setup.

```tsx
import { BloomProvider } from '@oxy.so/bloom/provider';

<BloomProvider defaultMode="system" defaultColorPreset="blue">
  <App />
</BloomProvider>
```

### Defaults, controlled identity and preferences

`defaultColorPreset` and `defaultMode` initialize uncontrolled state when there
is no persisted preference. A user's saved choice takes precedence over those
defaults. Use controlled `colorPreset` or `mode` when the app owns that value:

```tsx
<BloomProvider defaultMode="system" colorPreset="orange">
  <App />
</BloomProvider>
```

Here the preset stays orange even if storage contains a different preference;
mode remains user-selectable. Controlled props take precedence over hydration.
Use `onColorPresetChange` and `onModeChange` to receive requested changes when
controlling values from application state.

For Bloom-owned preferences, pass both `persistKey` and `storage`. Use the
public `webLocalStorage` adapter from `@oxy.so/bloom/theme` on web, or an
AsyncStorage-compatible adapter on native. Descendants change preferences with
`useBloomTheme().setMode()` and `.setColorPreset()`; `.resetTheme()` restores the
provider defaults and clears the persisted entry. No separate theme store or
manual localStorage edits are needed. `useTheme()` returns resolved paint;
`useBloomTheme()` also exposes the selected mode, preset and setters.

`BloomThemeProvider` remains the lower-level theme provider. Use `BloomProvider`
for an app root so scroll, locale and other Bloom contexts share that root.

## Modes

| Mode | Behavior |
|------|----------|
| `light` | Force light theme. |
| `dark` | Force dark theme. |
| `system` | Follow OS preference (`useColorScheme`). |
| `adaptive` | iOS/Android native dynamic colors when available, falls back to `system`. |

## Color presets

Named presets include `blue`, `orange`, `teal`, `green`, `yellow`, `red`,
`purple`, `pink`, `sky` and `mint`, alongside extended and paired palettes.
`yellow` is the supported name; there is no `amber` preset.

Use the public registry rather than copying a fixed list or count:

```tsx
import { APP_COLOR_NAMES, COLOR_PRESET_REGISTRY, FREE_COLOR_NAMES } from '@oxy.so/bloom/theme';
```

`APP_COLOR_NAMES` is the ordered list of valid names. `COLOR_PRESET_REGISTRY`
adds picker metadata such as display name, family, description, pairing and
access gate. `FREE_COLOR_NAMES`, `HANDLE_COLOR_NAMES` and `PREMIUM_COLOR_NAMES`
partition that registry by availability; consumers own the corresponding
identity or entitlement checks.

Each preset supplies light and dark tokens. The public `seed` prop can drive
an app-wide dynamic palette; clearing it restores the named preset.
`secondaryColor` and `tertiaryColor` optionally pin its additional accents.

## Reading theme values

```tsx
import { View } from 'react-native';
import { Text } from '@oxy.so/bloom/typography';
import { useTheme } from '@oxy.so/bloom/theme';

function MyComponent() {
  const theme = useTheme();
  return (
    <View style={{ backgroundColor: theme.colors.card }}>
      <Text style={{ color: theme.colors.text }}>{theme.isDark ? 'Dark' : 'Light'}</Text>
    </View>
  );
}
```

### Tokens

Every preset exposes:

- `colors.primary` — brand color.
- `colors.background` — page background.
- `colors.card` — card surface; `colors.backgroundSecondary` and
  `colors.backgroundTertiary` expose the secondary and tertiary backgrounds.
- `colors.text` — body text.
- `colors.textSecondary` — secondary text.
- `colors.border` — divider lines.
- `colors.success` / `colors.warning` / `colors.error` / `colors.info` —
  semantic colors, with corresponding `*Foreground` and `*Subtle` pairs.
- `isDark` — boolean.
- `mode` — resolved mode (`'light' | 'dark'`).

<Callout variant="info" title="Web CSS variables">
On web, Bloom writes the active palette to canonical CSS variables on `:root`,
including `--primary`, `--primary-foreground`, `--background`, `--foreground`,
`--card` and `--muted-foreground`. Raw HTML can read `var(--primary)`; configured
Tailwind/NativeWind consumers use the matching semantic utilities such as
`bg-primary` and `text-primary-foreground`. Do not redefine Bloom tokens in an app
to choose a preset: configure the provider instead.
</Callout>

## Mobile web document appearance

The app-wide provider is the sole runtime owner of document appearance. It
paints `html` and `body` from the canonical `--background` token, applies the
resolved `color-scheme`, and owns one `theme-color` meta so browser chrome
follows manual modes, system changes, presets and dynamic seeds. On first
mount it adopts one startup meta and removes the remaining fallback entries;
app-specific runtime writers must therefore be removed. Color and seed scopes
do not change these document-wide settings.

These settings take effect when the provider mounts. Prerendered apps may
supply media-qualified light/dark metadata and background CSS as a startup-only
fallback; Bloom transfers that ownership during hydration. Server rendering
cannot know a local persisted preference, so the OS preference is the honest
pre-hydration fallback. Loading and auth gates should paint with
`theme.colors.background`, never a hardcoded light or dark colour.
Browser and operating-system navigation areas may ignore `theme-color`; their
final appearance must be checked on a real mobile device.

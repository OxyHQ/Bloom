# TagField

Tags as an input. A CRM's skills, a task app's labels, a document's access list
and a notes app's tags are the same control, so **nothing in this family says
"note"** — the day it learns about one domain it stops being usable by the other
three.

```tsx
import { Field, TagField } from '@oxy.so/bloom';

<Field label="Tags" description="Anything you will want to search for later." error={error}>
  <TagField value={tags} onChange={setTags} suggestions={vocabulary} placeholder="Add a tag" />
</Field>
```

## Geometry

**The field IS a `text-field` box, not something that resembles one.** The fill,
the 10px radius, the 2px inset ring, the hover and focus rings, the invalid tint
and the disabled tint are all `text-field/shared.ts`'s, resolved through
`useTextFieldPalette()` for the surface this field actually lands on. An empty
`TagField` and an empty `TextFieldInput` in the same form are the same object.

|  |  |
| --- | --- |
| height, empty | 36 (`medium`) / 32 (`small`) — the text field's rung, exactly |
| shell inset | 4 above and below the chips; it **grows** as they wrap |
| chips | `Chip` at the rung that fills that inner height: 28 (`large`) / 24 |
| input | flexes to the end of the last line, 120 minimum, caret at 8 + 4 |
| suggestion panel | the menu surface: 16px corner, hairline, dropdown shadow |
| suggestion row | 36 tall on a 10px corner, the menu row highlight when active |

**The ring is an OVERLAY, not a border on the flex box.** `TextField` paints its
shell as an absolutely positioned child and this field copies that element,
because a 2px border would take its width out of the content box: with the chips
and the caret inside it, an empty tag field came out 40 tall beside a 36-tall
text field in the same form. That chrome is the one thing here that is copied
rather than reused — `text-field` exports its palette and its geometry, but not
the shell as a part.

The input flexing to the end of the line is deliberate: a press in the empty part
of that line lands on the caret itself. The whole shell is a hit area for it too,
through the same web `onClick` the text field's shell carries.

**The placeholder is drawn whenever the CARET is empty**, not only when the
field is. A box of chips with no visible caret and no prompt does not read as an
input at all, which is how this control once came to look like a container with
pills in it.

## It is a Field member

`useFieldMembership()` resolves the four things a form asks of a control, each
with a direction that is silently wrong the other way round: the **name** defers
to the field (`??`), `disabled` and `invalid` **combine** with it (`||`), the
**id** is the caller's then the field's, and `aria-describedby` is an id **list**
so the field's error is joined to the control's own hint rather than replacing
it. The full rule is in [Composition](/docs/composition) §Field.

The label placement is `stacked`: `TagField`'s own `label` says the same thing a
`Field`'s label above the box says, so the field wins.

## The three decisions that a render tree cannot show you

All of these live in `shared.ts`, pure and exported, because each fails
**invisibly**: a duplicate that is added anyway renders a perfectly ordinary
second chip.

**A duplicate is rejected quietly.** No error, no shake, no hint. The tag is
already there, so the field is already in the state the typist asked for, and
telling them off for it is noise. The comparison is case-insensitive —
"Design" and "design" are one tag to everybody except a string comparison.

**Being full is the one refusal with a consequence**, so it is the one reported
back (`onMaxReached`) and the one the hint names. At the ceiling the input stops
accepting; it is not hidden, because a disappearing caret reads as a bug.

**Suggestions exclude what is committed**, and match on a case-insensitive
**substring** rather than a prefix: tag vocabularies are compound ("Q3 planning",
"planning — legacy") and a prefix match hides the entry the typist was after.

## Input

- **A comma commits, wherever it comes from.** It is handled in the text change
  rather than in a key event, so it works on both platforms and a pasted
  `"a, b, c"` becomes three tags instead of one string with commas in it.
- **Enter commits** the highlighted suggestion if there is one, otherwise the
  typed text.
- **Backspace on an empty caret removes the last chip**, on both platforms.
- **Arrow keys and Escape move through the suggestions on web.** Native gets no
  arrow keys from a soft keyboard, so the list is a press target there.

The suggestion list is a real `listbox` of `option` rows with `aria-selected`,
and the input is a `combobox` carrying `aria-expanded`, `aria-controls` and
`aria-activedescendant`. It is painted in the **menu vocabulary** — the panel
surface, hairline and dropdown shadow of `floating/menu-palette.ts`, the 16px
panel corner and the 36-tall rows on a 10px corner every Bloom menu and select
draws — so a consumer reads it as the same kind of surface a `DropdownMenu`
opens. It sits **inline under the field** rather than in an overlay: nothing here
needs to escape a clipping ancestor, and an inline list is one less stacking
decision.

## Traps

- **`normalize` runs before every comparison**, so it is where any other answer
  to "are these the same tag?" goes — case-sensitivity, diacritics folding, a
  slug. The default only trims.
- **`allowCreate={false}` makes it a picker**, and a picker with no `suggestions`
  accepts nothing at all. That is the honest behaviour, not a bug to route
  around.
- **Each chip's × is `Chip`'s own**, named after the tag through `closeLabel`
  (`labels.remove`). A row of removable pills whose buttons are all called
  "Remove" gives a screen reader no way to say which one it is about. The ×
  therefore carries a NAME rather than a testID of its own — find it the way
  `mail-compose`'s suite does, inside `<testID>-chip-<tag>` by its label.
- **A suggestion row must not take focus, twice over.** It is `tabIndex={-1}`,
  because the combobox holds focus and points at the active row with
  `aria-activedescendant`; and it cancels the mousedown's default, because
  otherwise the press blurs the caret, `focused` goes false, the list unmounts
  under the pointer and the click lands on nothing. Measured in Chrome: every
  suggestion unclickable while the keyboard path worked perfectly. Neither is
  visible in a render tree, and `focusable={false}` does NOT do the first one —
  react-native-web's `Pressable` still emits `tabindex="0"`.
- **`value` is controlled.** There is no uncontrolled mode, because the
  interesting half of this control is what the app does with the list.

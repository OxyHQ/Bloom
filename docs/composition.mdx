# Composition

Bloom components share tokens. Sharing tokens is not the same as working together: a control still has to be told what material the container around it is painting, a label still has to be wired to the control it names, and a header still has to know which scroller it is following. Written as props, each of those is a thing the app repeats at every call site and gets wrong at one of them.

This page is the set of small, explicit contracts that answer those questions, and the rules that keep them small. Each is a context a container publishes and a component opts into. None of them is a framework, a singleton, or a component that reads its children's types to decide what to do with them.

## The precedence rule

Every contract on this page resolves the same way:

```
an explicit prop  >  the nearest container  >  the component's own default
```

`undefined` is the only value that defers. Passing `material="solid"` inside a glass island paints a solid control — the container is a default, not an override, and a caller can always win.

**A constraint is not a default.** Anything that RESTRICTS a control — `disabled`, a modal's inertness, the user's reduce-transparency or reduce-motion preference — travels on its own channel and combines with `||`, never `??`. The rule above is exactly wrong for those: a descendant must not be able to re-enable an action its group disabled by passing a prop.

**State does not travel either.** `checked`, `selected`, a field's value, a business datum: those belong to the component that holds them. A visual context that also carried state would make every container a place state can leak from.

## Control presentation — `ControlSurface`

`@oxy.so/bloom/control-surface`

What a container tells the controls inside it about presentation, and nothing else. Two fields, both visual configuration:

| field | values | meaning |
| --- | --- | --- |
| `material` | `'solid'` \| `'glass'` | the surface a control CONTAINER paints |
| `density` | `'md'` \| `'sm'` (also `'medium'` \| `'small'`) | the size controls default to |

```tsx
import { ControlSurface } from '@oxy.so/bloom/control-surface';

<ControlSurface material="glass">
  <ButtonGroup accessibilityLabel="Playback">…</ButtonGroup>
</ControlSurface>
```

It renders no node of its own, so it can be dropped anywhere without moving anything. Bloom's own containers mount it for you — `glass/GlassIsland` does, which is why a `ButtonGroup` inside a floating `PageHeader` is glass with no prop written on it.

A field left `undefined` inherits rather than resetting: `<ControlSurface density="small">` inside a glass island stays glass.

**Who reads it today:** `ButtonGroup` and `ButtonGroupItem` read `material`; `TextField`, `Textarea` and `TimeField` read `density`, and `PhoneInput` gets it by passing its `size` straight to `TextField`. `density` accepts `'medium' | 'small'` alongside `'md' | 'sm'`; legacy form sizes retain their public spellings — so a filter row can ask for `small` once instead of writing it on five controls:

```tsx
<ControlSurface density="small">
  <TextFieldInput label="Search" value={q} onChangeText={setQ} />
  <Textarea label="Notes" />
  <TimeField accessibilityLabel="From" value={from} onChange={setFrom} />
</ControlSurface>
```

A family whose sizes are a THREE-rung scale of its own (`small | medium | large`) is deliberately not a subject: a container setting `density` could not say which rung it meant.

**`Button` does not read it** — a `Button` in a floating header keeps its own chrome, which is right for a primary action in its own capsule and wrong for an icon action that should sit flush on an island. Use `ButtonGroup`/`ButtonGroupItem` for the latter.

Which families read it, which are exempt and why: [Adoption matrix](/docs/adoption-matrix).

Precedence is gated in both directions by `src/__tests__/ControlSurface.test.tsx`, including the assertion that the context carries exactly two fields.

## Field membership — `Field`

`@oxy.so/bloom/field`

A `Field` used to draw a label, a control and a hint, and wire none of them together. It associates them now: the control's id, `aria-describedby` for whichever of description/error is showing, the invalid state, the required state and the disabled state.

```tsx
<Field label="Email" description="We never share it." error={emailError} required>
  <TextFieldInput label="Email" value={email} onChangeText={setEmail} />
</Field>
```

- **Ids come from `useId`** when no `nativeID` is given, so they survive SSR and hydration. An explicit `nativeID` still owns every derived id.
- **The control's accessible NAME is the field's label.** On web a `<label for>` is a real association, but `aria-label` would override it; on native there is no association at all and the control must carry the name. So a control inside a field defers to the field's label text, and the visible label and the announced name cannot disagree.
- **`disabled` is a constraint.** A control inside a disabled field is disabled, and cannot opt out.
- **`multiple` is the several-controls case** — a radio set, a date's three boxes. The field becomes a labelled `group`, publishes no control id and describes the GROUP rather than each control: one id on three inputs is invalid HTML, and one error described by three inputs is announced three times.
- **A floating label and a `Field` label are alternatives, not layers.** `<TextFieldInput floatingLabel>` inside a `Field label="…"` shows the same words above the box and inside it. Pick one.

A control opts in with `useFieldMembership()`, which resolves the four decisions in one place:

```tsx
const field = useFieldMembership({ accessibilityLabel, label, disabled, invalid: isInvalid });

<Pressable
  nativeID={field.nativeID}
  accessibilityLabel={field.accessibilityLabel}
  aria-describedby={field.describedBy}
  aria-invalid={field.invalid || undefined}
  disabled={field.disabled}
/>
```

It is a function rather than a convention because each of the four has a direction that is silently wrong the other way round:

| what | direction | why |
| --- | --- | --- |
| the NAME | `??` — the field's, then the control's | a switch or a slider draws no words, so the field's label is the only name available |
| `disabled`, `invalid` | `||` — both | they RESTRICT; a control that could re-enable itself inside a disabled field is the bug |
| the ID | the caller's, then the field's | an app that wired its own association keeps it |
| `aria-describedby` | JOINED | it is an id LIST, so the field's error is added to the control's own hint rather than replacing it |

**`labelPlacement` decides which label wins.** A label drawn ABOVE the control (`TextField`, `Textarea`) is the same thing the field's label says, so the field wins. A label BESIDE the control (a checkbox's caption, a radio's option text) is the words the user reads AS the control, so it keeps its own and the field only fills a gap — otherwise a screen reader says one thing while the eye reads another.

Opt-in, not magic. A child that does not read the context renders exactly as before — a container cannot give an arbitrary child behaviour by wrapping it, and one that inspected its children's types to try would be guessing.

**Who reads it today:** `Checkbox`, `FileUpload`, `InputGroup`, `InputOtp`, `PhoneInput`, `Radio`, `RadioGroup`, `RatingInput`, `SegmentedControl`, `Select` (its trigger), `Slider`, `Stepper`, `Switch`, `Textarea`, `TextField`/`TextFieldInput` and `TimeField`.

Two consequences worth knowing:

- **A control that cannot name itself no longer needs a name prop inside a field.** `accessibilityLabel` on `Stepper`, `RatingInput` and `TimeField`, and `label` on `RadioGroup`, `SegmentedControl` and `SelectTrigger`, were required props and are now optional — with neither the prop nor a field the control announces nothing and warns once in development.
- **A composite hands the field's state to the halves that cannot read it themselves.** `PhoneInput`'s country picker is the measured case: the number input read the field, the picker did not, so it stayed operable inside a disabled field.

Gates: `src/__tests__/FieldAssociation.test.tsx` (the field publishes) and `src/__tests__/FieldMembership.test.tsx` (fifteen families apply, in both directions, and the subject list is asserted against the matrix).

## Trigger composition — `asChild`

Every anchored family (`Popover`, `DropdownMenu`, `ContextMenu`, `Menubar`, `Select`) takes `asChild` and merges its open handler and a11y state onto the caller's single element child. Three properties are worth knowing:

- **The child's handler runs first, and can CANCEL the open.** `event.preventDefault()` in the child's `onPress` stops the surface from opening — for a trigger that has just found the form dirty, or the row it belongs to gone. It is the event's own vocabulary because both platforms hand `onPress` a React synthetic event. On web the same call also suppresses the browser's default for that click, so cancelling on an anchor child cancels its navigation too.
- **A fragment child is refused.** `<Trigger asChild><>{control}</></Trigger>` passes every check a clone can make and then drops every prop, because a fragment has no host node. It throws now, naming the fix.
- **`disabled` is read from BOTH sides** — the trigger's own prop and the child's — in `cloneTrigger`, not left to whatever element the caller passed.

**A control used as a trigger must DECLARE the props it will be handed.** A component whose props are a closed list drops the ones it does not name, silently, because all of them are optional. `ButtonGroupItem` declares them, so this works:

```tsx
<ButtonGroup accessibilityLabel="Page actions">
  <Popover>
    <PopoverTrigger asChild label="More">
      <ButtonGroupItem iconOnly leadingIcon={RiMore2Line} accessibilityLabel="More" />
    </PopoverTrigger>
    <PopoverContent label="More">…</PopoverContent>
  </Popover>
</ButtonGroup>
```

**A trigger that IS a form control carries the field's wiring too** — `nativeID`, `aria-describedby` and `aria-invalid` are part of the handle, and `SelectTrigger` passes them. The other four families deliberately do not: a `Popover` inside a `Field` is not that field's control and must not take its id, so `TriggerSlot` reads no field context itself and each family decides whether it is the control.

Gate: `src/__tests__/TriggerComposition.test.tsx`.

## Scroll ownership — `ScrollOffsetProvider`

`@oxy.so/bloom/layout`

A screen has exactly one scroll owner, and the owner publishes its offset. Chrome reads it. Neither imports the other, so the provider's position in the tree is what pairs them — two panels side by side, each with its own header and its own scroller, resolve correctly.

```tsx
const scrollY = useSharedValue(0);
const onScroll = useAnimatedScrollHandler(
  { onScroll: (e) => { scrollY.value = e.contentOffset.y; } },
  [scrollY],
);

<ScrollOffsetProvider value={scrollY}>
  <PageHeader title="Inbox" />
  <Animated.ScrollView onScroll={onScroll} scrollEventThrottle={16}>…</Animated.ScrollView>
</ScrollOffsetProvider>
```

The context carries the `SharedValue`, not a number. It crosses once, at mount; every subsequent frame reaches the chrome on the UI thread through `useAnimatedStyle`, with no React render. A context whose value changed per frame would re-render every consumer per frame, which is the cost this exists to avoid.

`PageHeader` resolves its offset as: the `scrollY` prop, then the nearest `Screen`, then this context, then `window.scrollY` on web. Without any of the three on native it stays at rest. The context step is the one that matters for a desktop shell, where `window.scrollY` never moves and a header that followed it looked deliberately inert.

## Edge claims — `TopEdgeProvider` / `BottomEdgeProvider`

`@oxy.so/bloom/layout`

A surface that parks at a window edge CLAIMS its footprint; a surface or a scroll container that must clear it READS the total. Claims combine with `max`, not sum — every claim is measured from the same edge, so two surfaces at that edge overlap rather than stack.

`BottomBar` coordinates its navigation and lateral FAB footprint (`docs/bottom-bar.mdx`). The top edge is chrome that overlays content:

```tsx
<ScrollView contentContainerStyle={{ paddingTop: useTopEdgeInset() }}>
```

`BloomProvider` mounts both. A nested provider scopes a subtree to its own claims — which is what the next section is.

A claim registers in an effect, so a reader mounted in the same commit sees `0` on its first render. `PageHeader` narrows that to one frame by claiming its resting height (safe area + 56) immediately and replacing it with the measured height when `onLayout` reports.

## Screen scope — `ScreenScope`

`@oxy.so/bloom/layout`

A modal, a bottom sheet or a detail panel is a second SCREEN drawn over the first, and two of the contracts above are per-screen by design. Without a boundary they reach across it, in both directions and with no error either way:

- A header inside a full-screen dialog **claims the top edge of the page underneath it**. Claims combine with `max`, so the page behind the modal is padded for chrome it does not have — and the padding appears and disappears with the modal, because the claim unregisters on unmount.
- Chrome inside the sheet **reads the page's scroll offset** and follows a scroller the user is not touching. The sheet's own list scrolls and its header does not react; the page behind scrolls and it does.

`ScreenScope` is the boundary: a fresh top-edge registry, a fresh bottom-edge registry and a `null` scroll offset, which is the honest value — nothing inside has said which scroller it owns yet. A scroll owner INSIDE publishes in the ordinary way and wins, because it is nearer.

```tsx
<ScreenScope>
  <PageHeader title="Edit listing" onBack={close} />
  <ScrollView contentContainerStyle={{ paddingTop: useTopEdgeInset() }}>…</ScrollView>
</ScreenScope>
```

The bottom edge is scoped for the mirror reason: the bottom edge is the tab bar and the FAB, and a sheet is drawn OVER both, so a form inside it that cleared the tab bar would end in a band of empty space.

**Bloom's own surfaces mount it** — `DialogBody` (so every `Dialog` placement, including the bottom-sheet one, gets it) and `BottomSheetBase`. Mount it yourself only around a surface Bloom does not own: an app's own full-screen route presented over another.

Gate: `src/__tests__/ScreenScope.test.tsx`, asserting both directions — a claim inside must not escape, and the surface's own chrome must still be readable inside.

## Five compositions that are not a header

The contracts are worth nothing if they only work in the screen they were built for, so these five are gated together in `src/__tests__/composition-integration.test.tsx`:

1. **A form in a bottom sheet** — the field's error reaches the input across the sheet boundary, `Field disabled` reaches the input, the select trigger AND the switch, the switch takes its name from the field, and submit fires once per press.
2. **An interactive card with a secondary action** — pressing "Archive" inside a pressable row does not also open the row. (React Native does not bubble a press; a web build does bubble a click, so this half is a browser check, not this one.)
3. **A chat composer** — two presses send twice, and a disabled bar fires nothing at all.
4. **A data screen** — a table inside a panel inside a card keeps its own accessible name and renders its empty state; a filter in a `ControlSurface density="small"` draws the small geometry rather than merely receiving a prop.
5. **A screen with overlaying chrome and a modal over it** — the page pads for its own chrome, the modal's chrome does not reach it, and a sheet on that screen clears nothing of the page.

What that instrument cannot see is written at the top of the file: no paint, no layer order, no hit testing, no focus. Those have their own scripts in `scripts/verify-*.mjs`.

## What is not done

This page describes contracts that exist and are gated, and the [adoption matrix](/docs/adoption-matrix) measures where they are read. What is still open, named rather than implied:

- **Three families hand-roll the semantics of a grouped choice.** `questionnaire`, `listing-editor` and `listing-actions` write `role="radiogroup"`/`role="checkbox"` over their own cards instead of composing `RadioGroup`/`Checkbox`, so a `Field` can neither name nor disable them. Each is a redesign of an answer control rather than an import, which is why it is recorded instead of rushed. The matrix names them and the gate keeps the list from growing.
- **Seven families reconcile a controlled/uncontrolled pair by hand** rather than through `useControllableState`. The matrix names them too; `input-otp` has a reason (it cleans and pads the string), the rest do not.
- **State-family naming is not unified.** `value`/`defaultValue`/`onValueChange`, `checked`/`onCheckedChange` and `open`/`onOpenChange` are used consistently by the families that have them, but no sweep has been made to rename the exceptions (`onChangeText` among them, which is a React Native contract worth keeping).
- **`BloomProvider` still imports the Expo Router adapter directly.** Decoupling the core from the router is listed in #145 §8 and is not in this change.
- **No adaptive overflow.** Actions that do not fit are not collapsed into a menu. #145 says explicitly that this is not required for the first header, and nothing here does it.
- **iOS and Android are not device-verified for any of this.** The instruments used are `tsc`, the jest suites and a real Chrome; a native run is not among them.

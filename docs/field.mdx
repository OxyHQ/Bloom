# Field

`Field` wraps a control with the things around it — a label, a hint, an error —
and, more importantly, the associations that make a screen reader read them as
belonging to that control rather than as loose text near it.

```tsx
import { Field } from '@oxy.so/bloom/field';
import { TextField, TextFieldInput } from '@oxy.so/bloom/text-field';

<Field
  label="Email address"
  description="We only use this for sign-in."
  error={errors.email}
  required
>
  <TextField>
    <TextFieldInput label="Email" value={email} onChangeText={setEmail} />
  </TextField>
</Field>
```

## Which prop decides what

| prop          | decides                                                     |
| ------------- | ------------------------------------------------------------ |
| `label`       | the control's name                                           |
| `description` | a persistent hint, shown whether or not there is an error     |
| `error`       | the message; `null` or omitted means valid                    |
| `required`    | the required marker and the announced requirement             |
| `disabled`    | dims the whole group                                         |
| `multiple`    | the field holds several controls — a labelled `group`         |
| `nativeID`    | the id the label and control are wired through; generated when omitted |

## What the wiring actually does

The label, description and error are ASSOCIATED with the control, not merely stacked around it. A control opts in by reading `useFieldControl()`; Bloom's `TextFieldInput` does.

| the field publishes | the control applies |
| --- | --- |
| `controlId` | its `nativeID`, so the label's `for` points at it |
| `describedBy` | `aria-describedby` — the description, or the error once there is one |
| `labelText` | its accessible NAME |
| `invalid` | `aria-invalid` |
| `required` | `aria-required` |
| `disabled` | its own disabled state |

Three things worth knowing:

- **The ids come from `useId`** when no `nativeID` is given, so they survive SSR and hydration. An explicit `nativeID` still owns every derived id (`<id>-description`, `<id>-error`), so a form already wired by hand keeps working.
- **The field's label wins over the control's own.** On web `aria-label` OVERRIDES a `<label for>`, and on native there is no association at all and the control must carry the name — so a control inside a field defers to the field's label text, and the visible label and the announced name cannot disagree.
- **`disabled` is a constraint, not a default.** A control inside a disabled field is disabled and cannot opt out.

Opt-in, not magic: a child that does not read the context renders exactly as before. A container cannot give an arbitrary child behaviour by wrapping it, and one that inspected its children's types to try would be guessing. See [Composition](/docs/composition).

## One control, or several

A field with ONE control gives it the field's id and describes the error BY that control. A field with several — a radio set, a date's three boxes — must not: three inputs sharing one id is invalid HTML, and one error described by three inputs is announced three times.

```tsx
<Field label="Date of birth" multiple error={dobError}>
  <DayInput /> <MonthInput /> <YearInput />
</Field>
```

`multiple` makes the field a `role="group"` labelled by its own label and described by its own hint, and publishes no control id. Each control keeps its own id and its own name.

## Floating labels are an alternative, not a layer

`<TextFieldInput floatingLabel>` inside a `Field label="…"` shows the same words above the box and inside it. The ids and the described-by still travel, so the error is still announced — but pick one of the two labels.

## `error` is a string, not a boolean

Because the message *is* the value. A boolean `hasError` forces the message to
live somewhere else, and the two then disagree — a red border with no
explanation, or an explanation after the user already fixed it.

```tsx
<Field error={touched ? validate(value) : null}>
```

## A description is not an error, and an error is not a description

Keep both. The description says what the field is for and stays put; the error
says what went wrong with what was typed. Replacing the description with the
error means the user loses the instructions at the exact moment they need them.

## Placeholder is not a label

A placeholder disappears as soon as there is text, so a form filled in from
autofill or a paste has no visible labels at all. `Field`'s `label` is the
label; a placeholder is at most an example of the format.

## What it looks like

The field stack: the [`Label`](/docs/bloom/main/label), the control 4px
under it, and the description or error 4px under the control —
Inter `caption-1-medium` (12/16, tracking .15) with a 1px top inset,
`text-secondary` for a description and the error colour for an error. It lines
up to the pixel with a `TextField` built from `TextFieldLabel` / `TextFieldHint`.

## Composition

`Field` does not care what it wraps — a `TextField`, a `Switch`, a
`SegmentedControl`, a custom control. It supplies the label/description/error
and the id wiring; the control supplies its own role and state.

For the label alone, without the surrounding structure, use
[`Label`](/docs/bloom/main/label). For a control with attached buttons or
prefixes, use [`InputGroup`](/docs/bloom/main/input-group) *inside* a `Field`.

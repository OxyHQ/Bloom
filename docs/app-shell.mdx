# AppShell

`AppShell`, with `AppShellPanel`, `AppShellPanels`, `useAppShellPanel`, `AppShellHeader`, `AppShellMenuButton`, `useAppShell`, `NotificationBell` and `ProOfferCard`.

```tsx
import { AppShell, NotificationBell, ProOfferCard } from '@oxy.so/bloom/app-shell';

<AppShell
  sidebar={{ items, secondaryItems, selected, onNavigate, account, team }}
  title="Welcome Maya"
  breadcrumb={<Breadcrumb>…</Breadcrumb>}
  actions={<>
    <NotificationBell notifications={inbox} onAction={handle} />
    <Button  leadingIcon={RiAddFill} tone="accent" appearance="solid">Create ticket</Button>
  </>}
  overlay={showOffer ? <ProOfferCard … onDismiss={hideOffer} /> : null}
>
  {page}
</AppShell>
```

## Variants

One engine, four shapes. `variant` picks the shape; everything else — the nav,
the drawer, the pinned regions, the slots, the sizes, and the [panels](#panels)
the routes are made of — works the same in all four.

| `variant` | The page | Scroll |
| --- | --- | --- |
| `dashboard` (default) | nav + one fluid column capped at `contentMaxWidth`, optional `aside` | `document` / `container` / `fixed` |
| `feed` | nav + a `contentWidth` reading column CENTRED in what the nav leaves, optional `aside` beside it | `document` / `container` / `fixed` |
| `focus` | one centred `contentWidth` column and NO nav | `document` / `container` / `fixed` |
| `canvas` | ONE edge-to-edge area — no column, no cap, no padding — with the chrome floating over it | always one screen |

`dashboard` is what this component always was, unchanged to the pixel — the
existing stories render byte-identically against the version before variants
existed.

### `feed`

```tsx
<AppShell variant="feed" sidebar={sidebar} title="Home" aside={<Trending />} contentWidth={600}>
  {posts}
</AppShell>
```

The nav sits in flow, and the content column plus the aside are centred as a
PAIR in the space it leaves. The column is `flexBasis: contentWidth` with
`flexShrink: 1` and a matching `maxWidth`, never a `width` — so on a 360px phone
it shrinks to the screen instead of pushing the page sideways.

With `scroll="document"` (the default on web) the nav and the aside pin
themselves (`position: sticky`) and the centre column scrolls the page. Measured
in Chrome at 1440: after scrolling 406px the nav stayed at `y = 121` and the
aside at `y = 16` while the content moved from `16` to `-390`.

With `panels` the reading column is the REGION the routes' [panels](#panels)
are framed in: one `AppShellPanel` for a reading page, or several side by side.

### Screen pages

A route written once for both platforms —

```tsx
<AppShell variant="feed" panels scroll="page" sidebar={sidebar} bottomBar={<Tabs />}>
  <AppShellPanel>
    {/* the router's outlet; each route is: */}
    <Screen documentScroll header={<PageHeader title="Notes" safeArea={false} />}>
      <ScreenScrollView contentContainerClassName="gap-4 p-4" onEndReached={fetchNextPage}>…</ScreenScrollView>
    </Screen>
  </AppShellPanel>
</AppShell>
```

— needs the shell to scroll the DOCUMENT on web and to be one screen on native,
where the route's `ScreenScrollView` is the scroller. `scroll="document"`
cannot say that: native has no document, so it resolves to `container` and
wraps every route in the shell's own `ScrollView`, nesting the route's scroller
inside it. `scroll="page"` resolves to `document` on web and `fixed` on native:

- **Web:** identical to `scroll="document"` (the window scrolls; the route's
  `Screen documentScroll` keeps `ScreenScrollView` in document flow).
- **Native:** no shell `ScrollView`. A panel fills the screen under its pinned
  header, and the route's `ScreenScrollView` scrolls inside it. The shell pads
  nothing; it hands the occupied bottom edge (bottom bar, floating action) to the
  routes' Screens as their bottom inset, so content scrolls under the bar and the
  last row clears it plus the Screen's 16 of clearance. A shell without its own
  navigation scope gives its routes one, so their collapse motion is shared.
- `canvas` stays one screen, as for every mode, and `AppShellPanels` is one
  viewport tall in a document, so a route made of several panels never scrolls it.
- In a panel, a document `Screen` is one REGION tall (`100dvh` less the shell's
  gutters, top bar and reserved bottom bar), not one window: a `100dvh` page in a
  panel that starts a gutter down overflowed it, and every short page scrolled
  the document by the two gutters.

Apps that wrote `scroll={Platform.OS === 'web' ? 'document' : 'fixed'}` (Noted,
Mention) drop the ternary for `scroll="page"`.

Both are right; they are different apps. A feed with the address bar collapsing
on a phone and real anchor links wants `document`; a workspace whose regions
each keep their own position wants `fixed`. The panel adds no content padding:
`gutter` controls the outside frame, while each screen owns its title and body
insets. `contentWidth` is the full column width. Only measured bottom chrome
clearance is reserved automatically. Do not render a `ContentPanel` inside an
`AppShellPanel`; it trips the nesting guard.

### `canvas`

```tsx
<AppShell
  variant="canvas"
  sidebar={{ ...sidebar, surface: 'docked' }}
  aside={<PlacesInView />}
  floatingAction={<Button  leadingIcon={RiAddFill} tone="accent" appearance="solid">Add a pin</Button>}
>
  <Map />
</AppShell>
```

The content **is** the screen: one area, edge to edge, no reading column, no max
width, no padding, exactly one viewport tall. A map, a board, an editor, a photo
viewer. The header (if you pass one) sits above it in flow, because a toolbar
over a map belongs to the map; `topBar`, `bottomBar`, `floatingAction` and
`overlay` float over it as everywhere else.

The shell's padding moves OUT of the row and onto the regions, so the nav is
still a card with a gutter around it and the aside keeps its inset while the
canvas alone runs to the window's edge — no negative margins anywhere: each
region states its own inset.

**`canvas` never scrolls the document**: a canvas that grew the page would pan
the page instead of the canvas.
`scroll="document"` resolves to `fixed`, `scroll="container"` is honoured.

### `focus`

A single centred column and no navigation at all — sign-in, onboarding, a
reader. A `sidebar` passed to a `focus` shell is ignored (and `AppShellMenuButton`
renders nothing, because there is no drawer to open). The header and all three
bar slots still work, so a sign-up flow gets its pinned footer CTA:

```tsx
<AppShell variant="focus" contentWidth={480} title="Create your account"
  bottomBarVisibility="always" bottomBar={<Footer />}>
  {form}
</AppShell>
```

## Panels

A route is made of PANELS: rounded surfaces on the page background — one reading
panel, or several side by side (results and a map; a list, a message and its
details). The shell frames them; the routes say how many.

```tsx
// The frame: `panels` says the region holds AppShellPanel surfaces.
<AppShell variant="feed" panels scroll="page" sidebar={sidebar} aside={<RightBar />}
  gutter={8} navigationGap={8} navigationAlign="content" contentWidth={1800}>
  <Slot />
</AppShell>

// A layout whose every page is ONE reading panel (an Expo Router group: no URL segment).
export default function PagesLayout() {
  return <AppShellPanel><Slot /></AppShellPanel>;
}

// A route made of TWO.
<AppShellPanels collapseBelow={900} show={showMap ? 'map' : 'results'}>
  <AppShellPanel id="results" width={900} minWidth={520} maxWidth={1200} resizable>
    <Results />
    <Toggle to="map" />            {/* `useAppShellPanel().alone` → shown only alone */}
  </AppShellPanel>
  <AppShellPanel id="map" minWidth={380}>
    <Map />
  </AppShellPanel>
</AppShellPanels>
```

**Who owns what.** The SHELL owns the frame and publishes it to the panels (one
context, downward; nothing below ever reports back):

- **The gutter, on all four sides.** While framed, the region is `gutter` from
  the window's top, bottom and end edge and from the nav. A plain or docked nav
  runs flush to the start edge, so the row keeps only its END padding and the
  region pads its own top and bottom — the end side is the one a content-aligned
  row once forgot (a page without an aside ran to the window's edge). The aside
  column takes the same end gutter.
- **Framed or compact.** ONE rule, read off the shell's own width: framed while
  the navigation is in flow (`md` without navigation), or from `framedFrom` (a
  tier or any width). Compact means full-bleed panels and NO gutter on any side,
  in every mode — a phone never shows a strip of page background above a panel.
- **The gap between panels** is the same `gutter`. Separated panels each draw
  their own surface with the page background between them; `joined` panels
  share one surface with hairline dividers; compact panels are full-bleed with
  hairlines either way.
- **Viewport geometry and bottom clearance** per mode — below.

A PANEL (`AppShellPanel`) draws a surface (a [`ContentPanel`](/docs/bloom/main/content-panel)
underneath) and nothing else: `header` (chrome spanning it), `scroll`,
`colorPreset`, `appearance`, `chrome`, `errorBoundary`. A GROUP
(`AppShellPanels`) lays several out:

- **One workspace header.** Put chrome spanning every panel in `layout.header`.
  The compositor uses its existing `Screen` to reserve the header once; the
  tracks measure the remaining space and their own `ScreenScrollView`s retain
  scrolling. In a joined group the header and tracks share one Surface. In a
  separated group the header sits above the individual panel surfaces. Keep
  the property present and use `header: null` to temporarily hide it without
  remounting panel content. Stable panel IDs preserve editors and open overlays
  when sibling panels appear or disappear.
- **Inherit an existing surface.** `appearance="plain"` (or
  `layout.appearance: 'plain'`) uses joined geometry and dividers without
  painting another material. Use it for a local workspace inside a Dialog that
  already owns its Surface. It supports the same shared header and scrolling
  contracts; it does not introduce another viewport or scroll owner.
- **Sizes without arithmetic.** A panel with `width` rests at it and shrinks
  down to its `minWidth`; a panel without one takes the room left, never below
  its own `minWidth`. Flexbox sums the min-clamped bases first, so a narrow group
  shrinks the SIZED panel before the flexible one gives up its minimum — a map
  beside a results list stays a map.
- **`resizable`** puts the shared `ResizeHandle` (pointer capture on web, a
  `PanResponder` on native, arrow keys ±16) on the panel's end edge, centred in
  the gap. A drag starts from the width the panel is DRAWN at and is clamped to
  `minWidth`/`maxWidth`; `onWidthChange` reports where it settled.
- **`collapseBelow`** — a width of the group's OWN box, so a sidebar or an aside
  beside it counts — below which exactly ONE panel renders: the one `show` names,
  else the first. Mounted inline content is retained, inert and hidden from accessibility. Set `keepMounted` on a panel to mount it even while initially hidden.
- **Controlled sizes.** Pass `widths` and `onWidthsChange` to the group using panel IDs as keys. These delegate to `panelLayout`'s existing size contract; `onWidthChange` on an individual panel also reports the settled width.
- **`useAppShellPanel()`** inside a panel returns `{ id, alone, framed }`.
  `alone` is true while the group is collapsed (or has one panel): a panel shows
  its own way to the other one — a Map / List toggle — exactly then.
- **`hideBelow`** on a trailing panel (a message's details) drops it below the
  group width it needs.

The JSX group translates its direct panel children into the same descriptors used by `AppShell.panelLayout`. IDs, sizing, responsive selection, retention and dividers share one engine. Conditional panel children remain supported.

### Bounded reveal workspaces

`drawer="reveal"` keeps its page host mounted across compact and desktop
navigation. In `fixed` and `container` modes, every host between the shell and
its panel row must use the shared bounded flex recipe (grow 1, shrink 1, basis 0,
minimum height 0). Growing alone lets a long sidebar determine the page height:
a 900px viewport previously produced 1922px panels with 40 navigation entries.
The sidebar and panel contents must scroll inside the available height. Document
mode keeps intrinsic growth and must not acquire clipping from this recipe.

The `BoundedRevealPanels` story exercises long navigation and content;
`AppShellScrollSwitch.web.test.tsx` checks the complete retained ancestor chain
and round trips through document flow. Browser verification must measure panel
bottoms at short viewport heights, since jsdom does not perform flex layout.

### Scroll ownership

| Region (`scroll`) | A sole `AppShellPanel` | `AppShellPanels` |
| --- | --- | --- |
| `document` / `page` on web | grows with the page; its frame is a screen-tall sticky rectangle pinned at the gutter; reserves the bottom bar under its content | one viewport tall less the gutters and top bar — the document has nothing to scroll |
| `fixed` / `page` on native | fills the region; the content (a `ScreenScrollView`, a `FlatList`, a navigator) scrolls itself and clears the bar with `useBottomEdgeInset()` | fills the region; each panel's content scrolls itself |
| `container` | grows inside the shell's `ScrollView` | fills the scroller's viewport |

`scroll="panel"` on a panel in a bounded region wraps its content in Bloom's own
`ScrollView`, padded clear of the bottom bar, for content that does not scroll
itself. The default, `scroll="content"`, never nests a second scroller.

Because a group bounds itself, a route made of several panels needs no `scroll`
of its own: the shell stays `page` for every route. (Switching `scroll` per route
is still supported — and never remounts the routes, see below.)

An inline work area, such as a database board inside a document, uses
`AppShellPanels scope="local"`. This explicitly establishes its own bounded
composition: page viewport insets and bottom-edge claims stop at that boundary,
and its mask follows the actual containing surface. Its panels may therefore
live inside a page panel without pretending to be another page frame.
Default `scope="region"` still rejects nested page panels, as does a direct
`ContentPanel` inside any local panel. The host supplies the local work area's
available space; its deck and column Screens own scrolling within that space.
`ProjectBoard variant="embedded"` and `"grouped"` establish this scope internally.

### Where the panel goes

Put it where the layout is DECLARED: around the outlet when every page is one
panel; in a route group's layout for a section (Homiio: every page in an
`app/(pages)/` group whose layout is `<AppShellPanel><Slot/></AppShellPanel>`,
and `/explore` outside it rendering two); in a route that is several. The shell
never wraps its children in a surface itself, which is what lets a route choose:
a shell that drew a default panel could only learn that a route wanted two by
being told from below. A route can also change its mind per state — explore
renders one panel for an error and two for results.

`canvas` hosts no panels: the screen is the canvas.

## Pinned slots

`topBar`, `bottomBar` and `floatingAction` exist so that **nothing in a
consumer's code needs `position: fixed`, a negative margin, or a window-width
hook to sit in the right place.** Every app that has drawn a phone tab bar has
written the same four lines, and all four are wrong somewhere: a fixed bar is
wrong inside an embedded shell, a hardcoded `bottom` is wrong on a notched
phone, and a negative margin is wrong the moment the page's padding changes.

```tsx
<AppShell
  variant="feed"
  sidebar={sidebar}
  topBar={<PhoneHeader leading={<AppShellMenuButton />} />}
  bottomBar={<Tabs />}
  floatingAction={<Button iconOnly leadingIcon={RiQuillPenLine} accessibilityLabel="Compose" />}
>
  {feed}
</AppShell>
```

- **`topBar`** is a sibling ABOVE the shell's columns, so it spans the shell edge
  to edge without escaping the frame's padding. Sticky to the top with document
  scroll; simply outside the scroller otherwise. It takes the TOP safe-area inset
  as padding. `header` is the in-column page heading and is unaffected — a shell
  may have both — but while a `topBar` is drawn the default header does not add a
  SECOND hamburger under it; put an `AppShellMenuButton` in the bar.
  Not drawn under `drawer="reveal"`, which slides the whole page sideways.
- **`bottomBar`** is pinned to the bottom of the viewport (document scroll) or of
  the frame, with the BOTTOM safe-area inset as its own padding — so the bar's
  background paints under the home indicator instead of leaving a stripe of page
  showing through.
- **`floatingAction`** sits a `gutter` above the bar (or above the safe area when
  there is no bar), in the `floatingActionPlacement` corner (`end` by default).
  The wrapper spans the width and ALIGNS its child, so the button never has to
  know its own width. It has no `compact`/`always` switch: a compose button is
  not phone chrome, so it is drawn whenever it is given — pass `null` to drop it.

Both bars are MEASURED. By default the content column reserves their height, so
the last row of a feed is never hidden behind them. A dashboard with
`reserveBottomBarSpace={false}` keeps the bottom bar over the full-height content,
including with `scroll="fixed"`. Its scrollers should apply
`useBottomEdgeInset()` from `@oxy.so/bloom/layout` as bottom content padding, so
the final item can scroll clear while the page background continues underneath. Measured in Chrome at 390,
scrolled to the page end: last item bottom `768`, action top `784`, bar top `844`.

With a content panel, the reserved clearance stays inside its painted surface.
In the compact full-width layout, bottom chrome also inherits that panel fill,
so its fading backdrop does not introduce a strip of the outer page color.


**Native safe-area ownership.**

Use `<AppShell safeArea scroll="fixed" ...>` when the shell owns the whole
native screen. The frame protects its top and side edges, including landscape
notches, and keeps reveal navigation inside the same safe frame. Portaled
navigation drawers use the device's original insets. Web geometry is unchanged;
`safeArea` defaults to `false` for existing embedded shells.

When bottom chrome is visible, the bottom-bar slot or floating action retains
ownership of the bottom inset. Otherwise the frame reserves it. There is no
second bottom inset around a bar. Set `safeArea={false}` on descendant
`PageHeader` components because the shell already protects their top edge.
The real `SafeAreaInsetsContext` remains intact for fullscreen dialogs.

`topBarVisibility` / `bottomBarVisibility` are `compact` (the default — only
while the nav is a drawer, the phone case the slots exist for) or `always`, for
a bar that is part of the app at every width.

## Breakpoints an app can name itself

For centred feed layouts, `navigationGap` and `asideGap` control the gaps on
either side of the reading column independently of the panel's `gutter`.
Set both to the same value for symmetric columns.

Leave navigation tiers unset for automatic drawer, tablet rail and capacity-aware desktop panel behavior. For exceptional layouts, every `*From` prop accepts a named tier (`sm` 640 · `md` 768 · `lg` 1024 · `xl` 1280) **or a width in pixels**. This example deliberately overrides the standard navigation placement:

```tsx
<AppShell
  variant="feed"
  panels                    // the routes are AppShellPanels the shell frames
  navFrom={500}             // rail in flow from 500, a drawer below it
  navExpandedFrom={1300}    // icons until 1300, labels past it
  asideFrom={990}
  asideWidth={350}
  sidebar={sidebar}
  aside={<SideColumn />}
>
  {feed}
</AppShell>
```

The tiers stay the default vocabulary — `breakpointPx` resolves either — so a
shell that says nothing still lays out on Bloom's own scale.

## Sizes and breakpoints

Every number is a prop, and `APP_SHELL_DEFAULTS` is the exported record of the
defaults.

| Prop | Default | Why |
| --- | --- | --- |
| `contentMaxWidth` | 1300 | `dashboard`'s cap. The column is fluid and stops growing here. |
| `contentWidth` | 600 | `feed`/`focus`. The measure a single column of `body-regular` holds at ~75 characters — wider loses the line, narrower breaks too often. |
| `asideWidth` | 320 | |
| `asideFrom` | `xl` (1280) | 272 (panel) + 600 + 320 + three gutters is 1216: `xl` is the first tier where three columns fit without squeezing the content. |
| `navFrom` | `md` automatically; `lg` for an explicit panel, `sm` for an explicit rail | Where the nav sits in FLOW; below it the same props drive the drawer. |
| `navExpandedFrom` | `lg` automatically | Icons below, labels above: the shell swaps `sidebar.variant` between `rail` and `panel`. Setting it also makes `navFrom` default to `sm`, because below that tier the nav IS a rail. |
| `gutter` | 12 (`dashboard`), 16 (others) | The space between the shell's edge and its regions, and between the regions. `dashboard` keeps the 12-padding/16-gap pair it shipped with, because changing either moves every existing page by four pixels. |
| `framedFrom` | the nav's own tier (`md` without nav) | `panels`: where panels turn from full-bleed to framed. |

## The shell measures ITSELF

Every breakpoint above is read off the shell's own laid-out width, not the
window. A shell mounted in a preview pane, in one half of a split view, or
inside a desktop app's own chrome is narrower than the window, and a
window-width decision puts three columns into a 480px box.

The fallback before the first layout is the WINDOW rather than zero: otherwise
frame one would be a phone layout for every shell and the correction would be a
visible reflow on every page load. A shell that spans the page is therefore
right on the first paint, and only an embedded one pays a single layout pass.

One consequence worth knowing: where the browser draws a CLASSIC (space-taking)
document scrollbar, the shell's box is `innerWidth` minus its width, so a
breakpoint crossed within ~15px of the boundary lands one tier lower than the
equivalent CSS media query would. That is the layout reading the space it
actually has, and it is the same reason the measurement exists — but it is a
real difference from `@media`, not an accident. (Chrome's headless shell uses
overlay scrollbars, so every measurement below has the shell's width exactly
equal to `innerWidth`.)

(The measurement is `useContainerWidth`, the hook `listing-details` already uses
for the same reason.)

## Why there are no tricks in here

The shape this replaced was a template full of them: negative margins to escape
the preview's padding, an ad-hoc `position: fixed` for the bottom bar and the
floating button, a per-story sticky column — and it broke at phone widths. None
of that is in the shell, and none of it is left for a consumer:

- Every region is a flex child of one row, sized by `flexBasis` + `maxWidth` and
  allowed to SHRINK. A `width` is what overflows; a basis that shrinks cannot.
- The only `position` values in the family are the sticky nav/aside and the bar
  slots' own anchor, all inside the shell. No `100vw`, no negative margin, no
  window-width hook anywhere.
- Stories set `parameters: { bleed: true }` (see `.storybook/preview.tsx`) and
  the shell fills what it is given — no per-story CSS.

Verified in Chrome across `dashboard`, `dashboard + aside`, `feed`,
`feed + panel`, `feed + chrome`, `split` (now `panels`) and `focus`, at 360, 390, 414, 768,
834, 1024, 1280, 1440 and 1920, in light and dark: 126 renders, no sideways
scroll anywhere (`scrollWidth === innerWidth` in every one), no sibling region
overlapping another, and no console error.

## Layout

- `lg` and up: the rail sits in flow; the content column is centred, max `contentMaxWidth` (1300), header then content 16 apart.
- Below `lg` the header shows a menu button. `drawer="overlay"` is the default; dashboard and feed also take `drawer="reveal"`:
  - `overlay` — a drawer over the page on a 40% black backdrop (portaled through `OverlayRoot`, so it ranks with every other overlay).
  - `reveal` — the rail waits flat beneath the page; the page slides 272 toward the end edge (right in LTR, left in RTL) and rounds to 32 while the rail scales in from 0.94 (325ms). Pressing the page closes it.
- `drawerOpen` / `onDrawerOpenChange` control it.
- `drawerSwipe` (native, default off) adds the edge swipe expo-router's `Drawer` has: see [Edge swipe](#edge-swipe-native).
- `sidebar={{ variant: 'rail', … }}` keeps the 80px navigation rail in flow from `sm` instead of `lg`; below `sm` the menu button opens the drawer, which always shows the full panel.

Web reveal writes its target once and uses one CSS transition recipe for the
page, rail, chrome and veil (325ms, `cubic-bezier(0.42, 0, 0.58, 1)`), without
JavaScript work on each animation frame. Native retains UI-thread timing.
Reduced motion uses zero duration on both platforms. Closed reveal navigation
is hidden from accessibility and inert to keyboard focus on web.
Reveal uses the shared compact-panel interaction contract: initial focus, Tab
containment and focus restoration on web; keyboard dismissal and Android back
on native. Escape and back yield to overlays above the navigation. The displaced
page and its bars are inert while navigation is open; its closing veil remains
interactive. Dashboard and feed share this frame and their ordinary body layout.

### Edge swipe (native)

`drawerSwipe` gives the narrow-screen drawer the gesture expo-router's `Drawer`
has with `swipeEnabled`, so an app that moves from that navigator to AppShell
keeps it:

```tsx
<AppShell sidebar={{ items }} drawerSwipe drawerOpen={open} onDrawerOpenChange={setOpen}>
```

- **Closed:** a pan that STARTS within 32 of the start edge (the left in LTR,
  the right in RTL; `DRAWER_SWIPE.edgeWidth`, expo-router's `swipeEdgeWidth`
  default) and moves toward the end edge drags the drawer open, 1:1 with the
  finger. A touch outside the strip is turned away on touch-down, so the page
  keeps its own gestures.
- **Open:** a pan toward the start edge closes it, from anywhere on the drawer
  or its backdrop (`overlay`), or on the drawer or the page it pushed aside
  (`reveal`).
- **Release:** faster than 500 points/s settles in the fling's direction;
  slower settles on whichever side of half way the drawer was let go. The
  remaining distance eases out over at most 325ms; reduced motion snaps.
- **State:** the landing, and only the landing, reaches React: the shell calls
  `onDrawerOpenChange` once the drawer is at rest (nothing for a pan that
  snapped back to where it was), so `drawerOpen` stays the one source of truth,
  controlled or not. A controlled parent that keeps it closed gets the request,
  and the drawer slides back.
- **Scrolling:** 10 points of horizontal travel in the drag's own direction
  claim the touch and 15 vertical fail it first, so the sidebar's list and the
  page keep scrolling.
- **Motion:** the finger drives the drawer's existing open amount on the UI
  thread (gesture-handler + reanimated worklets). `reveal` moves the page, as
  its press animation does; `overlay` slides the drawer box in from off-screen
  over a backdrop that fades with it — and under `drawerSwipe` it also slides
  in and out (325ms) when the hamburger or the backdrop opens or closes it,
  rather than appearing.

Off by default: a left-edge pan competes with the iOS native-stack back swipe,
so only an app whose drawer is ITS edge gesture opts in. The web has no edge
swipe and ignores the prop. It needs the app-root `GestureHandlerRootView` that
gesture-handler always does. The gesture is an addition: the hamburger, the
backdrop, the `reveal` veil and the sidebar's close button stay the accessible
way to open and close the drawer. Gate: `src/__tests__/AppShellDrawerSwipe.test.tsx`
drives the recorded pan callbacks; a real finger against a real ScrollView, or
against iOS's back swipe, is for a device.

### A complete domain sidebar

`AppShellSidebarProps` extends the ordinary Sidebar configuration with `width`
and `render`. `width` is the expanded region width; finite numbers clamp to zero,
and omitted or nonfinite values fall back to the selected size's metrics. The
same resolved width drives CSS capacity, native geometry, and the reveal rail
and page displacement. The ordinary medium geometry stays 260px expanded with
a 272px reveal displacement; custom widths replace that expanded measurement.

`render` receives the resolved Sidebar props, including its `variant`, collapse
state, `mobile`, `onClose`, style and navigation callbacks. An explicit width also
enables Sidebar's fluid measurement so its content follows the region. Return a complete
domain sidebar, without nesting it inside another Sidebar:

```tsx
<AppShell
  sidebar={{
    variant: 'panel', collapsed: false, collapseDisabled: true,
    render: props => <ConversationSidebar {...props} conversations={conversations}
      activeId={activeId} onSelect={setActiveId} />,
  }}
  panelLayout={workspacePanels}
/>
```

Use Sidebar `content` for destinations inside its existing scroller. Use the
shell's `sidebar.render` slot when the domain component already owns the whole
Sidebar. Store durable conversation/search state in the host when it is shared
across desktop and compact presentations. The shell remains the sole owner of
navigation geometry and reveal motion.

## Aside

```tsx
<AppShell sidebar={sidebar} title="Tickets" aside={<ActivityPanel />} asideWidth={320} asideFrom="xl">
  {page}
</AppShell>
```

A second column at the end edge of the page — the right in LTR, the left in RTL (`dashboard` and `feed`; a
route's own extra column is a trailing [panel](#panels) instead, and `focus` has no second column at all). From `asideFrom` (`xl`, 1280; or `md` / `lg`) it sits beside the content at `asideWidth` (320), pinned like the sidebar — with document scroll it stays in natural document flow. A tall aside scrolls with the page until its lower edge is visible, then sticks; it does not capture wheel gestures in a nested ScrollView. Container and fixed modes retain bounded aside scrolling. Below the breakpoint it is stacked after the content (`asideCollapse="stack"`, the default) or dropped (`"hidden"`). Under `drawer="reveal"` it slides with the page.

**An aside that renders nothing takes no room.** Build a rail from data-driven
widgets that each return `null` when they have nothing to show, and pass it
unconditionally — don't pre-compute emptiness in the app. The shell measures the
aside's content: at zero height the column gives up its width AND its gap (a
centred feed re-centres the reading column alone), and a stacked aside takes no
slot. The content stays mounted, invisible and out of flow, still measured at
the aside's width, so the column returns as soon as a widget renders. Works
beside the content in `document`, `container` and `fixed` modes, and stacked.

The trade-off is deliberate: the column is reserved until the first
measurement, so the common non-empty aside never jumps on first paint, while an
empty one shows its reserved space for that one layout pass. Emptiness means
zero height: a wrapper with padding or a border around empty widgets is not
empty — put spacing in `gap`, which a lone or absent child does not spend.

## Eight shells, one component

The shape (`variant`), what scrolls (`scroll`), whether the routes are panels
(`panels`) and the nav's own look (`sidebar.surface` / `sidebar.size`) are
independent. That is the point: an app picks a row from this table and does not
look like the app that picked the row above it.

| The app | variant | scroll | nav |
| --- | --- | --- | --- |
| Product dashboard | `dashboard` | `document` | `card`, `md` |
| Social reader | `feed` + `panels` | `fixed` | `plain`, `lg` |
| Long-form feed | `feed` | `document` | `card`, `md` |
| Workspace (channels, files) | `dashboard` | `fixed` | `docked`, `sm` |
| Messenger | `dashboard` + `panels`, `joined` | `fixed` | `docked`, `sm` |
| Map / board / editor | `canvas` | one screen | `docked`, `md` |
| Marketplace | `dashboard`, no `sidebar`, `topBar` `always` | `document` | — |
| Sign-in, onboarding, reader | `focus` | `document` | none |

```tsx
// Social reader: a framed column that fills the screen, a nav with no edge.
<AppShell variant="feed" panels scroll="fixed" sidebar={{ items, surface: 'plain', size: 'lg' }}>
  <AppShellPanel header={<PageHeader title="Home" />}>{feed}</AppShellPanel>
</AppShell>

// Workspace: a column flush to the window, the page bounded, its own scrollers.
<AppShell scroll="fixed" sidebar={{ items, surface: 'docked', size: 'sm' }} title="Reports">
  {report}
</AppShell>

// Marketplace: no rail at all — the navigation is the bar across the top.
<AppShell topBar={<MarketHeader />} topBarVisibility="always" contentMaxWidth={1280}>
  {results}
</AppShell>
```

The stories **Three identities**, **Feed in a full-height panel** and **Canvas**
render three of these side by side with nothing positioned by hand.

## The nav's identity is not the shell's layout

`variant` picks the LAYOUT; `sidebar.surface` and `sidebar.size` pick what the navigation looks like. They are separate axes on purpose — the same shell carries a social reader, a workspace and a product dashboard without any of them re-implementing it:

```tsx
<AppShell variant="feed" sidebar={{ items, surface: 'plain', size: 'lg' }} />     {/* a reader */}
<AppShell sidebar={{ items, surface: 'docked', size: 'sm' }} />                    {/* a workspace */}
<AppShell sidebar={{ items }} />                                                     {/* the floating card */}
```

A `docked` nav is flush to the window: the shell drops its start (left in LTR) and vertical padding around that column, gives up the column gap and lets the nav run the full height, because the nav's own hairline is the separator. Everything else about the shell is unchanged. The surfaces and sizes themselves are in [`Sidebar`](/docs/bloom/main/sidebar).

## Opening the drawer without a title

The default header renders whenever it has something to show, and below `lg` the menu button counts — so `<AppShell sidebar={…}>` with no `title` still gets a hamburger, and nothing at all while the sidebar sits in flow.

A page that draws its own `header` keeps the drawer reachable with either:

```tsx
import { AppShellMenuButton, useAppShell } from '@oxy.so/bloom/app-shell';

<AppShell sidebar={sidebar} header={<MyHeader leading={<AppShellMenuButton />} />}>…</AppShell>

function MyHeader() {
  const { drawerAvailable, drawerOpen, openDrawer, closeDrawer, toggleDrawer } = useAppShell();
  …
}
```

`AppShellMenuButton` is the same button the header uses and renders nothing while the sidebar is in flow. `useAppShell()` works anywhere inside the shell (the header, the page, the aside); `drawerAvailable` says whether there is a drawer to open right now.

`header={null}` means **no header**: not the default one, and not the menu button either — the page has said it owns that corner, so it also owns getting the drawer open (`useAppShell()`, an `AppShellMenuButton` of its own). Leave `header` off to get the default.

## A fixed screen

`scroll="fixed"` makes the shell exactly one screen tall (`100dvh` on web, its parent on native) and scrolls nothing: the header stays, and the content column fills the height left under it (`flex: 1`). The page owns its scrolling — a chat with a pinned composer, a map, a board:

```tsx
<AppShell scroll="fixed" sidebar={sidebar} title="Chat">
  <View style={{ flex: 1, minHeight: 0 }}>
    <MessageList style={{ flex: 1 }} />
    <Composer />
  </View>
</AppShell>
```

Give the page `flex: 1` and `minHeight: 0`, or a tall child grows the column past the screen instead of scrolling inside it.

### Switching `scroll` per route

An app whose routes differ can pick the mode per route — a map screen fixed, the rest of the app a page:

```tsx
<AppShell variant="feed" panels scroll={isMapRoute ? 'fixed' : 'page'} sidebar={sidebar}>
  <Slot />
</AppShell>
```

That is supported: after any switch the shell lays out exactly as a fresh mount in the new mode would. The regions that change with the mode keep their DOM node across the switch, so on web what lands is React DOM's DIFF of their two inline styles — a dropped key is cleared with `style[key] = ''`, and only keys whose value changed are written. The shell therefore spells every mode-dependent flex in longhands (`flexGrow`/`flexShrink`/`flexBasis`), never `flex: 1`: clearing a `flex` shorthand also clears the longhands beside it, and an unchanged longhand is never written back. That is how a switch from `fixed` to `page` once left the reading row with no flex at all — as wide as its content, pushing the sidebar off the page — with React warning "Removing a style property during rerender (flex) when a conflicting property is set (flexShrink)". Gate: `AppShellScrollSwitch.web.test.tsx` switches every variant between every pair of modes, at a desktop and a phone width, and compares each against a fresh mount.

**A switch never remounts the routes** between `document`, `page` and `fixed`: the shell's tree around its children is the same node in all three, and the panels inside only read the new region (gate: the same suite mounts a route through `page → fixed → document → fixed → page` and counts one mount). `container` scrolls in a `ScrollView`, a different element, and is outside that promise. Before panels, a shell `panel` built different trees for bounded and document modes, and an app switching per route remounted its router outlet every time.

## Scrolling on web

The page scrolls the **document**, like a [`ContentPanel`](/docs/bloom/main/content-panel) page — not a scroll view inside the frame. The shell is at least one viewport tall and grows with its content; the in-flow sidebar is `position: sticky`, so it stays put while the page moves under it. That is what makes scroll restoration, the mobile address bar collapsing, anchor links and `window.scrollTo` behave as they do on any web page.

- Nothing between the shell and the document may become a scroll container: a parent with `height: 100%` plus `overflow: hidden` (or `auto`) around `AppShell` pins the sidebar to a box that never scrolls. Mount it straight under the app root.
- Compact `reveal` clips the sliding page with `overflow: clip`, not `hidden`, for the same reason — and so the 272px slide never adds a horizontal scrollbar. The waiting rail is `position: fixed`. The stable feed wrapper returns to visible overflow on desktop, allowing document decks to extend horizontally.
- `scroll="container"` restores the old behaviour — the shell fills its parent and the page scrolls inside its own `ScrollView` — for a shell embedded in a bounded box rather than owning the page.

Native has no document: `document` behaves as `container` there, and `fixed` works the same as on web.

## On native

Every variant and every slot works on native; what changes is the mechanism,
never the arrangement:

- The nav and the aside are not sticky — on native the shell is always a bounded
  box (`container` / `fixed`), so they are ordinary full-height flex columns and
  stay put by construction.
- `bottomBar` and `floatingAction` anchor `position: absolute` inside the
  shell's own frame rather than `fixed` to a viewport. Yoga has no `fixed`, and
  it ignores it SILENTLY — a bar written that way would scroll away with no
  error to explain it.
- `topBar` is simply the first child above the columns and outside the scroller,
  which pins it without any positioning at all.
- Safe-area insets come from `SafeAreaInsetsContext` — read with `useContext`,
  not `useSafeAreaInsets`, which throws outside a provider. `AppShell` is
  mounted at an app's root, and making a previously optional provider mandatory
  would break every consumer that never had a bar to inset. Outside one the
  insets are zero.
- A resizable panel's divider drags through a `PanResponder` (`ai-chat`'s handle
  owns both paths).
- An `AppShellPanel` resolves to `ContentPanel`'s native variant — a plain rounded,
  bordered surface, with none of the web sticky-overlay machinery, which is what
  it should be where there is no document to bleed into.

None of this is exercised by the web gate: jest resolves no platform extensions
here, and Storybook is react-native-web. It is reasoned, not measured.

## Right-to-left

`AppShell`, `Sidebar`, `BottomBar` and the tab bar under it mirror for
right-to-left languages. Bloom never decides the direction — it reads the one
the platform's layout engine is already using:

- **Web:** `document.documentElement.dir`. Set `<html dir="rtl">` (and `lang`)
  when the locale is Arabic, Hebrew, Persian or Urdu; change it at runtime and
  the shell follows on the next frame, no reload.
- **Native:** `I18nManager.isRTL`. Call `I18nManager.allowRTL(true)` and
  `I18nManager.forceRTL(true)` for an RTL locale; React Native applies it on
  the NEXT launch, so reload the app (e.g. `expo-updates`' `reloadAsync`) after
  changing it. A running app cannot mirror itself.

That is all a consumer does. Inside, two mechanisms:

- **Insets are logical.** The drawer rail, the overlay drawer, the docked
  hairline, the aside's padding, the notification count, the offer card and the
  bottom bar's action use `insetInlineStart`/`paddingInlineEnd`/`borderEndWidth`
  and friends. Yoga resolves them against `I18nManager`. react-native-web does
  NOT resolve them against `<html dir>`: its inline and atomic style paths
  rewrite them to PHYSICAL properties against its own direction context — a
  `dir` prop on an ancestor `View` — defaulting to left-to-right (measured on
  0.21.2: `insetInlineStart: 0` renders `left: 0px` with no context). So each
  family root (`AppShell`, the portaled drawer, `Sidebar`, the rail,
  `BottomBar`, the tab bar, `ProOfferCard`, `NotificationBell`) spreads
  `dir="rtl"` on web when the document is right-to-left. A screen of your own
  that uses logical insets outside those roots needs the same:
  `<View dir={useIsRtl() ? 'rtl' : undefined}>` on web.
- **The CSS spelling, not React Native's.** `paddingInlineStart`, never
  `paddingStart`: reanimated's web writer hands a mapper's result to
  react-native-web's `createReactDOMStyle`, which does not rewrite
  `paddingStart`, so the browser would drop it inside an animated style. The
  CSS spelling passes through as a real logical property (and Fabric parses it
  on native).
- **Signs read `useIsRtl()`** (`@oxy.so/bloom/hooks`): the `reveal` slide, the
  `drawerSwipe` strip and drag direction, the rail's `transformOrigin`, the sidebar's collapse control and glyph, the
  folder connector, the offer card's shimmer, the tab bar's highlight and scrub
  hit-testing, and the account/team menus' floating `side`/`align` (floating
  sides are physical).

`src/__tests__/app-shell-rtl-census.test.ts` fails the build on a new one-sided
physical key, a React Native logical key, or a sign without `useIsRtl` in these
families. Jest has no layout engine, so the mirrored PAINT is verified in a
browser with `dir="rtl"` and on a device with `forceRTL` — not by the suite.

## Adaptive navigation

# AppShell

`AppShell` composes `Screen`, `PageHeader`, `ScreenScrollView` and navigation.
Use `navigation={[{ value, label, icon }]}`, `value` and `onValueChange` once.
`navigationPlacement="auto"` chooses bottom below 768, rail from 768 through 1023,
and sidebar from 1024. Explicit `bottom`, `rail` or `sidebar` overrides that choice.

`primaryAction` accepts Fab props. In bottom placement it appears beside the tab
capsule and shares its animation; wider placements float it at the bottom-end corner (bottom-right in LTR)
of the content area, independently of the sidebar.
`header` overrides the default header; `title`, `breadcrumb` and `actions` configure
that default. `contentMaxWidth` defaults to 1300. `overlay` stays in the screen's
content tree, before its chrome; dialogs and toasts should use their proper outlets.

Existing `sidebar` data remains accepted and supplies mobile navigation too. An
explicit `navigation` model wins when both are supplied. The old `drawer`,
`drawerOpen` and `onDrawerOpenChange` API is removed: select a responsive placement
and use a separate dialog/sheet when a secondary navigation drawer is needed.

Placement follows the measured shell width (window width is only the pre-layout
fallback). The bottom bar is intrinsically translucent; it has no material variant.
Use `scroll="external"` when the child owns scrolling. For example:

```tsx
import { AppShell } from '@oxy.so/bloom/app-shell';

<AppShell navigation={items} value={selected} onValueChange={setSelected} scroll="external">
  <VirtualList screen={{ active: focused }} data={rows} renderItem={renderRow} />
</AppShell>
```

There is no surrounding ScrollView in this mode. Native binds the animated list;
web retains VirtualList's document virtualizer and pins chrome within the shell
column. Restore by passing `screen={{ active: focused, restoration }}` with the
same list ref used by `useScrollRestoration`.

## Sidebar surfaces

The desktop navigation uses `Sidebar` for both `navigation` and `sidebar.items`.
Use `sidebar={{ surface: 'card' }}` for the detached panel (the default): 12px
space around it, 24px rounded corners, the panel hairline and shadow. Use
`sidebar={{ surface: 'docked' }}` for a column flush with the shell: no outer
spacing, square corners, and a separator on its inner edge. These surfaces apply
to the expanded panel; `navigationPlacement="rail"` keeps the compact rail.

```tsx
<AppShell navigation={items} sidebar={{ surface: 'card' }} />
<AppShell navigation={items} sidebar={{ surface: 'docked' }} />
```

Sidebar configuration (including its logo, collapse control and size) also applies
when `navigation` supplies the items.

### Responsive navigation motion

The sidebar/rail change fades the existing navigation out, swaps the single
rendered tree, then interpolates its width while revealing it. Selection remains
controlled and reduced motion applies the new placement immediately. After the
transition the animated width resets explicitly to `auto`: returning an empty
style or an undefined width retained the old width in the browser, leaving a
260px space after the sidebar itself collapsed to 52px.

The navigation convenience entry point is selected when `navigation`, `navigationPlacement`, `primaryAction`, or `scroll="auto" | "external"` is supplied. On web it defaults to `scroll="document"` and adapts navigation/actions into the same layout engine used by `dashboard`, `feed`, `focus`, and `canvas`: aside, width, drawer and slot props remain effective. Native defaults to `scroll="auto"`. Explicit `auto` keeps the animated adaptive container for navigation-only shells. Supplying a layout variant, aside or `panels` uses the layout engine instead: `auto` becomes container scrolling, and `external` a fixed frame whose child owns scrolling. Document scrolling shares Screen navigation motion with the bottom bar and FAB. Explicit slots override the generated bottom bar or floating action, including `null` to suppress one. A primary action remains a separate floating action when a custom bottom bar replaces the generated bar. The focus variant never generates navigation.

For a centered feed whose navigation belongs beside the reading column, use
`navigationAlign="content"`. The shell centers navigation, content and the visible
aside as one group; `"edge"` preserves the existing edge-aligned layout.


### Header width inside a panel

An `AppShellPanel`'s `header` spans the full panel width. The
shell leaves body padding to the screen; PageHeader owns the insets of its title
and action islands. Padding a shared header/body wrapper shortened the scrim by
one gutter on each side (32px total at gutter16), leaving scrolling content
visible beside it. Both document and bounded panel layouts use this separation.
The real-browser mask check also asserts the header’s left/right edges match the
panel at rest and during scroll.

`navigationGap` controls the space between the sidebar and content independently of
`gutter` and the aside gap. The social template uses `navigationGap={0}` to bring
plain navigation up to the reading panel while retaining the panel frame insets.

A content-aligned shell with a plain sidebar and no top bar has no root padding,
whichever way it scrolls: native resolves every shell to container scroll, and
the same layout draws the same frame there as on the web. The sidebar spans the viewport; the reading/context group
owns the vertical gutter, which still supplies the panel mask and header inset.
The social template uses an 8px gutter, matching the compact framed layout.

Dashboard and feed take `drawer="reveal"` on compact screens (the default is the portaled `overlay` drawer): the page slides aside and rounds its corners to expose the sidebar. While it is open the drawer is modal: focus moves in and Tab stays inside, Escape, Android back and the VoiceOver escape gesture close it, and the page and its veil leave the accessibility tree. Feed keeps the same page wrapper and content subtree when navigation crosses between compact and desktop; the desktop navigation stays in the body row. Put `AppShellMenuButton` in a custom header’s `leading` slot; it hides automatically when navigation is in flow. Shells without navigation do not acquire a sidebar or drawer.


The `bottomBar` slot publishes its measured footprint through the shared bottom-edge registry. Measurement includes the slot’s safe-area padding; embedded bars must not add that inset again. Native feeds and separately positioned FABs can read `useBottomEdgeInset()` without importing the navigation component. Claims combine by maximum, not addition, and disappear when the slot unmounts. The slot never reads its own claim to size itself; repeated equal layout measurements do not trigger another height callback.

For fullscreen video or a child scroller that accounts for the occupied bottom edge itself,
set `reserveBottomBarSpace={false}`. The visible bar still publishes its measured height
through the shared edge registry; document/container content receives no duplicate bar padding.
`scroll="fixed"` always leaves scrolling and clearance to the child navigator or list.

ProOfferCard retains its animated complementary host and decorative artwork, with shared SurfacePaint beneath it and contextual backing published for descendant controls. Explicit background overrides remain supported.

### Full-width content

To fill wide displays without a reading-column cap, set
`contentMaxWidth="none"`. The default remains 1300. Dashboard reveal layouts
honor an explicit `gutter`, including `gutter={0}` for edge-to-edge compact
content; omitting it preserves the existing 12px frame and wider-screen top gap.


### Automatic sidebar capacity

With no navigation overrides, AppShell owns the whole progression: a drawer below
`md`, a rail from `md` to `lg`, then a panel. The desktop panel collapses when its
expanded size plus the preferred `contentWidth`, visible aside and layout gaps
cannot fit the shell's measured container. It expands again when space returns;
a manual collapse remains collapsed. While capacity requires collapse, the expand
control is disabled. No window-width hook or app breakpoint is
needed. `sidebar.collapsed` explicitly overrides automatic collapse. Explicit
`sidebar.variant`, `navFrom` and `navExpandedFrom` preserve custom placement tiers;
panel capacity still applies unless its collapsed state is controlled.


### Content spanning the aside track

For a feed route that needs a wider content panel, set
`contentSpan="content-aside"`. Keep `contentWidth`, `aside`, `asideWidth`,
`asideFrom`, and the gaps unchanged. The shell transfers the aside's width and
its gap to the content inside the same outer envelope; sidebar placement and
automatic collapse continue to use that envelope. No aside width is added below
`asideFrom`, and any stacked aside is hidden. The aside stays mounted while
spanning, but is inert and hidden from accessibility. Bloom animates its width
and opacity with the expand motion recipe, honoring reduced motion. Switching
back to `contentSpan="content"` restores the normal two-column layout.

## Modular root panels

`panelLayout` lets the shell own the complete content layout. Existing `children`,
`AppShellPanel`, `AppShellPanels`, `aside`, and `contentSpan` compositions remain supported
when this prop is absent. Do not put a second `AppShellPanel` around descriptor content:
the root supplies its surface, framing, scroll scope and optional navigation history.

```tsx
<AppShell variant="feed" navigationAlign="content" gutter={8}
  panelLayout={{
    flow: 'document', gap: 0, activePanel: 'main',
    expandedPanel: expanded ? 'main' : undefined,
    panels: [
      { id: 'main', width: 620, content: <Page /> },
      { id: 'context', width: 350, hideBelow: 990, content: <Context /> },
    ],
  }}
/>
```

Routes declare `Screen scroll="auto"` with their own `header` and `bottomBar`;
set their descriptor's `scroll` to `content` (the default). The same route then
owns document scrolling in a feed and its column scrolling in a Deck. Persistent
workspace controls can use descriptor `headerActions`, composed into the route's
existing PageHeader actions inside the panel navigation scope. Descriptor `header` and
`scroll="panel"` remain compatibility adapters for content that does not declare
a Screen. Do not supply a second route header through those legacy props.

The JSX `AppShellPanels` family now translates its children into this same shared
renderer; it retains its own-container breakpoint semantics. Its panels use the
same resizing, visibility, screen scopes and scroll contracts as root descriptors.

The preferred feed envelope is the sum of eligible base widths and gaps. Expansion
transfers that existing envelope to one panel; it does not move navigation or change
its automatic capacity threshold. `hideBelow` and `collapseBelow` use the measured
**shell** width, not the capped reading column. Hidden panels mount lazily on first
eligibility and then stay mounted, inert, inaccessible and inactive. The
`useAppShellPanel()` result includes `visible` and `active` for suspending background work.

`mode="split"` fits the available region. Fixed `width` tracks coexist with flexible
tracks; positive `span` weights (including fractions) divide remaining space. `minWidth`
and `maxWidth` constrain tracks, including both sides of a resize. If their minima
cannot fit, only `activePanel` (or the first eligible panel) is shown. A sole compact or
expanded panel fills the available region, overriding its ordinary maximum width.
`appearance="joined"` draws a shared surface and separators; `separated` draws individual
surfaces. Appearance is a structural choice: keep it stable to preserve mounted content.
An individual panel can use `chrome="none"` with `surfaceClassName` for a flat custom
fill while retaining the same framing, clipping and scroll owner. `surfaceColor`
publishes that fill to descendant chrome, following `ContentPanel`'s contract.
For a transparent panel that inherits its enclosing surface, use `appearance="plain"`.

For a three-column workspace, keep navigation in `sidebar` and give the secondary
content panel a `floating` presentation. Below `floating.below` (the shell width), its
inline track releases its space and the main conversation stays visible. Opening
the secondary panel uses Bloom's floating side sheet, including its animation, modal
focus, Escape/Back, backdrop dismissal and close control:

```tsx
{
  id: 'context', width: 410, minWidth: 320, maxWidth: 560,
  floating: {
    below: 'xl', open: contextOpen, onOpenChange: setContextOpen,
    label: contextTitle,
  },
  content: <ContextScreen />,
}
```

`floating.open` controls only the compact surface. On desktop the descriptor uses
its ordinary inline visibility; `visible: false` hides both presentations.
`activePanel` continues to select collapsed tracks, so it does not replace the
conversation when opening this dialog. `useAppShellPanel().presentation` is
`'floating'` inside the floating surface. Keep the route's same `Screen` and
`PageHeader`: the host composes dismissal into its header actions, while the
surface owns focus, Escape/Back and the animated exit. No second modal header or
scroll wrapper is added. Each surface has its own Screen scope; bounded panels
use their own viewport, and their header and bottom bar read that viewport's
metrics. The descriptor retains panel navigation history across presentation changes. Content moves between inline and modal hosts
at the breakpoint; keep component-local edits that must survive that move in the
workspace's state. Hidden inline tracks retain content; closed Dialogs follow the
normal Dialog unmount lifecycle.

`resizable` adds Bloom's existing pointer, native pan and keyboard grip. In split mode
resizing transfers room to the next visible panel, preserving their combined width.
Use `widths` and `onWidthsChange` for controlled sizes; descriptor `width` is the resting
size. `onWidthChange` on a descriptor also reports changes. The feed envelope uses
resting widths, so resizing cannot move navigation. `gap` defaults to the shell gutter
(or a hairline for joined panels).

During a pointer/native drag, Bloom previews geometry directly, without a React
render or a controlled-state callback for each movement. `onWidthsChange`,
`onHeightsChange`, `onWidthChange` and `onHeightChange` report the committed sizes
when the gesture ends. Keyboard nudges report immediately. Both adjacent limits
apply throughout the preview; a Deck updates its document scroll extent as it grows.

`mode="deck"` keeps track widths. On web, horizontal decks use the **document's
horizontal scrollbar** by default; the navigation stays sticky at the inline-start
edge while each column keeps its own bounded vertical scroll. The shell's vertical
gutters remain above and below the panels, including clearance above bottom chrome.
Bounded modular web shells fill their containing block with percentage heights.
The host page should give `html`, `body`, and its root element `height: 100%`
and allow document overflow. This uses the viewport available above a classic
horizontal scrollbar; `100vh` would include the scrollbar and create a second,
unwanted vertical scroll range. Document-flow panels still grow naturally.

The sticky navigation gains Bloom's panel surface, border and shadow as document
scroll moves panels underneath it. A CSS inline scroll timeline drives the visual
change in either reading direction; reduced motion switches it without a fade.
Browsers without scroll timelines retain the opaque surface for legibility.
No navigation nodes or layout dimensions change.

Use `horizontalScroll="contained"` for an explicitly embedded horizontal workspace.
Native uses its native scroll viewport; a vertical deck owns its vertical group
viewport. Navigation capacity never uses the sum of offscreen columns. A widthless
deck track defaults to 360px.

`flow="document"` selects document **vertical** scrolling for split layouts on web.
The viewport host and keyed content survive split/deck, expanded/compact and
bounded/document switches. Web geometry uses CSS flex and container queries,
with compositor-owned CSS transitions and reduced-motion rules. Native uses
Reanimated for the same ordered layout phases. The root reading envelope also transitions when changing layouts;
no app resize hook or measured-width interpolation is required.
The initial panel tree renders at its final size and scale on both platforms;
entry motion starts with subsequent insertions or visibility changes.
`transition="exit-before-enter"` orders semantic panel changes: outgoing panels
fade and recede first, frame and track geometry then move together, and incoming
panels reveal after reaching their usable width. The default `simultaneous`
retains overlapping transitions. Both directions and reduced motion use the same
compositor; no application timers or alternate page copies are needed. Centered frame
alignment interpolates with the panel widths when the reading envelope becomes an
overflowing workspace, in either direction and in RTL. Keep the same panel ID and
content mounted to retain the reading surface; a mode change does not require
routing to another page.

A mounted `Screen scroll="auto"` transfers its last live vertical offset when its
host changes between document and bounded scrolling. This happens before paint,
independently of route restoration, and inactive retained screens never write to
the new owner. The browser may clamp the offset if the content becomes shorter.
Panel descriptors can declare `bottomBar` for shared panel chrome (an account
prompt, connection state, or workspace controls). The first route `Screen`
composes it below its local bottom bar or primary action and measures their
combined footprint once. Nested Screens do not repeat the host footer. This
requires route content to use `Screen`; it never inserts another scroll owner or
Screen around the router outlet. Add/remove the footer without remounting the route.

Document Screen footers also stay above the host's bottom frame and reserved
chrome, rather than painting underneath its rounded mask.

For controlled panel order, set `onPanelOrderChange(ids)` on the layout and
`reorderable: true` on movable descriptors. The callback receives every panel ID;
fixed and hidden descriptor slots keep their indices. `reorderLabel` names each
panel for the localized grip and announcement. Bloom composes the grip into the
route Screen header actions. Pointer/touch dragging uses the same Pan gesture and
order model on native and web. Native continuous translation stays in Reanimated
shared-value worklets. Keyboard arrows, Home and End reorder on web; native
accessibility actions move before/after. Escape or a cancelled gesture restores
positions without committing, and edge dragging scrolls the actual group owner.
The callback captured at gesture start receives the result, allowing account or
workspace guards to reject a stale gesture.

Reordering moves the keyed hosts in actual logical/DOM order. A move is distinct
from an entrance: its mutation boundary preserves descendant scroller state and
commits resting geometry before paint, avoiding entry animations or virtualizer
remeasurement at zero width. It uses no timer, alternate content copy, or CSS-only
visual order. Bounded content panels clip their real rounded content; their
corners reveal overlapping panels instead of painting a page-colored corner mask.
Document-flow panels retain their viewport bleed masks.

A descriptor with `visible: false` releases its track and retains previously mounted
content, inert and hidden from accessibility. `keepMounted: true` also mounts it
when initially hidden, useful for the one permanent host router. Keep descriptors
and their IDs stable when routes select different groups of panels. Semantic
visibility changes animate the outgoing track toward zero while its opacity fades;
it becomes inert and inaccessible immediately. CSS discrete display transitions
remove its box at the end. Entering tracks start at zero with `@starting-style`.
The track width, gaps and reading envelope transition together. Previously the
semantic visibility path disabled transitions to avoid obsolete Deck columns
adding their full widths to an incoming envelope; retaining full outgoing widths
would reintroduce that overflow, so exits must shrink with the envelope.

Use `scroll="panel"` for Bloom-owned vertical scrolling and restoration; leave it as
`content` for a map, virtualized list or route that owns its scroll. Never wrap an
already scrolling list in panel scrolling. A document-flow main panel grows the web
page; a deck or bounded split keeps vertical scrolling inside its panels.
`usePanelScrollContainer<HTMLElement>()` (also available from `app-shell/hooks`)
returns the stable ref to that existing viewport for a virtualizer or scroll listener;
`null` means document/outside. Do not add a second scroller or a second restoration
owner around a virtualized list using this ref.

### Embedded layouts and viewport access

`AppShellPanels layout={layout}` accepts the same descriptor contract without
creating another shell; it defaults to bounded flow and contained horizontal
scrolling. Use it for workspace columns in the application content region, or
set `scope="local"` for an explicitly bounded workspace inside a page panel.
Positive deck `span` shares spare width above each track’s width basis; omitted
span keeps fixed-width columns.

Pass `viewportRef` (a React ref to `AppShellPanelViewport`) to access `getOffset`,
async `measure`, relative `scrollBy`, and imperative `reveal(id)` on the existing
owner. `onViewportScroll` observes that owner only when supplied. Native and
contained layouts expose their viewport; a web document Deck exposes the document.
Do not add another horizontal ScrollView around this group. The imperative
handle operates on laid-out panels; transient `revealPanel` coordinates insertion
transitions specifically for document Decks. See the complete
[viewport contract and examples](/docs/bloom/main/compose-layouts#viewport-access-and-platform-boundaries).

### Independent panel navigation

```tsx
const panel = {
  id: 'inbox', width: 380, minWidth: 320, resizable: true, scroll: 'panel',
  header: <PanelToolbar />,
  navigation: {
    initialEntries: [{ key: 'inbox', name: 'list' }],
    render: (entry, navigation) => entry.name === 'list'
      ? <Messages onSelect={id => navigation.push({ name: 'message', params: { id } })} />
      : <Message id={entry.params.id} />,
  },
};
```

Both header and content can call `usePanelNavigation()`. Shared link adapters can call
`useOptionalPanelNavigation()` to use a panel history when present and fall back to their
host router outside a panel. The controller exposes `entry`,
`entries`, `index`, `push`, `replace`, `go`, `back`, `forward`, `canGoBack`, and `canGoForward`.
Each panel owns a memory history and a separate restoration store; entry keys are
namespaced by panel ID. `scroll="panel"` binds the actual viewport to this adapter,
so back/forward restores that viewport. Hidden panels cannot write scroll offsets.

Panel IDs and history entry keys must be nonempty and unique within their collection.
The same entry key in different panels is valid. Supply `state` and
`onNavigationChange` to control a history or persist it in a host URL. Memory histories
never modify global browser history and do not create Expo Router roots. Existing
router content without a `navigation` descriptor keeps its host router adapter in an
independent panel restoration scope.

Storybook: **Modular Deck**, **Modular Inbox**, **Modular Map**, and
**Modular Expanding Feed** demonstrate these contracts. Existing map/results users can
keep `AppShellPanels`; an older two-pane mailbox can migrate its list width/min/max
and `resizable` props directly into root panel descriptors.

### Vertical and responsive layouts

`axis` defaults to `horizontal`. Use `vertical` for stacked panels, or a responsive
map such as `axis={{ base: 'vertical', lg: 'horizontal' }}`. The shell resolves
`sm`, `md`, `lg`, and `xl` against its own measured width. Orientation changes
preserve panel mounts, histories and both sets of resized dimensions.

```tsx
<AppShell panelLayout={{
  axis: { base: 'vertical', lg: 'horizontal' },
  panels: [
    { id: 'editor', width: 480, minWidth: 300,
      height: 300, minHeight: 160, maxHeight: 450,
      resizable: true, scroll: 'panel', content: <Editor /> },
    { id: 'preview', span: 1, minWidth: 250, minHeight: 180,
      scroll: 'panel', content: <Preview /> },
  ],
}} />
```

A bounded vertical split divides available **height**. `height`, `minHeight`,
`maxHeight`, and `span` follow the horizontal width rules. A horizontal separator
uses vertical pointer/native drag distance and Up/Down keys; horizontal panel
layouts keep their Left/Right behavior and RTL handling. Control vertical sizes
with `heights` / `onHeightsChange`; `onHeightChange` on each panel reports its size.
Width and height maps remain independent when the axis changes.

A panel with `sticky: true` in a horizontal document layout stays attached to the
shared page scroll. Short panels stick below top chrome; tall panels first travel
with the page until their bottom clears the viewport's bottom chrome, then stick.
Bloom measures the panel and applies the shell insets. It creates no inner vertical
scroller. The option is ignored in bounded and vertically stacked layouts.

A vertical `flow="document"` split stacks natural-height sections; it never adds
one viewport of height per section. Explicit heights and minimum heights remain
available. Its preferred horizontal envelope is the widest base panel width;
heights do not influence navigation capacity. Deck columns remain vertically bounded;
horizontal scrolling belongs to the document by default on web. This is a linear panel model, not an arbitrary nested grid.

The **Modular Responsive Workspace** story retains an interactive counter while
changing orientation and demonstrates height resizing. **Modular Vertical Document**
shows a short summary above a long activity section sharing the page scroll.
Responsive and expanded-panel exits use CSS discrete display transitions on web;
native retains the previous measured height through its shared exit animation.
Explicit semantic visibility uses the same shared exit. Reduced motion settles
immediately, without timers or app-owned transition state.

The web compiler emits rules from the descriptors, not from measured viewport
widths. Container queries choose the axis, visible tracks, navigation tier and
capacity, and framing; CSS allocates the space. Observers only synchronize those
CSS states with lazy mounting, inert/accessibility and navigation effects. Pointer
and keyboard resizing may read the current boxes during interaction. Existing
intrinsic measurements still account for bottom chrome and tall sticky panels.
Native and browsers without container-query support use the shared native resolver.
With `BloomProvider ssrStyles="inline"` (or an authorized stylesheet nonce),
server HTML includes the descriptor's container-query rules and all eligible
panel content. The browser selects navigation, tracks, framing and capacity
before JavaScript runs, using the same CSS tree as the first hydration render.
Without that explicit CSP opt-in, the server renders its active eligible panel
at the available width (or the first eligible panel when none is selected) and
hydrates the same compact snapshot before enabling the CSS compositor.
Before the first client paint, layout effects synchronize active tracks and
navigation state. Initial dimensions resolve with transitions disabled, then
motion becomes available for subsequent changes. Server styles are adopted
before their DOM elements are removed; changes to descriptors update the adopted
sheet without a stale SSR cascade. Native and unsupported browsers retain the
shared resolver. The host owns available height for bounded layouts; document
layouts retain natural height.

In bounded web layouts, a reserved bottom bar participates in the shell's flex
column at its intrinsic height, just like the top bar. Its space is already
occupied in server HTML; hydration does not shrink the panels after measuring
the bar. The content translates outer edge claims by the height already occupied
by the slot, combines the remainder with its local claims by maximum, and keeps
the bar's outer claim available to sibling overlays. A hidden slot consumes zero.
Document layouts, native,
and `reserveBottomBarSpace={false}` retain the anchored overlay behavior.

For presentation that depends on whether a panel is alone, use
`AppShellPanelVisibility when="alone"` (or `when="multiple"`) around that content.
The compositor supplies CSS visibility before JavaScript; native uses the same
panel context. Hidden content remains mounted and takes no layout space. A
`useAppShellPanel().alone` boolean cannot choose responsive server markup because
the server does not know the viewport. Keep that hook for client behavior.

The `verify-css-panel-layout.mjs` browser gate pauses application JavaScript and
verifies that width changes still update panel geometry and framing.

### Deck edge action

`panelLayout.trailingAction` accepts the application's action (for example, an
add-column button opening a dialog). In a web document Deck it occupies no
track width. At the logical horizontal end, hovering the screen edge or
focusing the action reveals it. The reveal uses CSS scroll timelines and
respects reduced motion. Browsers without timelines place the action at the
actual end of the group instead of showing it over unrelated panels.

After adding a panel, set `revealPanel: { id, requestKey }` to reveal its existing
host. `PanelRevealRequest` is exported from `@oxy.so/bloom/app-shell`.
`requestKey` is a string or number identifying the action: change it to reveal
the same panel again. Bloom consumes each new id/key request once, when the panel is
eligible in a horizontal document Deck. Rerenders and leaving/re-entering Deck
do not repeat a consumed request. If the compositor is animating insertion or
geometry, reveal waits for those transitions to finish before consuming the
request; replacing the request or unmounting cancels the pending reveal.
Content animations do not delay it. The browser scrolls the nearest edges using
smooth motion, or instant motion when reduced motion is enabled. A request does
not change selection: set `activePanel` separately when the action also selects.

`activePanel` is passive selection state. Loading a workspace, restoring the last
active panel, or switching layout modes must not move the document horizontally.
Keep reveal requests transient and outside persisted workspace snapshots.

**Migration from 12.2:** selection no longer implicitly scrolls a document Deck.
Where an explicit action should reveal its panel (for example, adding a column),
issue a fresh `revealPanel` request along with the selection update. Do not issue
requests while hydrating account state, and do not reset document scroll in the
application to counteract restoration.

The sticky navigation's raised surface follows actual horizontal overlap.
When the Deck fits, CSS scroll-state queries keep that elevation absent;
browsers lacking those queries retain the opaque navigation background without
an unconditional shadow.

### Lightweight panel hooks

Route screens and reusable headers should import `useAppShell`, `useAppShellPanel`,
`usePanelScrollContainer`, `usePanelNavigation`, and `useOptionalPanelNavigation`
from `@oxy.so/bloom/app-shell/hooks`. This entry shares the shell contexts and
panel history without pulling shell rendering and sidebar components into the
route's bundle. The full `app-shell` entry continues to export these hooks for
compatibility.


With root `panelLayout`, `contentMaxWidth="none"` makes a split workspace use all space remaining beside navigation and framing. Fixed-width descriptors keep their basis; descriptors without a width share the remainder according to `span`. Omitting this opt-in retains the preferred reading envelope. The same contract applies to web container-query layout and native measurement.

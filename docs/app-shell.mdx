# AppShell

`AppShell`, with `AppShellHeader`, `AppShellMenuButton`, `useAppShell`, `NotificationBell` and `ProOfferCard`.

```tsx
import { AppShell, NotificationBell, ProOfferCard } from '@oxy.so/bloom/app-shell';

<AppShell
  sidebar={{ items, secondaryItems, selected, onNavigate, account, team }}
  title="Welcome Maya"
  breadcrumb={<Breadcrumb>…</Breadcrumb>}
  actions={<>
    <NotificationBell notifications={inbox} onAction={handle} />
    <Button variant="primary" leadingIcon={RiAddFill}>Create ticket</Button>
  </>}
  overlay={showOffer ? <ProOfferCard … onDismiss={hideOffer} /> : null}
>
  {page}
</AppShell>
```

## Variants

One engine, five shapes. `variant` picks the shape; everything else — the nav,
the drawer, the pinned regions, the slots, the sizes — works the same in all
five.

| `variant` | The page | Scroll |
| --- | --- | --- |
| `dashboard` (default) | nav + one fluid column capped at `contentMaxWidth`, optional `aside` | `document` / `container` / `fixed` |
| `feed` | nav + a `contentWidth` reading column CENTRED in what the nav leaves, optional `aside` beside it, optionally in a `ContentPanel` | `document` / `container` / `fixed` |
| `split` | a list pane, a detail pane and an optional info pane, each scrolling on its own, with a draggable divider | always one screen |
| `focus` | one centred `contentWidth` column and NO nav | `document` / `container` / `fixed` |
| `canvas` | ONE edge-to-edge area — no column, no cap, no padding — with the chrome floating over it | always one screen |

`dashboard` is what this component always was, unchanged to the pixel — the
existing stories render byte-identically against the version before variants
existed.

### `feed`

```tsx
<AppShell variant="feed" sidebar={sidebar} title="Home" aside={<Trending />} contentWidth={600}>
  {posts}
</AppShell>
```

The nav sits in flow, and the content column plus the aside are centred as a
PAIR in the space it leaves. The column is `flexBasis: contentWidth` with
`flexShrink: 1` and a matching `maxWidth`, never a `width` — so on a 360px phone
it shrinks to the screen instead of pushing the page sideways.

With `scroll="document"` (the default on web) the nav and the aside pin
themselves (`position: sticky`) and the centre column scrolls the page. Measured
in Chrome at 1440: after scrolling 406px the nav stayed at `y = 121` and the
aside at `y = 16` while the content moved from `16` to `-390`.

`panel` wraps the centre column in a [`ContentPanel`](/docs/bloom/main/content-panel),
so the page background reads as a gutter around a framed surface; `framedFrom`
is forwarded.

**The panel occupies the screen either way — what differs is what scrolls.**

- `scroll="document"` (the default): the page scrolls, and the panel's frame is
  a screen-tall sticky rectangle pinned at the shell's own `gutter`, so the
  panel reads as a surface filling the window while the content moves inside
  it. Measured in Chrome at 1280 × 900: the frame reports `top: 16, height: 868`
  at scrollY 0, 1, 200, 600 and 846 — the same rectangle every time — while the
  content behind it travels from 16 to −830. (The inset is what makes that
  true: at the 8px default the frame would sit above the panel's real top edge
  and snap down on the first scroll.)
- `scroll="fixed"` / `"container"`: the shell bounds the panel, so the panel IS
  the box — it closes at the bottom like the rail beside it, the header is
  pinned inside it, and only the routed content scrolls, under the frame. The
  document never moves at all.

Both are right; they are different apps. A feed with the address bar collapsing
on a phone and real anchor links wants `document`; a workspace whose regions
each keep their own position wants `fixed`. The panel's content is inset by `gutter` — without it the page sits
ON the frame, and a radius-28 corner clips whatever is in it (the heading loses
its first letter). So `contentWidth` is the COLUMN's width, and the reading
measure inside a panel is that minus two gutters. Do not render your own
`ContentPanel` inside this one; it trips the nesting guard.

### `canvas`

```tsx
<AppShell
  variant="canvas"
  sidebar={{ ...sidebar, surface: 'docked' }}
  aside={<PlacesInView />}
  floatingAction={<Button variant="primary" leadingIcon={RiAddFill}>Add a pin</Button>}
>
  <Map />
</AppShell>
```

The content **is** the screen: one area, edge to edge, no reading column, no max
width, no padding, exactly one viewport tall. A map, a board, an editor, a photo
viewer. The header (if you pass one) sits above it in flow, because a toolbar
over a map belongs to the map; `topBar`, `bottomBar`, `floatingAction` and
`overlay` float over it as everywhere else.

The shell's padding moves OUT of the row and onto the regions, so the nav is
still a card with a gutter around it and the aside keeps its inset while the
canvas alone runs to the window's edge — no negative margins anywhere: each
region states its own inset.

**`canvas` never scrolls the document**, for the same reason `split` doesn't: a
canvas that grew the page would pan the page instead of the canvas.
`scroll="document"` resolves to `fixed`, `scroll="container"` is honoured.

### `split`

```tsx
<AppShell
  variant="split"
  sidebar={sidebar}
  title="Inbox"
  list={<ThreadList />}
  info={<ThreadDetails />}
  pane={selected ? 'detail' : 'list'}
>
  <Thread id={selected} />
</AppShell>
```

`list`, then `children` as the detail pane, then `info`. Each pane gets its own
`ScrollView` (`paneScroll={false}` when the pane's content already scrolls — a
`FlatList`, a virtualizer). The divider between the first two is `ai-chat`'s
`AiChatResizeHandle`, reused rather than rewritten: pointer-capture dragging on
web, a `PanResponder` on native, arrow keys, and the same grip. It is named
`resizeLabel` (`"Resize panes"`) with `role="separator"`. `listWidth` (360) is
the resting width and a drag is clamped to `listMinWidth`/`listMaxWidth`
(280/520); `onListWidthChange` reports where it settled.

Two panes from `splitFrom` (`md`, 768), three from `infoFrom` (`xl`, 1280).
Below `splitFrom` EXACTLY ONE pane renders — the one `pane` names, falling back
to the detail pane when that one was never given content.

**`split` never scrolls the document**, whatever `scroll` says: there is one
document, so at most one region could scroll it, and three columns that each
keep their own position is a bounded-box layout by definition. `scroll="document"`
resolves to `fixed` (one screen) and `scroll="container"` is honoured as-is.

### `focus`

A single centred column and no navigation at all — sign-in, onboarding, a
reader. A `sidebar` passed to a `focus` shell is ignored (and `AppShellMenuButton`
renders nothing, because there is no drawer to open). The header and all three
bar slots still work, so a sign-up flow gets its pinned footer CTA:

```tsx
<AppShell variant="focus" contentWidth={480} title="Create your account"
  bottomBarVisibility="always" bottomBar={<Footer />}>
  {form}
</AppShell>
```

## Pinned slots

`topBar`, `bottomBar` and `floatingAction` exist so that **nothing in a
consumer's code needs `position: fixed`, a negative margin, or a window-width
hook to sit in the right place.** Every app that has drawn a phone tab bar has
written the same four lines, and all four are wrong somewhere: a fixed bar is
wrong inside an embedded shell, a hardcoded `bottom` is wrong on a notched
phone, and a negative margin is wrong the moment the page's padding changes.

```tsx
<AppShell
  variant="feed"
  sidebar={sidebar}
  topBar={<PhoneHeader leading={<AppShellMenuButton />} />}
  bottomBar={<Tabs />}
  floatingAction={<Button iconOnly leadingIcon={RiQuillPenLine} accessibilityLabel="Compose" />}
>
  {feed}
</AppShell>
```

- **`topBar`** is a sibling ABOVE the shell's columns, so it spans the shell edge
  to edge without escaping the frame's padding. Sticky to the top with document
  scroll; simply outside the scroller otherwise. It takes the TOP safe-area inset
  as padding. `header` is the in-column page heading and is unaffected — a shell
  may have both — but while a `topBar` is drawn the default header does not add a
  SECOND hamburger under it; put an `AppShellMenuButton` in the bar.
  Not drawn under `drawer="reveal"`, which slides the whole page sideways.
- **`bottomBar`** is pinned to the bottom of the viewport (document scroll) or of
  the frame, with the BOTTOM safe-area inset as its own padding — so the bar's
  background paints under the home indicator instead of leaving a stripe of page
  showing through.
- **`floatingAction`** sits a `gutter` above the bar (or above the safe area when
  there is no bar), in the `floatingActionPlacement` corner (`end` by default).
  The wrapper spans the width and ALIGNS its child, so the button never has to
  know its own width. It has no `compact`/`always` switch: a compose button is
  not phone chrome, so it is drawn whenever it is given — pass `null` to drop it.

Both bars are MEASURED, and the content column reserves exactly their height, so
the last row of a feed is never hidden behind them. Measured in Chrome at 390,
scrolled to the page end: last item bottom `768`, action top `784`, bar top `844`.

`topBarVisibility` / `bottomBarVisibility` are `compact` (the default — only
while the nav is a drawer, the phone case the slots exist for) or `always`, for
a bar that is part of the app at every width.

## Breakpoints an app can name itself

Every `*From` prop takes a named tier (`sm` 640 · `md` 768 · `lg` 1024 · `xl` 1280) **or a width in pixels**, because a real app's layout rarely lands on the tiers. A feed whose side column earns its place at 990 and whose rail goes in flow at 500 says so:

```tsx
<AppShell
  variant="feed"
  panel                     // the reading column inside a framed ContentPanel
  navFrom={500}             // rail in flow from 500, a drawer below it
  navExpandedFrom={1300}    // icons until 1300, labels past it
  asideFrom={990}
  asideWidth={350}
  sidebar={sidebar}
  aside={<SideColumn />}
>
  {feed}
</AppShell>
```

The tiers stay the default vocabulary — `breakpointPx` resolves either — so a
shell that says nothing still lays out on Bloom's own scale.

## Sizes and breakpoints

Every number is a prop, and `APP_SHELL_DEFAULTS` is the exported record of the
defaults.

| Prop | Default | Why |
| --- | --- | --- |
| `contentMaxWidth` | 1300 | `dashboard`'s cap. The column is fluid and stops growing here. |
| `contentWidth` | 600 | `feed`/`focus`. The measure a single column of `body-regular` holds at ~75 characters — wider loses the line, narrower breaks too often. |
| `asideWidth` | 320 | |
| `asideFrom` | `xl` (1280) | 272 (panel) + 600 + 320 + three gutters is 1216: `xl` is the first tier where three columns fit without squeezing the content. |
| `navFrom` | `lg` for the panel, `sm` for a rail | Where the nav sits in FLOW; below it the same props drive the drawer. |
| `navExpandedFrom` | unset | Icons below, labels above: the shell swaps `sidebar.variant` between `rail` and `panel`. Setting it also makes `navFrom` default to `sm`, because below that tier the nav IS a rail. |
| `gutter` | 12 (`dashboard`), 16 (others) | The space between the shell's edge and its regions, and between the regions. `dashboard` keeps the 12-padding/16-gap pair it shipped with, because changing either moves every existing page by four pixels. |
| `splitFrom` | `md` (768) | 360 of list still leaves ~380 of detail (~280 once a nav rail takes its share) — a phone's worth of reading width. Below it a second pane is a sliver, not a pane. |
| `infoFrom` | `xl` (1280) | Same headroom the aside needs. |
| `listWidth` / `listMinWidth` / `listMaxWidth` | 360 / 280 / 520 | |
| `infoWidth` | 320 | |

## The shell measures ITSELF

Every breakpoint above is read off the shell's own laid-out width, not the
window. A shell mounted in a preview pane, in one half of a split view, or
inside a desktop app's own chrome is narrower than the window, and a
window-width decision puts three columns into a 480px box.

The fallback before the first layout is the WINDOW rather than zero: otherwise
frame one would be a phone layout for every shell and the correction would be a
visible reflow on every page load. A shell that spans the page is therefore
right on the first paint, and only an embedded one pays a single layout pass.

One consequence worth knowing: where the browser draws a CLASSIC (space-taking)
document scrollbar, the shell's box is `innerWidth` minus its width, so a
breakpoint crossed within ~15px of the boundary lands one tier lower than the
equivalent CSS media query would. That is the layout reading the space it
actually has, and it is the same reason the measurement exists — but it is a
real difference from `@media`, not an accident. (Chrome's headless shell uses
overlay scrollbars, so every measurement below has the shell's width exactly
equal to `innerWidth`.)

(The measurement is `useContainerWidth`, the hook `listing-details` already uses
for the same reason.)

## Why there are no tricks in here

The shape this replaced was a template full of them: negative margins to escape
the preview's padding, an ad-hoc `position: fixed` for the bottom bar and the
floating button, a per-story sticky column — and it broke at phone widths. None
of that is in the shell, and none of it is left for a consumer:

- Every region is a flex child of one row, sized by `flexBasis` + `maxWidth` and
  allowed to SHRINK. A `width` is what overflows; a basis that shrinks cannot.
- The only `position` values in the family are the sticky nav/aside and the bar
  slots' own anchor, all inside the shell. No `100vw`, no negative margin, no
  window-width hook anywhere.
- Stories set `parameters: { bleed: true }` (see `.storybook/preview.tsx`) and
  the shell fills what it is given — no per-story CSS.

Verified in Chrome across `dashboard`, `dashboard + aside`, `feed`,
`feed + panel`, `feed + chrome`, `split` and `focus`, at 360, 390, 414, 768,
834, 1024, 1280, 1440 and 1920, in light and dark: 126 renders, no sideways
scroll anywhere (`scrollWidth === innerWidth` in every one), no sibling region
overlapping another, and no console error.

## Layout

- `lg` and up: the rail sits in flow; the content column is centred, max `contentMaxWidth` (1300), header then content 16 apart.
- Below `lg` the header shows a menu button, and `drawer` picks how the rail arrives:
  - `overlay` — a drawer over the page on a 40% black backdrop (portaled through `OverlayRoot`, so it ranks with every other overlay).
  - `reveal` — the rail waits flat beneath the page; the page slides 272 right and rounds to 32 while the rail scales in from 0.94 (325ms). Pressing the page closes it.
- `drawerOpen` / `onDrawerOpenChange` control it.
- `sidebar={{ variant: 'rail', … }}` keeps the 80px navigation rail in flow from `sm` instead of `lg`; below `sm` the menu button opens the drawer, which always shows the full panel.

## Aside

```tsx
<AppShell sidebar={sidebar} title="Tickets" aside={<ActivityPanel />} asideWidth={320} asideFrom="xl">
  {page}
</AppShell>
```

A second column on the right of the page (`dashboard` and `feed`; `split` has
its `info` pane instead and `focus` has no second column at all). From `asideFrom` (`xl`, 1280; or `md` / `lg`) it sits beside the content at `asideWidth` (320), pinned like the sidebar — with document scroll it is sticky and scrolls its own overflow, so give it `flex: 1` content if it should fill the height. Below the breakpoint it is stacked after the content (`asideCollapse="stack"`, the default) or dropped (`"hidden"`). Under `drawer="reveal"` it slides with the page.

## Eight shells, one component

The shape (`variant`), what scrolls (`scroll`), whether the column is a panel
(`panel`) and the nav's own look (`sidebar.surface` / `sidebar.size`) are
independent. That is the point: an app picks a row from this table and does not
look like the app that picked the row above it.

| The app | variant | scroll | nav |
| --- | --- | --- | --- |
| Product dashboard | `dashboard` | `document` | `card`, `medium` |
| Social reader | `feed` + `panel` | `fixed` | `plain`, `large` |
| Long-form feed | `feed` | `document` | `card`, `medium` |
| Workspace (channels, files) | `dashboard` | `fixed` | `docked`, `small` |
| Messenger | `split` | one screen | `docked`, `small` |
| Map / board / editor | `canvas` | one screen | `docked`, `medium` |
| Marketplace | `dashboard`, no `sidebar`, `topBar` `always` | `document` | — |
| Sign-in, onboarding, reader | `focus` | `document` | none |

```tsx
// Social reader: a framed column that fills the screen, a nav with no edge.
<AppShell variant="feed" panel scroll="fixed" sidebar={{ items, surface: 'plain', size: 'large' }} title="Home">
  {feed}
</AppShell>

// Workspace: a column flush to the window, the page bounded, its own scrollers.
<AppShell scroll="fixed" sidebar={{ items, surface: 'docked', size: 'small' }} title="Reports">
  {report}
</AppShell>

// Marketplace: no rail at all — the navigation is the bar across the top.
<AppShell topBar={<MarketHeader />} topBarVisibility="always" contentMaxWidth={1280}>
  {results}
</AppShell>
```

The stories **Three identities**, **Feed in a full-height panel** and **Canvas**
render three of these side by side with nothing positioned by hand.

## The nav's identity is not the shell's layout

`variant` picks the LAYOUT; `sidebar.surface` and `sidebar.size` pick what the navigation looks like. They are separate axes on purpose — the same shell carries a social reader, a workspace and a product dashboard without any of them re-implementing it:

```tsx
<AppShell variant="feed" sidebar={{ items, surface: 'plain', size: 'large' }} />     {/* a reader */}
<AppShell sidebar={{ items, surface: 'docked', size: 'small' }} />                    {/* a workspace */}
<AppShell sidebar={{ items }} />                                                     {/* the floating card */}
```

A `docked` nav is flush to the window: the shell drops its left and vertical padding around that column, gives up the column gap and lets the nav run the full height, because the nav's own hairline is the separator. Everything else about the shell is unchanged. The surfaces and sizes themselves are in [`Sidebar`](/docs/bloom/main/sidebar).

## Opening the drawer without a title

The default header renders whenever it has something to show, and below `lg` the menu button counts — so `<AppShell sidebar={…}>` with no `title` still gets a hamburger, and nothing at all while the sidebar sits in flow.

A page that draws its own `header` keeps the drawer reachable with either:

```tsx
import { AppShellMenuButton, useAppShell } from '@oxy.so/bloom/app-shell';

<AppShell sidebar={sidebar} header={<MyHeader leading={<AppShellMenuButton />} />}>…</AppShell>

function MyHeader() {
  const { drawerAvailable, drawerOpen, openDrawer, closeDrawer, toggleDrawer } = useAppShell();
  …
}
```

`AppShellMenuButton` is the same button the header uses and renders nothing while the sidebar is in flow. `useAppShell()` works anywhere inside the shell (the header, the page, the aside); `drawerAvailable` says whether there is a drawer to open right now.

`header={null}` means **no header**: not the default one, and not the menu button either — the page has said it owns that corner, so it also owns getting the drawer open (`useAppShell()`, an `AppShellMenuButton` of its own). Leave `header` off to get the default.

## A fixed screen

`scroll="fixed"` makes the shell exactly one screen tall (`100dvh` on web, its parent on native) and scrolls nothing: the header stays, and the content column fills the height left under it (`flex: 1`). The page owns its scrolling — a chat with a pinned composer, a map, a board:

```tsx
<AppShell scroll="fixed" sidebar={sidebar} title="Chat">
  <View style={{ flex: 1, minHeight: 0 }}>
    <MessageList style={{ flex: 1 }} />
    <Composer />
  </View>
</AppShell>
```

Give the page `flex: 1` and `minHeight: 0`, or a tall child grows the column past the screen instead of scrolling inside it.

## Scrolling on web

The page scrolls the **document**, like a [`ContentPanel`](/docs/bloom/main/content-panel) page — not a scroll view inside the frame. The shell is at least one viewport tall and grows with its content; the in-flow sidebar is `position: sticky`, so it stays put while the page moves under it. That is what makes scroll restoration, the mobile address bar collapsing, anchor links and `window.scrollTo` behave as they do on any web page.

- Nothing between the shell and the document may become a scroll container: a parent with `height: 100%` plus `overflow: hidden` (or `auto`) around `AppShell` pins the sidebar to a box that never scrolls. Mount it straight under the app root.
- `reveal` clips the sliding page with `overflow: clip`, not `hidden`, for the same reason — and so the 272px slide never adds a horizontal scrollbar. The waiting rail is `position: fixed`.
- `scroll="container"` restores the old behaviour — the shell fills its parent and the page scrolls inside its own `ScrollView` — for a shell embedded in a bounded box rather than owning the page.

Native has no document: `document` behaves as `container` there, and `fixed` works the same as on web.

## On native

Every variant and every slot works on native; what changes is the mechanism,
never the arrangement:

- The nav and the aside are not sticky — on native the shell is always a bounded
  box (`container` / `fixed`), so they are ordinary full-height flex columns and
  stay put by construction.
- `bottomBar` and `floatingAction` anchor `position: absolute` inside the
  shell's own frame rather than `fixed` to a viewport. Yoga has no `fixed`, and
  it ignores it SILENTLY — a bar written that way would scroll away with no
  error to explain it.
- `topBar` is simply the first child above the columns and outside the scroller,
  which pins it without any positioning at all.
- Safe-area insets come from `SafeAreaInsetsContext` — read with `useContext`,
  not `useSafeAreaInsets`, which throws outside a provider. `AppShell` is
  mounted at an app's root, and making a previously optional provider mandatory
  would break every consumer that never had a bar to inset. Outside one the
  insets are zero.
- `split`'s divider drags through a `PanResponder` (`ai-chat`'s handle owns both
  paths).
- `panel` resolves to `ContentPanel`'s native variant — a plain rounded,
  bordered surface, with none of the web sticky-overlay machinery, which is what
  it should be where there is no document to bleed into.

None of this is exercised by the web gate: jest resolves no platform extensions
here, and Storybook is react-native-web. It is reasoned, not measured.

## NotificationBell

A medium secondary icon button with the unread count (16px red disc, 1.5px ring in the button's surface that drops on hover) and a `NotificationCenter` in a bottom-end popover, 440 wide. `unreadCount` overrides the computed count.

## ProOfferCard

280 wide, 12 from the bottom-left (`placement="inline"` renders in flow), radius 16, card-coloured hairline, the waitlist shadow; a light band across the top (default: an accent gradient; pass `backdrop` for your own, masked the same way on web), the copy, a full-width CTA with a sweeping shimmer (hidden under reduced motion) and an xs close button. It rises in after `enterDelay` (1.2s). Persisting the dismissal is the host's job.

A live ray-field WebGL backdrop and animated Pro logo are brand artwork and are not included — pass `backdrop` / `logo`.

# AppShell

`AppShell` composes `Screen`, `PageHeader`, `ScreenScrollView` and navigation.
Use `navigation={[{ value, label, icon }]}`, `value` and `onValueChange` once.
`navigationPlacement="auto"` chooses bottom below 768, rail from 768 through 1023,
and sidebar from 1024. Explicit `bottom`, `rail` or `sidebar` overrides that choice.

`primaryAction` accepts Fab props. In bottom placement it appears beside the tab
capsule and shares its animation; wider placements float it at the bottom-right
of the content area, independently of the sidebar.
`header` overrides the default header; `title`, `breadcrumb` and `actions` configure
that default. `contentMaxWidth` defaults to 1300. `overlay` stays in the screen's
content tree, before its chrome; dialogs and toasts should use their proper outlets.

Existing `sidebar` data remains accepted and supplies mobile navigation too. An
explicit `navigation` model wins when both are supplied. The old `drawer`,
`drawerOpen` and `onDrawerOpenChange` API is removed: select a responsive placement
and use a separate dialog/sheet when a secondary navigation drawer is needed.

Placement follows the measured shell width (window width is only the pre-layout
fallback). `navigationMaterial` chooses `solid` or `translucent` on the bottom bar.
Use `scroll="external"` when the child owns scrolling. For example:

```tsx
import { AppShell } from '@oxy.so/bloom/app-shell';

<AppShell navigation={items} value={selected} onValueChange={setSelected} scroll="external">
  <VirtualList screen={{ active: focused }} data={rows} renderItem={renderRow} />
</AppShell>
```

There is no surrounding ScrollView in this mode. Native binds the animated list;
web retains VirtualList's document virtualizer and pins chrome within the shell
column. Restore by passing `screen={{ active: focused, restoration }}` with the
same list ref used by `useScrollRestoration`.

## Sidebar surfaces

The desktop navigation uses `Sidebar` for both `navigation` and `sidebar.items`.
Use `sidebar={{ surface: 'card' }}` for the detached panel (the default): 12px
space around it, 24px rounded corners, the panel hairline and shadow. Use
`sidebar={{ surface: 'docked' }}` for a column flush with the shell: no outer
spacing, square corners, and a separator on its inner edge. These surfaces apply
to the expanded panel; `navigationPlacement="rail"` keeps the compact rail.

```tsx
<AppShell navigation={items} sidebar={{ surface: 'card' }} />
<AppShell navigation={items} sidebar={{ surface: 'docked' }} />
```

Sidebar configuration (including its logo, collapse control and size) also applies
when `navigation` supplies the items.

### Responsive navigation motion

The sidebar/rail change fades the existing navigation out, swaps the single
rendered tree, then interpolates its width while revealing it. Selection remains
controlled and reduced motion applies the new placement immediately. After the
transition the animated width resets explicitly to `auto`: returning an empty
style or an undefined width retained the old width in the browser, leaving a
260px space after the sidebar itself collapsed to 52px.

The adaptive entry point is selected when `navigation`, `navigationPlacement`, `primaryAction`, or `scroll="auto" | "external"` is supplied. Existing layout calls keep their `dashboard`, `feed`, `split`, `focus`, and `canvas` engine, document/container/fixed scrolling, slots and drawer behavior. Both paths render the same Sidebar, PageHeader and themed surfaces.

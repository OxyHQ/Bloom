# Overlay

`overlay/` exports `OverlayRoot` and `Backdrop`: the one way a portaled surface
establishes its interactive root, its position in the stack, and its
press-to-dismiss dim. Do not hand-roll either.

```tsx
import { OverlayRoot, Backdrop } from '@oxy.so/bloom/overlay';

{open ? (
  <Portal>
    <OverlayRoot>
      <Backdrop onPress={close} progress={progress} />
      <Panel />
    </OverlayRoot>
  </Portal>
) : null}
```

## A surface opened LATER paints above one opened earlier

That is decided once, in `overlay/stack.ts`, and applied by `OverlayRoot`.
**Never give an overlay surface a `zIndex` of its own.**

A per-component constant answers "which is on top" by what a surface *is*
rather than by when it was opened, so some pairings end up permanently
inverted — a menu that can never appear above a dialog, whatever order the user
opened them in.

To add a surface: render its portal body inside `<OverlayRoot>`, and put that
`OverlayRoot` **inside the guard that makes the surface appear**. The rank is
taken on mount, so the depth is right on the first paint. Order the parts
*within* one surface using `useOverlayLayerContext()`.

Toasts are the one deliberate exception: `ToastHost` mounts for the app's whole
life, so taking a rank would wedge the counter, and it passes an explicit
`zIndex` instead.

## An overlay starts a new painting context

`OverlayRoot` publishes surface level 0 for everything inside it (the ladder in
[Styles](/docs/bloom/main/styles)). React context reaches through a portal even
though the DOM does not, so without that reset a dialog opened from a control
inside a `ContentPanel` would inherit "I am on a card" and paint itself
differently from the same dialog opened on a bare screen — a surface taking its
colours from where its TRIGGER lives.

It publishes the **rung alone, with no `fill`**, and that is the shape of what an
`OverlayRoot` knows. It paints nothing itself — it is a transparent, `box-none`
full-screen layer — so it has no colour to report. What it can say truthfully is
"you are not on the surface your trigger was on", and level 0 is the assumption
that costs least when nothing better arrives: the page rung, which is what every
unwrapped consumer already assumed.

The surfaces that DO know their colour declare it INSIDE their own `OverlayRoot`,
which is what makes each claim absolute rather than a step off an ancestor it
cannot see:

| Surface | Publishes |
| --- | --- |
| `dialog/Dialog` (both forks) | level 0, `fill` = `colors.background` |
| `bottom-sheet/BottomSheetBase` | level 0, `fill` = `colors.background` |
| `floating/FloatingPanel` | level 1 — the menu/popover surface |

**Not every overlay body paints `colors.background`.** `SettingsModal` paints
`resolveSettingsPalette(theme).full` and `Tooltip` paints the menu palette, and
neither publishes a fill — so content inside either reads the page rung rather
than the real colour behind it. That is an approximation inherited from before
the ladder existed, not a claim this root makes; the fix is for each surface to
publish its own `fill`, not for `OverlayRoot` to guess one on its behalf.

Native bottom sheets never reach an `OverlayRoot` (they mount in an RN
`<Modal>`), so `bottom-sheet/BottomSheetBase` does the same reset itself, once,
for every sheet-presenting family.

## Android back and screen readers belong to the root

A portaled surface is not an RN `Modal`, so nothing consumes Android's hardware
back for it. Pass `onRequestClose` to its `OverlayRoot` and the root registers
the listener while mounted. `BackHandler` runs the newest listener first, so the
surface opened last closes first. The media viewer once registered nothing, and
back fell through to the app, which finished the activity at the root of its
stack: pressing back to close an image closed the whole app
(OxyHQ/Mention#1126). A surface that refuses dismissal still passes a handler,
so the press is swallowed instead of reaching the screen underneath.

`modal` sets `accessibilityViewIsModal` on the root. It goes on the root and
not the panel because iOS hides only the modal view's siblings, and at the
native outlet the root is the app content's sibling while the panel is not.

Geometry matters to accessibility too. Android reports every view under a
zero-area ancestor as not visible to the user. The settings modal's centring
box once spread the removed `StyleSheet.absoluteFillObject` and collapsed to
zero height. The panel still painted and took touches, but TalkBack saw only the
backdrop's "Close". `absolute-fill-object.test.ts` now bans the property.

## The `pointerEvents` rule

`box-none` and `box-only` are React Native-only values and **must be passed as
a prop, never inside a `style` object**.

```tsx
<View pointerEvents="box-none" style={styles.root} />          // ✅
<View style={[styles.root, { pointerEvents: 'box-none' }]} />  // ✗ silently dropped
```

react-native-web resolves those two values from the prop path only; as a style
entry they are dropped with no warning. `'auto'` and `'none'` *do* survive as
styles, which is exactly what makes the mistake easy to make and hard to see.

Why it is catastrophic: the web `Portal` root is `pointer-events: none`, and the
property **inherits**. A dropped opt-in makes the entire surface click-through —
backdrops do not dismiss, buttons do not press, clicks land on the app behind.
Escape still works, so it presents as a dismissal bug rather than as a
pointer-events bug. Outside a portal the same mistake inverts, and a full-bleed
band silently eats presses.

Verify dismissal in a real browser. Jest cannot see inheritance through a
portal, and the markup is valid either way.

## Not everything overlay-shaped is in the stack

The **web** tooltip is not portaled and has no rank; the native one is and does.
Check for a `Portal` before assuming a surface participates.

On native there is a second mechanism z-index cannot reach: each of these
surfaces is its own RN `<Modal>` window.

# MediaFlight

A picture — or a **playing video** — moves from where it is to where it is
going, across a navigation, without restarting and without being re-downloaded.

```tsx
// app/_layout.tsx — mounted ONCE, at the root, above the router.
import { MediaFlightLayer } from '@oxyhq/bloom/media-flight';

<MediaFlightLayer />
```

```tsx
// the origin: a feed thumbnail
import { useMediaFlight } from '@oxyhq/bloom/media-flight';

const flight = useMediaFlight();

<Pressable
  ref={(node) => flight.registerAnchor(mediaId, node)}
  onPress={async () => {
    const from = await flight.measureAnchor(mediaId);
    // AWAIT, then navigate. Never the other way round — see below.
    await flight.flyTo(mediaId, targetRect, { kind: 'video', player, poster }, { from: from ?? undefined });
    router.push(`/videos?id=${mediaId}`);
  }}
>
  {/* while it is in flight, render a HOLE here — never a second copy */}
</Pressable>
```

```tsx
// the destination: it says where it wants the surface, and takes it over by
// reporting its own first frame. `flightId` is the entire wiring.
<MediaSurface content={{ kind: 'video', player, poster }} flightId={mediaId} />
```

## The one rule: await `flyTo` before tearing the origin down

expo-video's **web** player keeps a `Set` of mounted `<video>` elements and, on
each new mount, copies `currentTime`, play state, volume, muted and rate from
`[...set][0]`. If that set is EMPTY when the new element mounts it returns early
and the element starts **at zero**.

So the layer's surface has to enter the set while the origin's is still in it.
On web, navigating unmounts the origin route — so navigating before the layer
has committed is exactly the restart, and it is intermittent, because whether
you win the race depends on a commit you do not control.

`flyTo` returns a promise that resolves on that commit. Awaiting it is the whole
contract, and it is the only ordering fact a consumer has to know — everything
else is the layer's problem. It resolves on a short timeout when no
`<MediaFlightLayer>` is mounted, so a missing root component degrades to "no
transition" and warns once in dev, rather than leaving a feed whose videos
cannot be opened.

It does **not** wait for a decode. `MediaSurface` renders the poster BEHIND the
video on both platforms, and neither an unpainted `<video>` (expo-video sets no
`poster` attribute) nor an Android `TextureView` with the ExoPlayer shutter off
draws anything opaque — so the still shows through until the first frame lands.
Waiting for paint would trade an invisible problem for a laggy tap.

## The poster must already be in the image cache

`flyTo` resolves on the layer's COMMIT, not on its first painted pixel. That
trade is only sound if committing is *effectively* painting — and whether it is
depends entirely on one thing. Measured in Chrome, milliseconds from `flyTo`
resolving to the flying surface having visible pixels:

| the poster URI | ms |
| --- | --- |
| already rendered by the page (in the image cache) | **1–5** |
| never requested before (same file, cache-busted) | **510–900** |

So a **warm** poster makes the commit a frame, and a **cold** one would open a
half-second hole exactly where the origin has just disappeared.

**The remedy is not to make `flyTo` wait.** Waiting would move that half second
in front of the user's tap, which is worse in the place people actually feel it.
The remedy is to make sure the origin has already painted the exact URI the
flight will carry.

<Callout variant="warning" title="expo-video will not fetch your poster for you">
On web, expo-video's `VideoView` renders `<video src=…>` with **no `poster`
attribute**, so passing a poster to the video view does not cause that URL to be
requested. Something else has to paint it — render the still yourself under the
video (`MediaPoster` is exported for exactly this, and Mention does it with
`expo-image` at `cachePolicy="memory-disk"`), or prefetch it. Do that and it is
warm by the time anything flies.
</Callout>

One-minute check: in the Network panel, does the poster request appear **when
you tap**, or was it already there?

<Callout variant="info" title="A poster is invisible to `requestVideoFrameCallback`">
If you measure continuity by counting decoded video frames, **a flight covered
by its poster reads as a gap** — `requestVideoFrameCallback` fires only for
decoded VIDEO, and a poster is an `<img>` that never triggers it. A ~350 ms
"hole" measured that way in a consuming app turned out to be exactly this: a CDP
screencast over the same transition showed 25 frames in 844 ms, luminance gliding
218 → 99, **zero black frames**, with the frame at t=360 ms — inside the supposed
hole — showing video filling the viewport. Measure what the screen shows, not
what one API reports.
</Callout>

`scripts/verify-media-flight.mjs` gates Bloom's half — that a warm surface
presents within a frame or two, with no re-fetch and no fade. Its control flies
a cold poster over a latency-throttled link, so "warm is fast" cannot be
reported by a harness that always says zero.

## The layer leaves when the DESTINATION is live, not when the animation ends

Measured against production: opening a full-screen video route takes **~996 ms**
(median, n=10) from tap to first presented frame — ~545 ms to mount the route,
~380 ms to `loadedmetadata`, ~40 ms to the frame. A flight animation lasts about
300 ms. Releasing the surface when the animation ends would therefore uncover a
~700 ms hole *exactly* where the transition was supposed to hide one.

So the release condition is an observable fact, not a clock: the destination's
own first frame. Give the destination's `<MediaSurface>` a `flightId` and it
reports that itself (expo-video's `onFirstFrameRender`, expo-image's `onLoad`).
`flight.handOff(id)` is there for a destination that renders something else.

Called mid-flight, a hand-off is remembered rather than obeyed — the surface
finishes travelling first, or it would vanish between the two rects.

On web the release then renders one commit with `player={null}` before the node
leaves the DOM. What that buys is **not** the unbind beside it: expo-video
answers a null player with `removeAttribute('src'); load()`, and the media
element load algorithm pauses WITHOUT firing `pause`, so the outgoing element
goes quiet and its removal mirrors nothing. Unbinding alone would not help —
`unmountVideoView` never clears the `onpause` it installed
(`scripts/probe-expo-video-listener-leak.mjs` measures that upstream defect
against expo-video's own class, and confirms the fix it is missing would close
it). Measured in real
Chrome with controls, and against real builds: without that commit the
destination ends stopped, with it playing and in position.

**The success criterion is continuity, not speed.** With a shared player the
frame is already on screen before the tap; the flight does not make the video
appear sooner, it makes it never disappear. Measure "was there ever no frame?"
and "did `currentTime` advance monotonically?", not time-to-first-frame.

## Why this exists rather than `react-native-teleport`

A shared-element transition normally assumes the origin screen is still mounted
while the element travels. That is why `react-native-teleport` requires
`presentation: 'transparentModal'`, and why it has no web story at all.

Under expo-router on web the origin route is **unmounted** the moment the URL
changes. Anything the origin was rendering — a `VideoView`, a decoded image —
is gone before the first frame of the transition.

So the surface is moved OUT of both screens for the duration of the flight.
`MediaFlightLayer` is mounted once at the app root and renders through Bloom's
`Portal`, whose outlet lives above the router on both platforms. The surface it
paints belongs to neither route, so neither route can take it down. Origin and
destination only **declare** where they want it; the layer is what paints it.

## Why the layer does not own the surface at rest

A tempting design is for the feed cell to render only an anchor and let the
layer paint every video, so there is never a swap at all. It does not work, and
the reason is not performance.

The layer paints through the `Portal`, which is outside every `overflow: hidden`
and every z-index in the app. A feed video painted there would render **over** a
sticky header, over a sidebar, over any open sheet, and it would not be clipped
by the feed column's own rounded corners. That is not a risk to be measured away
— the layer would have to know the app's clip regions, which is exactly what it
cannot know. It holds on web and on native alike.

Covering the whole screen is correct for the ~300 ms of a transition and wrong
for the rest of the time. So: the cell owns its surface at rest, the layer owns
it during the flight, and the handshake above is what makes the two swaps
invisible.

## One live surface per id

That is the contract, and for video it is the whole feature. expo-video keeps
the `VideoPlayer` **object** separate from the `VideoView` that shows it, and
one player may feed several views — so moving a video is a matter of mounting
ONE view in the right place, never of creating a second player.

Concretely:

- `flyTo` on an id that is already flying **retargets** the same surface. It
  never adds a second one, and the surface resumes from where it currently is
  rather than snapping back to the original origin.
- The origin and the destination must render a **hole** (or the poster still —
  `MediaPoster` is exported for exactly that) while the surface is in the layer.
  Two copies is what this exists to prevent.
- `flyBack` measures the current anchor, lands there, and releases. With no
  measurable anchor it releases immediately, because a flying copy held over a
  destination that has already drawn its own media is the duplicate again.

## The API

| member                          | does                                                          |
| ------------------------------- | ------------------------------------------------------------- |
| `registerAnchor(id, node)`      | declares the host view that anchors `id`; `null` clears it     |
| `measureAnchor(id)`             | that node's window rect, or `null` when it has none            |
| `flyTo(id, rect, content, opts)`| takes the surface live and moves it to `rect`                  |
| `flyBack(id)`                   | flies it to its anchor and releases it on landing              |
| `progress`                      | `SharedValue<number>`, 0 → 1 for the most recent leg           |

And one component, `<MediaFlightHost id content style … />` — where the media
lives when it is not flying. See below.

The most recently registered node for an id **is** the anchor, which is what
makes a destination mounting over an origin take over as the fly-back target
without either of them coordinating.

## `MediaFlightHost`: one element for the whole flight, on web

Everything above is what a flight does with a **picture**. A video needs one
more thing, and it is not a matter of ordering: on web the pause and the
restart are properties of TWO elements sharing one player.

Measured against expo-video's real `VideoPlayerWeb` (57.0.2), across every
element topology a consumer can produce on one player:

| topology                                   | position | playback |
| ------------------------------------------ | -------- | -------- |
| origin dies BEFORE the destination mounts   | `ct=0`   | playing  |
| origin dies AFTER the destination mounts    | `ct=4.28`| paused   |
| one element, re-parented                    | `ct=4.28`| playing  |

The first two rows contain no Bloom surface at all — a feed row and a fullscreen
player sharing a player produce them on their own. Two elements give you the
position or the playback, never both, because `mountVideoView` seeds a new
element from the first one already mounted and `_addListeners` gives every
element an `onpause` that pauses all the others — handlers `unmountVideoView`
never removes. An element on its way out still governs the player.

So on web, Bloom paints the media **once**, into a wrapper it created outside
React, and moves that wrapper between the boxes that want it:

```tsx
// The feed row
<MediaFlightHost id={mediaId} content={{ kind: 'video', player }} contentFit="cover"
  style={{ width: 320, height: 180, borderRadius: 12, overflow: 'hidden' }} />

// The fullscreen route, later, with the same id and the same player
<MediaFlightHost id={mediaId} content={{ kind: 'video', player }} contentFit="contain"
  style={StyleSheet.absoluteFill} />
```

A host **declares a box**; it does not own the media. It also registers itself
as the flight's anchor, so `flyTo`/`flyBack` measure the box the media actually
paints in rather than a box the consumer measured separately.

On **native** `MediaFlightHost` renders its own `MediaSurface` inline, exactly
as consumers did before it existed. One API, two implementations, and nothing
about the call site says which one you got.

### Why it works, in three parts

- **React never sees the move.** The media is rendered with `createPortal` into
  a container whose identity never changes, and a portal's container is not part
  of React's tree. `createPortal` to a container that *changes* unmounts and
  remounts — the thing being avoided — so the container is created once, outside
  React, and only its position in the document changes.
- **The browser never sees a removal.** HTML's removal steps for a media element
  await a stable state and then abort if the element is back in a document, so a
  synchronous `appendChild` from one parent to another does not pause playback.
  (This is why re-parenting a `<video>` works and re-parenting an `<iframe>`
  does not: an iframe reloads.)
- **A node with no host waits IN the document.** It parks in a 1×1 transparent
  holder, because a detached `<video>` is auto-paused. It is disposed when
  nothing can want it back — no claim and no flight live for that id — which is
  a fact the registry reads rather than a timeout it guesses.

### Paint the video yourself

`MediaFlightHost` mounts a `VideoView` with the handful of props Bloom knows
about. That is not enough the moment a consumer needs something only its OWN
element can give it — a `ref` for `startPictureInPicture()` or
`enterFullscreen()`, expo-video's picture-in-picture callbacks,
`onFirstFrameRender`, anything expo-video adds next. Measured in a consuming
app: adopting the host without this left a picture-in-picture BUTTON on screen
whose ref was attached to nothing. It rendered, it was pressable, and it did
nothing, silently.

So build the element yourself and let Bloom decide only what it must:

```tsx
<MediaFlightHost
  id={mediaId}
  content={{ kind: 'video', player }}
  renderVideo={useCallback((props) => (
    <VideoView
      {...props}                       // player, style, contentFit
      ref={videoViewRef}
      allowsPictureInPicture={isWatched}
      onFirstFrameRender={handleFirstFrame}
    />
  ), [isWatched, handleFirstFrame])}
/>
```

Three things about the props Bloom passes:

- **Spread `style`.** A DOM `<video>` is a replaced element: `inset: 0` with
  `width/height: auto` paints it at its intrinsic 300×150 inside whatever box it
  was given. Bloom's style carries the sizing.
- **Pass `player` straight through, including `null`.** Null means unbind now,
  and expo-video answers it by emptying the source — which pauses the element
  without an event, which is what stops an outgoing surface from pausing the one
  the viewer just landed on.
- **Memoise the slot.** It is part of what a host publishes to the layer,
  compared by identity.

All three fail silently and only in production, so Bloom says so in development
instead: a slot that changes identity five times warns once about `useCallback`,
and a media element that does not fill its wrapper warns once with both
rectangles. Neither is a gate — they are the three trap-doors of this contract
turned into three messages.

**The invariant that keeps this a primitive and not a coupling:** Bloom decides
`player`, `style` and `contentFit`, and those three are exactly the three that
depend on WHERE THE NODE IS. Nothing else about the media is Bloom's business.
If a fourth prop ever has to be added beside them, that is the signal that
coupling is leaking in — not a reason to add a fifth.

The player's own type flows from `content` into the slot, so a slot hands it
straight to `VideoView` with no cast. Bloom transports that object; it never
reads it, and narrowing what you only transport is what pushes a consumer
towards `as`.

The flight itself never brings an element. Its claim on a shared node says only
WHERE the node lives — a flight that published its own render would swap a
consumer's element out for Bloom's and back again, which is two remounts in the
middle of the one operation whose whole point is that the element is never
rebuilt.

### What the slot proved about the mechanism

The slot exists because of picture-in-picture. What it FOUND is worth more.

Before it, a flight published a *render* of its own alongside its position — so
for the length of a leg the layer painted the media its own way. With Bloom's
own view that is invisible: rebuilding the element and not rebuilding it produce
exactly the same tree, the same props and the same picture. The moment a
consumer's element went through the same path, it stopped being invisible: the
element was swapped out at take-off and back at the landing, two remounts inside
the one operation whose entire purpose is that the element is never rebuilt, and
the original ended the flight disconnected.

**The abstraction was hiding the defect the abstraction existed to prevent.** No
sharper test found it; giving up ownership of the element did. That is why a
flight's claim on a shared node now says only WHERE the node lives, and why the
mutation that gives it a render back fails three identity tests by name.

Keep it that way. A claim that carries a render again will look like a
simplification and will pass everything except those three.

### The flight outranks every host

A destination that mounts mid-flight claims its id, and the layer keeps the node
anyway until the leg ends — otherwise the media would jump to its landing place
while still travelling. That claim IS the hand-off: with one element there is no
first frame to wait for, because the element the destination just claimed has
been playing since the origin. `flightId` and `handOff` remain for native and
for a destination that paints its own surface.

### What it does not change

`flyTo` with an id that has no host still paints its own `MediaSurface`, which
is what every image flight does. Nothing about the gallery, the anchors or the
animation changes.

## It never takes a click

Every node the layer renders is `pointerEvents="none"`, inside an `OverlayRoot`
that is `box-none`. A flying surface is a picture of something the app is
already showing; the controls underneath it stay the ones the user is pressing.

The layer also renders **nothing at all** while no flight is live — which is
what keeps it out of the overlay stack's live set, so the rank counter can
still reset (see `overlay/stack.ts`). It takes a rank only while it is
actually painting, and therefore stacks by open order like every other Bloom
surface.

## Why the size is animated rather than scaled

`ZoomableMediaGallery` flies its media with a uniform `scale`, which is right
there: it opens from a thumbnail into a box of the same aspect ratio. A flight
does not have that luxury — it routinely goes from a cropped square tile to a
16:9 player — and a uniform scale would leave the first frame the wrong height,
i.e. visibly not the thumbnail it is replacing. `width`/`height` are
interpolated instead; the position still rides a transform, so the only layout
work per frame is one absolutely-positioned node resizing.

## Open: three decoders on native, and why the obvious cut is wrong

On web a flight re-parents one element, so there is exactly one video view for
the whole leg. **On native there is no re-parenting**, so during a flight the
origin host, the destination host and the layer's own flying surface are three
views on one player — and the flying one is a `TextureVideoView`, because a
`SurfaceView` composites outside the view hierarchy and would ignore the clip,
radius and transform that a flying box is made of.

Three concurrent decoders is not a detail on a phone. Many Android devices
guarantee only one or two concurrent hardware decoders; the third falls back to
software or fails, which on a low-end device is a black video — worse than
anything this transition is trying to hide.

**The obvious cut is to paint the poster on the flying surface for the ~300 ms
of the leg. Do not do that.** It is the same artefact this package spent a day
removing from the web path: a 267–282 ms frozen picture mid-flight was measured,
treated as the defect, and made the merge criterion. A still frame for 300 ms
cannot be a defect on web and an optimisation on native. And it is in fact
worse, because the poster is a *different image* — usually frame zero, not the
frame the viewer was looking at — so the sequence becomes playing at 4.28 s, a
jump to an unrelated still, then live again at 4.6 s. Two content jumps instead
of one freeze.

**If the decoder count does turn out to hurt, the cut goes the other way: the
ENDS paint posters and the flying surface keeps the video.** During a leg the
two hosts are covered by the surface that is flying; nobody is looking at them.
The one being watched should be the one that plays.

That costs something honest: it needs the layer to arbitrate who paints while a
leg is live — the rank machinery that exists on web and that native deliberately
does not have. It may not be worth it.

### What is measured about it, and what is not

Measured on an Android emulator (2026-08-26), with the flight isolated from the
route change by clearing app data and deep-linking straight into the fullscreen
route:

```
                              slot called    Cannot set prop 'player'
cold, no flight   x2             0 / 3                0 / 0
with a flight     x2             4 / 4                2 / 2
```

**The third view is real and its mount already fails at something.** With no
flight there is no `TextureVideoView` and no error; with one, the layer mounts
its own `MediaSurface` (no `renderVideo`, so `surfaceType` defaults to
`'textureView'`) and expo-video raises `PropSetException: Cannot set prop
'player' on view 'TextureVideoView'`, twice per flight. That name is the
RUNTIME class of the instance — `ConcreteViewProp.kt` throws
`PropSetException(name, onView::class, …)` — so it is not a mislabelling: a
`TextureVideoView` is genuinely there.

**No observed consequence.** Playback continues, and picture-in-picture opens
with the video playing rather than black or frozen, so the view and the player
do end up correctly married; the assignment that fails is not the one PiP needs.

**What is NOT measured: whether any of this costs anything on real hardware.**
An emulator has no real hardware decoders, so the decoder-count question — the
reason this section exists — cannot be answered where everything else in this
package was measured. It needs a physical device.

Until then this section is the decision, not the code. The upstream report is
written and deliberately not filed: an issue about an error with no symptom is
easy to archive, and it may share a root with the web-side defect already filed
(`expo/expo#49359` — expo-video handling several views on one player). If a real
device shows a consequence, it goes up with this attached.

## Android: a flight crosses a surface-type boundary

expo-video renders Android video into a `SurfaceView` by default. A flight
cannot: a `SurfaceView` is composited by the system OUTSIDE the view hierarchy,
so it ignores its parent's clip, corner radius and transform — every property a
flying box depends on. The layer therefore flies as a `textureView`.

**So unless one side changes, the hand-off swaps surface types.** Whether that
is visible is a device question and nothing here answers it. Measured on a real
device it may not flicker at all, in which case the right action is none.

The knob exists so both arrangements can be measured:

```tsx
// fly as a surfaceView, matching a destination that has not changed
flight.flyTo(id, rect, content, { surfaceType: 'surfaceView' });
```

```tsx
// …or leave the flight alone and give the DESTINATION a textureView
<MediaSurface content={content} flightId={id} surfaceType="textureView" />
```

Flying as a `surfaceView` will not transform correctly on Android — that is the
trade the first option makes. `surfaceType` is captured on first render on both
sides (expo-video forbids changing it at runtime), so a retarget deliberately
does not accept a new one.

## Peers

`expo-image` is required (hence the subpath — the family is deliberately not on
the root barrel, because Metro does not tree-shake). `expo-video` is
**optional**: an app that flies only images never installs it, and one that
flies video without it gets the poster plus a single dev warning naming the
package.

<Callout variant="warning" title="On Vite (or any ESM web bundler) you must hand expo-video over">
Bloom loads optional peers through a `require()` that Metro marks optional.
**An ESM web bundle has no `require` at all** — measured: `typeof require` is
`undefined` in a Vite bundle — so the load cannot run and video degrades to its
poster **even when `expo-video` is installed**. Metro has a real `require` and
is unaffected, which is why this only shows up off Metro.

One line at startup fixes it:

```ts
import * as ExpoVideo from 'expo-video';
import { provideExpoVideo } from '@oxyhq/bloom/media-flight';

provideExpoVideo(ExpoVideo);
```

How to tell whether it applies to you: run `typeof require` in your app's
console. If it answers `"undefined"`, you need this. The dev console also says
so directly — the warning ends `Reason: this bundle has no CommonJS require`.
</Callout>

## What a jest run can and cannot see

The registry: that a flight is created, that a second `flyTo` retargets rather
than duplicating, that `flyBack` releases, that the layer renders nothing while
idle and a surface when one is live, and that `flyTo` really waits for the
layer's commit.

What it can never see is the MOTION. Every reanimated animation resolves
synchronously under the test mock, so a mapper that runs once and freezes at the
opening frame — the documented web failure mode of this package — produces the
same tree as one that animates. Two browser gates cover it, both headful against
real Chrome:

- `node scripts/verify-media-flight.mjs` samples the flying surface's
  `getBoundingClientRect` during and after the flight, and distinguishes frozen
  (never leaves the origin) from snapped (already at the destination) from
  animating, then asserts it lands on the destination rect and is released.
- `node scripts/verify-overlay-stacking.mjs` parks a surface over a button and
  clicks the button with trusted input, which is the only way to tell a layer
  that is `pointer-events: none` from one that merely looks like it.

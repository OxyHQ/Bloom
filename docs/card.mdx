# Card

`Card` is the answer to "what is a card made of". One component owns the `card`
background role, the border colour and width, the elevation and the corner
rung — and the platform split those imply, since a shadow is a `box-shadow` on
web and `elevation` on Android.

Five families used to draw that chrome by hand, with five different radii and
three different elevations. That is what `Card` removes. It does **not** remove
the variety: a settings group, a hover card and a link preview are legitimately
different surfaces, and the radius scale has rungs precisely so they can differ.

```tsx
import { Card, CardHeader, CardBody, CardFooter, CardTitle, CardDescription } from '@oxy.so/bloom/card';

<Card appearance="outline" radius="radius-16">
  <CardHeader>
    <CardTitle>Weekly digest</CardTitle>
    <CardDescription>Sent every Monday at 09:00.</CardDescription>
  </CardHeader>
  <CardBody>…</CardBody>
</Card>
```

`tone` inherits from `BloomScope` and defaults to `neutral`. Neutral solid cards use the card surface token; semantic tones use Bloom’s paired foreground and fill recipe.

## Which prop decides what

| prop        | decides                                                          |
| ----------- | ---------------------------------------------------------------- |
| `appearance`   | the preset combination of background, border and elevation        |
| `radius`    | the corner, as a **rung of the `RADIUS` scale** — never a number  |
| `border`    | `none` · `hairline` (0.5px) · `thin` (1px) · `medium` (2px)                        |
| `elevation` | `none` · `s` (a subtle raise) · `m` (the overlay role)            |

`appearance` is only a named default for the other three. An explicit `border` or
`elevation` wins, in both directions — you can add a shadow to `plain` and take
one away from `solid`. That is deliberate: a surface that is "an outlined
card but flatter" should refine the axes rather than earn a fifth variant name.

```tsx
<Card appearance="plain" border="hairline" elevation="m" radius="radius-20" />
```

## Appearances

- `plain` — transparent, with no border or shadow.
- `solid` — `shadow-s`. The default.
- `outline` — a 1px border in the `border` role.
- `subtle` — paints from `backgroundSecondary` instead of `card`, for a surface
  that sits **on** a card rather than being one.

## `radius` is a rung, not a number

```tsx
<Card radius="radius-20" />   // ✅
<Card radius={20} />          // ✗ does not type-check
```

The scale has 2 / 4 / 12 / 16 / 20 / 24 / 28 / max. Taking a rung rather than a
number is what keeps "this surface is a bit rounder" to eight values instead of
eight hundred, and it is why a design change to a rung moves every surface that
uses it.

## The mistake it prevents

Hand-rolling the chrome means hand-rolling the platform split too, and the
usual result is a `Platform.OS` branch with slightly different numbers from the
one next to it. Worse, on web it is tempting to reach for classes —
`border border-border bg-card` — which are **inert until the consumer wires the
Tailwind pipeline**. That failure is silent: the card renders as an unbordered
transparent block, nothing throws, and it looks like a spacing bug.

`Card` resolves border, radius and shadow from tokens and delegates fill to Surface,
so the surface paints with or without a consumer's CSS pipeline.

## Pressable cards

Passing `onPress` makes the card a `Pressable` with a press dip. Say what it
is: a card that opens a URL is a `link`, a card that performs an in-app action
is a `button` (the default).

```tsx
<Card onPress={open} accessibilityRole="link" accessibilityLabel="Read the post" />
```

## Clipping

`Card` uses the shared Surface material (`material="solid"` by default, retaining the gradient and rim; `material="glass"` opts into translucent refraction), while preserving the current appearance, tone and compatibility variant APIs. On native, the outer node keeps its shadow unclipped; an inner content node clips cover images and receives resolved padding, gap and child layout. Web retains one content layout node, where CSS overflow clips children without clipping the box shadow, preserving utility-class layout.
A surface that must *not* clip — because it has an Android elevation, or
because a child deliberately overflows — opts out through `style`:

```tsx
<Card clipContent radius="radius-20" contentStyle={{ gap: 12 }} />
```

`cornerCurve="smooth"` is the default: CSS squircle on supporting browsers,
iOS continuous curves, circular corners on Android and unsupported browsers.
`cornerCurve="round"` is circular everywhere. `radius-max` always remains a pill.
`border="medium"` supplies a 2px selection border.
Both layers use the same curve; the inner radius accounts for the border width.
`radius`, `cornerCurve` and `border` own geometry. Set layout and paint in `style`,
not border radii, border widths or overflow; `contentStyle` follows the same rule.

## Parts

`CardHeader`, `CardBody`, `CardFooter`, `CardTitle` and `CardDescription` are
spacing and type conventions, not requirements. A card with entirely custom
content is a normal thing; use the parts when you want the same rhythm as every
other card.

`LinkPreviewCard` composes Card and inherits this material without a separate glass implementation.

`appearance="plain"` is an unpainted container: it does not mount SurfacePaint or add a gradient/rim. Explicit caller backgrounds, borders and elevation remain authoritative. This differs from the legacy `variant="plain"`, which retains its solid, unelevated contract.

## Parent-aware surface hierarchy

Neutral, non-plain cards keep `colors.card` on the page and derive nested fills from the actual parent surface. The published level caps at three; the fill continues to step from its parent, so deeper cards do not collapse into the same colour. Children receive both the resolved fill through `SurfaceLevelProvider` and its web CSS variable.

Explicit style backgrounds (including resolved class utilities) take precedence. Translucent solid fills are composited against the known parent before painting and publishing. Coloured semantic tones preserve their authored fill/foreground pairs. Glass publishes that same composite as an estimate for descendants; it cannot describe the exact refracted backdrop.

`appearance="plain"` adds neither material nor a hierarchy step. Its transparent background preserves the inherited fill. An explicit background on a plain card updates the published fill at the current level.


Backgrounds resolved by the styled adapter into `style` participate in this contract. CSS-only paint that never reaches those resolved styles cannot be inferred without reading the DOM; use an explicit `style.backgroundColor` when descendants must follow a custom web fill. The hierarchy publishes the base fill, not sheen, images, gradients or disabled-opacity composites. No runtime style observer is installed.


`ref` and `onLayout` address the outer card host in both passive and pressable forms. Responsive card families reuse that measurement rather than adding a layout wrapper. Dashboard, chart, booking, tenancy and specialized cards compose this base; their custom content retains its geometry and semantic colours while neutral fills derive from the surrounding surface.

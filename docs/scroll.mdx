# Scroll restoration

`@oxy.so/bloom/scroll` remembers where the user was and puts them back. The core
is router-agnostic; one adapter binds it to a router.

```tsx
import { ScrollRestorationProvider } from '@oxy.so/bloom/scroll';
import { expoRouterScrollAdapter } from '@oxy.so/bloom/scroll/expo-router';

<ScrollRestorationProvider adapter={expoRouterScrollAdapter}>
  <App />
</ScrollRestorationProvider>
```

An expo-router app gets this from [`BloomProvider`](/docs/bloom/main/provider)
already. A Vite/SPA consumer mounts it directly with its own adapter.

**The adapter must be a module-level constant** — the core calls its members as
hooks, so a value built inside a component changes the hook identity every
render.

## Global adapter keys and independent panel histories

The global router adapter stores an offset against the content's identity (route name plus sorted
params) and the caller's optional `key` — deliberately **not** against the
history entry.

So content the user has already seen restores however they arrived at it, and
only unseen content opens at the top. The accepted trade-off: the same content
open in two live entries shares one offset. Independent panel histories are the
exception: each panel includes its history entry in the key so Back/Forward
restore that particular visit, without sharing offsets with another column.

`contentId` comes from the adapter via `useRoute()`, never `usePathname()` —
`usePathname` reads the globally focused route, so a background screen would
adopt the foreground one's path and restore to a stranger's offset.

## A miss RESETS to 0; it is not a no-op

On a document-scrolled web app, one window scroller serves every route. If
arriving at unseen content did nothing, it would inherit the previous screen's
offset — you would open a new page halfway down.

## Native is deliberately narrower

The native hook is keyed on the storage key, never on focus, and it **returns**
`{ onScroll, restorePending }` for the caller to wire up rather than attaching
itself.

`enabled` is how the caller says *its rows exist yet* — restoring to an offset a
list cannot reach yet lands at the bottom of a short list. It is not a feature
flag.

## What to expect on web

- The restore re-applies across a bounded run of frames, because a re-shown
  virtualized list reaches full height over several.
- It **aborts on user input** (`wheel`, `touchstart`, `pointerdown`, `keydown`).
  If the user starts scrolling, they have taken over.
- `history.scrollRestoration` is set to `'manual'` only while the provider is
  mounted, and handed back on `pagehide` — so an app that unmounts it does not
  leave the browser's own restoration disabled.


When navigation collapses the document, the browser may clamp its offset to a
shorter page's bottom before the outgoing screen blurs. Bloom preserves the
previous offset only if that trusted offset exceeds the new maximum, the range
shrank, and the observed position is at the new bottom. Merely measuring rows
shorter than their estimates is not a navigation clamp: scrolling from above to
the measured bottom must still be remembered.

## Layout changes are not navigation

Changing a retained Screen from document flow to a bounded column transfers its
live reading offset to the new owner; changing back transfers the latest offset.
The transfer remains available until the incoming owner's router focus effect
runs, including adapters that initialize navigation on a later commit. It expires
when that Screen changes content identity, changes owner, blurs or unmounts, and
is consumed once. Standalone Screens therefore cannot leave an offset for a
future route on the shared window.

This handoff belongs to Screen and does not need an application scroll listener,
remount, snapshot reload or compensating scroll write. A new route or accepted
workspace snapshot still follows the restoration rules above.

Horizontal panel visibility is separate. `activePanel` selects compact content;
`revealPanel` requests a transient document-Deck reveal after layout settles.
`viewportRef` accesses the compositor’s existing horizontal owner for domain
interactions. Neither request is a vertical restoration snapshot. See
[Compose application layouts](/docs/bloom/main/compose-layouts).

## Persist an opt-in workspace

The default store is session memory. Hosts may pass `initialSnapshot` and
`onSnapshotChange` to `ScrollRestorationProvider`, or place them in a panel's
`navigation.scrollRestoration` options. `ScrollRestorationSnapshot` is a JSON-safe
`Readonly<Record<string, number>>`. Keys are URI-encoded by Bloom, so internal
separators never appear as control characters in SQL JSON storage. Treat keys
as opaque and store the snapshot unchanged. Bloom decodes them when hydrating
and ignores malformed encodings. Bloom never reads local storage or calls a backend.

```tsx
navigation: {
  initialEntries: panel.navigation.entries,
  state: panel.navigation,
  onNavigationChange: saveNavigation,
  scrollRestoration: {
    scopeKey: acceptedWorkspaceIdentity,
    initialSnapshot: panel.scrollOffsets,
    onSnapshotChange: saveScrollOffsets,
  },
  render: renderScreen,
}
```

Offsets hydrate before descendants render. The callback coalesces scroll updates
for 200ms and flushes on navigation, unmount, pagehide, hidden documents and
native backgrounding. No React render is scheduled for each scroll event. Hosts
should persist locally in the callback and independently batch their network writes.

`initialSnapshot` is read once per scope. Change `scopeKey` only when replacing
an accepted workspace or account; this resets just the panel's restoration scope
and screen, preserving the surrounding shell. Do not derive it from every saved
revision. Ignore outgoing callbacks from a superseded workspace generation.

Snapshots reject nonfinite offsets, clamp bounce overscroll to zero and retain
at most 256 recently updated keys. Panel histories prune offsets for removed
entries. Each panel's store is independent, including nested panels. Panel keys
include the history entry so Back and Forward restore the particular visit.

On web, when cold-loading content is still too short after the initial frame
budget, restoration waits for content growth through size/content observations.
The screen remains visible and no animation loop runs while waiting. The first
user scroll input cancels this waiting, so newly loaded content cannot pull the
user back. On native, enable restoration when the content is ready, as above.

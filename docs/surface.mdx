# Surface

`Surface` is a passive container. It owns material, not interaction, navigation or spacing. It is distinct from `surfaces`, Bloom's imperative dialog and sheet API.

```tsx
import { Surface, Button } from '@oxy.so/bloom';

<Surface style={{ padding: 24 }}>
  <Button>Continue</Button>
</Surface>
```

Surface has one material: a subtly translucent body, shared sheen and rim, and subtle backdrop refraction on web. There is no material selector. Opaque semantic fill colours receive 90% opacity; caller-supplied alpha remains explicit. With no fill override, a Surface on the page uses the card role, and a nested Surface derives its fill from the actual parent. `radius` defaults to 20. Geometry precedence is explicit `radius` → resolved `style.borderRadius` → family default, shared with Card and GlassIsland. Host and paint always receive the same resolved radius, including percentage style values. Use `radius` or `style.borderRadius` to set native clipping, rather than a class utility the inner paint cannot inspect. `className` belongs to the root layout node; padding, size and layout remain caller-owned. `children`, `accessibilityLabel` and `testID` pass through.

Surface publishes its resolved base fill to `SurfaceLevelProvider` and `--bloom-surface`, so nested cards, fields and other controls read the same backing that it paints. The gradient and rim decorate this base; they do not create another level. Stepping is based on the actual fill even beyond named level 3. Explicit `fill` takes precedence over `style.backgroundColor`; both are respected and published. Material fills are composited onto the declared parent, an estimate rather than a measurement of the refracted backdrop.

`Surface` has no press, disabled, loading or business state. Controls such as Button own those states and consume the **same paint** directly: `SurfacePaint` for universal components and `surfaceMaterialCss` for web roots. These are internal implementation primitives, not alternate public components. Button keeps its single interactive root without wrapping it in another Surface.

The shared implementation lives in `surface/shared.ts`, `SurfacePaint.tsx`, `web-material.ts` and `web-refraction.ts`. Web material samples the backdrop with blur and SVG displacement beneath the paint; its 90%-opaque body keeps the fill dominant across the whole shape. One filter definition serves all material instances in a document. Native uses a single SVG tint/sheen layer, with explicit stop opacity and no blur or displacement. A surface's own shadow belongs on the outer node; do not clip the native outer node if it needs a shadow.

For existing web hosts, `useSurfaceMaterial` applies the shared decoration through pseudo-elements without adding layout nodes. Painted hosts pass their tint source to `SurfacePaint` and keep the host background transparent; omitting `fill` is reserved for an intentionally tintless optical layer. Native paint uses one sheen gradient and an optional flat fill rectangle; SVG IDs are stable across server and client rendering. See [Material composition](./material-composition.mdx) for consumers and exceptions.

The web material is verified in Chromium. It remains backdrop-dependent and incurs compositor cost per painted surface; large or densely repeated panes need visual and performance checks. A Surface containing another glass control can establish a different backdrop for that control, so inspect nested compositions rather than assuming independent panes. Button, Card and the floating Sidebar share this material; unfilled controls and docked backing containers retain their own contracts. `SurfacePaint` selects web optics at runtime, so universal consumers do not need platform forks merely to paint glass.

Every web material keeps its filtered layer within the pane bounds, preserving rounded corners even in nested controls. The body softly transmits the sampled image with no separate transparent border. The displaced image comes from the real backdrop; the specular sheen and rim remain decorative lighting. Both modes share the same sampling and displacement, with theme-adjusted lighting intensity.

Run `node scripts/verify-surface-refraction.mjs` with `CHROME_PATH` pointing to Chromium. It changes only the colours outside the pane while holding the background directly beneath it constant, then checks that body transmission stays small while displacement remains detectable in both modes, for neutral and saturated fills. Disabling displacement distinguishes refraction from ordinary blur. A separate pixel check verifies that the material does not escape rounded corners, with a square-corner mutation as its control. **Capture the full viewport, then crop the captured image:** Chromium screenshots taken with a capture `clip` can trim the backdrop input itself and falsely suggest lateral sampling is absent.

Storybook: **Base / Surface / Nested**, **Base / Surface / Material** and **Base / Surface / Backdrop Reflection**. The latter lets you change only the sides. See [Button](./button.mdx) for the reference comparison and measured stress case.

`SurfaceLevelProvider` publishes the tint composited over the known parent fill, so descendants and scoped CSS use the same estimated backing. Actual refracted pixels can differ when a photograph or another scene lies behind the pane; this value describes the known colour composition, not sampled backdrop imagery. Explicit `fill="transparent"` creates no painted layer and keeps the parent's depth and fill.

Native uses the same translucent tint and optical lighting. It does not emulate web displacement or add a BlurView per component; exact refraction is currently a web capability.

The internal `resolveSurfaceMaterial` resolves paint fill, published backing, depth and CSS aliases together. `useResolvedSurface` supplies contextual defaults. Plain/backing hosts use `paint: false`; portals pass an explicit depth origin. Consumers must not recreate tint-plus-composite chains.

# Dialog

A single `<Dialog>` component for every overlay surface — centered modal, side-sheet (left/right or logical start/end drawer), or bottom-sheet — controlled by the `placement` prop. Same component, same props on every platform.

<Callout variant="warning" title="Required providers (native)">
Your app root **must** be wrapped with `GestureHandlerRootView` from `react-native-gesture-handler` for the bottom-sheet pan gestures to work. See [Getting started](/docs/bloom/main/getting-started).
</Callout>

## Declarative (the 90% case)

```tsx
import { Dialog, useDialogControl, Button } from '@oxy.so/bloom';

function SignOutButton() {
  const control = useDialogControl();
  return (
    <>
      <Button onPress={() => control.open()}>Sign out</Button>

      <Dialog
        control={control}
        title="Sign out?"
        description="You'll need to enter your password to sign in again."
        actions={[
          { label: 'Sign out', color: 'destructive', onPress: doSignOut },
          { label: 'Cancel', color: 'cancel' },
        ]}
      />
    </>
  );
}
```

## Controlled open state

<Callout variant="warning" title="Prefer useDialogControl">
The controlled path fires `onClose` synchronously on `open` flipping to `false` — ahead of the exit animation. If your `onClose` handler unmounts the consumer (navigates away, removes the dialog from the tree), it races the animation still in flight. `useDialogControl()` doesn't have this footgun: it closes imperatively and only resolves once the exit finishes.
</Callout>

Pass `open` + `onClose` to drive the dialog from external state instead of `useDialogControl`:

```tsx
<Dialog
  placement="center"
  open={isOpen}
  onClose={() => setIsOpen(false)}
  title="Confirm?"
  actions={[
    { label: 'OK', onPress: handleOk },
    { label: 'Cancel', color: 'cancel' },
  ]}
/>
```

## Side-sheet (drawer)

```tsx
// Fixed left side-sheet
<Dialog placement="left" control={control} title="Filters">
  <FilterPanel />
</Dialog>

// Responsive: bottom-sheet on mobile, left drawer on desktop
<Dialog placement={{ base: 'bottom', md: 'left' }} control={control} title="Filters">
  <FilterPanel />
</Dialog>
```

## Custom content

Provide any JSX as `children`. Combine with `title` to keep a consistent header. Set `contentPadding={0}` when the children own their own insets.

```tsx
<Dialog control={control} title="Pick a tag" contentPadding={0}>
  <YourCustomBody />
</Dialog>
```

## Pure custom

Drop the declarative props entirely — `children` owns every pixel.

```tsx
<Dialog control={control}>
  <YourEntirelyCustomLayout />
</Dialog>
```

## Placement

`placement` accepts a single value or a **responsive map** resolved by `useWindowDimensions()`:

```ts
type DialogPlacement = 'center' | 'left' | 'right' | 'start' | 'end' | 'bottom';

type ResponsiveDialogPlacement =
  | DialogPlacement
  | { base: DialogPlacement; sm?: DialogPlacement; md?: DialogPlacement; lg?: DialogPlacement; xl?: DialogPlacement };
```

Breakpoints (px): `sm` 640 / `md` 768 / `lg` 1024 / `xl` 1280. The largest breakpoint whose min-width is `<=` the viewport wins; falls back to `base` below all breakpoints.

A responsive map is resolved **when the dialog opens**, and that presentation
stays fixed until its exit has completely finished. Resizing an open dialog still
updates its available width/height, but never swaps between the centered, side or
bottom renderers mid-edit. This preserves the content tree, draft state, focus,
scroll owner and the current dismissal lifecycle. Close and reopen to use the
placement for the new viewport. The same session contract applies to imperative
controls, controlled `open`, and `startOpen`; `startOpen` seeds only the first
responsive session, so resizing a dismissed dialog cannot reopen it.

Previously, crossing a breakpoint replaced the entire renderer. An imperative
dialog could disappear because its replacement started closed; even forcing that
replacement open lost child state. The shared session owner prevents that swap
without duplicate mounted dialogs or consumer state/scroll workarounds.

Per-placement behavior:
- `center` — DOM-portal modal (web) / detached floating card (native).
- `left` / `right` — animated side-sheet anchored to that PHYSICAL viewport edge.
- `start` / `end` — the same side-sheet on the LOGICAL edge: `start` is the left in a left-to-right layout and the right in a right-to-left one (`end` the reverse), read from `useIsRtl()`, and the panel slides in from that edge. The matching `inset` side applies (`inset.right` for `start` in RTL). On native the panel is positioned with `insetInlineStart`/`insetInlineEnd`, which Yoga resolves against `I18nManager` — a physical `left`/`right` would be swapped by React Native's default `swapLeftAndRightInRTL`. On web the drawer is portaled outside any `dir` context, so it takes the physical edge `useIsRtl()` names. An app that ships Arabic or Hebrew wants `start`/`end`: `{ base: 'bottom', md: 'start' }` is the mirrored store drawer.
- `bottom` — reuses the cross-platform `BottomSheet` on BOTH web and native (drag-to-dismiss + internal scroll work everywhere). The shared surface owns scrolling by default; `scrollable={false}` delegates it to content with its own bounded scroller.
  The sheet is flush with the bottom of the window, so the Dialog ends its content with a spacer the height of the bottom safe area (the Android gesture bar, the iOS home indicator). This spacer is inside the scroll content. Content keeps its own padding; do not add `insets.bottom` yourself. Without the spacer, the last row sat under the gesture bar. A body taller than the sheet could not scroll it out, because the scroll range ended where the bar began.

## Nav header: the title beside the ✕

In `header` mode every large title starts below the 56px navigation row and its 20px gradient tail. Root and nested screens share the same full-width title area, regardless of back, close or trailing actions. The title therefore keeps its position and wrapping when navigation controls change. As content scrolls, the small title still appears in the navigation row.

The bar's background is an SVG gradient Bloom paints itself. It is solid in the surface colour across the nav row and fades out over the 20px below it. Do not bring back the old Tailwind gradient class. On native it compiles to a CSS gradient with Tailwind v4's `in oklab` interpolation, which React Native cannot parse, so the bar was transparent and a collapsed title sat on top of the rows scrolling under it. On web it also depended on the consumer scanning Bloom's `lib/`.

## Blurring the backdrop on Android

A backdrop blurs its content on iOS and web with no setup. **On Android it needs
the app content wrapped in a blur target**, which `BloomProvider` composes — so
if you mount it, there is nothing to do:

```tsx
import { BloomProvider } from '@oxy.so/bloom/provider';

<BloomProvider>{children}</BloomProvider>
```

An app that does not mount `BloomProvider` keeps the tint-only backdrop. That is
a supported state, not a missing step — see below.

Two things are worth knowing rather than discovering:

- **It applies to the bottom-sheet path only.** `expo-blur` on Android blurs a
  target view, and a blur view that is a DESCENDANT of its own target crashes
  the app — `SIGSEGV`, an unbounded render-tree recursion. Only a surface in a
  separate native window is safe, which means a real RN `<Modal>`: that is
  `BottomSheet`, and `Dialog`'s bottom placement through it. `Dialog`'s centre
  and side placements portal into the same window and keep the tint-only
  backdrop. Bloom enforces this structurally — the target is simply not
  reachable from a surface that has not crossed a window boundary — so there is
  no wiring you can get wrong.
- **Not mounting it is a supported state**, not a broken one. The backdrop still
  paints its tint at full intensity; you lose the blur and nothing else, with no
  warning and no crash.

## Keyboard and focus (web)

The centred card and the side drawers own the keyboard while they are the
top-most surface:

- **Focus moves in on open** — to whatever the content focused itself (an
  `autoFocus` field), else the first tabbable control, else the panel — and
  **returns to the element that opened it** as the dialog starts closing, unless
  the host has already moved it somewhere else.
- **Tab and Shift+Tab wrap** at the panel's edges.
- **Escape dismisses** (when `dismissOnBackdrop` allows it) from anywhere,
  including the dialog's own text field. react-native-web's `TextInput` stops
  the propagation of every keydown, so a dialog listening on `document` never
  heard Escape while focus was in its search box. The key is claimed in the
  capture phase, dismissed in the bubble phase, and — for a key a text field
  swallowed — after dispatch. A control that keeps Escape for itself calls
  `preventDefault()` (the tag field and the composer do).
- **One layer per Escape.** A menu, select or second dialog opened from this
  one takes a higher place in the overlay stack and gets Escape, Tab and focus
  until it closes. Gate: `DialogKeyboard.web.test.tsx`,
  `SelectKeyboard.web.test.tsx`.

The `bottom` placement is the shared `BottomSheet`, which does the same on web
(`docs/bottom-sheet.mdx`). A controlled bottom dialog the SHEET closes — the
backdrop, a drag, Escape — now calls `onClose`, so the host's `open` does not
stay `true` over a closed sheet; a close the host made by flipping `open` still
does not call it again. The native `center` card follows the same rule for the
backdrop, a swipe down and Android Back; the native side drawers already
reported those through `onClose`.

## Examples

### Three-action confirmation

```tsx
<Dialog
  control={control}
  title="Delete project?"
  description="This will permanently delete the project and all of its files."
  actions={[
    { label: 'Delete', color: 'destructive', onPress: handleDelete },
    { label: 'Archive', onPress: handleArchive },
    { label: 'Cancel', color: 'cancel' },
  ]}
/>
```

### Async confirm with loading state

```tsx
const [busy, setBusy] = useState(false);

<Dialog
  control={control}
  title="Submit?"
  actions={[
    {
      label: 'Submit',
      loading: busy, // spinner, busy, presses ignored
      shouldCloseOnPress: false, // keep dialog open while we work
      onPress: async () => {
        setBusy(true);
        try {
          await submit();
          control.close();
        } finally {
          setBusy(false);
        }
      },
    },
    { label: 'Cancel', color: 'cancel' },
  ]}
/>
```

### Form inside a dialog

```tsx
<Dialog control={control} title="Add tag">
  <TextFieldInput label="Tag name" value={name} onValueChange={setName} />
  <Button onPress={() => { save(name); control.close(); }}>Save</Button>
</Dialog>
```

### Responsive drawer→sheet

Bottom-sheet on small screens, left drawer on `md` and wider:

```tsx
<Dialog
  placement={{ base: 'bottom', md: 'left' }}
  control={control}
  title="Store settings"
  containerClassName="md:left-[4.75rem]"
>
  <SettingsPanel />
</Dialog>
```

## Migration from CenteredDialog / ResponsiveSheet

`CenteredDialog` and `ResponsiveSheet` were removed in 0.16.x.

```tsx
// Before
<CenteredDialog visible={v} onClose={c}>…</CenteredDialog>
// After
<Dialog placement="center" open={v} onClose={c}>…</Dialog>

// Before
<ResponsiveSheet side="left" open={o} onClose={c}>…</ResponsiveSheet>
// After
<Dialog placement={{ base: 'bottom', md: 'left' }} open={o} onClose={c}>…</Dialog>
```

Removed exports: `CenteredDialog`, `CenteredDialogProps`, `BLOOM_CENTERED_DIALOG_CSS`, `CENTERED_DIALOG_BACKDROP_TESTID`, `ResponsiveSheet`, `@oxy.so/bloom/responsive-sheet` subpath.

The default panel uses Bloom’s shared `SurfacePaint` with its gradient and rim. The paint is absolute inside the existing measured panel, so gestures, focus, imperative controls and layout retain their hosts. Explicit caller backgrounds and BottomSheet’s `backgroundComponent` remain overrides. The composited painted color supplies descendant tokens; the default body has 90% opacity with one backdrop blur on web.

Dialog panels publish level 0 with the painted tint composited against the page backing. Explicit style backgrounds are resolved against the page backing once and shared by paint, descendant context and web surface variables; opening inside a card does not leak its level into the dialog.

### Shared surface paint

The painted host delegates its fill to Surface: a 90%-opacity body with a backdrop blur on web, plus the shared sheen and rim. The host itself stays transparent to avoid painting twice. Explicit alpha colours retain their alpha; descendants receive the corresponding composited fill. Plain or unframed content keeps its existing layout behavior.

### Custom presentation motion

`presentation="custom"` on a centered card lets its content own panel paint and entry/exit motion. Its backdrop is transparent; Bloom retains the portal, overlay ordering, inertness, keyboard/focus behavior, screen scope and imperative close lifecycle. Set `exitDuration` in milliseconds to retain content through its exit. `useDialogContext().isClosing` becomes true when any dismissal starts, including Escape and the backdrop. The default presentation and its material/timings are unchanged. Bottom placement retains the BottomSheet presentation.

Project Board composes its original 480ms create Genie and 560ms detail exit lifetime through this opt-in. On native, this custom centered presentation uses the existing side-sheet overlay infrastructure while its content supplies the panel layout.

### Modal semantics

On web, every placement exposes a modal `dialog` panel. Its accessible name
comes from `title` or `label`; bottom sheets with navigation chrome also use
`header.title` when no label is supplied. The panel includes the sticky header
and scrolling body, so header actions stay inside the dialog's keyboard and
accessibility boundary. `description` is associated with that same panel.
Wrap application content (not the surface outlet) in `OverlayInertBoundary` to
exclude the underlying page while a modal is open.


### Content that owns scrolling

With `scrollable={false}`, each placement passes a bounded flex height to the
child instead of nesting it in a disabled ScrollView. This includes side drawers
with a header and native centered cards. Give the child scroller `flex: 1` and
`minHeight: 0`; the dialog supplies the viewport bound and header spacing. A
footer after the child stays inside the surface.

Initial keyboard focus chooses the first control visible inside the panel, or
the panel itself when all controls are below its viewport. Focusing the surface
and restoring its opener preserve scroll position, so a pagination action at
the end of a long list does not pull a newly opened dialog to the bottom.
Content that explicitly focuses itself retains that focus.

## Flat panel material

`material="flat"` paints the authored panel fill directly, omitting the shared
surface tint, sheen, rim and web blur. It applies to center, side and
bottom placements on both platforms, including responsive placement changes.
`panelStyle.backgroundColor` remains the authored fill; without it the panel
uses its theme background. Descendants receive that exact backing through the
surface context. The navigation header uses the same solid backing rather than
a fading scrim (an explicit image-tone header keeps its image treatment).
Geometry, shadow, focus, dismissal and motion contracts are unchanged.

The default `material="surface"` keeps the existing optical treatment. Buttons
and other controls inside the panel retain their own material choices.
Standalone `BottomSheet` exposes the same material option with `backgroundFill`;
an explicit `backgroundComponent` remains authoritative.

`minSideGutter` controls the minimum opposite-edge space when capping a side sheet’s width (default 24px). Pass `0` with a viewport-sized `width` for a full-width side sheet. Insets are still subtracted; negative gutters clamp to zero and non-finite gutters use the default. This applies to both physical and logical side placements on web and native; center/bottom geometry is unchanged.

## Backdrop paint and timed presentation

`backdrop?: BackdropAppearance` configures only the shared backdrop's paint. It
accepts `blurIntensity` (zero disables blur), `blurTint`, `dimColor`, `dimOpacity`
and `dimGradient`. A gradient replaces the uniform dim color; opacity still
multiplies it. Geometry, layering, dismissal and focus remain Dialog-owned.

```tsx
<Dialog
  control={control}
  placement="end"
  backdrop={{
    blurIntensity: 0,
    dimOpacity: 1,
    dimGradient: {
      direction: 'start-to-end',
      stops: [
        { offset: 0, color: 'transparent' },
        { offset: 0.7, color: 'rgba(0,0,0,0.35)' },
        { offset: 1, color: 'rgba(0,0,0,0.35)' },
      ],
    },
  }}
  transition={{ duration: 300, easing: [0, 0, 0.58, 1] }}
>
  {children}
</Dialog>
```

`transition?: SurfaceTransition` opts into one duration/easing for panel and
backdrop entry/exit on web and native, including centered and bottom placements.
The exit lifecycle waits for that duration before dismissing; live OS reduced
motion settles immediately. Drag-following remains direct and a cancelled drag
keeps the default spring; a completed dismissal uses the requested timing.
Omitting the prop preserves each renderer's existing timings/springs.
`presentation="custom"` continues to own its motion via `exitDuration`; these
options do not replace that separate contract. Content morphing retains its own
configuration.

Durations clamp to zero; non-finite durations use 300ms. Easing is a CSS
cubic-bezier tuple, with finite coordinates and x coordinates in 0..1; invalid
curves use CSS `ease`. Gradient directions are logical horizontally
(`start-to-end` / `end-to-start`) and physical vertically (`top-to-bottom` /
`bottom-to-top`). RTL reverses horizontal direction. Stops clamp to 0..1 and
cannot move backwards relative to the preceding stop; fewer than two stops,
non-finite offsets, empty colors or invalid directions fall back to `dimColor`.
Blur intensity clamps to 0..100 and dim opacity to 0..1; non-finite values retain
the default. Both options also exist on the underlying `BottomSheet`.


## Screens inside one dialog

Use `frame` when a dialog hosts a sequence of screens. Keep the `Dialog` and its
control mounted; change `frame.key` as your router or local state changes. Bloom
owns the shared floating page header, grouped actions, title reveal on scroll,
and panel size morph. No app-side animation or header renderer is needed.

```tsx
const control = useDialogControl();
const [screen, setScreen] = useState('summary');

<Dialog
  control={control}
  frame={{
    key: screen,
    header: {
      title: screen === 'summary' ? 'Summary' : 'Details',
      onBack: screen === 'details' ? () => setScreen('summary') : undefined,
    },
  }}
>
  {screen === 'summary' ? <Summary onDetails={() => setScreen('details')} /> : <Details />}
</Dialog>
```

`frame.header` merges over `header` defaults. A frame enables screen-header mode
even when its header is initially empty, keeping the content host stable during
navigation. Natural content height is measured; `frame.size` can declare
`height` and `maxWidth` in pixels for an independently scrolling screen.
`frame.morph={false}` opts one frame out; `morph={false}` disables panel resizing
for the dialog. Side drawers retain their fixed geometry. Reduced-motion policy
continues to follow the shared motion implementation.

A changed frame key resets the dialog-owned scroller and header reveal to the top.
A rerender or size change within the same key preserves scroll and form state.
With `scrollable={false}`, the screen owns scroll restoration.

The router remains yours: Bloom does not depend on Expo Router, application
routes, authentication, or a navigation store. For deeply nested route hosts,
`useDialogFrame` and `useDialogHeader` remain the advanced equivalent. Use one
frame owner per dialog; do not combine a `frame` prop with another frame writer.
The same `frame` option is accepted when presenting a Bloom surface.


Dialog cards use the shared 28px dialog shape; bottom placement applies the same
radius to its top corners. Content and surface paint share this geometry so
images, scroll content and the header clip together. `style`/`panelStyle` can
still override the radius for a particular dialog.

### Screen-to-screen content motion

Changing `frame.key` (or the key declared with `useDialogFrame`) gives the incoming
screen a brief 160ms settle alongside the existing size morph. Real children mount
immediately, remain interactive, and never pass through a blank opacity-zero state.
`direction: 'forward'` is the default; use `'backward'` when returning through
history or `'none'` to disable content motion while retaining size morphing.
Reduced motion skips the content transition. First mount and unchanged frame keys
do not trigger this transition; Dialog's entrance animation is independent.

Header icon `actions` and the close button share one trailing `ButtonGroup`. Back stays in the leading PageHeader island, and `primaryAction` renders separately beside the trailing group. Close remains available alongside back and actions unless `showClose: false`; a custom `right` replaces the entire trailing slot.

A frame can set `colorPreset` to scope the entire dialog, including its navigation, to a Bloom recipe. Use either `frame={{ key, colorPreset }}` or the existing single `useDialogFrame({ key, colorPreset })` declaration. Leaving the preset out on the next frame restores the enclosing palette; changing it preserves mounted content and media.

For content that supplies its own hero heading, declare `header={{ title, titleLayout: 'hero' }}` (also supported by `useDialogHeader`). The content starts under the floating navigation without a duplicate large title or top spacer. The navigation title and scrim appear as the hero scrolls away. `titleLayout: 'large'` uses the standard in-content large title and `titleLayout: 'bar'` keeps the small title visible. Existing `largeTitle` behavior is unchanged when `titleLayout` is omitted.

A frame may also declare `typography: 'system'` to use the platform system font throughout its body and navigation while preserving Bloom's semantic type scale. Omitting it on the next frame restores the enclosing typography. The same scoped policy is available independently as `TypographyScope` from `@oxy.so/bloom/typography`; `mode="system"` uses system-ui on web, System on iOS, and sans-serif on Android. The default remains Bloom typography.

## Fullscreen workspaces

`presentation="fullscreen"` fills the overlay viewport while retaining Dialog's
Surface, modal focus, layering, dismissal and opening/closing lifecycle. It
supersedes `placement`, `width`, `maxWidth`, `maxHeightRatio` and side insets. It
uses the existing centered modal engine on web and the existing overlay drawer
engine on native; there is no consumer viewport calculation or alternate modal.

For independent panes, use `scrollable={false}` and `contentPadding={0}`, then
compose `AppShellPanels scope="local"` with each pane's `Screen` and
`ScreenScrollView`. That compositor owns responsive collapse and each region's
bounded scroll. `label` names the dialog accessibly without adding another visible
title; leave `title` and `header` unset when pane Screens own their headings.
Screen's normal safe-area contract remains responsible for its chrome.

```tsx
<Dialog
  control={history}
  presentation="fullscreen"
  label="Version history"
  scrollable={false}
  contentPadding={0}
>
  <AppShellPanels scope="local" layout={historyLayout} />
</Dialog>
```

Fullscreen content remains mounted when the viewport changes. Closing and later
reopening starts a new normal Dialog session. Default centered cards, side sheets,
bottom sheets and custom-painted surfaces retain their existing geometry.

A fullscreen workspace can use `AppShellPanels scope="local"` with
`layout.appearance: 'plain'` to inherit the Dialog's Surface. Keep Dialog
`scrollable={false}` when panel `ScreenScrollView`s own scrolling. A shared
workspace heading belongs in `layout.header`; individual panel headings stay
in each panel's `Screen`. Supply the Dialog's accessible `label` even when its
visual title is omitted.

Dialog appearance scopes compose onto the actual panel renderer. They do not
insert a host beside the calling page, even while the dialog is closed. A
consumer may place Dialogs beside flex content without reserving invisible
gaps; frame palette changes still preserve the mounted content and portal scope.

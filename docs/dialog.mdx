# Dialog

A single `<Dialog>` component for every overlay surface — centered modal, side-sheet (left/right or logical start/end drawer), or bottom-sheet — controlled by the `placement` prop. Same component, same props on every platform.

<Callout variant="warning" title="Required providers (native)">
Your app root **must** be wrapped with `GestureHandlerRootView` from `react-native-gesture-handler` for the bottom-sheet pan gestures to work. See [Getting started](/docs/bloom/main/getting-started).
</Callout>

## Declarative (the 90% case)

```tsx
import { Dialog, useDialogControl, Button } from '@oxy.so/bloom';

function SignOutButton() {
  const control = useDialogControl();
  return (
    <>
      <Button onPress={() => control.open()}>Sign out</Button>

      <Dialog
        control={control}
        title="Sign out?"
        description="You'll need to enter your password to sign in again."
        actions={[
          { label: 'Sign out', color: 'destructive', onPress: doSignOut },
          { label: 'Cancel', color: 'cancel' },
        ]}
      />
    </>
  );
}
```

## Controlled open state

<Callout variant="warning" title="Prefer useDialogControl">
The controlled path fires `onClose` synchronously on `open` flipping to `false` — ahead of the exit animation. If your `onClose` handler unmounts the consumer (navigates away, removes the dialog from the tree), it races the animation still in flight. `useDialogControl()` doesn't have this footgun: it closes imperatively and only resolves once the exit finishes.
</Callout>

Pass `open` + `onClose` to drive the dialog from external state instead of `useDialogControl`:

```tsx
<Dialog
  placement="center"
  open={isOpen}
  onClose={() => setIsOpen(false)}
  title="Confirm?"
  actions={[
    { label: 'OK', onPress: handleOk },
    { label: 'Cancel', color: 'cancel' },
  ]}
/>
```

## Side-sheet (drawer)

```tsx
// Fixed left side-sheet
<Dialog placement="left" control={control} title="Filters">
  <FilterPanel />
</Dialog>

// Responsive: bottom-sheet on mobile, left drawer on desktop
<Dialog placement={{ base: 'bottom', md: 'left' }} control={control} title="Filters">
  <FilterPanel />
</Dialog>
```

## Custom content

Provide any JSX as `children`. Combine with `title` to keep a consistent header. Set `contentPadding={0}` when the children own their own insets.

```tsx
<Dialog control={control} title="Pick a tag" contentPadding={0}>
  <YourCustomBody />
</Dialog>
```

## Pure custom

Drop the declarative props entirely — `children` owns every pixel.

```tsx
<Dialog control={control}>
  <YourEntirelyCustomLayout />
</Dialog>
```

## Placement

`placement` accepts a single value or a **responsive map** resolved by `useWindowDimensions()`:

```ts
type DialogPlacement = 'center' | 'left' | 'right' | 'start' | 'end' | 'bottom';

type ResponsiveDialogPlacement =
  | DialogPlacement
  | { base: DialogPlacement; sm?: DialogPlacement; md?: DialogPlacement; lg?: DialogPlacement; xl?: DialogPlacement };
```

Breakpoints (px): `sm` 640 / `md` 768 / `lg` 1024 / `xl` 1280. The largest breakpoint whose min-width is `<=` the viewport wins; falls back to `base` below all breakpoints.

Per-placement behavior:
- `center` — DOM-portal modal (web) / detached floating card (native).
- `left` / `right` — animated side-sheet anchored to that PHYSICAL viewport edge.
- `start` / `end` — the same side-sheet on the LOGICAL edge: `start` is the left in a left-to-right layout and the right in a right-to-left one (`end` the reverse), read from `useIsRtl()`, and the panel slides in from that edge. The matching `inset` side applies (`inset.right` for `start` in RTL). On native the panel is positioned with `insetInlineStart`/`insetInlineEnd`, which Yoga resolves against `I18nManager` — a physical `left`/`right` would be swapped by React Native's default `swapLeftAndRightInRTL`. On web the drawer is portaled outside any `dir` context, so it takes the physical edge `useIsRtl()` names. An app that ships Arabic or Hebrew wants `start`/`end`: `{ base: 'bottom', md: 'start' }` is the mirrored store drawer.
- `bottom` — reuses the cross-platform `BottomSheet` on BOTH web and native (drag-to-dismiss + internal scroll work everywhere). Custom `children` on bottom placement are rendered in a NON-scrollable body — children own scrolling.
  The sheet is flush with the bottom of the window, so the Dialog ends its content with a spacer the height of the bottom safe area (the Android gesture bar, the iOS home indicator). This spacer is inside the scroll content. Content keeps its own padding; do not add `insets.bottom` yourself. Without the spacer, the last row sat under the gesture bar. A body taller than the sheet could not scroll it out, because the scroll range ended where the bar began.

## Nav header: the title beside the ✕

In `header` mode the large title normally starts below the 52px nav row. When that row would hold **only** the close button, the title starts level with the ✕ and wraps before it. That means no `onBack`, `left`, `right`, `actions` or `primaryAction`, and no `titleContent` or `tone: 'onImage'`. The row's scrim fades in once content scrolls under it. Without this, every entry view of a flow began with an empty band above its title. As soon as a back button or trailing actions appear, the title returns to its own row below the bar. `isInlineCloseHeader()` in `dialog/DialogHeader.tsx` is the rule.

The bar's background is an SVG gradient Bloom paints itself. It is solid in the surface colour across the nav row and fades out over the 20px below it. Do not bring back the old Tailwind gradient class. On native it compiles to a CSS gradient with Tailwind v4's `in oklab` interpolation, which React Native cannot parse, so the bar was transparent and a collapsed title sat on top of the rows scrolling under it. On web it also depended on the consumer scanning Bloom's `lib/`.

## Blurring the backdrop on Android

A backdrop blurs its content on iOS and web with no setup. **On Android it needs
the app content wrapped in a blur target**, which `BloomProvider` composes — so
if you mount it, there is nothing to do:

```tsx
import { BloomProvider } from '@oxy.so/bloom/provider';

<BloomProvider>{children}</BloomProvider>
```

An app that does not mount `BloomProvider` keeps the tint-only backdrop. That is
a supported state, not a missing step — see below.

Two things are worth knowing rather than discovering:

- **It applies to the bottom-sheet path only.** `expo-blur` on Android blurs a
  target view, and a blur view that is a DESCENDANT of its own target crashes
  the app — `SIGSEGV`, an unbounded render-tree recursion. Only a surface in a
  separate native window is safe, which means a real RN `<Modal>`: that is
  `BottomSheet`, and `Dialog`'s bottom placement through it. `Dialog`'s centre
  and side placements portal into the same window and keep the tint-only
  backdrop. Bloom enforces this structurally — the target is simply not
  reachable from a surface that has not crossed a window boundary — so there is
  no wiring you can get wrong.
- **Not mounting it is a supported state**, not a broken one. The backdrop still
  paints its tint at full intensity; you lose the blur and nothing else, with no
  warning and no crash.

## Keyboard and focus (web)

The centred card and the side drawers own the keyboard while they are the
top-most surface:

- **Focus moves in on open** — to whatever the content focused itself (an
  `autoFocus` field), else the first tabbable control, else the panel — and
  **returns to the element that opened it** as the dialog starts closing, unless
  the host has already moved it somewhere else.
- **Tab and Shift+Tab wrap** at the panel's edges.
- **Escape dismisses** (when `dismissOnBackdrop` allows it) from anywhere,
  including the dialog's own text field. react-native-web's `TextInput` stops
  the propagation of every keydown, so a dialog listening on `document` never
  heard Escape while focus was in its search box. The key is claimed in the
  capture phase, dismissed in the bubble phase, and — for a key a text field
  swallowed — after dispatch. A control that keeps Escape for itself calls
  `preventDefault()` (the tag field and the composer do).
- **One layer per Escape.** A menu, select or second dialog opened from this
  one takes a higher place in the overlay stack and gets Escape, Tab and focus
  until it closes. Gate: `DialogKeyboard.web.test.tsx`,
  `SelectKeyboard.web.test.tsx`.

The `bottom` placement is the shared `BottomSheet`, which does the same on web
(`docs/bottom-sheet.mdx`). A controlled bottom dialog the SHEET closes — the
backdrop, a drag, Escape — now calls `onClose`, so the host's `open` does not
stay `true` over a closed sheet; a close the host made by flipping `open` still
does not call it again.

## Web setup

Inject the CSS animations into your global styles once:

```tsx
import { BLOOM_DIALOG_CSS } from '@oxy.so/bloom/dialog';

// In your HTML head or global CSS file:
<style>{BLOOM_DIALOG_CSS}</style>
```

## Examples

### Three-action confirmation

```tsx
<Dialog
  control={control}
  title="Delete project?"
  description="This will permanently delete the project and all of its files."
  actions={[
    { label: 'Delete', color: 'destructive', onPress: handleDelete },
    { label: 'Archive', onPress: handleArchive },
    { label: 'Cancel', color: 'cancel' },
  ]}
/>
```

### Async confirm with loading state

```tsx
const [busy, setBusy] = useState(false);

<Dialog
  control={control}
  title="Submit?"
  actions={[
    {
      label: busy ? 'Submitting…' : 'Submit',
      disabled: busy,
      shouldCloseOnPress: false, // keep dialog open while we work
      onPress: async () => {
        setBusy(true);
        try {
          await submit();
          control.close();
        } finally {
          setBusy(false);
        }
      },
    },
    { label: 'Cancel', color: 'cancel' },
  ]}
/>
```

### Form inside a dialog

```tsx
<Dialog control={control} title="Add tag">
  <TextFieldInput label="Tag name" value={name} onValueChange={setName} />
  <Button onPress={() => { save(name); control.close(); }}>Save</Button>
</Dialog>
```

### Responsive drawer→sheet

Bottom-sheet on small screens, left drawer on `md` and wider:

```tsx
<Dialog
  placement={{ base: 'bottom', md: 'left' }}
  control={control}
  title="Store settings"
  containerClassName="md:left-[4.75rem]"
>
  <SettingsPanel />
</Dialog>
```

## Migration from CenteredDialog / ResponsiveSheet

`CenteredDialog` and `ResponsiveSheet` were removed in 0.16.x.

```tsx
// Before
<CenteredDialog visible={v} onClose={c}>…</CenteredDialog>
// After
<Dialog placement="center" open={v} onClose={c}>…</Dialog>

// Before
<ResponsiveSheet side="left" open={o} onClose={c}>…</ResponsiveSheet>
// After
<Dialog placement={{ base: 'bottom', md: 'left' }} open={o} onClose={c}>…</Dialog>
```

Removed exports: `CenteredDialog`, `CenteredDialogProps`, `BLOOM_CENTERED_DIALOG_CSS`, `CENTERED_DIALOG_BACKDROP_TESTID`, `ResponsiveSheet`, `@oxy.so/bloom/responsive-sheet` subpath.

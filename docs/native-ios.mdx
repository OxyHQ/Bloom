# Native iOS: `.bloom` to Swift + SwiftUI

Status: in progress, 2026-11-28 (lang-native-iOS-1). [ADR 0003](./adr/0003-native-backends.md) decided
that `.bloom` compiles straight to native code, with no JavaScript on the device. The shapes both
platforms share are in [the native runtime API](./native-runtime-api.mdx); this page covers what is
specific to iOS.

## What is built

| Part | Where | State |
|---|---|---|
| The Swift backend | `packages/bloom-language-compiler/crates/native/src/swift/` | NativeBench emits with nothing left uncovered; across the goldens, 16 constructs are recorded as uncovered (mostly structural records) |
| Golden tests, one per construct | `crates/native/tests/golden-swift/` (`cargo test -p bloom_native --test golden_swift`) | 13 own cases, plus every TypeScript emitter fixture with no TS import (the Kotlin goldens' selection): 55 cases. 33 type-check as Swift; 21 are queued in `NOT_YET_SWIFT` with their reasons; 1 is TS-only. |
| `Bloom`: the standard library on Foundation | `crates/native/runtime/ios/Sources/Bloom` | Ported; see its tests |
| `BloomTheme`: the colour engine, roles, presets, ambient, scopes, persistence | `runtime/ios/Sources/BloomTheme` | Byte-identical to the TS goldens (`swift test --filter BloomThemeTests`) |
| `BloomUI`: BloomUI on SwiftUI | `runtime/ios/Sources/BloomUI` | The feed's and Settings' nodes, the material, the router |
| Tokens, glyphs and the node table, generated | `scripts/generate-swift-tokens.mjs`, `crates/native/scripts/icons.py`, `scripts/generate-swift-theme.ts` | From `spec/language.json`, `src/icons` and `src/theme`; nothing copied by hand |
| `bloom-native emit --target swiftui <package> --ios-project <dir>` | `src/swift/project.rs` | A SwiftPM package of the app's modules, an XcodeGen `project.yml`, the `@main` app, the fonts, and a UI-test target that measures the bench |
| Islands | `BloomUI/Island.swift`, `stdlib/Bloom/Native/BloomIsland/ios/` | The Swift side type-checks. The Fabric component is written but not built. |

## The mapping

Bloom 2.0's surface is Swift's (ADR 0002), so the backend mostly prints the checked tree: a
`struct` stays a `struct`, and an `enum`, `protocol`, `@Observable final class` or `actor` stays what
it is. `async`, `throws`/`try`, `switch`, labels and generics are Swift's own. What it rewrites:

| Bloom | Swift |
|---|---|
| A body's last expression is its value | `return` (into an `if`'s or a `switch`'s branches) |
| `none`; `none` in a builder | `nil`; `EmptyView()` |
| `task { … }` | `Task { … }` |
| `Binding(get: v, set: f)` | `Binding(get: { v }, set: f)` |
| A struct's or a view's construction | An explicit memberwise `init`: Swift's is internal, and it leaves out a `let` with a default |
| A public type's protocol witnesses | `public` (`body`, `==`, `id`, a public protocol's requirements) |
| A view's `static func ==` | `nonisolated`: a view is main-actor isolated, `Equatable` is not |
| A function-typed parameter | `@escaping` |
| `Float` | `Double` (Bloom's `Float` is 64-bit) |
| `[String: V]`, `Set<T>` | `OrderedDictionary`, `OrderedSet` (insertion order, as on every backend) |
| `xs.prefix(n)` on a list or a string | `Array(…)`, `String(…)` (Swift returns a slice) |
| `a ?? b == c` | `a ?? (b == c)`: Bloom's `??` binds loosest, Swift's binds tighter than `==` |
| An enum that holds itself | `indirect enum` |
| A thrown type | Gains `Error` |
| `enum Route: Routable` | Its route table, `routeTag`, `routeValues`, `route(tag:params:)` |
| `let content: View`, `var children: View?`, `let rows: () -> View` | Type parameters of the view, taken as `@ViewBuilder` closures |
| `public let k = EnvironmentKey("k", default: v)` | An `EnvironmentKey` type and an `EnvironmentValues.k` |
| A universal modifier (`.padding(.horizontal, .lg)`) | `.bloomPadding(.horizontal, .lg)`, kept out of SwiftUI's overloads; the effects (`.task`, `.onAppear`, `.onChange`) stay SwiftUI's |
| A node's own modifiers after universal ones | Hoisted onto the node: they are its methods |
| `extern native "M" { func … }` | A protocol that the native side implements and registers |

An emitted file imports `Foundation`, `Bloom` and `BloomUI`. When it has views, it also imports the
SwiftUI declarations it means as SwiftUI means them, one by one (`import struct SwiftUI.State`),
so an unqualified `Text`, `Image` or `Toggle` is always BloomUI's. Swift 6 takes a type in a
public signature only from a module the file imports; this is why the shared doc's scoped-import
proposal is the right one.

**TS-only on Swift.** `surface_protocols`' `static let self: Codec<Post>` and `T.self.name` are the
TypeScript backend's codec witnesses, with no Swift meaning. They are listed in
`tests/golden-swift/KNOWN_NOT_SWIFT` rather than imitated.

## BloomUI on SwiftUI

Parity is with today's Bloom on iOS, so BloomUI follows Bloom's layout and paint, not SwiftUI's
defaults:

- **Stacks are flexbox** (`Layout/FlexLayout.swift`, a SwiftUI `Layout` doing Yoga's single-line
  algorithm):
  - children stretch and the gap is 0 by default;
  - `.grow()` is `flex: 1` from a zero basis;
  - only a `.shrink()` child shrinks (React Native's default shrink is 0);
  - a child that is not stretched gets fit-content (`min(ideal, room)`);
  - `.frame(width: .full)` takes the parent's whole cross size;
  - an unsized `Image` is 0 × 0, and `.aspectRatio(r)` takes its height from its width.
- **Type:**
  - Inter for text steps, BlomusModernus for display and title steps (as `src/typography`).
  - The ramp's size, line height, tracking and weight. The line height is laid out as React
    Native's iOS text lays it out: the extra space is split above and below the glyphs.
  - With no font: 13 pt Inter, its natural line height, in `text`.
- **Colour:** every colour is BloomTheme's, by role. `BloomColor` is a role at an opacity
  (`.primary.opacity(0.1)`). `BloomThemeProvider` resolves a preset (`oxy` by default) or a seed,
  and caches the result. With no provider, a role draws magenta.
- **Nodes for the feed and Settings**, each with today's numbers (sizes, paddings, colour roles,
  press paint, haptics, accessibility, taken from `src/`):
  - `Text`, `Icon` (every glyph: 580 sources, 1,035 names, even-odd, stroke-only where the source
    strokes), `Avatar` and `Image`;
  - the image pipeline (URLSession, memory and disk caches, ImageIO decoding at the drawn size,
    `data:` URLs, retries after 2 s and 8 s, never on a 404);
  - `ActionBar`/`Action`, `GroupedSection`/`GroupedSectionItem` (with `wrapControl`'s wrap rule),
    `Toggle` (React Native's spring), `Button`, `Loading`, `Divider` and `TextField`;
  - `ScrollView`, `VirtualList` (a reused-cell `List`, rows `VirtualListRow<T>`);
  - `NavigationStack(root:tabs:sheets:)` with `push`, `replace` and `dismiss`.
- **Not done yet:** every other node family and modifier of the spec. `Loading` turns its first
  shape; the Material 3 morph is to come. The avatar's hashed fallback tints are to come.

### The material, once

`BloomUI/Material/` is the only code that blurs, tints, rims, presses or plays a haptic (the
owner's rule; the API is `BloomMaterial`, `.bloomMaterial(_:in:)`, `BloomSurface`, `.bloomPress`
and `.bloomHaptic`, as in the shared doc):

- **iOS 26 and later:** `glassEffect` with Bloom's tint and opacity, `interactive()` for a control.
- **iOS 17 to 25:** the spec's `iosFallback` material, then Bloom's tint at 0.72 (0.8 for a control
  fill), then the rim.
- **Solid and flat materials:** Bloom's paint, and today's press (the fill mixed 8% toward black,
  100 ms `inOutQuad`, no scale).
- **Accessibility:** reduce transparency and increased contrast paint glass solid, with a hairline.
- **Scheme:** the material's scheme is Bloom's theme, not the window's.
- **Haptics:** Bloom's intents (`tap`, `confirm`, `selection`, `success`, `warning`, `error`) through
  `sensoryFeedback`.

What iOS's system effects do not give directly, and the plan for each:

| Today's effect | On iOS |
|---|---|
| The frost radius, rim and glow optics on glass | The system's own on iOS 26. The tokens apply on the fallback. |
| The lens jelly (swell, lean, the tanh stretch on drag) | The system's interactive glass, its press and bounce |
| The scrubbable tab capsule: a 1:1 highlight, a haptic at each boundary, minimize/hide progress | Bloom's own bar over the material with a drag gesture; the system `TabView` until then |
| The header's flat smoothstep scrim, `titleReveal` | Bloom's overlay over the system toolbar |
| Custom menu rows (swatches, sub-flyouts), the menu's tint | The system `Menu`/`contextMenu`; custom rows as a Bloom popover on the material |
| The detached sheet (16 pt gaps, radius 24), its dismiss physics, backdrop blur 80 at dim 0.28 | The system `.sheet` with detents; the detached sheet as a custom presentation |
| The progressive blur band under the bottom bar | Stacked masked materials |

**Decided by the owner, 2026-11-28: Liquid Glass for everything on iOS**
([surface material study](./surface-material-study.mdx), decision 7). Buttons, the FAB, header
controls, the bottom bar, tabs and menus all draw through the one material, as on Android: system
Liquid Glass on iOS 26 and later, the blur fallback before. BloomUI's `Button` paints its solid
style as `glassProminent` and its subtle and outline styles as tinted glass; plain stays flat.
Side-by-side recordings on the Mac are the evidence that it is at least as good as today.

## Verified without a Mac (SuperPC, Linux)

- **The toolchain.** Swift 6.4.3 for Debian 13, swift.org's release, signature verified, installed in
  user space at `~/.local/swift/swift-6.4.3-RELEASE-debian13` (no sudo, nothing system-wide).
  Foundation, Codable, actors and Observation compile and run.
- **`swift test`** for `Bloom` and `BloomTheme`: the Foundation code runs for real, against
  fixtures recorded from Node (`Intl`, the theme goldens).
- **`crates/native/scripts/typecheck-swift.sh`** type-checks, in Swift 6 mode:
  - `BloomUI`;
  - every golden except the TS-only one and those queued in `tests/golden-swift/NOT_YET_SWIFT`
    (each with its reason: flow narrowing, TS-shaped records, nodes not on SwiftUI yet, a few
    emitter gaps);
  - the bench's three modules (Feed, Settings, NativeBench) and its `@main` app.

  It checks against `runtime/ios/Stubs/SwiftUI`, SwiftUI's signatures for what BloomUI uses, copied
  from the SDK, with their availability and isolation.
- **What this does not prove:** layout and drawing, the SDK's full overload set and its
  concurrency annotations, ImageIO, UIKit, the island's Fabric component, and anything about speed.
  The stub never ships (`--ios-project` leaves it out).

## What the Mac lane needs (hangar phase 6)

To build, run, measure and record. Please confirm each version against what Apple ships on the
day.

- **The Mac:**
  - Apple silicon, on the macOS the current Xcode requires;
  - 60 GB free (Xcode, three simulator runtimes, DerivedData);
  - reachable from SuperPC over SSH as the other hangar hosts are.
- **Xcode:**
  - The current stable Xcode, whose Swift is 6.4 (the same compiler as the Linux toolchain,
    6.4.3), with its iOS SDK.
  - Selected with `xcode-select -s`, its license accepted, `xcodebuild -runFirstLaunch` run.
  - **Simulator runtimes:** the current iOS, **iOS 26** (Liquid Glass's first release) and **iOS 17**
    (the deployment floor, where the material falls back).
- **Tools:**
  - `xcodegen` (Homebrew, a pinned version);
  - `ffmpeg` (screen recordings);
  - Rust stable at least the workspace's `rust-version` (1.97), with clippy;
  - Node 24 and Bun, for the TS goldens and the React Native build;
  - Ruby with Bundler and CocoaPods at Mention's `Gemfile` versions, for today's React Native iOS
    build, which the bench compares against.
- **Signing:**
  - The Apple Developer team ID, as `BLOOM_IOS_TEAM`.
  - An Apple Development certificate in a keychain that SSH sessions can unlock
    (`security unlock-keychain`, and `security set-key-partition-list` so codesign does not
    prompt).
  - Automatic provisioning for `so.bloom.nativebench.swiftui` and `.rn`, and later Mention's ids.
- **The iPhone:**
  - One with ProMotion (120 Hz, like the Pixel 8a), on iOS 26 or later.
  - Developer Mode on, paired and trusted, on USB-C, shown by `xcrun devicectl list devices`.
  - During runs: auto-lock off, fixed brightness, Low Power Mode off, the same appearance as the
    Pixel.
- **Hangar wiring**, as `hangar lock` / `hangar adb` do for the Pixel:
  - a lock on the iPhone;
  - `hangar xcrun <host> …` (or SSH) to run `xcodebuild`, `xcrun devicectl` (install, launch with
    `--console`, terminate), `xcrun simctl` and `xcrun xctrace` (the Animation Hitches, App Launch
    and Allocations templates);
  - screen capture of the device: CoreMediaIO's screen-capture devices enabled
    (`kCMIOHardwarePropertyAllowScreenCaptureDevices`), recorded with `ffmpeg -f avfoundation`, and
    `simctl io recordVideo` for simulators, for the side-by-side recordings of glass and motion.

## Measuring on the Mac

`bench/native/swiftui-build.sh simulator|device` writes the project and builds it.
`bench/native/swiftui-bench.sh '<destination>'` runs the UI-test target and leaves a `.xcresult`.
The measurements are the Android bench's four, through XCTest:

- **Cold start:** `XCTApplicationLaunchMetric`, 5 runs.
- **Fast scroll:** 30 flings down the 500 rows, `XCTOSSignpostMetric.scrollingAndDecelerationMetric`
  (hitch time ratio, frame rate).
- **Memory:** `XCTMemoryMetric`, after the feed.
- **Toggle:** the app's own `BENCH toggle <ms>` lines, from the same `.onChange` as on Android, over
  20 taps.

Against them, the React Native build of the same package (`bloom build ios --release`) runs the
same metrics, and `xctrace` adds frame-level hitches. The glass and motion recordings compare
today's build with the SwiftUI one, side by side, for the header, the bottom bar, the FAB, menus
and sheets.

## For the checker's owners

Found while writing the goldens:

- **Overloads that differ only by label are rejected:** `B0217`, "`Point$moved` is declared twice",
  for methods (extension mangling) and for free functions. ADR 0003 lists label overloading in the
  2.0 language. Swift needs nothing once the checker takes them.
- **Function types drop `throws`:** `(T) async throws -> U` parses with no record of `throws`. The
  Swift backend reads it from the source span. A flag on `TypeKind::Fn` would make that exact.
- **Bloom's built-in `sorted()` takes a comparator:** `xs.sorted()` is `B0207`, where Swift and the
  2.0 surface read `sorted()` as the natural order.

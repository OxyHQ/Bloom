# Bloom language

Bloom's UI language is a way to write Bloom interfaces in TypeScript the way
SwiftUI writes them in Swift: a component is a function, and its look is a chain
of modifiers applied in order. Every modifier value is a Bloom token, never a
pixel or a colour. The package is `packages/bloom-language`
(`@oxy.so/bloom-language`, a working name). It is not published.

The language renders through React Native and react-native-web, using Bloom's
existing components and tokens, so a screen written in it looks the same as the
JSX it replaces. A build-time compiler (`packages/bloom-language-compiler`)
optimises it; the runtime stays complete without it. One spec
(`packages/bloom-language/spec/language.json`) defines the vocabulary both use.
Native renderers come later (see [Built and not built](#built-and-not-built)).

## Syntax

```ts
import { view, HStack, VStack, Text, Avatar, Spacer, Action, ActionBar } from '@oxy.so/bloom-language';
import { ReplyIcon } from '@oxy.so/bloom/icons/ReplyIcon';
import { LikeIcon } from '@oxy.so/bloom/icons/LikeIcon';

export const PostRow = view(function PostRow({ post }: { post: Post }) {
  return HStack(
    Avatar(post.author.avatar).size('lg'),
    VStack(
      HStack(
        Text(post.author.name).font('body').weight('semibold'),
        Text(`@${post.author.handle}`).foreground('muted'),
        Spacer(),
        Text(post.time).font('caption-1').foreground('muted'),
      ).spacing('sm'),
      Text(post.text).font('body'),
      ActionBar(
        Action(ReplyIcon, 'Reply').count(post.replies).onPress(reply),
        Action(LikeIcon, 'Like').count(post.likes).active(post.liked).tint('error').onPress(like),
      ),
    ).spacing('xs'),
  )
    .padding('md')
    .spacing('sm')
    .onPress(() => openPost(post.id));
});
```

Differences from the first draft, each forced by the real components:

- `Icon` and `Action` take the icon component (`ReplyIcon`), not a name. A
  name would need a registry that imports every icon, and Metro cannot tree-shake it.
- The colour roles are Bloom's: `error`, not `red`; `muted` is `text-muted-foreground`.
- Avatar sizes are Bloom's avatar rungs (`xs` 20, `sm` 24, `md` 32, `lg` 36), or an app token.
- `count && Text(count)` is a type error: with a count of 0 it would put a bare
  `0` in a view. Write `count ? Text(count) : null`.
- Glass takes SwiftUI's materials: `.glass()`, `.glass(clear)`,
  `.glass(regular.tint('primary'))`, `.glass(clear.tint('primary', 'subtle'))`.
  A tint's transparency is a named token, never a number (see [Glass](#glass)).
- A view takes one props object, as a React component does (`Row({ post })`).

## Node model

A chain produces plain data: a **node** (`kind`, `props`, `children`) plus an
ordered list of **modifiers**. Each modifier is an object with its kind, its
token value and a precomputed cache key (`p:leading:md`). A chain call never
changes the node it is called on. It returns a new node with one more
modifier, so a node can be shared and branched safely.

Children are nodes, `false`, `null`, `undefined` or arrays of those. Strings and
numbers go in `Text`. Each child keeps its position: a child that becomes
`false` leaves a gap, so its later siblings keep their state. An array
(`items.map(...)`) is one position, and its items are keyed by `.id()` or by
index.

## Order means nesting

SwiftUI wraps a new view per modifier. The renderer gets the same meaning from
fewer React Native views. Within one view, the effects stack as padding, then
frame, then background or glass, then border, then corner, then opacity. A chain
that follows that order is one view. A modifier that comes against the order
starts a new view around the previous ones:

- `.padding('md').background('surface')` is one view: the fill covers the padding.
- `.background('surface').padding('md')` is two: the padding sits outside the fill.
- `.corner('lg').background('surface')` is two: a fill after the clip is not clipped.
- A second padding on the same edge adds to the first, so it wraps.

Text and icon traits (`foreground`, `font`, `weight`, `leading`, `tracking`) are an
**environment**: set on a stack, they reach every `Text` and `Icon` inside it,
including inside nested views. `grow` and `shrink` place a view in its parent,
so they always go on its outermost box. Press, hover and accessibility props
go there too.

## `view()`

`view(body)` returns a function that makes a node. The body takes one props
object, as a React component does, and runs when React renders the node, as a
React function component of its own, so hooks work in it.

```ts
const Badge = view(function Badge(props: { label: string }) {
  return Text(props.label).font('caption-1').foreground('muted');
});
HStack(Badge({ label: 'New' }), …)
```

- **One fiber.** The component is React's own `memo` of the body's host, with
  no comparator: props compare key by key, `Object.is` each, and the body
  re-runs only when one changes.
- **No theme read.** Nothing above a leaf resolves a colour (see
  [Rendering](#rendering)), so a theme switch re-runs no view body.
- **The environment** (text traits set above the view) arrives through a
  context that is provided only where an environment modifier changed it. A
  view under an unchanged environment adds no provider.

A view node takes the universal modifiers. Environment modifiers flow into its
body, and box modifiers wrap it.

**React Compiler.** Expo runs it in `infer` mode, which finds components by JSX
or hook calls. A body that returns chains has neither, so naming the function
is not enough: it needs `"use memo"`. The language compiler adds it to every
function passed to `view()`; without the compiler, write it yourself. A body
that holds manual `useMemo`/`useCallback` still does not compile ("could not
be preserved"), so keep the controller in a custom hook (`usePostRowModel`).

## Rendering

| Node | Draws |
| --- | --- |
| `HStack` / `VStack` / `ZStack` | React Native `View` (`Pressable` when it takes presses or hovers) |
| `Spacer` | `View` with `flex: 1` |
| `Text` | Bloom `Text` (or the typography component its `textStyle` names), its ramp font as `variant`. A nested `Text` is a React Native span inside it. |
| `Icon` | the Bloom icon component, at a size rung, filled with the foreground |
| `Avatar` | Bloom `Avatar` (with a presence, `AvatarPresence`) |
| `AvatarGroup` / `Badge` / `IconCircle` / `Loading` | Bloom `AvatarGroup` / `Badge` / `IconCircle` / `Loading` |
| `Skeleton` / `SkeletonGroup` | Bloom's skeleton shapes / `Skeleton.Region` |
| `.pressScale()` / `.hoverHighlight()` | Bloom `PressableScale` as the pressable host / `SubtleHover` as the stack's first child |
| `Image` | Bloom `BloomImage` (`@oxy.so/bloom/image`), sized and clipped by its own box (see [Image](#image)) |
| `Button` | Bloom `Button` (`style` is its appearance, `tint` its tone, `shape` is icon-only: `circle` square, `pill` wide, `fit` grows; see [Button](#button)) |
| `ButtonGroup` | Bloom `Button.Group` |
| `Shape` | Bloom `shapes`' `Fill`, `Border` or `Image` (see [Material](#material)) |
| `ActionBar` / `Action` / `ActionGroup` | Bloom `EngagementBar` / `EngagementAction` / `EngagementGroup` |
| `.glass()` | Bloom `Surface` (see [Glass](#glass)) |
| `.blur()` | Bloom `BlurIsland` (`@oxy.so/bloom/blur`; see [Material](#material)) |
| `.corner('concentric')` | Bloom `ConcentricView` (a glass: `Surface radius="concentric"`) |
| `Divider` | Bloom `Divider` (in a menu, the line between rows) |
| `Fill` / `AspectRatio` / `Grid` | Bloom `Fill` / `AspectRatio` / `ResponsiveGrid` |
| `Embed` | the React element as given |

**Styles are theme-free.** A style resolves once per modifier key into numbers
and colour *roles*, and one cache serves every theme. Each role is painted where
it is cheapest:

- **Native:** a `Painted` leaf (`BloomPaint` in the React tree) reads the theme
  and draws its host with that palette's colours, built once per palette. It is
  the only reader of the theme, so a theme switch re-renders those leaves and
  nothing above them.
- **Web:** a role is its canonical CSS variable (`muted` is
  `var(--muted-foreground)`) inside a class (below), so a theme switch renders
  nothing. Colours that are props, not styles (an icon's `fill`, a glass
  Surface's `fill`), still paint from a `Painted` leaf.

**A node remembers what it rendered.** Rendering a node in the same environment
and slot gives the same element, so a node that keeps its identity across renders
(a module constant, a chain the compiler hoisted, a node the React Compiler kept)
costs one comparison, and React skips its subtree. A fresh node is interpreted.

**Web CSS is generated at build time.** `scripts/generate.mjs` writes one atomic
class per property and token value (about 1,800 today), with declarations from
react-native-web's own style compiler, so a class says exactly what
react-native-web would have written inline. The runtime hands react-native-web
`$$css` class objects for language hosts; a value with no class (an app token's
own number) stays inline beside them, and a Bloom component (Avatar, Surface…),
which reads its style as an object, gets an inline object with roles as CSS
variables. The whole vocabulary has to be in the sheet, not only what sources
name, because a token can be a runtime value (`.spacing(gap)`), so the sheet is
generated from the spec, not by scanning (no PostCSS plugin).

- *Delivery:* the sheet is a constructed stylesheet adopted once per document
  through Bloom's `adoptStyleSheet` (`@oxy.so/bloom/styles`), as Bloom's web
  forks inject theirs (CSP-safe).
- *Order against react-native-web:* react-native-web inserts its sheet at the
  top of `<head>`, and adopted sheets come after every document sheet, so a
  language class beats react-native-web's base `View`/`Text` reset at equal
  specificity. One host never has a language class and a react-native-web class
  for the same property (styleq keeps one per property). Within the language
  sheet, rules follow react-native-web's precedence groups (shorthands such as
  `flex` before longhands such as `flex-shrink`).
- *Logical edges* (`paddingStart`…) are CSS logical properties, resolved by the
  document's direction, which Bloom sets on the root (`useDirectionProps`);
  react-native-web resolves its own against the nearest `dir` prop.
- *Not covered:* server rendering. An adopted sheet is not in server HTML; an
  app with Expo static rendering needs the sheet in its document head first.

Fonts are Bloom's: a language `Text` is Bloom's `Text`, so it takes Bloom's
families (Inter, the display face for titles), its desktop scale under a
`TypographyScope` and its own ink when no colour is set (see [Text](#text)).

## Modifiers

**Colours.** A role is a theme colour on native and its canonical CSS
variable on the web. `mutedFill` is `--muted` (the subtle fill of `bg-muted`;
`muted` stays the quiet ink, `--muted-foreground`), `card` is `--card`,
`destructive` is `--destructive` (Bloom's `ThemeColors.destructive`, which
the engine's error role fills; `error` is the policy's status colour),
`primaryText` is `--primary-text`, `errorText` `--error-text`, `onSurface`
`--surface-foreground`, `accent` `--accent`, and `white`, `black` and
`transparent` are Tailwind's fixed colours (Bloom's `ThemeColors.white`,
`black` and `transparent`, the same in every theme). A role at an opacity is one token, `'role/opacity'`,
with an `opacity` token for the amount: `text-muted-foreground/70` is
`.foreground('muted/70')`, `bg-primary/10` `.background('primary/10')`.
Native paints the role's colour at that alpha; the web writes the mix
Tailwind writes for the class (`color-mix(in oklab, var(--muted-foreground)
70%, transparent)`), inline, as no class exists for each pair; an icon's fill
is painted at that alpha from the theme.

**Named rungs and numeric tokens.** A scale has two kinds of token, one
mechanism each:

- **Named rungs are the design scale**: Bloom's own (`xs` `sm` `md`…, `tight`
  `snug` `normal`…), held equal to Bloom's tables by `spec.test.ts`. New
  design reaches for these.
- **Numeric tokens are exact values carried over from apps**: the token's
  name is its number, in the unit of its scale, so `'44'` is 44 and cannot
  mean anything else (`spec.test.ts` holds every name equal to its value).
  Space, corner and font size are in points (`'6'`, `'22'`, `'16'`); a line
  height is a named ratio or an exact px height (`'28px'`); tracking is a
  named em amount, an em value (`'-0.02em'`) or px (`'-0.5px'`); an opacity
  is its percent (`'60'` is 0.6, as Tailwind's `opacity-60` and `/60`). They
  are a closed set too: generated from the spec, checked by the compiler, never
  an arbitrary number at a call site. They exist so a codemod moves a screen
  without changing a pixel: Tailwind's `p-1.5` is `.padding('6')`,
  `text-base` `.font('16').leading('normal')`, `text-lg`
  `.font('18').leading('28px')`, `leading-5` `.leading('20px')`.

Which values are numeric tokens: every value the className table found in two
or more places that a request named (space, corner and type steps, the px line
heights, every tracking), and the frame sizes apps use ten times or more
(`'160'`, `'224'`, `'384'`, `'1200'`…). Tailwind's own values are numeric
tokens too where apps use them: its stacking levels `'20'` `'30'` `'50'`, its
shadows (each named by its exact box-shadow), the 3px ring (`'3'`), and the
scale factors apps write (`'95'` `'99'` `'103'` `'105'` `'110'`, in percent).
The same rule takes the leftovers apps write in two or more places: the
stacking levels `'2'` and `'60'` (`z-[2]`, `z-[60]`), the 4px border (`'4'`,
`border-4`), the opacities `'45'` and `'75'`, and the 45° turn (`'45'`,
`rotate-45`). Anything else stays an app's `defineTokens`. A raw hex colour is an app's
brand colour: the app's own token, never a Bloom one (see [className](#classname)).

The vocabulary is closed. Every value is a name from the spec, whose every rung
`spec.test.ts` holds equal to Bloom's own table, so a rung cannot drift from Bloom.

Each node type exposes only the modifiers that apply to it, so the editor
completes `Text(...).` with text modifiers and rejects `HStack().lines(2)`,
`.padding(12)` and `.foreground('#f00')` at compile time.

**App tokens.** When a screen being ported uses a measurement that Bloom's scales
lack, the app names it once with `defineTokens`. It is still a name at each call
site:

```ts
const row = defineTokens({ space: { context: 18 }, iconSize: { context: 13 } });
Icon(RiRepeat2Line).size(row.iconSize.context);
```

Mention's row needed seven of them. Two are Bloom rungs now: the 64px body
gutter is `'64'` and `leading-tight` (1.25) is `close`. The 18px context row,
the 3px gap before its text and the 13, 14 and 18px glyphs stay app tokens.

An app's brand colour is an app token too: `defineTokens({ color: { blue:
'#1877f2' } })` declares a hex (checked when it is declared), the same in both
schemes, and `.background()`, `.foreground()` (text and glyphs), `.border()`
and `.ring()` take it where they take a role. It paints as its hex on every
platform (inline on the web: no class names it). It does not vary: a live
`when()` keeps its roles only and says so once in development, since the web
would need a class for it. The paints that are props of a Bloom component
(`.tint()`, `.fill()`, `.stroke()`, a button's `.colors()`, a glass tint) take
roles only.

## Layout

```ts
HStack(Avatar(user.avatar), Text(user.name)).justify('between').wrap().spacing('sm')
VStack(...).frame({ width: 'full', maxWidth: '1/2' }).alignSelf('center')
Avatar(user.avatar).overlay(Badge(3).tint('danger'), 'top-trailing')
VStack(...).background(Image(cover).frame({ width: 'full', height: 'full' }))
Button(Icon(RiCloseLine)).position({ top: 'sm', trailing: 'sm' }).zIndex('floating')
VStack(...).background('surface').corner('xl').shadow('m')
```

- **Distribution.** `justify` is the main axis (Compose's arrangement):
  packed at `start`, `center` or `end`, or the free space `between`, `around` or
  `evenly` around the children. `spacing` is only the gap. `wrap()` flows
  children that do not fit onto further lines. `axis()` lays a stack out along
  the other axis, which is what a breakpoint variant uses (`flex-col
  md:flex-row`).
- **Self alignment.** `alignSelf` is the view's own place across its parent's
  axis, over the parent's `align`. `mx-auto` in a column is `alignSelf('center')`.
- **Lengths.** A frame takes a length of its parent (`full` is `100%`, `1/2` is
  `50%`) besides space rungs. `w-full` is `.frame({ width: 'full' })`: the same
  value, not SwiftUI's `maxWidth: .infinity`, so no rendered size moves.
- **Overlays.** `.overlay(view, alignment)` draws a view over this one, as
  SwiftUI's `overlay(alignment:)` does: a box the size of the view as drawn so
  far (its padding and frame before the overlay included), the view placed at
  the alignment. `.background(view, alignment)` is the same box under the
  content. They sit in the layer order between the frame and the fill, so
  `.padding('md').overlay(x)` covers the padding and `.overlay(x).padding('md')`
  does not. The box lets touches through outside its own content.
- **Pinned views.** `.position(edges)` takes the view out of its stack's flow
  and pins it at those distances from its parent's edges (React Native's
  absolute position); an overlay is the way to put one view on another, and
  `position` is for what is truly absolute. `.offset({ x, y })` draws the view
  shifted (`x` right, `y` down, physical) without moving its siblings.
- **Stacking.** `zIndex` takes Bloom's own levels (`Z_INDEX`): `base` 0,
  `raised` 1, `floating` 10, `dropdown` 40; Tailwind's `z-20`, `z-30` and
  `z-50` are the numeric tokens `'20'`, `'30'`, `'50'`.
- **Elevation.** `.shadow(role)` is Bloom's `bloomShadowStyle(role)`: the web's
  box-shadow, native's shadow and elevation (`floating` is a box-shadow on
  both). It is the outermost layer. A shadow never shares a view with a
  corner's clip, since iOS clips a view's own shadow: after a `corner` it is a
  view of its own around the clipped box, with the same radii. Tailwind's own
  shadows are tokens named by their exact box-shadow
  (`.shadow('0 1px 3px 0 rgb(0 0 0 / 0.1), 0 1px 2px -1px rgb(0 0 0 / 0.1)')`
  is `shadow-sm`), drawn as that box-shadow on every platform.
- **Corners per side.** `.corner(r, side)` rounds only those corners
  (`rounded-t-3xl` is `.corner('3xl', 'top')`); `leading` and `trailing`
  follow the reading direction, as the edges do. Corners of other sides join
  one view; a corner rounded twice wraps, as a padding of the same edge does.
  A glass or an island takes one radius, so a corner of some sides only is
  left out on it.
- **Scale and basis.** `.scale(s)` draws the view scaled about its centre,
  after its offset (Tailwind's translate, then scale), without moving its
  siblings. `.basis(length)` is its `flex-basis` (`basis-0` is
  `.basis('none')`).
- **Hit testing.** `.allowsHitTesting(false)` lets touches and the pointer
  through the view and everything inside it, as SwiftUI's does
  (`pointer-events-none`); `true` takes them again. react-native-web drops an
  inline `pointerEvents`, so on the web a Bloom component's is a box of its own
  around it.
- **Read, not drawn.** `.accessibilityOnly()` is Tailwind's `sr-only`: a
  1pt clipped box out of the layout that a screen reader still announces.
  Native has no clip path or white-space, so it is the box alone, as
  NativeWind drew it there.
- **Web lists.** `.listMarker('disc' | 'decimal')` on a stack makes it an
  HTML list and each child a list item, so the browser draws its markers
  (`list-disc`); give it the room with a leading padding. Native draws no
  markers, as React Native has none.
- **Rings.** `.ring(role, width?, offset?)` is an outline (Bloom's focus ring
  recipe): it draws outside the box and takes no room. `ring('none')` is the
  web's `outline: none`. It sits in the border's layer.
- **Hidden.** `.hidden()` takes the view out of the layout (`display: none`)
  and keeps it mounted, unlike SwiftUI's `hidden()`, which keeps its room. A
  child that is not there is a conditional child (`show && view`); `hidden`
  is for a variant (`.hidden().when('md', (v) => v.hidden(false))`).

Not verified on a device: a ring (React Native's `outline*`, 0.77+) and a
shadow beside a clip on iOS and Android.

## Variants

```ts
VStack(...).padding('sm').when('md', (v) => v.padding('lg'))
HStack(...).axis('vertical').when('md', (v) => v.axis('horizontal').justify('between'))
VStack(...).hidden().when('lg', (v) => v.hidden(false))
Card().background('surface').when('dark', (v) => v.background('popover'))
HStack(...).onPress(open).when('pressed', (v) => v.opacity('70')).when('hovered', (v) => v.foreground('foreground'))
VStack(...).when('web', (v) => v.padding('lg'))   // a platform: settled when it renders
```

`.when(condition, build)` is SwiftUI's environment-driven variant as a
modifier: `build` chains style modifiers onto the view, and while the
condition holds they **override the values the chain set before the call**
(Tailwind's `p-2 md:p-4`, not a second padding). Each goes where it
overrides: a box modifier into the view that set the same thing last (a
padding of the same edge, a border of the same side), else the outermost
view so far; a text trait into the environment, so it reaches the text
inside; a stack's layout to its host; a placement to its outermost box.

| Condition | Holds | Web | Native |
| --- | --- | --- | --- |
| `sm` `md` `lg` `xl` `2xl` | the window at that tier of Bloom's `BREAKPOINTS` or wider | `@media (min-width: …)` | the leaf reads `useWindowBreakpoint()`, which re-renders it only across a breakpoint |
| `dark` | the dark scheme | `.dark &` (Bloom puts `dark` on the root) | the leaf reads the theme it already paints from |
| `hovered` `focused` `pressed` | the view's own state (`focused` is a keyboard's focus, `:focus-visible`) | the view's outermost box carries the anchor class `blsg`, and a class answers its nearest anchor's state (see below) | the outermost box (`StateHost`) tracks the states its variants answer and hands them to the view's leaves |
| `disabled` | the view's own `.disabled()` (Button, FAB, a pressable stack) | settled when it renders | settled when it renders |
| `web` `native` `ios` `android` | the platform | settled | settled |

- **No view body runs.** A live condition is answered below the view: by CSS
  on the web, by the leaf that draws each host on native (`Conditioned`, a
  `Painted` leaf that also reads the breakpoint, the scheme and the state),
  which builds its props once per palette and set of holding variants.
- **The variant sheets** hold only the variant classes that have rendered.
  A variant is a generated class again under its condition (`<class>-md`,
  `<class>-hovered`…); the first time a style naming one is resolved (styles
  are cached by key, so once), its rule joins its condition's constructed
  sheet, kept in the generated sheet's order. One sheet per live condition,
  placed after the language's own in the order they override, so a page
  parses one rule per variant class it draws: the Variants parity story
  draws 13 (about 1.4 KB), where a whole sheet per condition was 1,806 rules
  and 69 to 186 KB each. A breakpoint's rule has the base's specificity and
  comes after it (a wider breakpoint after a narrower); the scheme's selector
  is one class stronger and a state's two, so a state beats the scheme and a
  press beats a hover. A value with no class (an app token, an offset)
  cannot vary on a language host on the web: it is left out, said once in
  development.
- **No build step.** The compiler checks every variant (its condition, its
  modifiers, each value) but emits no CSS: which classes a variant draws
  depends on where it lands (the text traits a font, weight or leading
  variant combines with, the layer a box modifier joins, the corner a
  shadow follows), which only the runtime resolves. Emitting at build time
  would be a second resolver; the runtime's rule per class is the same
  bytes, and only for what renders.
- **What varies** is the spec's `variants.modifiers`: box, text and stack
  style, placement (a basis and hit testing included), elevation and rings.
  A scale or an offset is a transform, which has no class to vary on the web. Anything else inside `when()` is left
  out and said once in development; the compiler rejects it (`A variant cannot
  change .onPress()`), and checks the condition and every value.
- **A Bloom component** (Avatar, Button, Image…) reads its style as an
  object, which CSS cannot vary, so on every platform its variants go into
  its own style, picked by a `Conditioned` leaf from the window's
  breakpoint, the scheme and its state (on the web each role is its CSS
  variable, as in its inline style). No view is put around it, so its layout
  is the one it has without a variant. Its state is tracked by its box in
  JavaScript on the web too (the component takes `onPressIn`/`onHoverIn`…
  as Bloom's Button, its FAB, Avatar and EngagementAction do; a Badge, an IconCircle, a
  Loading, a Divider, an AvatarGroup or a button group takes no press of its
  own, so its press, hover and focus are a language host's around it, whose
  box tracks them the same way), and its `focused` is the browser's
  `:focus-visible`, read when the focus arrives, as a view's selector is: a
  click's focus is not a keyboard's.
- **States are the view's**, as SwiftUI's: the anchor is the view's
  outermost box, and a class answers its NEAREST anchor (its own box or the
  closest around it), as a native leaf reads the nearest press host. A
  state is the innermost pressable's, as react-native-web's Pressable
  takes it (a hover or a press of an inner pressable is not the outer
  one's): the selector is the anchor in that state with no pressable in
  the same state inside it (`:has()`), and no anchor between it and the
  class (the spec's `variants.selectors`; the `:where()` parts add no
  specificity). A pressable is what react-native-web draws as one, and on
  the web it carries Bloom's press host class (`blsp`, `PRESS_HOST_CLASS`
  in `@oxy.so/bloom/styles`): every pressable host of the language, and
  Bloom's Avatar and EngagementAction, whose press is their own
  `Pressable`. Bloom's web Button and FAB are DOM buttons, which
  react-native-web does not keep a hover from, so a hover of one is the
  stack's too, as it is in Bloom JSX. So a pressable inside another, a
  Bloom one included, answers only its own press and hover, on every
  platform (the parity cases, held in Chrome by `verify-parity-web.mjs`,
  which holds every anchor and pressable). A text trait a variant sets
  above a nested pressable answers that nearest one on both platforms.
- **Icons** follow a varied foreground. On the web the glyph paints
  `currentColor` and its colour is a class under each condition (CSS answers
  a hover, as it does for text); on native the glyph's leaf is a
  `Conditioned` one that fills it from the environment.
- **A material's variants.** A glass, an island or a concentric box is a
  Bloom material drawn from its own props. A varied padding of one is a view
  just inside it, the same room, which takes the variant. A glass also varies
  its frame and border (the material's own style), its corner (the radius it
  clips to: one radius, so a corner of some sides or a concentric one is left
  out) and its fill (`.background(token)`: Surface's `fill`, the lens's tint,
  Liquid Glass's `tintColor`, over the glass's own tint while it holds). They
  reach the material as its props, picked by a `Conditioned` leaf from the
  breakpoint, the scheme and the state, built once per palette and set of
  holding variants (nothing is resolved per render); a state the material
  answers is tracked by the box around the glass, which is also the anchor
  of the CSS of the views inside it. A material is never faded (an opacity
  under `when()` is left out: an opacity on a material host or its ancestor
  takes its backdrop blur away), and an island's or a concentric box's other
  variants are left out too, each said once in development.
- **Variants nest.** `when('md', (v) => v.when('hovered', (h) => h.padding('lg')))`
  holds while both do (`md:hover:`): native reads both; the web writes the
  widest breakpoint's query around the other terms' selectors, each state's
  selector around the class (both answer its nearest anchor, so two states
  are one view's) and the scheme's around the states'. A joined condition's
  sheet comes after the single ones, and its selector is at least as specific
  as its strongest term's.

## Text

`Text(...runs)` is Bloom's `Text`: the type ramp, Bloom's families (Inter, and
the display face for `large-title`, `display-*` and `title-*`), the desktop
scale under a `TypographyScope`, and Bloom's ink when nothing sets a colour.

```ts
Text('Notifications').font('title-1').weight('bold')
Text(post.text).font('body').lines(3)
Text('Settings').textStyle('h2')
Text('Read the ', Text('terms').link('https://oxy.so/terms'), '.').font('caption-1')
```

- **Type.** `.font(family)` with `.weight(w)` is Bloom's `variant`
  (`body` + `semibold` is `body-semibold`; `regular` when no weight is set). A
  size rung (`.font('sm')`) sets the size alone, and a weight or a leading
  only when given. `.leading()` on a ramp font replaces its line height.
- **Bloom's typography components.** `.textStyle(name)` draws one: `title`,
  `subtitle`, `h1`…`h6`, `paragraph` (`P`), `lead`, `large`, `small`, `muted`,
  `blockquote`. Each keeps what the component brings: a heading's role and
  `aria-level`, `H2`'s rule, a paragraph's breakpoint spacing, `Lead`'s and
  `Muted`'s ink. A font of the chain is the component's `variant`, as Bloom's
  own props merge. A quotation is a box around its text: its layers go on the
  box, and what the chain sets for the text is a span inside it.
- **Truncation.** `.lines(n)` is `numberOfLines`, cut at the tail;
  `.truncation('head' | 'middle' | 'tail' | 'clip')` says where.
  `.noWrap()` keeps a web line from wrapping.
- **Selection.** `.selectable()` lets the reader select and copy it.
- **Links.** `.link(href)` is Bloom's inline link, as its Markdown draws one:
  the primary ink and an underline, announced as a link, an anchor on the web
  (a page of another site opens beside the app) and opened outside the app on
  native. Its own `.foreground()` replaces the ink, its own `.onPress()` the
  opening.
- **Lines and marks.** `.textAlign('start' | 'center' | 'end' | 'justify')`
  (`start` and `end` follow the reading direction), `.italic()`,
  `.underline()`, `.strikethrough()`, `.textCase('uppercase' | 'lowercase' |
  'capitalize')`. On the web the alignment stays inline: react-native-web
  writes it per direction, which one class cannot.
- **Spans.** A `Text` inside a `Text` is a React Native span, as Bloom's
  Markdown nests its runs: it writes only what its own chain names (a weight,
  an ink, a link) and inherits the rest, so a span of an `h1` keeps the
  heading's size.

- **Digits and breaking.** `.monospacedDigit()` draws digits of one width
  (`tabular-nums`, React Native's `fontVariant`). `.wordBreak('all')` lets a
  web line break anywhere (`break-all`), `.wordBreak('words')` only inside a
  word too long for its line (`break-words`); React Native has no such
  breaking, so native text keeps its own, as NativeWind drew it there.
- **Mono.** `.font('mono')` is Bloom's monospaced face, the family
  `font-mono` gives Bloom's `Text` (`fontFamilyStyle('mono')`, exported from
  `@oxy.so/bloom/typography`). A family sits beside the size: it keeps the
  ramp step or size rung the text has, and a later size keeps the face, so
  `.font('body').font('mono')` is body in mono.
- **Tracking.** `.tracking(t)` is letter spacing in em of the text's size,
  Tailwind's `tracking-*`: `tight` −0.025,
  `wide` 0.025, `wider` 0.05, `widest` 0.1, or an exact em or px token (an
  em token measures from the size, a px one does not). It is a
  trait of the environment, as `leading` is. Both measure from the text's
  size: its font's, or with no font the 13px of Bloom's `Text` without a
  variant (the size itself stays Bloom's, unwritten). Over a ramp step it
  replaces the step's own tracking.

## Icons

`Icon(X)` draws any Bloom icon component (`@oxy.so/bloom/icons`: Remix, the
Simple Icons brand marks and Bloom's own set, 588 today), as `<X size fill />`
draws it.

```ts
Icon(RiHeart3Line).size('sm').foreground('error')
HStack(Icon(RiRepeat2Line), Text('Reposted')).foreground('muted')
```

- **Size** is a rung of Bloom's icon scale (`2xs` 8, `xs` 12, `sm` 16, `md` 20,
  the default, `lg` 24, `xl` 28, `2xl` 32, `3xl` 48) or an app token
  (`defineTokens({ iconSize: { context: 13 } })`).
- **Colour** is the foreground: the icon's own `.foreground()`, else the
  environment's, else `foreground`. A bare Bloom icon element paints
  `primary` when given no fill; a language icon follows the text around it,
  as SwiftUI's does, so `Icon(X)` alone is `<X fill={colors.text} />`.
- **A box** (padding, a fill, a corner, a name) is one `View` around the glyph.
- Bloom's icon `gradient` prop has no modifier: no app passes one.

## Material

Bloom's material is the glass: the platform's own (the lens, Liquid Glass) or
Bloom's `Surface` and its blur where the platform has none (see
[Glass](#glass)). The rest of the material family are modifiers on any view
and three nodes.

```ts
VStack(
  Text('Storage').font('headline'),
  Divider(),
  Grid(...usage.map((item) => UsageCard({ item }))).columns(3).spacing('md'),
  VStack(AspectRatio(16 / 9, Image(cover))).corner('concentric'),
)
  .padding('md')
  .glass()
  .corner('2xl')
  .cornerCurve('smooth')
```

- **Concentric corners.** `.corner('concentric')` is Bloom's concentric
  geometry: the radius of the shape the box sits in, less the inset between
  them (a glass, a Bloom card or panel, another concentric box), drawn by
  `ConcentricView` (on a glass, `Surface radius="concentric"`). It clips, as
  every corner does.
- **Smooth corners.** `.cornerCurve('smooth')` is Bloom's platform-adaptive
  corner (`shapes`' `surfaceStyle`): continuous on iOS, a squircle on the web,
  round on Android; on a glass, Surface's `cornerCurve`. It sits in the
  corner's layer.
- **A glass's corner is its radius.** Surface clips itself, so the corner of a
  glass is Surface's `radius`, not a style of its host.
- **`Divider(label?)`** is Bloom's Divider, in its stack's direction:
  vertical in an `HStack`, as SwiftUI's is. `.lineStyle('single' | 'double' |
  'fill')`, `.align('start' | 'center' | 'end')` (the label's place),
  `.spacing(space)` (the room on each side), `.tint(role)` (the line). A label
  `Text` with nothing of its own is Bloom's divider label (its type and ink);
  any other view is drawn as it is. In a `Menu` it is the line between rows.
- **`Fill(...)`** covers the whole of the view it is in (a scrim, an overlay).
- **`AspectRatio(ratio, ...)`** is its parent's width and the height `ratio`
  (width over height) gives; a ratio that is not one yet (`0 / 0` before an
  image loads) is a square, as Bloom's is.
- **`Grid(...cells)`** is Bloom's `ResponsiveGrid`: `.columns(n)` the most
  columns, `.minCellWidth(space)` a cell's narrowest width (an app token for
  the widths apps use, 128 to 300), `.spacing(space)`, `.flow('rows' |
  'columns')`.

- **Islands.** `.blur()` floats the view over content as Bloom's
  `BlurIsland`: the shared material with its shadow, drawn by the lens on
  Android 13+ where the device has it. It is a capsule unless the layer's
  `.corner()` names a radius, and takes the layer's `cornerCurve`; a
  `.background(role)` in the layer is its fill, painted from the theme on
  every platform (the island composites its tint for what sits on it). It
  sits in the fill's layer, as `.glass()` does: `.padding('sm').blur()` is
  one island, `.blur().padding('sm')` pads outside it. A `Button` inside
  keeps its own material (see [Built and not built](#built-and-not-built)).

  ```ts
  HStack(Icon(RiFilterLine), Text('Filters')).spacing('xs').padding('sm').blur()
  ```

- **`Shape(name)`** is one of Bloom's silhouettes (`circle`, `squircle` and
  the named shapes) at a fixed side, `.size(space)` (`4xl`, 40, by default):
  `.fill(role)` (the default, in the foreground) is Bloom's `shapes` `Fill`,
  `.stroke(role, width?)` its `Border` (an outline inside the silhouette, a
  border width), `.image(source, alt?)` its `Image` (clipped to it). The last
  of the three in the chain is what it draws; two are an overlay
  (`Shape('heart').fill('primary').overlay(Shape('heart').stroke('border'))`).
  A silhouette takes no style, so its box is a view around it.

A glass is the platform's own material (see [Glass](#glass)); an island is
Bloom's.

## Button

`Button(...content)` is Bloom's `Button` in every variant apps use:

```ts
Button(Text('Save')).style('solid').tint('accent').size('md').onPress(save)
Button(Icon(RiAddLine), Text('New post')).loading(saving)
Button(Text('Next'), Icon(RiArrowRightLine)).style('outline')
Button(Icon(RiMoreFill)).style('subtle').shape('circle').label('More')
Button(Text('Bold')).style('subtle').pressed(bold).onPress(toggleBold)
Button(Text('Docs')).style('plain').link('https://oxy.so/docs').underline()
Button(Text('Continue with Oxy')).colors('primary', 'onPrimary')
Button(Text('Terms')).style('plain').linkTone('text')
ButtonGroup(Button(Text('Day')), Button(Text('Week'))).separated().size('sm')
```

- **Content.** An `Icon` before the `Text` is the leading glyph, one after it
  the trailing glyph; the `Text` runs are the label. A glyph with an ink of
  its own (`Icon(X).foreground(role)`) is drawn as it is.
- **Look.** `.style('solid' | 'subtle' | 'outline' | 'plain')`, `.tint(tone)`
  (Bloom's tones, `vivid` included), `.size('xs'…'lg')`; `.shape('circle')`
  is the square icon-only button, `.shape('pill')` the wide one.
- **Paired colours.** `.colors(fill, label)` is Bloom's `colors` from two
  colour roles (or roles at an opacity), painted from the theme; the geometry
  stays the button's. `.inverted()` swaps the theme's background and
  foreground; `.linkTone('primary' | 'secondary' | 'text')` is a plain link's
  ink; `.density('default' | 'compact')` its geometry over the nearest scope's.
  `.shape('fit')` is Bloom's `grow`: an icon button that grows with its
  content, never narrower than it is tall.
- **Groups.** `ButtonGroup(...buttons)` is Bloom's `Button.Group`:
  `.axis('vertical')` stacks them, `.size()` sizes every one, `.dividers(false)`
  drops the hairlines, `.separated()` gaps the segments, `.label()` names it.
- **State.** `.loading()`, `.disabled()`, `.pressed(on)` (a toggle,
  announced as pressed), `.link(href)` (an anchor on the web, opened on
  native), `.lines(n)`, `.underline()` (at rest).
- **On glass** it keeps its own press, ink and name; the glass draws its fill
  (see [Glass](#glass)).

Not in the language: a brand fill that is no colour role (a raw hex in
`colors`), the state colours over artwork (`color`, `hoverColor`…), which are
raw values with no token. A group's `material="lens"` is `.glass()` on the
`ButtonGroup`: the lens where the device has one, its shared Surface
elsewhere (the group's material has no tint or clear variant).

## Avatars

```ts
Avatar(user.avatar, { name: user.name, variant: 'thumb' }).size('lg').presence('online')
Avatar(null, { name: 'Ana Lima' }).tint('lime').shape('squircle')
Avatar(user.avatar).badge(Badge(unread).tint('danger'))
AvatarGroup(members).layout('row').max(4).total(count).initials()
```

`Avatar(source, options?)` is Bloom's `Avatar`: the image, else the account's
character, else initials on a tinted disc. The options are its data: `name`,
`initials`, `account`, `character`, `fallbackSource` and `variant` (the
rendition of a file id).

- `.size()` is an avatar rung or an app token (`defineTokens({ avatarSize: {
  feed: 48 } })`); with none, Bloom's 40.
- `.tint('neutral' | 'blue' | 'lime' | 'pink')` the initials disc;
  `.shape(name)` one of Bloom's silhouettes (`circle`, `squircle` and the 34
  named shapes); the image and the fallback keep it.
- Badges: `.verified()` (Bloom's mark), `.live()` (the ring and the LIVE pill,
  `.liveBadge(false)` for the ring alone), and any `Badge` attached with
  `.badge(Badge(…))`.
- Presence: `.presence('online' | 'idle' | 'busy' | 'offline')` is Bloom's
  `AvatarPresence`, the dot sized from the avatar.
- `.label(name)` is its `alt`; `.onPress` its own press.

`AvatarGroup(items)` takes Bloom's `AvatarGroupItem`s: `.layout('stack' |
'row' | 'cluster' | 'conversation')`, `.size()`, `.shape()`, `.max(n)`,
`.total(n)`, `.spacing(space)` (a row's gap), `.overflow('count' |
'truncate')`, `.initials()` (tinted initials instead of the neutral
placeholder), `.onPressItem(fn)`, `.hoverCard()`, and `.label()` to name it.

## Small pieces

- **`Badge(content?)`**: `.style('solid' | 'subtle' | 'outlined' | 'onMedia')`,
  `.tint(tone)`, `.size()` (the counters `xs`…`lg`, the labels `label-small`
  and `label-medium`), `.icon(X)`, `.dot()`, `.max(n)`, and `.placement()` when
  attached. `view.badge(Badge(…))` attaches it to any view.
- **`IconCircle(icon)`**: an icon on Bloom's tinted disc; `.size()` an icon rung.
- **`Loading(Text(…)?)`**: `.style('spinner' | 'top' | 'inline')`, `.size()`,
  `.tint(tone)`; the `Text` is what it says, `.label()` names it as a progress bar.
- **`Skeleton(shape)`**: `text`, `circle`, `pill` or `box`. Its frame is its
  size (a circle's and a pill's height, a box's width and height), a box's
  corner its radius, a text line's height its font's. It takes nothing else
  of a chain. `SkeletonGroup(...)` is `Skeleton.Region`, named with `.label()`.
- **`.pressScale()`**: a pressable view shrinks under the finger: its host is
  Bloom's `PressableScale`.
- **`.hoverHighlight(active?)`** on a stack: Bloom's `SubtleHover` wash behind
  it. With no argument it answers the pointer (the web; the stack becomes its
  hover group); with `active`, it is a coordinated highlight on every platform.

A pressable host is focusable by default, so the language writes `focusable`
only for a press modifier with no handler (`focusable={false}`).

## Glass

SwiftUI's `glassEffect` materials, drawn by each platform's own glass (below),
and by Bloom's `Surface` where the platform has none. `regular` and `clear` are
exported values; `.tint(role, opacity?)` returns a tinted copy.

| Chain | On Surface (the web, and native without the platform's glass) |
| --- | --- |
| `.glass()` = `.glass(regular)` | Surface with its own fill |
| `.glass(regular.tint('primary'))` | `fill` = the role's colour (the web paints an opaque fill at 72%, as Surface always does) |
| `.glass(regular.tint('primary', 'medium'))` | `fill` = the role at the named opacity |
| `.glass(clear)` | `sheen={false}`, `fill` = `surface` at `subtle` |
| `.glass(clear.tint('error'))` | `sheen={false}`, `fill` = the role at `subtle` (or the opacity given) |

Opacities are tokens (`glassOpacity` in the spec): `subtle` 0.24, `medium` 0.48,
`strong` 0.72 (`strong` is Surface's own web tint, `SURFACE_TINT_OPACITY`).
The fill is Bloom's `withAlpha` of the role's colour, as an app writes it:
Surface computes its material from its fill, and a `color-mix(…)` hid the
opacity from it (the web drew a `subtle` or `medium` tint at 72%, which the
Chrome check now catches: it compares a Surface's `::before` and `::after`,
where its material is drawn). A web paint that is a CSS variable (Bloom's
prepaint) is the one the browser mixes, with `color-mix(…)`.

Each platform draws the glass itself (`src/platform/glass-host.*`), and Surface
is what is left where it cannot:

- **Android and OxyOS:** the lens engine (`BloomLensMenu` with no rows, from
  `@oxy.so/bloom-lens`), on Android 13+ in a binary that has the module. The
  material's frost is the spec's `lensBlur` (`regular` 1, `clear` 0.5, a
  multiplier of the engine's own); the tint is the role at the named opacity,
  else the engine's own. The lens belongs to the fixed layer (a header, a bar,
  a floating button): the window draws it, so it does not follow a scroll
  view's overscroll, and each one is drawn every frame.
- **iOS:** Liquid Glass (`expo-glass-effect`'s `GlassView`, iOS 26), its style
  the spec's `iosStyle`, the tint as a colour with the token's opacity,
  interactive under a control; before iOS 26, `expo-blur`'s system material
  under the tint. Both are optional.
- **Web:** Surface, Bloom's frosted material (`blur(24px)` with the measured
  saturation and contrast under the tint). The web has no glass.

A glass's variants (its frame, border, corner and fill; see
[Variants](#variants)) reach each platform's glass as its props: the lens's
`cornerRadius` and tint, Liquid Glass's radius and `tintColor`, Surface's
`radius` and `fill`. Not verified on a device: they are held by unit tests
on the lens and iOS stand-ins, and by parity and Chrome on Surface.

**A control on glass.** A `Button` or `FAB` on glass keeps its own press,
ink, size and name (Bloom's `material="shared"`); the glass draws its fill.
An untinted glass under a solid control takes the control's fill (the spec's
`toneRole`: `accent` is `primary`, `action` is `tertiary`…), so the ink still
reads. A `FAB` is always on glass.

## Platform components

One API; each platform draws it with its own component (`src/platform/`,
`*.android.tsx`, `*.ios.tsx`, `*.web.tsx`; OxyOS takes the Android files).

```ts
Header('Notifications')
```

**Menu.** `Menu(trigger, ...rows)`: `Item` (`.icon`, `.subtitle`, `.destructive`,
`.disabled`, `.checked`, `.keepOpen`, `.onPress`), `Submenu` (one level),
`Section` (`.title`, set apart from the rows beside it) and `Divider`. A
row's glyph is a Bloom icon in the menu's quiet ink (the negative ink for a
destructive row). Rows built from hooks, or costly to build, go in one
`menu()` content, whose body runs only while the menu is open:

```ts
const PostMenu = menu(function PostMenu({ post }: { post: Post }) {
  const actions = usePostActions(post);
  return actions.map((action) => Item(action.label).icon(action.icon).onPress(action.run));
});
Menu(MORE, PostMenu({ post }))
```

- *Android:* the lens menu is the upstream app's menu component itself
  (`@oxy.so/bloom-lens`: its `Menu`, `Menu.Trigger` and `Menu.Content`,
  copied verbatim by `sync-from-upstream.sh`), and this host only adapts the
  `Menu` to it. Every trigger is the upstream app's glass trigger: its lens is
  the trigger's base, and that base itself becomes the menu (it squishes under
  the press, flows into the panel and takes it back, with the upstream app's
  trigger config, `absorb` over 0.48 s). A trigger on `.glass()` (the fixed
  layer: a header's, a bar's) is drawn as upstream, by the window, with the
  glass's tint and frost. Any other (a feed row's ⋯) draws its lens at rest in
  its own place in the page (`restBackdrop`, the engine's Bloom patch), against
  the fill of the surface it sits on: it scrolls, clips and stacks with the
  page, under the bars, and a layer keeps it, so a scroll redraws no lens. The
  window draws it only while its menu is open, from that same base. The
  trigger's `.corner()` is the base's radius (a capsule without one). The
  trigger's press layer opens the menu
  natively (a trigger's own press is left out); press-and-drag across the open
  panel, submenus, haptics and predictive back are the component's own. Rows
  given as they are (tagged, or with handlers) become its `Menu.Item`,
  `Menu.Submenu`, `Menu.Label` and `Menu.Separator`, a glyph a view in the row's
  ink (a submenu takes none; a disabled one is a disabled row). A `menu()`
  content is built by the trigger's own press: the view opens itself as its
  rows arrive (`openWithItems`) and lets them go once the menu has closed
  (`onMenuClosed`). Bloom gives only the colours (the panel's tint and the
  rows' ink from its menu palette, the theme's scheme) and the face (Inter);
  every other value is the upstream app's. A row's `.subtitle` is drawn only
  here. Without the lens, Bloom's menu.
- *iOS:* the system menu takes its rows before it opens and opens itself, so
  a `menu()` content (built only while open) is Bloom's menu there; rows given
  as they are (tagged, or with handlers) are the system's. Each row, submenu
  and toggle shows its icon's SF Symbol (see [Icons on iOS](#icons-on-ios)); an
  icon without one draws no glyph.

**Tagged rows.** A row can name its action instead of holding a handler, and
the menu takes what its tags do as an `actions()` view. The rows are plain data
a closed menu builds without a hook or a closure (so the system menu on iOS can
be given them); the body runs only when a row is chosen, in a component mounted
for that choice where the menu is placed, so it may call hooks. The choice
outlives the menu, so a menu that closes as it is chosen still runs it.

```ts
const PostActions = actions(function PostActions({ post }: { post: Post }) {
  const router = useRouter();
  return { open: () => router.push(`/p/${post.id}`), copy: () => copyLink(post) };
});
Menu(MORE, Item('Open').tag('open'), Item('Copy link').icon(RiLinkM).tag('copy'))
  .actions(PostActions({ post }))
```

Rows that only exist after a query (a submenu of the reader's lanes) stay a
`menu()` content, and on iOS that menu stays Bloom's.

### Icons on iOS

`spec/language.json`'s `sfSymbols` maps Bloom icons to SF Symbols, for iOS's
own components: the tab bar, the navigation bar's items and system menus.
`scripts/generate.mjs` checks both sides of every entry (a Bloom icon in
`src/icons/remix`, a symbol `sf-symbols-typescript` names) and writes the table
by icon component (`src/generated/sf-symbols.generated.ts`), which only
`*.ios.tsx` files import. An icon without an entry draws no glyph in a system
component; a toolbar button whose glyph has none stays Bloom's own view in the
bar.

**Header.** `Header(title)` with `.titleDisplay('large' | 'inline')` (large is
the ramp's `title-1-bold`), `.subtitle`, `.toolbar(...)`, `.toolbarLeading(...)`,
`.onBack(fn | null)`, `.scrollEdge('auto' | 'always' | 'none')` (Bloom's
scrim), `.scrollY` and `.presentation('floating' | 'bar' | 'navigation')`. On
iOS, in a screen of a native stack, the header sets the screen's options and
its `Stack.Toolbar`: a `Button` whose glyph has an SF Symbol (or a text label)
is a bar button, a `Menu` of plain or tagged rows opened from one is a bar
menu, anything else Bloom's own view in the bar. The system back button pops
the stack (a custom `onBack` is not called; `null` hides it). Outside a native
stack (a tab page without a stack of its own, a panel), Bloom's PageHeader.

**BottomBar.** `BottomBar(...tabs)`, `Tab(label, icon)` with `.id`,
`.activeIcon` and `.badge`; the bar takes `.selection`, `.onSelect`,
`.action(FAB(...))`, `.minimize` (Screen's collapse), `.progress` (a pager's
selection) and `.hide` (its presence). The system tab bar on iOS is a
navigator (expo-router's `NativeTabs`), not a view the bar could be: the
router's `TabView()` is it (see [Navigation](#navigation)).

## Navigation

`@oxy.so/bloom-language/router`, the only part of the language that imports
expo-router. expo-router's files stay the URL map, so deep links,
`+native-intent`, typed routes and the web fallback are untouched; the
language says what a layout file and a screen file render.

```ts
// app/(app)/_layout.tsx
export default layout(function App() {
  return AppLayout(Stack('(tabs)', Sheet('compose'), 'p/[id]/boost'))
    .primaryAction(RiQuillPenLine, t('sidebar.compose'), 'write')
    .bottomBar(signedIn)
    .shell((navigator) => ({ panelLayout: { panels: [{ id: 'main', role: 'main', content: navigator }] } }));
});

// app/(app)/(tabs)/_layout.tsx
export default layout(() => TabView());

// app/(app)/(tabs)/notifications/_layout.tsx: the page's own stack (its system bar on iOS)
export default layout(() => Stack());

// app/(app)/(tabs)/notifications/index.tsx
export default screen(function Notifications() {
  const [filters, setFilters] = useState(false);
  return Embed(<NotificationsList />)

```

| | Android, OxyOS | iOS (not verified) | Web |
| --- | --- | --- | --- |
| `Stack(...routes)` | `ExperimentalStack` (predictive back), Bloom's scenes | expo-router's native `Stack` | the route in place (`Slot`): the document scrolls |
| `Sheet(name)` | pushed | the system page sheet (`presentation: 'modal'`) | the route in place |
| `TabView()` | Bloom `TabPagerLayout` (swiped) | the system tab bar (`NativeTabs`) | Bloom `TabPagerLayout` (routed in place) |
| `AppLayout` | `AppShell`; the bar is the language `BottomBar` of the pager's pages with the FAB, on the lens | `AppShell` without a bar; the primary destination is the prominent tab | `AppShell`; the same bar, on Bloom's material |
| `screen()` | Bloom `Screen` + `PageHeader` | Bloom `Screen` + the system navigation bar, in a native stack | Bloom `Screen` + `PageHeader` |

**`layout(body)`, `screen(body)`.** A route file's default export. The body
runs as the route's component, so it may call hooks; a screen a route renders
with props (a post's id) is a `screen()` whose body takes them. Both provide the
environment's navigator (Bloom's panel-aware router, so a deck panel's routes
push in that panel on the web), which `navigate()` presses go through.

**`AppLayout(navigator)`.** Bloom's `AppShell` around the navigator. The shell
draws its navigation from the `TabPagerProvider` above it (the sidebar's rows
and selection), which stays above the shell: bottom sheets and Bloom's native
portal outlet render above the route, so a provider mounted in the layout is
invisible to them. `.primaryAction(icon, label, destination)` is the sidebar's
first row and the bar's FAB, and on iOS the destination's tab, drawn on its own
surface (`prominent`, iOS 27). `.bottomBar(shown)` says whether the bar shows on
this route. The shell's own options (layout mode, panels, error boundaries)
stay the app's: `.shell(navigator => options)` places the navigator in the
panel it names.

On a device the app runs edge to edge: `AppLayout` gives the shell no
safe-area frame (`safeArea: false`), whatever `layout` the app's options name.
The pages own the device's edges, as Bloom's `Screen` and `PageHeader` do: each
screen's header keeps its controls below the status bar and the camera while
its paint and the scrolling content reach behind them (on iOS the system
navigation bar does the same). The bottom bar, the FAB and the reveal drawer
clear their own insets. A semantic `layout` (`feed`, `deck`) on a bare
`AppShell` frames the top instead and paints a band behind the status bar; an
app that wants that frame asks for it with `.shell(() => ({ safeArea: true }))`.
The web has no frame either way.

**`Stack(...routes)`, `Sheet(name)`.** Each name is a route of the layout's
directory, pushed over the ones before it; with none, the directory's routes as
expo-router finds them. A tab page that should have the system navigation bar
on iOS is a directory with a `Stack()` layout: it holds the page alone, and
everything opened from it is pushed over the tabs, in the app's stack. On
Android and OxyOS a stack inside a page of Bloom's pager is the page in place:
the pager's pages are not fragments, and a native stack in one throws
(react-native-screens: "Parent fragment providing view returned nullish
fragment", on a Pixel 8a).

**`screen()`'s chrome** is the screen modifiers on its body's root (any view
takes them, as SwiftUI's `navigationTitle`, `toolbar` and `sheet`; elsewhere
they draw nothing): `.title`, `.titleDisplay`, `.subtitle`, `.toolbar`,
`.toolbarLeading`, `.onBack`, `.backLabel`, `.headingLevel` (the web's
`aria-level`), `.header(presentation | false | node)` (a
header node of the screen's own is drawn in the page on every platform),
`.footer(content, { placement, keyboard })` (Bloom Screen's bottom bar),
`.onReselect` and `.sheet(open, content, { onDismiss, title })`, Bloom's
`Dialog` from the bottom and centred from `md`, its content built while open
and kept while it closes. The root's `.testID` names the Screen itself, not a
box around the content.

The chrome around an app's pages, each the Bloom component an app draws

### Screen and ScrollView

```ts
export default screen(function Feed() {
  const { posts, more, refresh } = useFeed();
  return ScrollView(posts.map((post) => PostRow({ post }).id(post.id)))
    .contentMargins('horizontal', 'lg')
```

`ScrollView(...children)` is Bloom's `ScreenScrollView`, the screen's
scroller: it binds the header's scroll-edge fade, the bottom bar's fold, the
screen's reselect and, under a footer that follows the keyboard, keeps the
focused input above it. Its children are its content, in a column; it must be
inside a screen, as Bloom's is.

| Modifier | Bloom `ScreenScrollView` |
| --- | --- |
| `.contentMargins(edge?, space)`, `.spacing(space)` | `contentContainerStyle`'s padding (a later margin of an edge replaces the earlier) and `gap` |
| `.refreshable(action)` | a `RefreshControl` that spins from the pull until what `action` returns settles |
| `.onEndReached(action, threshold?)` | `onEndReached`, `onEndReachedThreshold` (2 viewports by default) |
| `.scrollIndicators('automatic' \| 'visible' \| 'hidden')` | `showsVerticalScrollIndicator` and `showsHorizontalScrollIndicator` |
| `.scrollDismissesKeyboard('never' \| 'immediately' \| 'interactively')` | `keyboardDismissMode` `none`, `on-drag`, `interactive` |
| `.keyboardTaps('never' \| 'always' \| 'handled')` | `keyboardShouldPersistTaps` |

Only what the chain names reaches the scroll view, so Bloom's own defaults
hold (`keyboardShouldPersistTaps="handled"` among them). Box modifiers
(`padding`, `frame`, `background`) are a view around the scroller, as
SwiftUI's are; room inside the scroll is `contentMargins`.

| --- | --- |

| `.screenScroll('auto' \| 'content' \| 'none')` | `scroll`: the screen's viewport, the list in it, or none |
| `.documentScroll()` | `documentScroll`: on the web the window scrolls the page |
| `.headerPlacement('inset' \| 'overlay')` | `headerPlacement` |
| `.scrollEdge('auto' \| 'always' \| 'none')` | the composed header's `scrim` |

The insets are Bloom `Screen`'s own: the header and the footer measure
themselves, the safe area comes from the screen's context, and the content
pads its ends clear of both. The keyboard is the footer's
(`.footer(content, { keyboard })`: `hide`, `visible`, or `follow`, which rides
the keyboard and keeps the focused field above it) and the scroll view's
(`scrollDismissesKeyboard`, `keyboardTaps`).

A seed is the one colour a screen takes as a value rather than a token: it
is data (what the person picked), as an image's source is. `screenActive`
is named for the screen, since `.active()` is an action's state.

### Bottom sheet


A `.sheet(open, content, options)` whose content is a `BottomSheet(...)` node
presents Bloom's `BottomSheet`; any other content keeps Bloom's `Dialog` (from
the bottom, centred from `md`). The node is the sheet's own options, as
SwiftUI's presentation modifiers are; placed anywhere else it draws nothing.

| Modifier | Bloom `BottomSheet` |
| --- | --- |
| `.detached()` | `detached` |
| `.dragIndicator('visible' \| 'hidden')` | `showHandle` |
| `.material('surface' \| 'flat')` | `material` |
| `.scrollable(false)`, `.sizing('content' \| 'fill')` | `scrollable`, `sizing` (a body that owns its list) |
| `.interactiveDismissDisabled()` | `enablePanDownToClose={false}` |

| `.shellLayout('workspace' \| 'collection-detail' \| 'feed' \| 'deck' \| 'catalog' \| 'map-browser')` | `AppShell`'s `layout` (a deck: columns side by side that scroll across) |
| `.shellPresentation('continuous' \| 'framed' \| 'floating')` | `presentation` |
| `.panels(...panels)` | `panelLayout.panels`, over the options' own `panelLayout` |
| `.destinations(...destinations)`, `.onReselect(name => …)` | a `TabPagerProvider` above the shell, with these `destinations` and its `onReselect` |

A `Panel(id, content?)` is an `AppShellPanelDefinition`: without content it
holds the layout's navigator, with it that view beside it. `.panelRole` is its
`role` (`main`, `collection`, `detail`, `inspector`, `context`, `canvas`,
each with Bloom's widths), and `.label`, `.width`, `.minWidth`, `.maxWidth`,
`.resizable`, `.hidden` (`visible={false}`), `.keepMounted` and `.testID` its
own. An **inspector** is a panel with the `inspector` role and
`.presented(open)`/`.onPresentedChange(fn)` (Bloom's `open`/`onOpenChange`,
and it needs a `.label`): a column at the end from `lg`, a floating sheet from
the end below it, as Bloom draws it.

A `Destination(name, href)` is Bloom's `AppDestination`: `.label`, `.icon`,
`.activeIcon`, `.badge`, `.bar()` (a tab of the bottom bar and a page),
`.page()` (a page without a tab), `.preload()`, `.sidebar(false)`,
`.sidebarAfter(name)`, `.onPress`, `.onLongPress`. With destinations the
layout draws Bloom's pager provider above the shell, so the app no longer
mounts one by hand; the router's `TabView()` is the pager itself (see
[Navigation](#navigation)).

The shell lays its panels out once it has measured itself, which neither jsdom
nor the test renderer does: the parity suite proves the shell's frame and
semantic layout there, the panels' definitions are unit tests, and Chrome
(`verify-parity-web.mjs`) compares the laid-out panels.

modifiers: a handle is placed by its container (an `.overlay(view, alignment)`
at a pane's edge). An `AutoHideBar`'s timings (`peekDelay`, `unpeekDelay`) and
its `motion` keep Bloom's, and its band is the surface it sits on (Bloom's

surface's or, with `.matchSurfacePaint()`, the nearest material's (its
`fadeColor` is a raw colour). The edge and scroll-metric providers are hooks
and providers an app's own chrome reads, not views.

## Image

`Image(source, alt?)` is Bloom's `BloomImage`: expo-image on a device,
react-native's `Image` on the web. `source` is anything `BloomImage` takes: a URL,
a bundled asset (`require()`) or a URI descriptor with headers.

```ts
Image(post.cover, 'Cover')
  .frame({ height: '5xl' })
  .aspectRatio(16 / 9)
  .contentFit('cover')
  .corner('lg')
  .crossFade('fast')
```

- **Box.** An image has no size until it loads, so it is sized like a view:
  `frame`, or one side and `aspectRatio` (width over height). The innermost
  layer is the image's own style, so `corner` clips the pixels and
  `background` shows until they arrive.
- **Options.** `contentFit` takes `BloomImage`'s vocabulary (`cover`, the
  default, `contain`, `fill`, `none`, `scale-down`). `tint(role)` paints every
  opaque pixel one colour role, from the theme like an icon's fill.
  `crossFade` is a Bloom duration (`instant` 100, `fast` 150, `normal` 200,
  `slow` 300 ms); without it the image appears at once. `onLoad` receives the
  intrinsic `{ width, height }` and `onError` `{ error }`.
- **Presses.** `BloomImage` takes accessibility props but no presses, so an image
  with `onPress`, `onHover` or `hoverGroup` is drawn inside its pressable host,
  which also takes `grow` and `shrink`.

## Interop

**JSX inside the language.** `Embed(element)` places any React element: a
third-party component, or a Bloom or app component the language has no node for
yet. `Embed((render) => <Link asChild>{render(Text('…'))}</Link>)` hands the
element a `render` function. That function draws language nodes in the current
environment as their host elements, so `asChild`, hover cards and slot props
receive a `Text` or `View` (on native, through its `Painted` leaf, which passes
every prop, `ref` included, to the host). An embed with box modifiers gets one `View`
around it.

**The language inside JSX.** `toElement(node)` returns a React element. A bare
`view()` node mounts its component directly. Anything else mounts under one
boundary component, which takes the environment provided where it is placed.

## Animations

The animation layer is Bloom's motion engine (`@oxy.so/bloom/motion`, see
docs/motion.mdx) in the language's words: Bloom's own animations (the
engagement bar's pop and count roll, the toast's enter and exit, press
feedback) play on the same engine.

Motion is a token, like every other value: Bloom's motion table (`MOTION`) by
name, `press`, `present`, `dismiss`, `fade`, `slide`, `thumb`, `pop`, `roll`,
`enter`, `exit`, `restack`, and the springs `select` and `expand` (SwiftUI's
`response` and `dampingRatio`); `spec.test.ts` holds the spec's table equal to
Bloom's. An app names its own with `defineTokens({ motion: { … } })`, which
gives Bloom `MotionSpec`s. Curves are named too (`ease`, `inOutQuad`,
`outQuart`, `outExpo`, `backOut`, `linear`).

| Modifier | Meaning (SwiftUI) |
| --- | --- |
| `.scale(s)`, `.offset({ x?, y? })`, `.rotation(r)` | Geometry that moves the view without moving its neighbours: `scale` tokens `dip` `pressed` `full` `swell`; offsets are space tokens (negative ones too); `rotation` `none` `quarter` `half`. Each takes a `MotionValue` in place of a token, and the view follows it. |
| `.animation(motion, value?)` | `.animation(_:value:)`: changes to this view's geometry and opacity, and what animates inside it in the same body (a matched geometry, a content transition, keyframes or a transition without their own motion), play with `motion`. With a value, only on a render where the value changed. |
| `.transition(t)` | Insertion and removal: `opacity`, `scale('dip')`, `move(edge, distance)`, `t.combined(u)`, `asymmetric(insert, remove)`, `t.animation(motion)`. A half may be keyframes of the app's own. |
| `.keyframes(k, trigger)` | `keyframeAnimator`: plays `k` each time `trigger` changes to a truthy value (a boolean turning on, or a counter such as a press id). |
| `.matchedGeometry(id, ns)` | `matchedGeometryEffect`: the view that takes `id` moves from where the last view with it was. `const ns = useNamespace()`. |
| `.contentTransition('roll', direction?)` | `Text` only; `.contentTransition(.numericText(value:))`: a change of the text inside an animation rolls the old text out and the new one in (Bloom's `rollKeyframes`, as `RollingText` rolls), up when `direction` rose and down when it fell. |
| `.pressScale()` | Press feedback (`PressableScale`): eases to `pressed` while a finger holds the view. Off for a mouse on the web and under reduced motion. |
| `.drag(value, { axis?, min?, max?, onEnd? })` | `DragGesture`: the finger moves `value` along `axis` (default `y`) from where it was, within the bounds. Bind the value to see it; `onEnd` (once per touch: the value and the finger's velocity) decides where it goes, with `animate()`. |
| `.swipe(direction, onSwipe)` | The view follows a swipe toward `direction` (`left` `right` `up` `down`) and, released past a quarter of the window across (or a tap's slop up or down), flies out and calls `onSwipe`; short of it, it comes back. |
| `Lottie(url)` | A node: `.loop()`, `.paused(bool)`, `.fallback(Image(still, label))`, `.frame({ width })`. Bloom's `Sticker` draws it (lottie-react-native on native, dotLottie on the web, both lazy), paused while its screen is not in front (`useScreenVisible`). |

Keyframes are frames, as CSS writes them:

```ts
const pop = defineKeyframes([
  { at: 0, scale: 1, easing: 'inOutQuad' },
  { at: 0.1, scale: 0.7 },
  { at: 0.4, scale: 1.2 },
  { at: 1, scale: 1 },
], 'pop');
Icon(liked ? LikeFillIcon : LikeIcon).size('md').keyframes(pop, press.on);
```

A frame's `easing` curves the stretch from it to the next; without one the
stretch takes the motion's curve, as a CSS animation applies its timing function
per stretch. Values are Bloom-internal numbers (a scale factor, an opacity, px or
a space token, degrees), as `defineTokens` allows.

A `MotionValue` is the one way to tie a gesture to geometry, and apps never
write a worklet:

```ts
const y = useMotionValue(screenHeight);
VStack(Grabber(), content)
  .offset({ y })
  .drag(y, { axis: 'y', min: 0, onEnd: ({ value }) => animate(y, value > 120 ? screenHeight : 0, 'expand') });
```

`animate(value, target, motion)` eases it from where it is, with a token or a
spec (a spring keeps its physics). A bound view's geometry follows its values:
`.animation()` does not ease it, `animate()` does.

### How it runs

Gestures and bound geometry are Bloom's gesture layer (docs/motion.mdx, Motion
values and gestures): Gesture Handler 3's hooks writing the values from their
own callbacks (worklets on the UI thread on native) and the one mapper Bloom
writes; the web restyles the bound views directly and eases with CSS
transitions. The engine plays everything else (docs/motion.mdx, The motion engine): native on
Reanimated 4's CSS engine (CSS animations and transitions on an `Animated`
host, no worklet, no JS per frame), the web with CSS transitions and the Web
Animations API (no Reanimated). Press feedback is the one shared value on
native, read by the one mapper Bloom writes; a class on the web. Reduced motion
(`usePrefersReducedMotion()`) plays nothing, and a removal leaves at once.

A moving node is drawn by one component (`MotionNode`), so nodes without motion
stay plain elements with no hooks. Its outermost host becomes its animated twin
(`Animated.View`, `Animated.Text`, an animated `Pressable`) when it rests moved or
animates its resting state (geometry, opacity, a transition, a matched geometry,
press feedback), from the first render, because a CSS transition needs its host
before the change. A node with only keyframes is animated only while they play,
as `EngagementPop` mounts its layer. A Bloom component (a Surface, an Avatar, a
bare glyph) cannot take motion itself, so it moves in one box, which takes the
view's place in its parent.

**Removal.** Native: a removed child unmounts at once and its removal plays
after, as a Reanimated layout animation on a native snapshot (no JS). Web: a
list slot (`items.map(…)`) is Bloom's `Presence`, which keeps a child that left
until its removal ends, holding its last frame. Only children keyed by `.id()`
can leave: by index, a removal and a reorder look the same.

**Glass.** On the web, an opacity below 1 on a glass host or any ancestor of one
flattens the material (AGENTS.rules.md, Material). The engine routes the fade of
a box that holds a material host: the box only moves, and the fade plays, with
the same frames, on the material's own layers and on each piece of content on
it. Native glass fades its own host. The compiler rejects a fade above glass
(`.transition(opacity)`, fading keyframes or `.opacity()` on a view whose
children hold `.glass()`), since the renderer cannot route a fade it does not
own.

**Compiler.** `motion`, `scale`, `rotation` and `contentTransition` values are
token sets it checks; `.offset()` keys and values are checked like `.frame()`'s;
a string where a transition or keyframes value belongs is an error. A `const`
from `useMotionValue` is a `MotionValue` in any scope: it may go in `.offset()`,
`.scale()`, `.rotation()` and as `.drag()`'s value; anywhere a token goes it is
an error, and so is a literal as `.drag()`'s value. `.swipe()`'s direction is a
checked token.
`opacity`, `move`, `scale`, `asymmetric` and `defineKeyframes` are pure, so a
chain that names them (`.transition(asymmetric(move('top', 'xl'), opacity))`)
hoists like any other static chain, and a module constant holding one is static.

## Component parity

Every node that stands for a Bloom component is proven against it:
`packages/bloom-language/parity` renders each case twice, the language node
and the Bloom element an app draws today, under Bloom's real provider, in light
and dark (`bun run test:parity`; `bun run test` runs it too).

- **Native:** Bloom's own test environment (its React Native and native-module
  mocks from the repository root), each module resolved as Metro resolves it
  for Android (its `.android`, then its `.native`, then its default file), with
  the portal host an app root mounts, so a modal's native portal draws its
  tree. The two committed host trees must be equal: every host's type, every
  prop (styles flattened, handlers by presence) and its children.
- **Web:** react-native-web in jsdom. Each element is compared on its tag, its
  attributes other than `class` and `style`, its text, and the CSS that
  reaches it: every matching rule of every sheet (the language's adopted one
  included) and its inline style, applied in order, variables resolved, one
  value per longhand.
- **In a browser:** the `Language/Parity` stories put each case's two sides in
  a row, and `scripts/verify-parity-web.mjs` compares every pair in Chrome:
  tags, attributes, text, every computed style property and the laid-out size.

The cases are one list per family (`parity/<family>.cases.tsx`), which the
three read. A case that cannot be equal is a decision, never a tolerance. A
case whose tree is empty fails, since two empty trees prove nothing, unless
drawing nothing is its claim on that platform (`drawsNothing`: a closed
palette on the web).

## One spec

`packages/bloom-language/spec/language.json` is the language as data: token
scales, the type ramp, colour roles (theme colour and CSS variable), glass
materials, layering, the environment, every modifier's parameters, and which
node kinds take which modifiers. `bun run generate` (in the package) writes:

- `src/generated/spec.generated.ts`: the runtime's tables;
- `src/generated/web-sheet.generated.ts`: the web stylesheet and its class table;
- `../bloom-language-compiler/crates/compiler/src/spec.generated.rs`: the
  compiler's tables.

Never edit those. A test fails when they are stale, another when a rung differs
from Bloom's, and a type-level test when a node's TypeScript modifiers differ
from the spec's list for its kind.

## Compiler

`packages/bloom-language-compiler` is a Rust pass (Oxc, through a Node addon)
that runs in front of the host's own transformer: a Metro `transformerPath`
wrapper (`withBloomLanguage(config)` from `@oxy.so/bloom-language-compiler/metro`)
and a Jest transformer (`/jest`). It is an optimisation: the runtime interprets
every chain, and the pass changes only what it proves keeps its meaning.

- **Hoists static chains.** A chain whose inputs are literals, imports and
  static module constants (a literal, a chain, a frozen `defineTokens` table)
  is the same immutable node on every call, so it is declared once at module
  scope, after the last declaration it reads. A dynamic chain keeps its runtime
  parts and hoists what is static inside it, including its longest static
  prefix (`HStack(…).padding('md')` before `.spacing(gap)`). Names resolve
  through scope analysis, so a local that shadows an import is never hoisted.
- **Adds `"use memo"`** to every function passed to `view()`.
- **Checks chains** against the spec: an unknown modifier for the node, a wrong
  argument count, or a literal token outside its set fails the build with the
  source line and a suggestion. Every chain is checked before anything is
  hoisted, including the chains nested in a hoisted one.

It does not resolve tokens: that stays the runtime's, so the two cannot disagree
about what a token means, and its output is the same program on every platform.

**Parity is the gate.** CI renders every fixture in
`packages/bloom-language-compiler/fixtures` interpreted and compiled, on native
and web, and compares the committed trees on mount, after a re-render, and after
a theme switch; each fixture also pins how many chains the compiler hoists.

## Built and not built

One line holds the whole language (`feat/bloom-language-next`): the core,
spec and compiler; the platform components and navigation; the primitives,
numeric tokens, layout and style modifiers and variants; the motion engine;
and `@oxy.so/bloom-data` beside it.

**Built**

- The node model, `view()`, the one spec (runtime tables, web sheet and the
  compiler's tables from `spec/language.json`) and the compiler (checks,
  hoisting), with unit tests, cargo tests and parity against hand-written
  Bloom on native and web, light and dark.
- Primitives: stacks, `Spacer`, `Text` (Bloom's `Text`, its families and
  ramp, mono), `Icon`, `Image`, `Embed`, `Avatar` and `AvatarGroup`, `Badge`,
  `IconCircle`, `Loading`, `Skeleton`, `Shape`, `Divider`, `Fill`,
  `AspectRatio`, `Grid`, `Button`, `ButtonGroup`, `FAB`, `Lottie`, the action
  bar.
- Platform components per platform (Menu, Button, Header, BottomBar, FAB, the
  glass: the lens on Android and OxyOS, `glassEffect` on iOS, Bloom's
  material on the web) and navigation (`AppLayout`, stacks, routes, tabs, the
  iOS system components).
- Tokens: Bloom's named rungs, numeric tokens by one rule (an exact value apps
  write in two or more places, named by its value), and an app's own tokens
  (`defineTokens`: space, icon and avatar sizes, leading, motion, and brand
  colours).
- Layout and style modifiers: distribution, placement, overlays, elevation,
  rings, corners and their curve, text styles, links, truncation.
- Variants: breakpoints, the scheme, a view's own hover, focus
  (`:focus-visible`) and press, `disabled` and the platforms; nested
  variants; a glass's padding, frame, border, corner and fill, as the
  material's own props; on the web a sheet per condition holding only the classes that
  render; a Bloom component's variants in its own style, its state tracked by
  its box (a component with no press of its own takes it on a host around
  it); the innermost pressable owns a hover or a press, as react-native-web's
  does, a Bloom Avatar or Action inside a stack included.
- Motion (`@oxy.so/bloom/motion`): motion tokens and curves, `.animation()`,
  `.transition()`, `.keyframes()`, `.matchedGeometry()`,
  `.contentTransition('roll')`, `.pressScale()`, geometry (`.scale()`,
  `.offset()`, `.rotation()`) as tokens or bound to a `MotionValue`, `.drag()`
  and `.swipe()` on Gesture Handler 3. Resting geometry that nothing plays is
  the box's own style. Bloom's pop, roll, toast and press feedback play on the
  same engine; the bottom sheet's drags are the same gesture layer's
  (docs/motion.mdx, Motion values and gestures).
- The className table (`docs/bloom-language-classnames.mdx`), which says what
  each utility the apps use becomes.
- App chrome (see [App chrome](#app-chrome)), each Bloom's own component with
  parity on native and web: `ScrollView` and the rest of `screen()`'s
  `Screen` (kind, scroll owner, document scroll, header placement and scroll
  edge, underlay, floating action, clearance, navigation scope); a `.sheet()`'s
  `BottomSheet` (iOS: the system sheet, not verified); `Sidebar` with its
  destinations and tree, `Rail`, `PageFooter`; `Command`; `SettingsModal`;
  `AppLayout`'s semantic layout, panels, deck and inspector, and its
  destinations (Bloom's pager provider); `Toolbar` and `StickySection`.

**Not built**

- Variants: a scale or an offset under `when()` (geometry is the motion
  layer's, and the web has no transform class to vary); an app colour under
  `when()` (it has no class); a material's opacity (never faded); an
  island's or a concentric box's frame, border, corner and fill (only their
  padding varies); a state variant of the glass under a Button or FAB (the
  control tracks its own state, inside the glass).
- A pressable of another component inside a pressable stack on the web
  (`Embed`, or a Bloom component the language does not draw): it carries no
  press host class, so the stack still answers a hover or a press of it.
- Motion: `transition-colors` (the engine plays geometry and opacity, not
  colour), loops (`animate-spin`, `animate-pulse`), a `delay`, a transform
  `origin`; `withAnimation`, `map()`, `.pinch`, `.onDoubleTap`,
  `.contentTransition('numeric')`, matched geometry across screens. An
  `.animation()` scope reaches its own body, not the bodies of `view()`s
  inside it; a removal plays only for a keyed list's child.
- Renderers: everything renders through React Native and react-native-web;
  no SwiftUI, native-view or CSS renderer yet. iOS is typechecked and tested
  against stand-ins, not run on a device. The web stylesheet is not in
  server-rendered HTML. On the web, `hoverGroup()` sets `group` through
  `react-native-css`.
- An island of shared controls: a `Button` inside `.blur()` draws its own
  material rather than Bloom's `material="shared"` on the island's.
- `ZStack` is basic: the first child sets the size and the rest cover it;
  `.overlay(view, alignment)` is the aligned form.
- Compiler distribution: prebuilt addons per platform from CI, and a WASI
  fallback.
- App chrome: the iPad's system sidebar; a screen's colour (`colorPreset`,
  `seed`) and `active`; the sidebar's modes, team, plan, onboarding, search
  query and tree drag and drop; the settings pages' own rows
  (`SettingsSection`, `SettingsSelect`, the text and date fields); Bloom's
  sheet detents (it has none); the rest of the layout family (`ScrollArea`,
  `ScrollSurface`, `AutoHideBar`, `ResizeHandle`). The shell's panels
  render only once it has measured itself, so they are compared in Chrome.
- Replacing `className`: the codemods read the className table; what it
  flags needs a modifier or a named token first.

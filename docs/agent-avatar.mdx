# Agent Avatar

`AgentAvatar` uses the recovered original beta engine for its 3D characters. With an `AgentAvatarProvider`, existing recipes for the paper and blob silhouettes also render through that engine, retaining its fur, lighting, volume and animation. Circle, triangle, flower, diamond and heart reuse the engine’s corresponding shapes. Eight distinct bodies extend that catalog: pebble, squircle, slender, pocket, petal, star, cloud and shield. Their contours come from Bloom’s existing artwork; saved recipes do not need rewriting. All supported bodies use the original 3D eye catalog and animation.

```tsx
import { AgentAvatar, AgentAvatarProvider, FOLD_CONFIG } from '@oxy.so/bloom/agent-avatar';

<AgentAvatarProvider runtimeUrl="https://example.com/bloom-character/runtime.mjs">
  <AgentAvatar
    config={{ ...FOLD_CONFIG, character: {
      preset: 'blue_beret', selections: { accessory: 'crown' },
    } }}
    size={128}
    interactive
    label="Peri"
  />
</AgentAvatarProvider>
```

Host the package's complete `assets/character-runtime/` directory. The provider takes the URL of `runtime.mjs` and loads it only when an avatar is visible. The original generated engine files are preserved byte for byte with an integrity manifest. See the asset directory's README for provenance and source limitations.

## Editing

The `character` recipe holds a `preset` and optional `selections` for shape, color, eyes, eyewear and accessory. Explicit selections override preset defaults. `none` removes eyewear or an accessory. Changing shape preserves all selected face and accessory parts. Editing the eyes, eyewear, accessories or color keeps the named preset's original body until a new shape is explicitly selected.

All 21 shapes use that same recipe. The additional contours have ordinary shape IDs: `slender`, `pocket`, `petal`, `star`, `cloud`, `shield`, `pebble` and `squircle`. For example, `{ preset: 'lime_frog', selections: { shape: 'cloud', eyes: 'cyclops', color: 'blue', accessory: 'felipe_beret' } }` selects a blue cloud with one eye and Felipe's hat. A shape contributes geometry only; it never selects another preset, palette or set of parts. Named presets retain their own default colors, while switching bodies keeps the chosen palette color or explicit `bodyColor`. Historical paper/blob recipes retain their saved paint when first edited and are promoted into the same recipe format.

The editor presents one shape catalog and one eye catalog through `ShapeArc` and `EmotionPicker`. Its eyes include the engine’s nine native styles, Todd’s authored eyes, Clippo’s eyes and a single-eye style. `eyes: 'todd'` and `accessory: 'felipe_beret'` select the actual eyes from Todd and the three-piece beret from Felipe across the body catalog. Their original meshes, materials and animation deltas are copied in the preparation worker, fitted to each body and included in cache identities. The editor uses a static Todd-eye thumbnail; the shape wheel still uses silhouettes. Historical recipes without an explicit eye selection default to oval eyes. Historical expression, eye-size, `eyeGap` and tilt fields remain readable without modifying a migrated face. The shared `GlossArt` palette and custom color picker edit either body source.

Each shape defines its own eye positions and size. Changing the eye style preserves that layout; changing shape adopts the new body's layout. Eye depth follows the actual body surface so shallow styles remain visible on bodies such as Todd. Eyewear fits the composed eyes, and a final rigid adjustment keeps crown accessories clear of eyes and frames. `selections.eyes: 'cyclops'` uses one large white eye with a teal iris, dark pupil and highlight at the shape's face center. There is no eye-placement control in AgentCreator. Historical `character.eyeSpacing` and `eyeGap` values remain readable but do not override the 3D layout. The **Universal Customization** and **Single Eye** stories exercise the shared editor and cross-body eye selections.

`selections.shape: 'todd'` selects Todd's original body independently of its eye style. Its selector silhouette is sampled from the original mesh; no avatar runs inside the shape wheel. Editing a named preset's face or accessories preserves its original body, while an explicit shape selection replaces that body and retains the selected parts.

`{ character: { preset: 'clippo' } }` selects Clippo’s grey open-wire body, large white eyes, dark pupils and asymmetric brows. `selections.shape: 'clippo'` and `selections.eyes: 'clippo'` are independent choices: other eyes can use the clip body, and other bodies can use Clippo’s face. Its tube is generated as a real hollow silhouette with rounded ends, without fur; it uses the same native character, lighting, interaction and work controller. Color, eyewear and headwear remain editable. The shape and eye wheels use static SVG thumbnails. Storybook’s **Clippo** story provides React/Work controls and cross-body examples.

Alien avatars have been removed from the available catalog. Saved aliens, mascots and hidden-face recipes retain compatibility rendering. The shape selector shows static silhouettes without eyes or accessories: original catalog PNGs and cached SVG contours for migrated bodies. Paper grain and material effects become the engine’s 3D surface. Migrated bodies accept the original eyewear and accessory catalog. Headwear, Bulb, bow and Tuft use rigid contour anchors; eyewear fits the final eye geometry and headphones use body anchors. Original meshes, materials and fur remain intact.

## Interaction and lifecycle

`interactive` enables the original engine's pointer tracking and touch/drag interaction. Change `reactionKey` from an accessible button to play the authored signature selected by the current body. Named bodies retain their native profile, including Todd and Jojo, after face, color or accessory edits. Catalog shapes with an authored counterpart use its body profile. Bodies without a matching profile, including Clippo and distinct migrated contours, use Todd's original signature as their shared standard. Pointer/touch reactions use the same body profile and preserve the edited appearance. Shape changes retain the last painted frame while the new geometry prepares. Changing `workingKey` starts a working episode and then returns to the interactive mode; `workingCycles` controls its duration. The creator’s **React** and **Work** buttons preview these original animations for both original and migrated bodies. Work preserves the chosen body and fitted face and accessories. Both modes retain the same native character, prepared geometry and clock while resident. Activity props are prepared up front; a verified adapter selects the original controller. A 180 ms transition interpolates body/skin transforms and camera in 3D from the last presented pose; added work props follow their original animation. Work finishes its original outro before a queued reaction starts. Repeated requests invalidate stale stop timers. Pause-related appearance changes and offscreen reclamation have separate lifecycles.

`paused`, reduced motion and `motion: 0` stop animation after a complete appearance frame. `portrait` prepares a static thumbnail. The beta can report readiness while drawing transparency if initialized with its reduced-motion flag; the adapter waits for painted pixels and then freezes its clock instead.

Web shares the beta engine and one animation clock per document, with a shared budget of **four live renderers** across original and migrated avatars. Additional avatars retain real 3D pixels from their last completed frame while their GPU renderer is released. Pointer interaction and React/Work commands prioritize reclaiming a renderer; overflow images remain visible while that renderer prepares. A newly visible avatar without a cached frame waits for its first rendering slot; preparation is one avatar at a time, and an `interactive` avatar (the editor's live preview, whose capabilities enable the editor's eye and colour controls) is admitted before passive thumbnails mounted ahead of it. This bounds graphics resources; the recovered engine’s synchronous first preparation can still cause a long task, especially for uncached migrated contours. Leaving the viewport or hiding the document releases the renderer lease, and returning avatars can display their retained image before resuming animation.
Web uses one physical WebGL2 context and a packed canvas shared by every visible, animated character. Each original or migrated avatar keeps its own animation, input, work state and render targets. `shared-surface.mjs` maps default-framebuffer operations into its region, resolves MSAA locally before the atlas copy, and clips presentation to prevent neighbouring avatars leaking into a fitted image. Deleting one character cannot destroy the shared context; the last lease releases it. The shared clock targets 30 fps with a round-robin submission allowance; this is a target, not a guarantee of 30 fps per avatar on every device.

Shaders and linked programs are shared by exact source and attribute bindings. Logical program handles retain independent uniforms and Emscripten metadata; switching skips values already present on the physical program. Small avatars (up to 128 CSS pixels) use the original compact mesh. The drawing resolution uses DPR at most 1 up to 64 CSS pixels, 1.5 up to 128, and 2 above that, with a 64-pixel floor and 512-pixel ceiling. The original engine derives its fur draw count from that drawing size, so reducing prepared fur arrays would not reduce its draw calls. Original fur and materials remain in use. The two 512-pixel mipmapped RGBA8 images and the 576×960 RGBA8 atlas share storage only when bytes and parameters match exactly; mutation or framebuffer attachment creates an independent copy. Private render targets, mutable geometry buffers and other textures remain per-character.

The scheduler submits at most eight avatars per batch within an 8 ms CPU allowance, then waits asynchronously on a WebGL fence before checking driver errors and copying images. This releases the JavaScript thread while the GPU finishes; it does not make that GPU work free. Native setup/probing and Emscripten’s own `GL.lastError` checks retain their behavior. A graphics error discards every pending image in that batch and reports failure to its touched characters. Appearance edits, resize and disposal wait for the batch to finish. Pointer capture happens synchronously on pointer-down; native input is queued in order. A single native render remains non-interruptible. Diagnostics separate `renderMilliseconds` (submission plus presentation CPU time) from `renderWaitMilliseconds` (elapsed wait and task dispatch, not a GPU timer).

Original and migrated bodies share one rendering WASM module and one preparation worker (the worker owns its own WASM instance). Prepared geometry identities include the contour and attachment transform. Cold preparation is admitted serially, while already painted moving avatars remain resident. Its owner receives a render turn every batch until its first complete paint, preventing the resident crowd from delaying the next preparation. The most recent interaction receives priority on alternate batches; the remaining turns use round-robin scheduling. Exact contour preparations are cached with an 8 MiB/16-entry LRU bound, keyed by appearance bytes, quality, activity mode, contour and authored parts. Cache hits receive independent buffer copies; native delivery still waits for the GPU boundary. Offscreen/background characters release their lease and retain their last complete 2D image. Static portraits use a bounded 64-image cache and release rendering resources after painting. Storybook’s **Many Avatars** story exercises 48 original/migrated avatars with React/Work controls and scrolling.

### Physical-device measurements

The [current controller/transition benchmark](./benchmarks/avatar-continuous-renderer.json) uses a Pixel 8a (Mali-G715, Android 16, Android WebView 148), with all avatars visible at 48 CSS pixels and 64 backing pixels. Original presets and migrated contours alternate. After every avatar is ready, a three-second warmup precedes a roughly five-second sample. Output pixel hashes confirm that every avatar moves; page RAF cadence is measured separately from each avatar's paint rate. The artifact records the exact tested asset hashes; it predates the authored Todd/Felipe part compositor.

| Visible avatars | Median paints per avatar per second | Page RAF interval, p95 | Time until all are ready | WebGL contexts |
| --- | --- | --- | --- | --- |
| 24 | 4.42 | 25.1 ms | 14.85 s | 1 |
| 48 | 2.29 | 25.1 ms | 24.80 s | 1 |

These results remove context loss, but **do not deliver fluid 30 fps animation**. The [previous baseline](./benchmarks/avatar-shared-renderer.json) took 24.6/74.1 seconds until all avatars were ready, with mean paint rates of 3.76/2.59 Hz. Startup improves substantially; drawing throughput does not improve uniformly. An [intermediate snapshot](./benchmarks/avatar-deferred-renderer.json) isolates deferred GPU waiting before eager activity preparation. These are individual runs, not controlled repeated trials or sustained thermal measurements. Readiness uses a new document/engine and warm HTTP caches. Pixel-hash sampling adds readback overhead.

Current CPU submission/presentation p95 is 10.0/10.4 ms per batch at 24/48, excluding asynchronous GPU wait. Exact texture sharing avoids a calculated 109.85/224.47 MiB of duplicate requested mip storage. These are payload calculations, not total GPU memory measurements. Both runs have nine physical programs, all avatars moving, zero graphics errors and zero live contexts/characters/preparation jobs after cleanup. Interaction and same-character React/Work continuity are checked separately in browser gates.

## Native and fallback

The optional native bridge uses `react-native-webview` and requires an absolute runtime URL reachable by the device. The web adapter is also exercised in a physical Android WebView; that does not validate a React Native multi-WebView screen. Each native WebView owns a separate document, so context sharing is **per document, not application-wide on native**. Separate WebViews cannot share engine memory, graphics contexts or the web document’s viewport reclamation.

An unavailable runtime or missing native peer displays the translated unavailable state. Consumers without a runtime provider retain the universal SVG renderer for procedural recipes. That renderer preserves the original contours, folds, expression springs and deterministic grain; it does not support the beta's new 3D parts.

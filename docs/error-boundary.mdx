# ErrorBoundary

Catches a render error below it and shows a fallback instead of unmounting the
tree above.

```tsx
import { ErrorBoundary } from '@oxy.so/bloom/error-boundary';

<ErrorBoundary
  title="This feed didn't load"
  message="Your other tabs are unaffected."
  retryLabel="Try again"
  onError={report}
>
  <Feed />
</ErrorBoundary>
```

## Which prop decides what

| prop         | decides                                                     |
| ------------ | ------------------------------------------------------------ |
| `title` / `message` / `retryLabel` | the wording of the default fallback (localised via `BloomProvider locale` when unset) |
| `fallback`   | replaces it entirely — a node, or a function                 |
| `onError`    | reporting; called with the error and the React error info    |

## Place it where a failure should cost a section, not the screen

Around a feed, a widget, a tab's content, a third-party embed. One boundary at
the app root turns every error into a blank page, which is the outcome a
boundary exists to prevent.

The useful question is: *if this subtree fails, what should the user still be
able to do?* Whatever the answer is, the boundary goes below it.

## The function `fallback` gives you `retryCount`

That is the reason to reach for it. After two or three failed retries, offering
the button again is dishonest — the same thing will fail the same way.

```tsx
fallback={({ error, retry, retryCount }) =>
  retryCount < 2 ? <Retry onPress={retry} /> : <Offline error={error} />
}
```

## Write the fallback for someone who does not know what a boundary is

Say what they lost and what the button will do. "This feed didn't load" is
useful; "Something went wrong" tells them only that we noticed.

Never show the error message itself in production UI. It is written for us, it
often contains internals, and it cannot be acted on.

## What it does not catch

React error boundaries catch errors thrown **during render**. They do not catch:

- errors in event handlers — those are just exceptions; catch them where they
  happen and surface them with a [toast](/docs/bloom/main/toast) or an
  [admonition](/docs/bloom/main/admonition);
- rejected promises and async failures — the same;
- errors in code above the boundary itself.

So a boundary is a safety net for the unexpected, not the way you handle a
failed request. A request that can fail has a designed failure state.

## Recover one pane inside a healthy shell

Use `PanelErrorBoundary` for content beneath Bloom's providers. It renders a themed
`EmptyState` with localized error text and a retry button. `ErrorBoundary` remains
the provider-independent last line of defense for failures outside those providers.

```tsx
<PanelErrorBoundary
  resetKey={pathname}
  emptyState={{ illustration: <BrandSticker />, title: 'Cannot open this message' }}
>
  <MessageContent />
</PanelErrorBoundary>
```

The boundary catches render and lifecycle failures, not rejected requests or event
handler exceptions. Keep expected loading/error data states in the content API.
Changing `resetKey` clears a failed boundary; healthy content retains its state.
Retry affects only this boundary. A supplied `emptyState.action.onPress` runs before
retry, so it can clear local error data or request a refresh. Omitting `action`
preserves the default retry button. `fallback` accepts the same node/render callback
and error context as `ErrorBoundary`; a failing fallback escalates to the next outer
boundary instead of retrying itself.

The default fallback scrolls when space is short and clears the inherited occupied
bottom edge. Set `bottomInset={0}` when its parent already reserves that space.
An explicit `bottomInset` takes precedence over the inherited occupancy.

`AppShellSplitPanes` installs independent boundaries for its list, detail and info
panes by default. Configure each through `listErrorBoundary`, `detailErrorBoundary`
and `infoErrorBoundary`, using the same options as `PanelErrorBoundary`; pass `false`
to delegate that pane to an outer boundary. Shell navigation and healthy panes remain
mounted. `ContentPanel errorBoundary` provides the same recovery inside the framed
surface for pages outside a split; it is opt-in to avoid redundant boundaries.

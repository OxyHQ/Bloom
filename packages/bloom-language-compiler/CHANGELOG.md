# Changelog

## 1.9.0

### Added

- `bloom build android` writes and drives its own Gradle project (no Expo prebuild, CLI or modules): the manifest from `Package.bloom`'s new `app: App(…)` (id, version, permissions, icon, splash, deep-link schemes), signing from a local keystore under `~/.bloom/keystores/`, React Native core (Fabric, Hermes), the React Native libraries it autolinks itself, and Metro driven by `bloom` (`bloom-metro.js`). `--with-expo` keeps the Expo path; `--generate` writes the project for Android Studio and stops.
- `extern native "Name" { … }` declares a Bloom native module's interface once; `bloom` generates React Native's TurboModule spec (the Kotlin side is checked against it) and a lazy bridge. `.native("Name", kotlin:, swift:)` targets in `Package.bloom`.
- The standard library's `KeyValueStore`, `SecureStore` and `FileStore` keep their values in Bloom's native storage module on Android (`BloomStorage`: SQLite, a Keystore-held AES-GCM key, the app's files), behind the same interface. (Its code already shipped in 1.8.0, whose notes left it out.)
- The Bloom router: in a Bloom build (`bloom build android`), `NavigationStack` is Bloom's own navigator (`stdlib/Bloom/router.ts`) instead of expo-router. Each route is a native screen of react-native-screens' stack, `sheets:` routes are the platform's form sheet, `tabs:` are Bloom's swipe pager under `BottomBar`, Android's back pops the route in front, and the manifest's schemes open the route their path names. The route table is written into the entry from the app's `Routable` enum: no file routes, no expo-router, and no shims for `expo-linking`, `expo-constants`, `expo-splash-screen` or `expo/dom`. The web and `--with-expo` keep expo-router's file routes (now through `routing-expo.ts`).
- Compose islands (ADR 0003). A module marked `.module("FeedIsland", native: .island)` in `Package.bloom` is also compiled to Kotlin + Jetpack Compose. `bloom build android` then writes the Gradle library `:bloom-islands`, and the app links it like Bloom's native modules. It holds the islands' Kotlin (from the native backend, `bloom-native`), Bloom's Kotlin runtime, a generated `IslandRegistry` and `BloomIslandPackage`, whose `BloomIsland` view draws an island by name (`island`) from its props (`props`, JSON) and sends its intents back as `onIslandEvent` (`{ name, payload }`). Compose (1.12.1, its compiler plugin) and coroutines (1.10.2) come in that library only.
- `bloom init --adopt`: an existing Expo app becomes a Bloom package. It writes `Package.bloom`
  from the app's `package.json` and app config (`app: App(…)` with the id, version, build, name,
  schemes, icon, splash, permissions and `reactNativeFromSource:`; `adopt: Expo(entry:)`), and
  keeps the app config plugins' native config as an override layer in `Native/android/` (the
  manifest entries, strings, colours and Gradle properties `bloom` does not generate, and
  `expo-build-properties`' ProGuard rules), read once from Expo's own introspection.
- Hybrid builds: `bloom build android` builds an adopted app. Its JS stays where its package
  manager installed it and bundles over its own Metro config (with its tsconfig path aliases);
  `bloom` generates and drives the Gradle project. The Expo packages listed in `stopgaps:`
  (`.expo("expo-image", until: "BloomUI.Image")`) are linked through Expo Modules autolinking,
  limited to them and the Expo modules they depend on, with Expo's lifecycle wrappers in the
  generated application and activity. Every other Expo module is left out, and an import of one
  fails the bundle naming the line to add, so the Expo surface that remains is the list in
  `Package.bloom`. The override layer merges over the generated manifest, resources, Gradle
  properties and ProGuard rules, and `Native/android/app.gradle` is applied to the app module.
- `App(reactNativeFromSource: true)`: React Native's Android libraries built from the installed
  `react-native` (its patches included).
- A Bloom build answers `expo-splash-screen` with a shim: its splash is the manifest's.
- `extern native` declares native views: a function that returns `View` is a Fabric component,
  its parameters the props (strings, numbers, booleans, unions of strings, arrays and optionals of
  them) and its `on…` closures the events, with a record of the event's fields. `bloom build
  android` writes its component spec, links it as a Fabric component and registers its
  component descriptor; the bridge draws it as an embedded view.
- The standard library's native image view, `BloomImage` (`stdlib/Bloom/Image.bloom`, Kotlin over
  React Native's image pipeline): memory and disk caches, decoding at the view's size,
  `contentFit`, cross-fades, placeholders, cache policies, recycling keys, tint and blur.
  `ImageCache.prefetch`, `ImageCache.size(of:)` and `ImageCache.clear` reach its cache.
- A Bloom build holds its launch splash until the app's first content appears, as an Expo build does with expo-splash-screen. The window draws no frame of the loading app, so the JS bundle and the first screen get the threads those frames took. On Mention's hybrid build this brought startup to the Expo build's or below: JS `main`, the first feed row and the first feed image. The standard library's `Splash` (`preventAutoHide()`, `hide()`, over the new native module `BloomSplash`) keeps the splash up until the app hides it. An adopted app's `expo-splash-screen` calls reach it through the hybrid build's shim.
- `bloom build android --store`: a store release, the signed app bundle (`<Name>.aab`) and one
  APK per ABI (`<Name>-<abi>.apk`, no universal APK), React Native's four ABIs unless
  `BLOOM_ANDROID_ABIS` names others. With `BLOOM_ANDROID_CERT_SHA256` set, every artifact must
  carry that signing certificate or the build fails.
- A hybrid build applies Google's services plugin when the overrides hold a
  `google-services.json` (the app's Firebase config, for FCM), as Expo's prebuild does.
- `bloom_lang::backend` (ADR 0003, from #1067): the checked program for the native backends, read-only. `backend::checked(source, filename, options)` parses, lowers and checks a file as `compile` does and returns the lowered tree and the checker's `CheckResult` (each expression's type and what each call, field, name, `await` and `try` resolved to), instead of emitting TypeScript. `compile`, `check` and `backend::checked` now share one front end (`check_source`), so a backend reads exactly what the TypeScript emitter reads and reports exactly its diagnostics.
- Swift's `break` and `continue` in `for` and `while` (2.0), with named loops: `outer: for row in grid { … break outer … }`. An unnamed `break` in a `switch` case leaves the `switch`, as Swift's does (its `if` chain takes a label). Outside a loop, inside a closure whose loop is outside it, or with a name no loop around it has, either is B0219. They were read as names (B0202 "cannot find `continue`", lang-mention-11's loop-continue: Mention's MediaGrid, VideosGrid, SuggestedUsers). The formatter keeps them.
- **A TS value callable beside its members is typed:** an object type with call signatures and members (zustand 5's store hook, `UseBoundStore<S>`: `(): S`, `<U>(selector: (state: S) => U): U`, `getState(): S`) keeps each signature, as a Swift value with `callAsFunction` overloads: a call takes the first signature its arguments fit, generic ones instantiated, so `useTrendsStore { s in s.trends }` is `[Trend]`, a Bloom list with Swift's members (`enumerated()`, `isEmpty`), and `useTrendsStore.getState()` stays a member. It was `Foreign`, and a Swift list method on its result B0601 (mention13 foreign-enumerated). A generic TS alias of an object type (`type UseBoundStore<S> = { … }`) is mapped with its arguments, and a type argument the module exports is named `import("…").Name` in the emitted TS.
- A closure may capture, read and write a function's own `var`, as Swift's does (a closure's or a handler's too): `var handlers: [String: () -> Unit] = [:]; let add = { tag in handlers[tag] = … }` records into the table, and the function reads every write once the closure ran (Mention's PostMenu). A write is a new value, as any `var` write is. A `var` of a view's render or of a hook function stays B0402: their closures are cached across renders.
- Bloom 2.0, from the Mention corpus (phase D):
  - a closure that returns nothing, or one that awaits, fits TS's `() => Promise<void> | void`;
  - `c ? s : opt?.x` joins to the optional;
  - a TS literal union compares with a `String`;
  - a token modifier whose TS value takes `undefined` (`.tint(c ? "success" : none)`) takes `none`, from the new generated `noneModifiers` table;
  - a module constant's record literal keeps its string literals' types (emitted `as const`);
  - TanStack Query's data type flows through a generic binding module (`useQuery<T>`). (Its code already shipped in 1.8.0, whose notes left it out.)
- A thrown JS `Error` is the standard library's `JSError` (`name`, `message`, `stack`): `error as? JSError` and `catch let e as JSError`.
- `error.jsValue: JSONValue?`, the thrown value itself, with lenient `JSONValue` reads: `value["key"]` / `value[i]` (an object's own member, an array's element, `none` at a missing key, a value of another type or `null`) and `.string`, `.number`, `.int`, `.bool`, `.array`, `.object` (`none` on a mismatch). `error.jsValue?["response"]?["data"]?["error"]?.string` reads an Axios error's server message and never throws (mention11 http-error-shape). `CheckResult.json_reads` marks the subscripts.
- Swift's `===` / `!==`: the same object, for class instances, TS objects and errors (JS's `===`); on a value type it is B0210. `BinaryOp::Identical` / `NotIdentical` in the AST.
- The standard library's formatting takes Swift's `FormatStyle` shapes over Intl, each writing exactly what the TS it replaces writes (tested against Intl in English, Spanish, Japanese and Arabic):
  - `Double.formatted(fractionDigits: 0...3, locale:)`: JS's `toLocaleString()` is `0...3`, `{ maximumFractionDigits: n }` is `0...n`. `formatted(digits:)` stays, and `formatted(fractionDigits: n)` stays JS's `toFixed(n)`.
  - `Double.formatted(currency: "USD", locale:)` and `Int.formatted(currency:locale:)`: Intl's currency style.
  - `Date.formatted(.dateTime.month(.abbreviated).day(), locale:, timeZone:)`, field by field (`year`, `month`, `day`, `weekday`, `hour`, `minute`, `second`, each in Swift's styles), and `Date.formatted(date: .abbreviated, time: .shortened, locale:, timeZone:)`. `locale` and `timeZone` default to the device's.
  - **Breaking (pre-1.0):** `DateFormat` is now a struct, Swift's `FormatStyle`. `.relative`, `.abbreviated` and `.iso8601` read as before. `.dateTime(.medium, .short)` is now `formatted(date: .abbreviated, time: .shortened)`, `DateStyle` takes Swift's names (`numeric`, `abbreviated`, `long`, `complete`), and `TimeStyle` is new. `formatted()` with no arguments is Swift's `.dateTime`: the numeric date and the time.
- A range `a...b` where a `ClosedRange` is expected is that value (`ClosedRange<Bound>`, in the standard library), and an implicit member chain (`.dateTime.month(.abbreviated)` where a `DateFormat` is expected) starts from the expected type's static member, as Swift's does. An implicit member also reads a struct's static members (`.relative`).
- Bloom 2.0's generic views: `struct ProfileGridList<T: ProfileGridEntry>: View` (or `where T: P`) compiles to one `view()` fiber whose body is generic, with `ProfileGridListProps<T extends ProfileGridEntry>` in the `.d.bloom.ts`. A type parameter bounded by a shape (a struct, a record type or a TS interface) is TS's `T extends Shape`: read directly, with no witness, and checked at the call site (B0232); a protocol bound passes its witness as a prop. A data struct's type parameters take no constraints (B0106). (Its code already shipped in 1.8.0, whose notes left it out.)
- A hook function's state is `@State var x = v` at the top of its body, as a view's `@State` is: one `useState`, read as `x`, written as `x = …` (or `x += 1`, a functional update) in its closures, and `$x` its binding (a `@Binding` view writes it). The setter never surfaces as a value (no `Foreign<Dispatch>`). Written in the body itself it is B0401; in a branch, a loop, a closure or a function that is not a hook it is B0420. The formatter keeps it.
- What is expected reaches into a closure called at once and a generic method's result, as Swift's type checking does: `let all: [Item] = { if … { return a.map { … } }; return b.map { u in ({ id: u, uri: u }) } }()` checks each `return` against `[Item]`, and the record literals in `map`'s closure are `Item`s, a defaulted field left out. It was typed from the first `return` (B0201, Mention's FeedCard). Swift's closure signature writes the result type by hand: `{ () -> [Item] in … }`, `{ (n: Int) -> Int in n * 2 }`, and the formatter keeps it. Only a declared type (an annotation, a parameter's, a modifier's) reaches a generic method's result, never one inferred from a sibling: `[{ kind: "header", … }, ..xs.map { … ({ kind: "item", …, item }) }]` with no context is typed as before (explore/trending). A record a closure gives, its result type not written, takes an expected type with extra fields, as TS checks no excess property on a callback's result (`let avatars: [AvatarGroupItem] = useMemo({ xs.map { m in ({ id, color }) } }, deps)`, Feed/PostItem); a literal written where the type is declared is still checked for them.
- Swift's overloading by argument labels: free functions, and one type's static functions and methods, may share a name when their labels differ (`describe(count:)` beside `describe(name:)`, `formatted(digits:)` beside `formatted(currency:)`). A call takes the overload its labels fit (a default may be left out; the one leaving out fewest wins); none fitting, or two fitting equally, is B0207 listing the overloads. Same labels stay B0217 (overloads differ by labels, not types), and an overloaded name read without a call is B0202. Each overload is emitted named by its labels (`describe$0$count`); a name declared once keeps its name. Overloads are declared in one file of a module.
- `x as? Tab` with `Tab` a string literal union is `x` when it is one of `Tab`'s values and `none` otherwise, a membership test that reads `x` once. `x as! Tab` is the `Tab` itself: a dev build traps (`TypeError`) when it is not one, and a release build is TS's plain `as`. This is the form for TS's `as Tab` casts.
- A module constant's list of string literals keeps their union (`let TABS = ["videos", "following"]` is `["videos" | "following"]`, emitted `as const`), as TS's `as const` tab lists do.
- `x.formatted(fractionDigits: n)` on an `Int` or a `Float` is JS's `x.toFixed(n)`: exactly `n` decimals, never localized (`formatted(digits:)` stays the localized one).
- `struct X: MenuActions` and `struct X: MenuContent` (2.0): a menu's actions and content, conforming as a view conforms to `View`. `MenuActions`'s `body` is the tag → action table (`[String: () -> Unit]`), emitted `actions(function X(props) { …; return { tag: action } })`, and given as `Menu(…) { … }.actions(X(…))`. `MenuContent`'s `body` is the rows, emitted `menu(function X(props) { …; return rows })`, and given as a `Menu`'s child. Stored `let`s are the props, members may call hooks, and neither has a memo cache or takes a view's modifiers. The declarations are `(props) => MenuActionsView` / `MenuContentView`.
- A file-scope `private var x: T = v` (2.0): the file's own mutable value, emitted as a JS module `let`, which any of its functions, closures and effects may read and write (Mention's ChannelInfoDialog, FediverseInfoDialog and ActionMenu registry callbacks). It is no dependency and no state. `var` and `public var` at file scope stay B0106.
- Swift's optional call `f?()` calls `f` when it is present, as `f?.()` does (it was read as `f?`, an early return, then a call).
- **`sorted()`, `min()` and `max()` for `Comparable` elements**, Swift's: a list of numbers, strings or dates in its natural order, beside `sorted(by:)`, `min(by:)` and `max(by:)`. Another element type is B0201 with the `by:` form as the fix. `CheckResult.natural_orders`.
- Swift's protocol composition in a constraint: `where T: P & Q` (as `<T: P & Q>` already was), and a module's `type PQ = P & Q` named in one (`<T: PQ>`, `where T: PQ`), each one constraint per protocol, with a witness each. A composition is not a value's type (B0232); `any P & Q` and an imported composition alias are deferred (ADR 0002).
- Swift's ranges: `a..<b` and `a...b`, collections of `Int`s (`[Int]` to the checker), binding
  below `+` and above the comparisons. `for i in 0..<n` is a counting loop, and
  `(0..<n).map { … }`, a builder's `for i in 0..<n` and `Array(0..<n)` are each one
  `Array.from({ length })`; no range builds an array it does not return. `Array(xs)` and
  `Array(set)` copy a collection. `bloom fmt` writes ranges with no spaces.
- A list or record literal is checked against its context, as Swift checks one: each element and each ternary branch against the expected type, never against its sibling's (lang-mention-10's record-context: Mention's BoostScreen, CaptureReview). A spec object parameter is now an expected type: `.accessibilityValue(c ? { text } : { min, max, now })` types both branches by `accessibilityValue`'s keys, where the first branch had typed the second (B0205).
- Typed object kinds in the spec (`objects.<name>.fields`: each key's type, `?` when it may be left out), and a parameter `[name]`, a list of one. `Dialog().buttons(…)` takes `[dialogButton]` (`label`, `color?` a `dialogActionColor` token, `onPress?`, `disabled?`, `loading?`, `shouldCloseOnPress?`, `initialFocus?`, `testID?`, Bloom's `DialogAction`), so a button without `onPress` is no longer B0206 for being unlike the first, a button without `label` is, and a key it does not take is B0205.
- **`Regex` in Swift's shape**, the one type: `try Regex("^\\d+$")` (throws a `RegexError` on an invalid pattern), `s.wholeMatch(of:)`, `s.firstMatch(of:)`, `s.matches(of:)`, `s.contains(r)`, `s.replacing(r, with:)` and `s.split(separator: r)`, beside `Regex(pattern:flags:)` and its methods. A group that did not take part in a match is `none` (`group(n)`, JS's `undefined`), where it was `""`; `RegexMatch.groups` is `[String?]`. Runtime tests compare each with JS's `RegExp`.
- **A struct's `init` in an extension** (`extension Regex { init(_ pattern: String) throws { … } }`) is called by its labels, beside the memberwise one, as Swift keeps both; its body gives the value it makes, as a built-in type's does.
- **Swift's slices:** `suffix(_:)` and `dropLast(_:)` on lists, `dropFirst()`/`dropLast()` dropping one, and `dropFirst(_:)`/`dropLast(_:)` on `String` (user-perceived characters, as its `prefix`/`suffix`). Past either end they give what there is and a count below zero takes or drops none, never JS `slice`'s negative-index reading (the codemod writes `slice(-n)` as `suffix(n)`). A list's `dropFirst(n)` clamps a negative `n` likewise.
- A TS discriminated union of object types (`{ kind: "sources"; … } | { kind: "lane"; … }`) is typed, not `Foreign`: a `match`/`switch` on its tag is exhaustive over the members' tags (B0301 names a missing one), and each arm reads its member's own fields (`rows.sources`, a Bloom list), as an `if rows.kind == "sources"` block and the rest after an early-returning `!=` do. It was B0601 (Mention's PostMenu `submenuRows`). The emitted tests are on the tag, which TS narrows the same way. A field every member has with one type is the union's too (`block.domain`, read without narrowing), and a member chain narrows on its tag as a name does (`item.media.mode == "override" ? item.media.media : none`).
- An element of a TS value Bloom does not map (`patch[key] = "show"`, a `Partial<Record<K, V>>`) is written in place as TS writes it, and `{}` where such a TS object type is expected is the empty object, not an empty closure.
- **`await Task.cancellation`:** in a `.task`, it returns once the task is cancelled (its id changes, the view leaves), so a setup's teardown is a `defer` before it and runs exactly when React's effect cleanup did: `.task(id: room) { let s = socket.join(room); defer { socket.leave(s) }; await Task.cancellation }`. A `defer` with nothing awaited after it still runs when the body returns, as spec 8 says; migrated effects whose cleanup ran at once (polling stopped, a debounce cleared, a socket left right after joining) take this form (mention15 task-defer-runs-at-once).
- **A `.task`'s work takes its cancellation:** a Bloom call in a `.task` that takes `cancellation: TaskSignal?` and is given none takes `Task.signal` (`sleep(for:)`, `HTTPClient`'s calls), as Swift's child work is cancelled with its task: a superseded debounce (`.task(id: query) { try? await sleep(for: .milliseconds(300)); search(query) }`) stops waiting. `CheckResult.implicit_signals`.
- **Implicit static functions:** `.milliseconds(300)` where a `Duration` is expected calls `Duration.milliseconds(300)`, as Swift's implicit member expression reads a static function giving the type (it was B0205, "a struct, with no `milliseconds`").
- `@Transparent` structs (Rust's `#[repr(transparent)]`): a struct with exactly one stored `let` is that field at run time, and a type of its own to the checker. Its TS type is the field's (`export type UserID = string`), `UserID(raw: v)` is `v`, `id.raw` is `id`, `==` compares the field and a derived `Codable` is the field's codec. B0106 for none or a second stored property, a `var`, or the attribute on anything but a struct. `CheckResult.transparent` names them for the native backends (a Kotlin `@JvmInline value class`, a Swift struct). Spec 4.4.
- `UniqueID`, the standard library's identity: `@State private var id = UniqueID()` (a view's, or a hook function's `@State var`) is one `const id = useId()`, never set (B0403), read as `id.string`. `UniqueID()` anywhere else is B0420 (`CheckResult.unique_ids`).
- **`struct X: ViewModifier`**, SwiftUI's: `func body(content: Content) -> some View` wraps the view `.modifier(X(…))` is applied to, with a view's members (props, `@State`, `@Environment`, hook `let`s). A stateless one is called in place (`X({ … })(view)`), rows included; one that keeps state is called once per render at the top of the view applying it, so its state is that view's, and its result is the screen's root: `content` keeps its `.title`, and a gated state hides the header with `.header(false)` (Mention's `SupervisedFeatureGate`). B0421: `X(…)` outside `.modifier(…)`; B0422: a stateful one in a closure, a `for` row or a member, or reading a body-local name. Spec 7.2b. **IR (additive):** `ViewKind::Modifier`, `ViewDecl.content`, `CheckResult.view_modifiers`.
- **A view's `static let` read qualified:** `struct Card: View { static let fallback = "Untitled" }` is the type's constant (`Card$$fallback`), so `Card.fallback` reads it in the view and outside it, as Swift's static does (it was B0205); the body still reads `fallback` unqualified.
- Swift's trailing row for a `VirtualList`, as SwiftUI's `List(data) { item in … }`: `VirtualList(posts) { post in … }` is handed each item, and `VirtualList(posts.enumerated()) { i, post in … }` its index and item, with no pairs built. It is emitted as one row function that reads FlashList's `{ item, index }` (`({ item: post, index: i }) => …`), hoisted to module scope when it reads nothing of the view, so the list's `renderItem` keeps its identity. A row closure passed as the argument, a function value and TS's `renderItem` keep FlashList's `{ item, index }`. A trailing row with the wrong number of parameters is B0503.
- `@Model` records persist in a `bloom build` without Expo: BloomData's persister runs over Bloom's
  native storage module (`BloomStorage`'s new `sql…` functions, Android's own SQLite with WAL and
  compiled statements), with no `expo-sqlite`. `--with-expo` keeps expo-sqlite.
- Module events in `extern native`: `func onStatus(_ listener: ({ player: Int, status: String }) -> Void) -> () -> Void` is an event the native module sends. The spec declares it as codegen's `EventEmitter`, so the Java spec has `emitOnStatus(ReadableMap)`, and the bridge adds the listener and returns what removes it.
- The Bloom video player: `extern native "BloomVideo"` (`stdlib/Bloom/Video.bloom`) in Kotlin over androidx media3, and a Bloom build's `expo-video`, a shim over it with expo-video's API (`useVideoPlayer`, `createVideoPlayer`, `VideoView`, the player's properties and events), so an app's call sites need no edits. The `expo` shim gains `useEvent` and `useEventListener`.
- A native module's `android/dependencies.gradle` is linked into its Gradle library.

### Changed

- The Bloom router draws each route with the language's screen host (`@oxy.so/bloom-language/screen-host`): a route's `.title()`, `.toolbar()`, `.header()`, `.footer()` and `.sheet()` are its Bloom `Screen`'s chrome, as under expo-router's `screen()`, and a pushed route's header offers Back. It needs the `@oxy.so/bloom-language` release that ships the subpath.
- The standard library's `Date` is a plain JS `Date` (zero cost), no longer a `{ timeIntervalSince1970 }` struct. It crosses the TS boundary as a JS `Date` in both directions, as Swift's `Date` bridges to `NSDate`: a TS function's `Date` parameter takes it and a TS `Date` result is one (lang-mention-11, about 12 corpus files).
  - Swift's API: `Date()`, `Date.now`, `Date(timeIntervalSince1970:)`, `Date(millisecondsSince1970:)`, `try? Date(text, strategy: .iso8601)` (JS's `Date.parse`; throws a `DateParseError`), `.timeIntervalSince1970`, `addingTimeInterval(_:)`, `timeIntervalSince(_:)`, and `date + seconds` / `date - seconds`, besides `formatted(…)`.
  - Two `Date`s are `==` at the same instant (a struct holding one compares it so), and they compare with `<`.
  - A built-in type's `init`s are told apart by their labels (`Date$$init$timeIntervalSince1970`), and each body gives the value it makes.
  - A `"js"` import of `Date` no longer shadows the standard library's.
- A function type keeps `throws` (beside `async`), as Swift's does: `(String) throws -> Int` is a type of its own in the checker and the IR (`FnTy.throws` read from a written type; AST `TypeKind::Fn.throws`). A value of a throwing type is called with `try`; a function that does not throw fits a throwing type, and a throwing one where a non-throwing one is expected is B0201 (TS callbacks excepted). A closure whose `try` nothing in it catches throws where a throwing type, or none, is expected. The standard library's list methods rethrow (`try xs.map(parse)`). `Codec.decode` is `(JSONValue, String) throws -> T` and `JSON.decode(_:from:)` throws (it already needed `try` in practice). The formatter writes Swift's spelling, `(A) async throws -> R`.
- A list of TS values fits a typed list (`[Foreign]` where `[Account]` is expected), and a function whose parameter is typed fits where TS passes it a TS value (`bans.map(renderBan)`); both are checked by `satisfies`, as a single TS value is.
- A `[View]` is a child: a conditional's branch (`c ? Text(…) : xs.map(f)`), a node's children argument, `Embed`'s value (`toElement(…)`), and a builder's last line, spread as its parent's children (`HStack(title, ...rows)`).
- A list of TS values, an optional list (`c ? rows : none`) and a list literal line are children too.
- A TS indexed access type (`FeedPostSlice['socialContext']`) is the member it names, so its fields are typed; an optional member's parts are named through `NonNullable<…>`.
- `x ?? e` whose two sides both fit what is expected is that type (`[Author]? ?? []` where `[Person]` is taken).
- String literals given for a generic parameter are read after the call's typed arguments, so `T` is a TS literal union rather than `String` (`choices(["a", "b"], chosen, onChoose)`).
- A TS value compared with a number or a string is one (`item.pokeCount > 1`, `page.page < page.totalPages`), as are a TS value beside an `Int` (`2 * Math.PI`) and a negated one (`-event.translationY`); each is checked by `satisfies number` (or `string`).
- `a || b` of two optionals that are not `Bool`s is an optional (`user.username || user.handle` is a `String?`), where it was refused as `String?` given for `String`; a chain that ends in a present value is present, through parentheses and branches.
- A hook given directly as an argument of a view member's call is a view member's hook (`let account = useProfileAccount(useRoutedProfileUsername())`), where it was B0420.
- A hook in a ternary's branch or on the right of `&&`, `||` or `??` is B0420 even as a view member's value: it runs on only some renders. It used to pass when it was the member's first call.
- A TS `view()` of the embedded language is called with its props (`Badge({ label: "a" })`) where it was mounted as a React component, which put a node where React takes an element.
- A Bloom view in an optional React-element prop (`footer: bare ? none : Text("foot")`) and in a prop of a TS component whose props Bloom cannot read (Bloom's `Screen(header:)`) crosses as `toElement(…)`; a declaration's `import("./types.js").T` names that module's type.
- A `struct X: Screen` (or `Layout`) outside the app's router folder is its file's named export, not the default export only a route has.
- A presence test in parentheses narrows as one without (`(room.status != none) ? room.status : "scheduled"`).
- `String(localized:)` and `Text("key")` in a view read the locale through `useLocalization()` and are memoised on it, so `Locale.prefer` re-draws a mounted view in the new language.
- A plural lookup with a count of 0 takes the catalog's `zero` form where it has one, in every language (i18next's `_zero`), before the CLDR category.
- An UpperCamel arrow in a `.tsx` (`const List = (props: ListProps) => …`) is a component, and so is its `memo(List, eq)`: mounted with `$jsx`, where it was called as a function and drew nothing.
- A stateless `struct X: View` whose body is one node is drawn in its caller's tree, with no component (fiber) of its own: it holds no `@State`, environment, `let` member, method, effect, comparator or observed model, and its body is one chain with no `.task`/`.onChange` and no `.id()` of its own. It is emitted as `inlineView(function X(props) { return …; })` (no memo cache: the caller's caches the call), keeps a view's semantics (modifiers on it apply around its body, its `.id()` is its key), and needs `@oxy.so/bloom-language` with `inlineView`. Measured with the cost harness on Mention's PostErrorBoundary, a struct around Bloom's `ErrorBoundary` in a feed row: 1 fiber, 1 hook slot and 3 context reads fewer per row than as a `view()`, and the same as TS's boundary class (`test/bloom.cost.test.tsx`). Golden `emit/inline_view`.
- `Int` is a 64-bit signed integer, Swift's (ADR 0003's native backends compile it to Kotlin's `Long` and Swift's `Int`). The JS backend keeps it a JS `number`, exact within ±(2^53 − 1), and a dev build now traps an `Int` `+`, `-` or `*` (and `+=`, `-=`, `*=`) whose result leaves that range (`$int`, a `RangeError`), as Swift traps an overflow; a release build emits the plain arithmetic. An integer literal outside the range stays B0105, now worded for the JS backend. The spec's 4.1 and 4.3 say so.
- Bloom 2.0 at the TS boundary:
  - a struct field whose default is `none` is optional in the emitted TS and `.d.bloom.ts` (`readonly boosts?: number`);
  - a TS `T | null` reads as `T?` (it was `Foreign`), and every test of an optional is loose (`!= null`), so a TS `null` is `none`;
  - `x || d` of a non-`Bool` optional is JS's `||`;
  - a keyword may name a struct's or a protocol's property (`let none: String`, read `copy.none`).
  - a TS value checked as a `T?` reads TS's `null` as `none` (`(x ?? undefined) satisfies T | undefined`), except in a record literal's field, whose check takes the `null` (`satisfies T | undefined | null`); a `??` chain already ending in such a check gets no second `?? undefined`.
- **`.share`, `.bookmark`, `.bookmarkFill` and `.menu` are Bloom's own glyphs:** `Icon(.share)` draws `ShareIcon` (and `BookmarkIcon`, `BookmarkFillIcon`, `MenuIcon`) from `src/icons/social`, as `.like` draws `LikeIcon`, matching Mention's post actions, not `RiShareLine`/`RiBookmarkLine`/`RiMenuLine`.
- A `private` top-level declaration is its file's only, as TS's file scope is: it may share a sibling file's `internal` or `public` name, which it shadows inside its own file, where it was B0807. Two `internal` or `public` declarations of one name in a module stay B0807.
- A string counts user-perceived characters, as Swift's does, on the TS backend as on the native ones: `"👍🏽".count` is 1 (it was JS's `length`, 4), and `slice(a, b)`, `firstIndex(of:)`, `lastIndex(of:)`, `paddingStart(to:)`/`paddingEnd(to:)` and a regex match's `start`/`end` are character offsets, so one read off one API indexes another. `s.count` compiles to `characterCount(s)` (no segmenting for a string with nothing at or past U+0300).
- `s.utf16`, Swift's `UTF16View` (`@Transparent`, the string itself at run time), has JS's UTF-16 units for what counts them (a server's length limit): `count`, `isEmpty`, `slice`, `prefix`/`suffix`, `firstIndex(of:)`/`lastIndex(of:)`, `paddingStart`/`paddingEnd`.
- The regex conformance corpus (`conformance/regex/`) is this package's; `record.mjs` records Node's `RegExp` on its own, and `test/regex-conformance.test.ts` runs the TS runtime against it (every case conforms, offsets in characters).
- TS's types are claims, Bloom's are guarantees. A `?.`, `?[…]` or `??` written on a value whose type comes from TS (a `Foreign`, a type read from a `.d.ts`, or what is read from one) keeps its runtime form where TS says the value is always there (`viewPost?.authors?.map { … } ?? []`), where it was B0201. On a Bloom type it stays B0201.
- `xs?[i]` is Swift's optional subscript, emitted `xs?.[i]` (it read as `xs?` then `[i]`, an early return).
- `{}` is the empty record where a struct's optional is expected too (`viewPost?.metadata ?? {}`), where it was read as a closure.
- `ts.state ?? {}` where the TS type has required fields is TS's `State | {}`: a `Partial<State>`, whose fields read as optional (emitted `{} as Partial<State>`).
- A `let`, and a view's `let` member, keep the claim of the TS value they hold (`let path = usePathname(); path?.endsWith(…)`).
- A closure's parameter may be wider than the one expected (`{ file: File? in … }` where `(File) -> Unit` is taken), as Swift's `(T?) -> U` fits `(T) -> U`.

### Performance

- Fewer emitted bytes: a `match` over a fieldless enum whose every arm reads or patches the field named like its case is one keyed access (`prefs[key]`, `{ [key]: v }`), a view body that is a hoisted tree returns it with no memo slot, a short string `let` of names is recomputed rather than cached, and a child that is a name has no cache slot. The cost gate's fixtures go from 1868 / 1341 / 3995 bytes (minified / gzip / Hermes bytecode) to 1709 / 1251 / 3707, below TypeScript with the React Compiler's 1684 / 1234 / 3804 in gzip; Mention's Notifications module from 4912 / 1792 / 7669 to 4598 / 1694 / 7386.
- Fewer emit allocations: a fragment's first piece is moved in, blocks, joins and wraps are built at their final size, and the token vector and the source map's mappings are sized once. (Its code already shipped in 1.8.0, whose notes left it out.)
- `bloom build android` bundles for Hermes: `bloom-metro.js` uses the `hermes-stable` transform
  profile (React Native's bundle command left it at `default`, the transforms for an older
  engine), and an adopted Expo app's Babel preset is told the engine is Hermes, as Expo's CLI
  tells it. bloom's own Metro files are inputs of the bundle task, so a change there rebundles.
- A hook function's (`func useX`) top-level `let`s are memoised in one cache on their exact dependencies, as a view's members are, and React's `useMemo`/`useCallback` there are plain `let`s: no hook slot each, as the React Compiler's cache for a custom hook did for the TS (PostItem's `usePostRowModel`: 45 of them). A `let` that calls a hook, a cheap read, a class instance and a value a later statement writes in place stay plain; a hook function with nothing to cache is emitted as before. A closure there is each caller's own, built once in its cache, never a module constant: what it builds can be an identity (`useState({ ({}) })`, a per-row owner). Each closure a view hoists to module scope has a name of its own in the module (two could both be `$fn2`).
- Smaller memo caches. Member `let`s (and `fn`s) written one after another on the same
  dependencies share one test, so Mention's ContentWarning's three `t(…)` strings are one `if`.
  A leaf (a node and its modifiers, with no child view, closure or call among its arguments)
  that reads its one dependency once is built with its parent instead of in slots of its own.
  ContentWarning drops from 35 slots to 27 and is 142 B smaller minified. Every golden that
  changed got smaller (the largest by 147 B), and the cost gate is unchanged.
- React's `useMemo` and `useCallback` written as a view's members (TS the codemod kept) are plain members, memoised in the view's one cache on their exact dependencies: no hook slot each, as the React Compiler folded them for the TS. `let f = useCallback({ … }, deps)` is `let f = { … }`, and `let x = useMemo({ e }, deps)` is `let x = e`. A hook function keeps its calls.
- A tree of TS components alone (`Suspense(fallback: none) { Panel(…) }`: no modifier, no Bloom node, no branch) where TS takes a React element is the TS element itself, `$jsx(Suspense, { children: $jsx(Panel, …) })`, as the TS wrote it. Before, it was `toElement(Embed(($render) => …))`, a `LanguageRoot` with an `Embed` per component, so TS could not read its props (`render(close).props.children.props.title`) and it mounted more fibers than the TS. Inside a Bloom tree, such a tree is one `Embed` of the TS element, with no render function. Several children are `jsxs`.
- `BloomVideo`: the players' first buffering goes in the order they were made, at most 3 at once,
  while the ones already playing load only the 2 s that keep them playing. On the 8-video bench
  this brought the first video's first frame and the 8th's ~65 ms earlier.

- A `@State` optional narrows as a local does: `selected == none ? "All" : label(selected)`, `if rating != none { onSubmit(rating) }` in a handler, a member chain of one (`draft.title != none`). A state's value is the render's, and a handler that writes it and reads it again is already B0410. It was B0201 (`found String?`) in Mention's saved posts and feed rating screens.
- **A silent change to JSON:** a struct's `static let` (`static let empty: [Post] = []`) was one of its fields, so `Post(…)` took it as an argument with its default and derived `Codable` wrote and read an `"empty"` key. It is the type's (`Post$$empty`), never a field. Classes and enums already kept theirs apart; a view's `static let` stays a constant of its body.
- **A cancelled task's request is cancellation only:** an HTTP call in a `.task` (it takes the task's cancellation, now through an extension method too: `api.send(.get, path)`) cancelled mid-flight rejected into the task's `catch`, which set an error state and reported a failure for a view that had moved on. A throw once the task is cancelled stops the task: no `catch` runs and nothing is set after it. Runtime tests abort a superseded request and one whose view left.
- **`fatal()` is `Never`:** `URL.parse(s) ?? fatal()` is a `URL`, not a `URL?` (`fatal` was generic in its result, which took the optional). `Never` is a type name: what does not return.
- An optional only by a guard Bloom kept on a TS value TS types as present fits a TS parameter: `postPermalink(viewPost?.id)` with a TS `viewPost: HydratedPost`, directly, through a chain (`post?.user.name`) or through a `let`. TS's own type there is `string`, and TS checks it where it lands; a cache of such a `let` declares no type, so TS's is the one it reads. A TS value TS types as optional (`metadata?.slug`) stays B0201. It was B0201 in Mention's postMenuActions.
- A TS function component typed as emitted declarations type it (`function EngagementBar(props):
  import("react").JSX.Element`, every Bloom component) is a component again: drawn with a trailing
  builder, its lines are the component's `children` (or the one node prop it declares in their
  place). It was called as a plain function, and the builder's nodes were dropped, so the file
  compiled and drew an empty bar.
- A builder's nodes are never dropped silently: a component with no `children` and no node prop
  left for the builder is B0506, `children:` beside a builder is B0207, a trailing closure past a
  TS function's parameters is B0207, and a node on a line of its own outside a builder is B0506.
- react-native's `View` (`declare const $$View: typeof View`) and a namespace's components
  (`import * as Skeleton`, `Skeleton.Region { … }`) and a component's UpperCamel static
  (`Button.Group { … }`) are components too, their builders their
  children. An `if` without `else` passed where a modifier takes a value
  (`.accessory(if open { row })`) is an optional child.
- One line of text in a TS component's builder (`TextFieldLabel { label }`) is its text children,
  as JSX's `<TextFieldLabel>{label}</TextFieldLabel>`.
- **A runtime crash:** a TS component declared as a function const and exported through `typeof` (react-native 0.81+'s `declare const Switch: (props) => ReactNode; declare const $$Switch: typeof Switch`) was called, `Switch({ … })`, so its hooks ran in the caller and React threw "Rendered more hooks" when it was drawn in a branch. It is an element, `Embed($jsx(Switch, { … }))`, as an `FC`, a `memo`, a `forwardRef` or a `NamedExoticComponent` is (mention13 ts-component-called).
- A TS generic parameter's constraint is the soft context of a literal given for it, as TS's inference reads it: `useAnimatedStyle(() => ({ transform: [{ scale: … }, { translateY: … }] }))` (`<Style extends DefaultStyle>`, Mention's ProfileHeader) checks the callback's result literal against `DefaultStyle` element by element, and `StyleSheet.create(video: { … })` each option against its member of the constraint. The type parameter is still TS's to infer from the literal, with no excess-field check. A literal given to any TS function Bloom cannot read is checked against that parameter's TS type the same way.
- A conditional where a TS type is expected checks each branch against it, never joining the branches: `minHeight: web ? "var(…)" : 384` (RN's `DimensionValue`, ContentSkeleton) was B0201.
- A generic TS interface named with the enclosing function's type parameter stays generic, so instantiating the function reaches its fields: `useSharedValue(0).value` is a `Float`, not the name `Value`.
- `==` and `!=` on a literal union narrow it in both branches, through `||`, `&&` and `!`, and after a guard that returns, as TS narrows it: `mode == "adaptive" || mode == "system" ? "system" : mode` gives the other branch `"light" | "dark"` (lang-mention-10's union-eq-narrowing, Mention's appearance page). The branch where a TS discriminated union's tag test fails is the other member, when one is left (`item.origin == "server" ? item.post.title : item.draft.name`, DraftsList).
- A list literal where a `[T]?` is expected is a `[T]`, its literals taking `T`: `post.metadata?.replyPermission ?? ["anyone"]` beside a TS `ReplyPermission[]` (a string literal union) fits, and so does `["nobody"]` given to a `[ReplyPermission]?` parameter. It was B0201 (`found [String]`).
- **A silent wrong render:** a view called through a `let` alias of it (`public let PostItem = PostItemContent`, from its own module or another) was emitted with positional arguments, `PostItem(post, open)`, so the view's props were the post itself. An alias of a view is that view: `PostItem({ post, openPostEngagement: open })` (mention13 view-alias-call).
- A `VirtualList`'s row closure written in place (`VirtualList(people, { row in … })`) is typed `VirtualListRow<T>`, what FlashList hands it at draw time: `row.item` is the item and `row.index` its index. A row that read the item's fields off the row itself (`{ person in Text(person.name) }`) type-checked and crashed on the first draw; it is now B0205, with the help "a row is `{ item, index }`: the item's `name` is `.item.name`".
- A TS component given by name to a TS component's prop (`EmptyState(icon: RiLinkM)`, the prop a `ComponentType`) is passed as it is. Where Bloom cannot read the props, every view among them crossed as an element, the named component too (`icon: toElement(RiLinkM)`), so the receiver got an element where it takes a component (Mention's SourcesSheet).
- A localization catalog rewritten within one tick of the kernel's coarse file clock is read again: the catalogs are cached on a hash of their content, not their modified time, which two writes in a row can leave unchanged (as on Seldon's CI VMs), so a key just added could be reported missing (B0840) until the next unrelated change. `clear_caches` now forgets them too. (Its code already shipped in 1.8.0, whose notes left it out.)
- A `struct X: ViewModifier` imported from another `.bloom` module is applied with `.modifier(X())`, as one of the same file is: it was B0421 "`X` is a modifier, applied to a view". A stateful modifier (`@State` in it) is never hoisted to module scope, where its hooks ran at import and threw ("Cannot read properties of null (reading 'useSyncExternalStore')"): it runs per render in the view applying it. Mention: every gated route (feeds, lists, lists/[id], lists/create, feeds/marketplace, communities/[id]/bans).
- A memoized value that calls a method on an optional (`let t = title?.trimmed()`) depends on its receiver, `title`. It was keyed on `title?.trimmed`, the method's name read as a JS property (always `undefined`), so it computed once and never again (Mention's PostArticleModal never showed a fetched article).
- A narrowed `@State` narrows its reads only (a regression of `==` narrowing a literal union: `if step == "review" { step = "edit" }` was B0403): inside `if report != none { … }` or `if step == "review" { … }`, `report = none` (in a closure too) and `$report` are the state's, `$report` a binding of the narrowed type (TS's `[report, setReport]`). They were B0403 "cannot assign to `report`" and B0505 (Mention's MembershipContentCard).
- Counting a string no longer loads the UI runtime. The standard library carries the language's string helpers (`text.ts` and its break table, the same source, written to `.bloom/std/Bloom/`), and its `runtime.ts` and a package's emitted `s.count` / character slices import them from there, not from `@oxy.so/bloom-language`'s index, which loads `render.tsx` and every Bloom component. Every std module (Core, Localization, JSON, …) loaded it before, an app load cost, and in Jest it ran before a test's `jest.mock('@oxy.so/bloom/button', …)`, so the mock was not drawn (Mention's commercePickerPaging, PostArticleModal, FeedInterstitial, TrendsWidget, savedScreenRevalidation). A file outside a package keeps the index. No new export subpath.
- **The grammars read what bloomc reads:** the tree-sitter grammar parses labelled loops (`outer: for … { break outer }`, `continue outer`), a hook function's `@State var`, `===`/`!==`, a protocol composition (`Named & Counted`) and a closure with its signature (`{ () -> [Row] in … }`), and highlights `===`/`!==` and loop labels; every tracked `.bloom` file parses again. The language server offers the 2.0 contextual keywords (`func`, `guard`, `break`, `continue`, `do`/`catch`, `try`/`throw`, `extension`, `protocol`, `class`, `actor`, …) beside the reserved ones (`bloom_lang::CONTEXTUAL_KEYWORDS`).

## 1.8.0

### Compatibility

- A `.bloom` module with an `@Observable` model needs `@oxy.so/bloom-language` 2.1.0 or newer, which has `Observable` and `useObserved`.

### Breaking

- The standard library's BloomData `Action` is now `Mutation` (`Mutation.make(name, optimistic:) { … }`, `run(input)`), so BloomUI's `Action` node in an `ActionBar` is no longer shadowed. The standard library's `HTTPError` gains `response` and `static func cast(_:)`, which also reads an Axios error.

### Added

- Bloom 2.0's surface (ADR 0002, phase A): views written as Swift writes them, `switch`, `guard`, `throw`, `try` and `do`/`catch`, typed errors, `@Observable` models whose views subscribe only to the fields they read (decided at compile time), protocols and extensions with static dispatch, constrained generics and `any P`, `@Binding` reads and writes, and `x!` (a trap on `none` in a dev build).
- The Bloom toolchain: directory modules and `Package.bloom`, `extern` binding modules generated from a `.d.ts` (`bloom bind`), `test("…") { #expect(…) }` on the test runtime, and the `bloom` command line (`new`, `check`, `fmt`, `build`/`run` for web and Android, `test`, `add`, `bind`; `bloomc` is its alias). `bloom new` pins the Bloom, language and compiler versions this release ships with. `bloom check` caches each file on the interfaces of the files it reads.
- The standard library (phase B), implicit in every package file: Core (`String`, `Array`, `Dictionary`, `Set`, `Optional`, `Result`, `Error`), `URL`, `Time`, localized strings checked against the catalogs, BloomData as `@Model`, `@Query`, `Source`, `Action` and `Realtime`, `async let` and actors, and `Ref<T>`.
- Bloom 2.0, from the Mention corpus: an unannotated TS hook's result is read from its body, and `ReturnType<typeof useX>` resolves through it (for a `.bloom` hook too); a TS optional parameter takes `T?`; a conditional ending in `none` is the optional of its branches, at any depth and as a list item; `.id()` works on every node; a TS type named through re-exports is its declaration, so a callback alias types a closure's parameters; `catch let e as T` tests the error and `e as? T` casts it, through `T`'s `static func cast`; TS object types fit structurally; a record indexed by a union of its keys is the type of those fields; react-i18next's `t` gives a `String`; and a Bloom view where TS takes a React element is emitted as `toElement(view)`.

### Changed

- An array's subscript `xs[i]` is a `T`, as in Swift: a dev build traps out of range (`RangeError` naming the index and the count), a release build reads it as is; `xs.at(i)`, `first` and `last` are the optional reads. A dictionary's `d[k]` stays `V?`.
- The Mention corpus' compiler gaps (M1–M9): platform files (`X.native.bloom`, `X.web.bloom`) are one module's alternatives, imported by their base name; a class of another file is imported with its `init`; a reference is a class in `@State`, and a host view's instance a `ViewRef<T>()`.

### Fixed

- The WASI `bloomc` (the fallback on a platform with no prebuilt one) starts in the working directory again, and on Windows, where Node's WASI cannot list a directory, `check` and `fmt` are handed the `.bloom` files under one.
- A route added within a clock tick of the last read is seen: the route table is read again for a folder modified within 2 seconds of the read, as git treats a racily clean file.
- `BLOOM_LINK` installs a linked checkout as it packs (its `pack:local` script when it has one, else `bun pm pack`), never as a copy of the directory. bun copied all of a `file:` directory, the checkout's examples and their `.bloom/build/` included, each holding the last linked copy, so every build nested one level deeper until the tree was too deep to delete. A pack that would carry a `.bloom` build is refused, and a rebuilt checkout is installed again on the next build (the tarball is named by its content), with no `.installed` stamp to delete.
- A native release bundle builds again with `withBloomLanguage`. 1.7.0 wrapped each Metro cache store with `Object.create(store)`, and Expo's `BinaryFileStore` keeps its state in private fields, so Metro's reset before a release bundle (`clear()` on the wrapper) threw "Cannot write private member #prepare to an object whose class did not declare it". The wrapper now hands every call (`get`, `set`, `clear`) to the store itself. The web export, which resets no cache, was not affected. (Mention's Android release bundle on 1.7.0.)
